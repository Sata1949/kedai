# Kedai 文档台账：写哪份、怎么写

## 一、先判类：六类互斥

新内容写进哪份文档，按下面**逐条套用，先命中先定**：

| 类 | 判据 | 判据的反面 |
|---|---|---|
| **契约** | 改了它，旧 exe / 旧数据 / 旧前端会坏。字面规定，不得随手改 | 只是实现细节（改了对使用方无感）→ 功能 |
| **功能** | 代码里已跑通、有实测证据。判据是「现在能用」 | 只有方案没落地 → 计划；有缺陷 → 遗留 |
| **计划** | 有批次号 / 有改动点 / 有验收断言 / 有人在跟踪 | 只有方向、无改动点 → 展望；条目本身是问题 → 遗留 |
| **展望** | 有方向判断，但无改动点、无验收断言、需外部触发条件 | 有验收断言 → 计划 |
| **经验** | 能写全「现象 → 根因 → 做法」三段，跨任务可复用 | 只是「某功能没做」→ 计划/遗留 |
| **遗留** | 现状行为 + 判定 + 归宿 | 有改动方案 → 计划（双向引用） |

两条最容易混的边界：

- **遗留 vs 计划**：条目本身是**问题** → 遗留；是**改动方案** → 计划。两边用同一 ID 互相引用。
- **遗留 vs 展望**：「有意裁剪」若无方向 → 只留遗留（判定「接受」）；若有方向与触发条件 → 遗留记现状、展望记方向。

## 二、遗留的 R1–R6 判定（写遗留时必用）

按顺序适用，先命中先定：

| 序 | IF（现状行为满足） | THEN 判定 | 归宿 |
|---|---|---|---|
| R1 | 行为与文档/契约承诺不符，且无「有意保留」的书面理由 | **缺陷** | 转计划 |
| R2 | 有意的兼容子集 / 安全取舍，且**没有**补齐方向 | **有意裁剪** | 接受（不修） |
| R3 | 有意的兼容子集 / 安全取舍，且**有**方向与触发条件 | **有意裁剪** | 接受 + 方向见展望 |
| R4 | 已知残缺，判定「现在不修」并有明确书面理由 | **知情接受** | 接受（不修） |
| R5 | 现象已记录但根因/边界未定，或结论来自推断而非实测 | **待验证** | 转计划或标注【待核实】 |
| R6 | 缺陷已修复并有验收证据 | **不登记为遗留** | 只进 §九「已封堵项索引」，指向变更史 |

**R4 是这份文档最独特的价值**：它把「我们决定不修」写成书面事实。后续会话读到「知情接受」就不会把它当 bug 反复排查，也不会反过来以为它已实现。写 R4 时**必须写清理由**，否则按 R1 判成缺陷。

## 三、条目模板（逐条套用）

**计划条目：**

```
### <ID> <标题>
- **目标**：
- **现状证据**（`文件:行号` 或实测输出）：
- **改动点**：
- **验收断言**：
- **实测证据**（真实模型实测：命令 + 结果 / 证据路径）：
- **风险 / 回滚**：
- **依赖 / 需确认**：
- **状态**：未启动 / 进行中 / 部分完成（注明已完成部分）
- **来源**：archive/2026-09-16-consolidation/<原文件名> §X
```

**遗留条目：**

```
### <ID> <标题>
- **现状行为**（`文件:行号` 或实测证据）：
- **判定**：缺陷 / 有意裁剪 / 知情接受 / 待验证
- **影响面**：
- **归宿**：转计划（`计划.md` <ID>） / 转展望（`展望.md` <ID>） / 接受（不修）
- **来源**：archive/2026-09-16-consolidation/<原文件名> §X
```

**经验条目**：三段必须齐全——**现象**（可观测的坏行为）/ **根因**（为什么会这样）/ **做法**（以后怎么办）。缺任一段就不算经验，应归入遗留或计划。

状态口径：`未启动` = 代码里查不到任何落地痕迹；`进行中` = 部分改动已提交但批次未收口；`部分完成` = 批次内部分项已落地并验证，余项未做（**须注明已完成部分**）。

## 四、ID 纪律：绝不重编号

`L16`、`T1`、`P-8`、`E28`、`PRODCAP-3`、`SKY-6`、`TMR-L1` 这些是**跨文档引用锚点**，源码注释里都在用。新条目应**向源文档编号体系靠拢**，不另起一套。发现同一 ID 在源文档状态不一致时，以**代码实测**为准，并登记进 `裁定.md`「状态漂移裁定登记」（原 `计划.md` §九）。

## 五、数字纪律：绝不手抄

测试数量、门禁阶段数、枚举变体数、ratchet 基线这类**由代码/脚本派生**的计数：

- 唯一真值源是 `MAINTENANCE.md`；用 `node tools/count-tests.mjs` 现取，**不要背数字也不要照抄旧文档**。
- 其他文档一律写「见 `MAINTENANCE.md` §2」，不复制具体数字。
- `check-doc-claims` 会把文档里的字面值与脚本现算值逐条比对——对不上就红。**历史层（「原文 + 变更标注」体例）保留旧值不判失配**，这是有意的设计。

## 六、物理约定（`check-docs` 规则 D2/D7 强制）

- `docs/` 根下**只允许**：六类活文档 + `README.md` + `fixtures/` + `archive/` + `plans/`。
- 仓库根 `*.md` **只允许** `README.md` / `AGENTS.md` / `MAINTENANCE.md`。
- `docs/plans/` **只放调查报告**（如 `FRONTEND-REPORT.md`）。**计划条目的唯一出口是 `docs/计划.md`**——临时执行稿必须在收口时并入台账并删除原稿（已有 8 次先例）。
- 新增不属于六类的文档，须先在 `docs/README.md` 登记其分类。

## 七、锚点体例（跨文档引用时必读）

GitHub 对中文标题的锚点生成有两处反直觉：

1. **全角标点整字丢弃且不占位**：`PRODCAP-1 进度可续：任务事件…` → `prodcap-1-进度可续任务事件…`
2. **标题里的 `+` 会保留**，它两侧的空格各产生一个连字符：`…持久化 + 断点补拉` → `…持久化--断点补拉`（**两个**连字符）

改了章节标题后要人工核一次外部引用——`check-docs` 的锚点校验是「尽量校验」，**覆盖不到时不报错**，别只信门禁绿。

## 八、批次收口时的回填清单

| 台账 | 什么时候动 |
|---|---|
| `功能.md` | 新增了用户可见能力 |
| `契约.md` / `契约-协议与配置.md` | 动了端点字段、SSE 负载、线格式、配置项、平台分支规则 |
| `契约-架构与数据.md` | 动了分层归属（并同步 `tools/arch-layers.json`） |
| `计划.md` | 条目状态变化 |
| `遗留.md` | 发现缺陷本批不修，或有意裁剪 |
| `经验.md` | 可复用的「现象→根因→做法」 |
| `功能-变更史.md` | 每批落地写一章：commit hash + 命令 + 当时实测数值 |
| `MAINTENANCE.md` | 可计数事实的唯一真值源 |

**R6 提醒**：修好一个遗留项时，不要把它从遗留里静默删掉——移到 §九「已封堵项索引」，并指向变更史对应章节，保留溯源。

相关技能：`kedai-batch-dev`（流程中的回填步骤）、`kedai-gate-runner`（文档段失败判别）。
