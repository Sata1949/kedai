## mvu 变量协议

> 本节是 kedai mvu 变量系统**前后端语义对齐的权威规范**，是「三结合梯队架构」中
> 老层兼容契约（L1）与跨端传帮带经验文本（见 `archive/2026-09-16-consolidation/ARCHITECTURE-3H.md`）。
> 双端实现：前端 `web/src/mvu/`（展示/交互层），后端 `server-rs/src/parsing/assistant/`
> （权威协议 + 持久化 + 注入 LLM）。语言不同不可合并代码，靠本节锁定行为一致。
> 前端 `web/src/mvu/parser.test.ts` 与 `variables.test.ts` 的测试用例是**跨端验收基线**。
> 原文：`archive/2026-09-16-consolidation/mvu-protocol.md`。

### 协议概览

- **变量树**：根即 `stat_data`（会话级持久化，SQLite `session_assistant_vars` 表）。前端另有
  `display_data` 展示树（`stat_data` 镜像，仅前端交互用，不参与后端落库/注入）。
- **输出协议**：模型回复中 `<UpdateVariable>…</UpdateVariable>` 块被剥离并应用为变量补丁。
- **初始化**：世界书条目注释含 `[InitVar]` / `[InitialVariables]` 时，条目内容作为初始变量树。

### UpdateVariable 块解析

- 正则：`<\s*UpdateVariable\b[^>]*>([\s\S]*?)</\s*UpdateVariable\s*>`，大小写不敏感（`(?is)` / `gi`）、容忍属性，并**额外容忍标签名与尖括号之间的空白**（`< UpdateVariable >`）——该宽容是刻意的双端对齐（后端 `parsing/assistant/patch.rs` 与前端 `web/src/mvu/parser.ts` 同形，已由 `docs/fixtures/mvu_patch_cases.json` 对拍）。
- 块内格式优先级：**① `<JSONPatch>` 数组（JSONPatch 协议）→ ② `_.set(...)` 语句序列
  （MagVarUpdate 兼容）**。JSONPatch 整块解析失败时回落到 `_.set` 解析。
- 同一文本可含多个 UpdateVariable 块，全部剥离（内容不保留）并依次应用。

#### JSONPatch 支持的操作（RFC 6902 子集 + 扩展）

| op | 语义 | 说明 |
|---|---|---|
| `replace` / `set` | 路径写值 | 中间对象/数组自动创建 |
| `delta` / `add` | 数值加 delta | **值为非数字时跳过整条**；路径不存在按 0 起步 |
| `insert` | 写值 | **与 replace/set 语义等价**（后端不设独立类型，并入 replace） |
| `remove` | 删除路径 | 不存在则忽略 |
| `move` | 移动 | `from` → `to`；**源缺失整条跳过**（容错优先，不整批失败） |

#### MagVarUpdate `_.set` 兼容

- 语句形如 `_.set('path', old, new);//原因`，`old` 为旧值占位（可任意），`new` 为真实新值。
- 解析取路径与**最后一个实参**为新值；字符串实参需**转义还原**（`\\ \' \" \n \r \t`，未知转义保留）。
- **reason**（原因注释）：`//行注释` 与 `/* 块注释 */` 均提取为补丁的 `reason` 字段
  （前端用于展示；后端持久化不依赖 reason，但解析结果与前端一致以保证可测性）。
- 路径支持点分（`a.b.c`）与斜杠（`/a/b/c`）两种分隔，剥 `stat_data.` 前缀。

### 路径规范（双端一致）

- **危险段过滤**：路径段为 `__proto__` / `constructor` / `prototype` 时整段丢弃
  （LLM 输出不可信，防御原型污染）。
- **数组访问**：数字段访问数组下标；`-` 表示数组追加。
- **自动创建**：写路径时中间标量被穿越 → 替换为对象/数组容器（下一段是数字则为数组）。
- **stat_data 前缀**：`stat_data` 或 `stat_data.xxx` 开头剥前缀；裸路径（`xxx`）等同 `stat_data.xxx`。

### 格式化输出

- `{{format_message_variable::path}}` / `{{get_message_variable::path}}`：大小写不敏感；
  path 省略 = 全树。输出格式：对象/数组 YAML 风格缩进，字符串带双引号，数字/布尔裸输出，null 输出 `null`。
- `<StatusPlaceHolderImpl/>`：替换为全树格式化文本。
- `<status_current_variable>` 起止标签：剥离（内容保留）。
- 数值显示：整数（|f| < 1e15）裸输出整数，浮点保留小数。

### 双端职责边界

| 层 | 职责 | 独有能力 |
|---|---|---|
| 前端 `web/src/mvu/` | 展示/交互：变量面板、快照回放、LLM 宿主全局（`Mvu`/`$`/`_`/`toastr`）、reason/oldValue 展示 | `stat_data`/`display_data` 双树、`replayMvuVariables`、`hasUpdateVariable` 快速判断 |
| 后端 `server-rs/src/parsing/assistant/` | 权威协议 + 持久化 + 注入 LLM + 两步生成状态栏 + EJS 桥接 | `AssistantVars` 持久化、`apply_patches`、EJS `get_js/set_js/add_js`、`parse_patch_array` 被 `update_variables` 工具复用 |

**红线**：

- `reason`/`oldValue` 仅前端展示用，后端不参与落库/注入（`PatchOp.reason` 解析保留但不持久化）；
- 后端是「权威」：生成流程、注入、落库均以后端解析结果为准，前端解析仅用于展示对齐；
- 双端任一改动本协议语义，必须同步更新本节 + 双端测试（前端 parser.test.ts 为基线）。

- 后端：`cargo test --manifest-path server-rs/Cargo.toml`（assistant 相关测试全绿）。
- 新增协议特性：先在**前端 parser.test.ts 加用例**（作为基线），再后端实现并加对应用例。

## @INJECT 注入协议

> ST-Prompt-Template(酒馆助手生态)兼容的精确消息插入协议。
> 代码事实源：`server-rs/src/agents/engine/messages/inject.rs`
> （`parse_inject_insertion` 解析 + `apply_inject_insertions` 应用）；
> 条目分离与内容渲染在 `server-rs/src/agents/engine/mod.rs`
> （检索 `parse_inject_insertion`）。
> 原文：`archive/2026-09-16-consolidation/inject-protocol.md`。

### 语法

@INJECT 指令写在**世界书条目的 comment(标题)**里；与 ST 原版语义一致，
**条目必须 enabled=false 才生效**（禁用条目不参与普通注入，只提供插入内容）。
条目内容先经 `render_assistant_content_with` 渲染（EJS/宏可用），
渲染后为空白的条目被跳过。

三种插入形式（参数大小写不敏感、逗号分隔、`role` 缺省为 `user`）：

```
@INJECT pos=N,role=R
@INJECT target=ROLE,index=N,at=before|after,role=R
@INJECT regex=PATTERN,at=before|after,role=R
```

参数解析规则（以 `parse_inject_insertion` 实现为准）：

- comment 中找不到 `@inject`(大小写不敏感)或其后无参数 → 返回 None(不解析)。
- 每个 `key=value` 对独立解析；空值、未知 key 静默忽略。
- 优先级：`pos` > `target+index` > `regex`——`pos` 存在即按 Pos 处理；
  否则 `target` 与 `index` 同时存在才按 Target；再否则 `regex` 存在按 Regex；
  都不满足返回 None(如 `@INJECT pos=abc` 解析失败 → None)。
- `at` 仅接受 `before`/`after`(大小写不敏感)，缺省 after；非法值视为未提供。
- `role` 为插入消息的角色(缺省 `user`)，与 `target` 的目标角色是两个参数。

### 插入位置语义（apply_inject_insertions）

- **system 锚定**：system 消息始终保持在数组开头；`pos`/`target` 的索引
  只针对**非 system 消息**计数，避免破坏系统提示词首位。
- **Pos**：`pos=0` → 第一条非 system 消息之前；`pos=-1` → 最后一条消息之后；
  负值从尾部数(`rel = n + pos + 1`)；最终位置 clamp 到 `[0, n]`(以代码实现为准)。
- **Target**：`target=ROLE` 指定目标角色(该角色的 system 消息不参与)；
  `index` 从 **1** 开始，`-1` 表示该角色最后一条(负值从尾部数)；
  `at=before|after` 插到目标消息之前/之后。
- **Regex**：pattern 编译为大小写不敏感正则，匹配**第一条**命中的
  非 system 消息，插到其前/后。
- **应用顺序**：所有插入先计算目标完整索引，升序排序后**从后往前**执行
  (先插后面的位置，前面索引不漂移)，与 ST 原版「位置从后往前执行」一致。
- **容错**：内容空白、正则编译失败、目标角色不存在、index 越界 →
  **静默跳过该条**，不 panic、不整批失败。
- 插入的消息为 `LlmMessage::plain(role, 渲染后内容)`。

### 执行时机

@INJECT 在引擎**消息构建期**应用：条目分离与渲染完成后、上下文裁剪
(`trim_to_context`)**之前**(位置以构建期消息数组为准；裁剪后再插入会被切掉
或定位漂移，见 `engine/mod.rs` 注释)。

GENERATE 的两个变体也转为本机制(见「GENERATE / RENDER 协议」)：

- `[GENERATE:{idx}:BEFORE]` → `Pos { pos: idx, role: "user" }`
- `[GENERATE:{idx}:AFTER]` → `Pos { pos: idx + 1, role: "user" }`
- `[GENERATE:REGEX:pattern]` → `Regex { pattern, at: After, role: "user" }`

同批 @INJECT 与 GENERATE 转换条目合并进同一 placements 列表，
统一按「从后往前」语义插入。

### 示例

```jsonc
// 绝对位置:第一条非 system 消息之前插一条 system 级注入
{ "comment": "背景注入 @INJECT pos=0,role=system", "content": "……", "enabled": false }

// 尾部追加(缺省 role=user)
{ "comment": "结语提醒 @INJECT pos=-1", "content": "(别忘了现在是台风夜)", "enabled": false }

// 目标消息:第一条 assistant 回复之前插一条 assistant 消息
{ "comment": "@INJECT target=assistant,index=1,at=before,role=assistant", "content": "……", "enabled": false }

// 正则:第一条提到「图书馆」的消息之后补充设定
{ "comment": "@INJECT regex=图书馆,at=after", "content": "(图书馆周三闭馆)", "enabled": false }
```

无效示例（全部静默跳过，消息数组不变）：

```
@INJECT pos=abc            # pos 解析失败 → None,不进插入列表
@INJECT                    # 无参数 → None
@INJECT regex=(            # 正则编译失败 → 应用期跳过
@INJECT target=assistant,index=9   # 越界 → 应用期跳过
```

### 测试锚点

`messages/inject.rs` 内测试覆盖：pos/负 pos 解析、target/regex 解析、
缺省 role、大小写不敏感、pos=0 插首条非 system、pos=-1 插尾部、
target before、regex 匹配第一条、多条从后往前、无效/空白跳过。

## GENERATE / RENDER 协议

> ST-Prompt-Template(酒馆助手生态)兼容的内容注入标签协议。
> 代码事实源：`server-rs/src/parsing/assistant/inject_tag.rs`（标签解析 + 条目收集）、
> `server-rs/src/parsing/assistant/render.rs`（内容渲染）、
> `server-rs/src/agents/engine/mod.rs`（引擎消费，检索 `collect_generate_entries_with`）。
> 原文：`archive/2026-09-16-consolidation/generate-render-protocol.md`。

### 标签语法

标签写在**世界书条目的 comment(标题)**里，大小写不敏感、容忍前后空白，
可嵌入标题文字中（如 `分阶段人设 [Render:After] 注入` 也能识别）。

| 标签 | 解析结果(InjectTag) | 含义 |
|---|---|---|
| `[GENERATE:BEFORE]` | GenerateBefore | 注入到 system 提示词开头 |
| `[GENERATE:AFTER]` | GenerateAfter | 注入到 system 提示词末尾 |
| `[GENERATE:{idx}:BEFORE]` | GenerateIndex{idx, before:true} | 第 idx 条消息(0-based，非 system)之前插入 |
| `[GENERATE:{idx}:AFTER]` | GenerateIndex{idx, before:false} | 第 idx 条消息之后插入 |
| `[GENERATE:REGEX:pattern]` | GenerateRegex{pattern} | 正则匹配到的第一条消息之后插入 |
| `[RENDER:BEFORE]` | RenderBefore | 渲染阶段注入(见下「RENDER 与 GENERATE 的语义差异」) |
| `[RENDER:AFTER]` | RenderAfter | 同上 |
| `[InitialVariables]` / `[InitVar]` | InitialVariables | 初始变量条目，**不进**注入收集 |
| 其他 / 畸形(如 `[GENERATE:MEOW]`、`[GENERATE:abc:BEFORE]`) | None | 无标签，走普通世界书注入链路 |

解析细节（以 `parse_inject_tag` 实现为准）：

- REGEX 的 pattern **原样保留**（不转大小写）；`before` 固定为 true（解析层），
  但引擎消费时实际语义是「匹配消息**之后**插入」（见「引擎注入时机与落点」）。
- 索引变体要求 `{idx}` 可解析为 usize 且后缀恰为 BEFORE/AFTER，否则整体判 None。
- `[InitialVariables]` / `[InitVar]` 独立优先匹配，不会被 GENERATE/RENDER 分支吞掉。

### 条目收集（collect_generate_entries_with）

引擎在消息构建期对世界书条目做分流：

- 仅 **enabled** 且 comment 带 GENERATE/RENDER 标签的条目进入注入收集；
  `[InitVar]` / `[InitialVariables]` 条目分流到初始变量阶段（`collect_init_vars`）；
  无标签条目走原普通世界书注入链路。
- 进入收集的条目**在分离阶段即完成渲染**（`render_assistant_content_with`，
  此时变量树已初始化），渲染结果存为 `GenerateEntry.rendered`。
- 排序：`GenerateIndex` 条目按 idx 升序（稳定排序）；其余标签保持 entries 原相对顺序。

渲染管线（以 `render.rs` 的 `render_assistant_content_with` 为准），依次执行：

1. **EJS 模板渲染**：内建 `getvar/setvar/addvar` 直接读写变量树；
   `getwi/getchar/getpreset/getqr/getChatMessage` 等经渲染上下文真实读取；
   `injectPrompt(key, prompt, order?, sticky?, uid?)` 登记注入清单。
2. **容错降级**：EJS 渲染出错且输出为空时回退保留原文（内容不丢失，记 warn 日志）。
3. `{{format_message_variable::path}}` / `{{get_message_variable::path}}` 宏
   → 变量树格式化文本（path 可省略 = 全树）。
4. `<status_current_variable>` 起止标签剥离（内部内容保留）。
5. `<StatusPlaceHolderImpl/>` → 全树格式化文本替换。

### 引擎注入时机与落点（agents/engine/mod.rs）

注入发生在**消息构建期**：变量树初始化、世界书分组之后，上下文裁剪
（`trim_to_context`）**之前**。各标签落点：

- **GenerateBefore / RenderBefore** → 拼到首个 system 消息**开头**
  （**2026-09-28 实测更正**：实际落在**运行时主提示词 AGENTS_RUNTIME.md 之前**，而非之后——执行顺序是
  `agents/engine/messages/context.rs` 先把运行时提示词前置到 `s0.content`、随后再把 generate_before
  前置到同一 `s0.content` 的开头，故本段文本最终排在 system 消息最前面；原文与代码注释同错，一并更正）。
- **GenerateAfter / RenderAfter** → 拼到首个 system 消息**末尾**，
  并计入 `protected_tail`（上下文裁剪时优先保留，防注入先于正文被切掉）。
  多条按收集顺序以 `\n\n` 拼接。
- **GenerateIndex{idx, before}** → 转 @INJECT 机制：
  `InjectInsertion::Pos { pos: idx(before)或 idx+1(after), role: "user" }`，
  由 `apply_inject_insertions` 插入消息数组（详见「@INJECT 注入协议」）。
- **GenerateRegex{pattern}** → 转 @INJECT 机制：
  `InjectInsertion::Regex { pattern, at: After, role: "user" }`，
  即「正则匹配到的第一条非 system 消息**之后**插入」（该消息的回应素材）。
  注意：解析层 `before` 字段当前未被引擎消费（以 engine 实现为准）。
- **injectPrompt 登记清单**：EJS 模板内 `injectPrompt(key, prompt, order?, sticky?, uid?)`
  登记的提示词，渲染后按 `(order, position)` 排序并入 generate_after(system 尾部，
  计入 protected_tail)；内容为空的登记被跳过。

### RENDER 与 GENERATE 的语义差异（重要）

ST 原版中 RENDER 标签仅影响**显示渲染**、不影响发送给模型的生成内容。
**kedai 没有独立的显示渲染管道**，因此 RENDER:BEFORE/AFTER 与 GENERATE 同路
并入 system 首/尾（即也影响生成）。这是有意的兼容取舍（以 `engine/mod.rs`
「RENDER 仅影响显示渲染……kedai 无独立显示渲染管道，故并入生成注入」注释为准）；
前端显示渲染留有扩展位（见 `archive/plan6-ecosystem-devtools.md` 6a 记录）。

### 与变量树 / mvu 的交互

- 渲染在变量树（`AssistantVars`）**初始化之后**进行：条目 EJS 可读到
  `[InitVar]` 建立的初始树与会话持久树。
- EJS 内 `setvar/addvar` 的写入是**真实副作用**：渲染结束后引擎把变更同步进
  scopes chat 镜像，供后续消息构建的宏展开读取（以 engine 实现为准）。
- 条目渲染读取的是本会话变量树；树内容变化（如 mvu `<UpdateVariable>` 补丁生效后）
  会在**下一轮**渲染中反映。
- mvu 状态块（变量树快照 + 更新协议）是独立注入通道（`make_state_block_with_contract`，
  位置跟随设置 `mvu_vars_position`：system 常态组 / user_tail 激发组），
  与 GENERATE/RENDER 注入互不覆盖。

### 示例

世界书条目（角色卡内嵌 character_book 或独立世界书均可）：

```jsonc
{
  "comment": "[GENERATE:BEFORE] 世界观总纲",
  "content": "本作世界观:近未来海滨小城,时间循环每 7 天重置。",
  "enabled": true
}
```

→ 每轮生成时，渲染后的内容拼到 system 提示词开头。

```jsonc
{
  "comment": "好感度播报 [GENERATE:REGEX:好感|心情]",
  "content": "<% const v = getvar('stat_data.affection') || 0; %>当前好感度:<%= v %>",
  "enabled": true
}
```

→ 历史中第一条匹配 `好感|心情`（大小写不敏感）的非 system 消息之后，
插入一条 user 角色的渲染结果（EJS 读取变量树求值）。

```jsonc
{
  "comment": "[GENERATE:0:AFTER] 开场补充设定",
  "content": "(补充:开场白发生时正值台风夜)",
  "enabled": true
}
```

→ 第 0 条非 system 消息（通常为首条 user/assistant）之后插入，role=user。

```jsonc
{
  "comment": "[RENDER:AFTER] 状态栏模板",
  "content": "{{format_message_variable::stat_data}}",
  "enabled": true
}
```

→ 变量树 stat_data 子树格式化文本拼到 system 末尾（计入 protected_tail）；
注意 kedai 中 RENDER 也影响生成（见「RENDER 与 GENERATE 的语义差异」）。

### 一、设置字段回退规则表

`RuntimeSettings` 扁平字段 = **roleplay 权威值**（引擎直接读）；`task: ModeSettings`
覆盖层字段全为 `Option`，`Some` = 覆盖、`None` = 沿用。连接信息始终全局共享，不入覆盖层：
扁平 `openai_base_url` / `openai_api_key` / `model` 自二维批次 4（2026-09-22）起是
**默认连接的派生视图**（唯一例外——这三个字段的真源在 `connections`，不再是可手改的权威值）；
多套连接的两个新键（`connections` / `active_connection_id`）及其真源与投影语义见本节末
「`connections` / `active_connection_id` 线格式与真源」。

| ModeSettings 字段 | task 回退规则（None 时） |
|---|---|
| `default_temperature` / `default_top_p` / `default_max_tokens` / `max_context_tokens` | 沿用扁平值 |
| **`agent_system_prompt`** | **不回退**（隔离）：None → 注入内置任务向默认词 `default_task_agent_prompt()`；`Some("")` → 显式清空不注入；`Some(v)` → 覆盖 |
| `task_persona_full`(R3a) | 沿用扁平值；扁平默认 `false` = 精简（旧配置无此字段，serde default 零迁移）。仅任务模式执行者人设拼装消费，roleplay 引擎侧无人设注入点、不读 |
| **`task_prompt_inject_enabled`**（2026-09-10） | 沿用扁平值；扁平默认 `false` = **隔离**（不继承注入）。仅任务模式 system 拼装消费，roleplay 引擎侧不读 |
| **`task_coding_bundle_enabled`**（2026-09-28 编码能力包） | 沿用扁平值；扁平默认 `false` = 不启用（旧配置无此字段，serde default 零迁移）。消费点两处：① 任务模式**缺省默认词**的二选一；② **内置流程库的包流程并入**（CODE-5，2026-09-30，见「能力包流程并入契约」节——开包并入 2 条编码流程、关包不回收）。roleplay 引擎侧不读 |
| `max_tool_rounds` / `tool_history_keep_rounds` / `tool_history_budget_tokens` 等任务侧参数 | 沿用扁平值 |
| **`max_flow_call_depth` / `max_flow_calls_per_task` / `default_node_max_context`**（A 批 A3/A4，2026-09-24） | 沿用扁平值；扁平默认 **2 / 8 / 0**（0 = 不裁剪 = 零行为变化）。三者都只被**任务侧**消费（流程动态调用闸与节点输入装配），roleplay 引擎侧不读——与 `max_tool_rounds` 同属「任务侧参数」家族 |
| `search_endpoint` / `mvu_vars_position` / `reflect_prompt` / `preset_tail_*` / `reflect_advice_*` 等其余字段 | 沿用扁平值 |

`task_prompt_inject_enabled` 口径（2026-09-10 六模式实跑修复 F2）：`false`(默认)时任务
执行/汇总/followup 轮次的 system **不注入** `prompt_floors.json`；`true` 时沿用旧行为
（与角色扮演共用同一注入源，经 `prompt_kit::system_inject_text` 只取 system 楼层）。
背景：`prompt_floors.json` 通常承载角色扮演的文章要求（如「1200 字/第三人称/禁词表」），
注入任务 system 会与任务目标对抗——实测 legacy 追加「压缩到 200 字」后结果反而从
1062 涨到 1305 字。该字段是开关而非文本，不进入 LLM 上下文；预览层同步门控
（`/api/settings/prompt-preview?mode=task` 在关闭时不推送注入层，保持「预览即真实下发」）。

`task_coding_bundle_enabled` 口径（2026-09-28 编码能力包，即 HARNESS3-6 的落点）：
`true` 时任务模式执行者/汇总者的**缺省** Agent 系统提示词改用编码执行者模板
（`default_coding_task_agent_prompt`——先读后写、遵循既有风格、最小改动、改完跑验证收尾）；
`false`（默认）仍用通用任务向默认词 `default_task_agent_prompt`。两种缺省词的**选择点唯一**：
`for_mode` 的 task 分支 match（与 `agent_system_prompt` 的三态判定同一处）。三类输入语义不变：
缺字段/null → 走该分支选默认词；`""` → 显式清空不注入；`"v"` → 用户自定义**逐字优先**，
与开关无关。该字段是**纯缺省值开关**：不改变工具面（`task_tool_policy` 与 platform/workspace
两道闸门不受影响）、不改变提示词分层结构、不影响角色扮演模式。**工具使用纪律不在本模板内**：
通用工具纪律的单一出处是 `task_core::prompt_consts::EXECUTOR_TOOL_DISCIPLINE`（按「本轮有工具」
条件追加），HARNESS3-6 的口径即「编码模板引用该常量，不写第二份」。
**CODE-5 起本开关多一个消费点**：内置流程库的**包流程并入**（开包 → 并入
`builtin-code-review` / `builtin-code-impl` 两条常量流程；关包不回收已注入副本；
运行期翻转经 `PUT /api/settings` 的写入钩子即时生效）——语义与边界见
「能力包流程并入契约」节。该消费点同样**不影响工具面**（流程里的工具白名单照旧走
`task_tool_policy` 与 workspace/platform 两道闸门）。

`task_persona_full` 三态口径（R3a，2026-09-02）：`None` / `Some(false)` = 精简（执行者
人设只注入 description + personality 两段，去掉 scenario 与 mes_example 文风示例——
对任务执行大部分无用，实测是 system 膨胀来源之一）；`Some(true)` = 完整（现状四段全量，
与改造前逐字节一致）。该字段是开关而非文本，不进入 LLM 上下文，无需 untrusted 包裹；
它改变的是 `persona_style` 产出内容，包裹约定不变（人设段仍经 `untrusted_boundary("character", …)`）。

`agent_system_prompt` 是唯一刻意隔离的字段：扁平值多为角色扮演人设词，直接继承
会污染任务执行（2026-08-25 实测「写秋天的短诗」被执行为言情小说）。WP7 起该隔离
由类型系统保证：扁平字段类型 `RoleplayPromptConfig`，覆盖层类型
`Option<TaskPromptConfig>`，两者不同源，`for_mode` 的 task 分支 match 是唯一
转换点——绕过它隐式继承扁平值无法通过编译。serde 均为 `transparent`，
settings.json 与 `/api/settings` JSON 线格式与旧 String/Option<String> 逐字节一致
（裸字符串；None 省略字段不落 null；null/缺字段读入均为 None）。

#### `RoleplayPromptConfig` / `TaskPromptConfig` 线格式真源

`server-rs/src/services/settings_service/params.rs` 是线格式的真源，字段定义如下要义：

- `RoleplayPromptConfig(pub String)`：`#[serde(transparent)]`，序列化为**裸字符串**，
  settings.json 与 `/api/settings` JSON 线格式**逐字节不变**；语义为「空串 = 使用内置
  默认角色扮演模板」。
- `TaskPromptConfig(pub String)`：`#[serde(transparent)]`；仅出现在 task 覆盖层
  （`Option<TaskPromptConfig>`）；`ModeSettings.agent_system_prompt` 声明为
  `Option<TaskPromptConfig>` + `#[serde(default, skip_serializing_if = "Option::is_none")]`
  ——None 由外层 Option 的 skip_serializing_if 省略，不落 null，settings.json 与 API
  线格式零变化。
- 两者**类型不同源**：task 覆盖值无法被误赋给 roleplay 扁平字段，「task 不继承 roleplay
  人设词」由类型系统而非注释约定保证（`for_mode` 是唯一转换点）。
- `ModeSettings` 全字段 `Option` + `#[serde(default, skip_serializing_if = "Option::is_none")]`；
  仅覆盖生成参数与 Agent 配置，连接信息始终共享。

三态语义（API 与磁盘一致）：

| 输入 | 语义 |
|---|---|
| 字段缺省 / null | 沿用（task：内置任务向默认词） |
| `""` | 显式清空（task 不注入 Agent 提示词） |
| `"v"` | 覆盖 |

#### `connections` / `active_connection_id` 线格式与真源（二维批次 4，2026-09-22）

`RuntimeSettings` 增两个字段，`settings.json` 与 `GET`/`PUT /api/settings` 的线格式**同步新增
这两个键**（**端点路径与方法零改动**，只增键，旧前端只读它认识的键即可）：

| 键 | 类型 | 语义 |
|---|---|---|
| `connections` | `Vec<ConnectionProfile>` | **多套连接的真源**；元素 `ConnectionProfile { id, name, connector_type, base_url, api_key, model, api_style, enabled }`（定义在 `server-rs/src/services/settings_service/connection.rs`） |
| `active_connection_id` | `Option<String>` | 默认连接 id；缺失或指向不可用连接时按下方回退规则重算 |

- **两个键都必须带 `#[serde(default)]`**：旧 `settings.json` 缺这两个键时若整文件反序列化失败，
  `load` 会整体回退环境配置 → **用户全部设置静默丢失**。由
  `old_settings_json_without_connections_key_still_loads` 锁死（删掉该属性即变红）。
- **`connector_type` 取值域** = `openai-compatible` | `mock`（`normalize_connector_type`，
  与 `connectors::available_connector_types()` 的展示项一一对应）；**非法值回退前者**、不报错
  （刻意不走 `build_connector` 的「未知类型回退 mock」——用户填了地址却被静默降级成演示最难排查）。
- **真源与投影**：`connections` 是真源；扁平 `openai_base_url` / `openai_api_key` / `model`
  是**默认连接的派生视图**。load / save / PUT **三处**统一走 `normalize_connections()`
  （逐条卫生清理 → id 去重 → 默认连接回退 → `apply_active_projection()`），投影**无条件重算**
  ——故**手改 `settings.json` 里的扁平字段不再生效**（改连接要改 `connections`）。
  PUT 的扁平字段分支改为**写入默认连接**（无可用连接时新建一条），旧客户端行为不变。
- **幂等播种**：load 时 `connections` 为空 → 用扁平字段播种一条「默认连接」
  （固定 id `default`、类型 `openai-compatible`、`enabled`），`active_connection_id` 指向它；
  判据**只有「数组为空」**，第二次读入不再播种，既有 id 一律不改写（id 是密文配对的键）。
  `from_config`（新装 / 无配置文件）同样播种一条（内容即 `.env` 值，故行为与播种前等价）。
- **默认连接回退**：`active_connection_id` 指向不存在或已停用的连接 → 回退「第一个启用的连接」；
  一个启用的都没有（全停用 / 删空）→ 投影为空 → 连接器回退 `mock`（与「未配置」的既有语义一致）。
  允许删除任意连接（含最后一个），**密钥一并丢弃、删除后不可恢复**。
- **连接器切换口径统一**：目标类型由 `resolve_connector_target(默认连接, 当前类型)` 一处决定，
  **启动装配与 PUT 重建共用**——无可用连接 → `mock`；连接显式声明 `mock` → `mock`；
  地址与密钥**没配齐** → 保持当前类型（当前是 mock 就继续 mock）；其余 → `openai-compatible`。
  判据取「地址 + 密钥都非空」而非「任一非空」：`openai_base_url` 的环境默认值本身非空
  （`config.rs` 的 `from_env` 缺省 `https://api.openai.com/v1`），只看地址会让全新安装 / 测试环境
  一启动就切到必然失败的真实连接器。旧实现启动用「都非空」、PUT 用「任一非空」两套口径，
  本批统一为前者（那次不一致会让无密钥的本地服务在重启后悄悄回落到 mock）。
  另：给显式 `mock` 类型的连接把地址与密钥都填上后，PUT 会自动把类型改回 `openai-compatible`
  （沿用既有「填了就生效」口径）。
- **接口方言 `api_style` 与端点后缀剥离（接口方言批次，2026-10-01）**：每套连接可选接口方言，
  取值域 `chat-completions`（默认）| `responses` | `anthropic`（`connectors::openai_compatible`
  的 `API_STYLE_*`；非法值 sanitize 回退默认档，与 `connector_type` 同纪律）。要点：
  - **线格式**：`settings.json` 与 `GET`/`PUT` 的连接元素**新增 `api_style` 键**
    （`#[serde(default = "默认 chat-completions")]`，旧文件缺键照常读入 → 既有行为不变）；
    PUT 元素 `api_style` 缺省 = 沿用已有值、非法值回退默认档，**不做** `Option::None` 与 `""` 的区分。
  - **端点后缀自动剥离**（`strip_endpoint_suffix`，Rust/前端 `normalizeUrl` 双端同规则）：
    BASE URL 尾部精确匹配 `/chat/completions`、`/completions`（→ chat）、`/responses`
    （→ responses）、`/v1/messages`、`/messages`（→ anthropic）、`/models`（只剥地址、不改方言）
    时剥回 base；**推断只改写默认档**（显式 `responses`/`anthropic` 不被 URL 后缀覆盖），
    两轮 sanitize 幂等。真实事故背景：用户把控制台文档的完整端点（含 `/chat/completions`）
    整段粘进 BASE URL → 连接器拼出 `…/chat/completions/models` → 模型列表静默回退成 1 个当前模型。
  - **各方言端点与鉴权**（连接器侧单一出处）：chat = `{base}/chat/completions`（既有）；
    responses = `{base}/responses`；anthropic = base 以 `/v1` 结尾时 `{base}/messages`、
    否则 `{base}/v1/messages`（官方 SDK base 不含 /v1 约定）。鉴权头：chat/responses 用 Bearer；
    anthropic 携带 `x-api-key` + `anthropic-version: 2023-06-01` + Bearer（兼容网关两种鉴权都收）。
  - **流式折算口径**（三方言统一产出 `LlmStreamChunk`，上层零分支）：Responses 的
    `response.completed/incomplete` 与 Anthropic 的 `stop_reason` 统一映射为
    `stop` / `length`（截断自愈只认 length）/ `tool_calls`；usage 字段逐方言映射，
    Anthropic 两段 usage（message_start + message_delta）合并为**唯一一块**（引擎对 Usage
    是累加语义）；`ping`/注释类心跳不算推进（停滞看门狗纪律不变）。
  - **连接器重建**：`api_style` 变化与 Base URL/Key/模型同权触发重建（PUT 判 `style_changed`；
    `ConnectorPool` 指纹含方言）——只改格式不改地址也必须立即生效。
  - **本批不做（登记）**：Responses 方言不下发停用序列（协议无对应参数）；Anthropic 方言
    temperature 钳制 0..=1、`tool_choice: none` 档以「不下发 tools」表达（协议无 none 值）、
    assistant 历史中的 `reasoning_content` 不回传（thinking 块需签名，原样拼接必被 400）。
- **凭据**：`connections[].api_key` 与顶层**同策略**（内存明文 / 落盘 `enc:v1:` 密文）、**逐条**加密；
  保存时磁盘密文**按 profile id 配对**（**绝不按数组下标**——删除中间一条或重排会让密文张冠李戴，
  且原值不可恢复）。两条既有不变量不变：① 内存为空而磁盘仍是密文 → 原样回写，**绝不擦成空串**；
  ② 落盘不得出现明文。GET **只回** `api_key_masked`（`****后4位`）与 `has_api_key`，

  接口层面无法把已配置的密钥改成空）。
- **上限与截断**：连接套数 ≤ 20（PUT 超限 → 400 `VALIDATION`，且校验在落盘之前返回，

### 三、untrusted 包裹约定

所有**外部来源文本**（角色卡、世界书、注入配置、用户可编辑提示词）进入 system
前必须经 `prompt_kit::untrusted_boundary(source, content)` 包裹：

- 包裹形态：`<UNTRUSTED_PROMPT_SOURCE source="...">` + 统一规则句 +
  `--- 内容开始/结束 ---` + `</UNTRUSTED_PROMPT_SOURCE>`（文本逐字节固定，
  引擎金样测试 `prompt_order_golden_with_untrusted_boundaries` 锁定）；
- 空内容返回空串，不产生空壳边界；
- source 命名（**2026-10-01 按 `grep untrusted_boundary` 实测重列**，TM-SCOUT-1 增
  `workspace_snapshot`）：引擎侧 `character_card`
  （含 `.description` / `.personality` / `.scenario` 三个分段）、`world_book`
  （**预设尾部也按此名包裹**，故不再有单独的 `preset_tail`）；任务侧 `character`（人设）/
  `world_book`（世界书）/ `prompt_inject`（注入）/ `agent_prompt`（用户可编辑 Agent 提示词）/
  `task_executor`（执行者指令）/ `task_goal`（任务目标）/ `flow_step`（流程节点产出）/
  `workspace_snapshot`（工作区侦察快照，规划调用动态追加层）；
- **内置指令不包裹**（引擎内置模板、「你是任务执行者/汇总者/规划者」）；
- 任务侧拼装点：`plan_task`/`plan_revise` **共用同一构建**（世界书 + 工作区侦察快照）、
  `generate_step_with`（人设/世界书/注入/Agent 提示词四段）、`summarize_task_with`
  （世界书/注入/Agent 提示词三段）。

### 四、新增字段时如何选择继承/隔离

1. **默认继承**：新字段进 `ModeSettings` 为 `Option<T>` + `for_mode` 的
   `if let Some(v) = ... { out.$field = v }` 三行——None 沿用扁平值。
2. **需要隔离**（扁平值对 task 有污染风险，如人设类文本）：
   - 为扁平字段与覆盖层各定义不同源的 newtype（参照
     `RoleplayPromptConfig`/`TaskPromptConfig`，`#[serde(transparent)]` 保持线格式）；
   - `for_mode` 分支显式 match 构造，None 时给 task 安全默认；
   - 在 `settings_service` 单测加：for_mode(Roleplay) 恒等扁平、for_mode(Task)
     三分支、serde 往返（参照 `prompt_config_serde_wire_format_unchanged` /
     `for_mode_prompt_isolation_is_type_level_invariant`）；
   - 若字段会进 LLM 上下文，拼装侧按第三节加 `untrusted_boundary` 包裹。
3. **判定口诀**：连接/资源类共享；数值参数默认继承；「文本内容会进入 system 且
   语义按模式不同」的字段必须隔离 + 包裹。

### 五、提示词预览口径（按模式）

`GET /api/settings/prompt-preview` 接受 `mode=roleplay|task` 查询参数（缺省
roleplay，旧客户端行为不变）：预览必须按 `for_mode(mode)` 的合并值展示，与对应
模式的实际下发一致——task 模式下 `agent_system_prompt` 层展示隔离后的任务向值
（而非 roleplay 扁平值），并追加规划器/执行者/汇总者三层固定提示词层（文本与
`task_service/prompt.rs` 单一来源逐字一致，执行与预览永不漂移）。前端在
`appMode` 切换时重拉预览。

> **口径澄清（2026-09-13 批次 6）**：「逐字一致」只对**task 三层固定指令**成立。
> 预览**不等于**最终 prompt 的逐字节镜像，以下两者有意不展示：
> ① 宏未展开（`{{char}}`/`{{world_info}}` 等按原文显示，真实下发经宏系统展开）；
> ② 运行期动态追加层（「可用工具」指南、技能渐进披露清单、摘要槽/记忆槽；**任务侧
> 「侦察指引」与「工作区侦察快照」段**同为动态追加层，随任务作用域/工作区内容变化）
> 在步骤确定后才拼接，预览不含。调试「模型到底看到了什么」应以服务端 `[[floors]]` 回显或
> 实际请求快照（`llm_requests`）为准，不要以预览反驳线上行为。

## 授权契约

> 活文档。描述 2026-09 授权改造后的判定规则、设置字段与前端入口。
> 相关代码：`server-rs/src/tools/permissions.rs`、`server-rs/src/tools/action_class.rs`、
> `server-rs/src/agents/engine/executor.rs`、`web/src/components/settings/AuthorizationSection.vue`。
> 原文：`archive/2026-09-16-consolidation/授权模式.md`（原题「授权模式(三档)」）。

### 一、为什么改

改造前的「授权 / 放行」二档有两个实际问题：

1. **放行模式黑名单形同虚设**：默认值 `delete_file / format_disk / modify_system / registry_write`
   四个名字都不是真实注册工具。打开「放行」后 `write`/`replace`/`create`/`update_variables`/
   `memory_write` 全部自动放行，一个都不拦。
2. **授权无法查看与撤销**：授权一经授予（尤其「允许当前角色」）便对该角色所有会话、
   含未来新建会话持续生效，而前端没有任何入口查看或撤销。
   另有「无角色会话点允许当前角色导致整轮生成报错中断」的缺陷。

因此把判定从「一个布尔开关」改为「**操作类型 × 路径区域**」的三档矩阵，并补上授权出口。

### 二、判定矩阵

先对一次工具调用分类（操作类型 × 路径区域），再按模式裁定。判定顺序：

```
未注册 → 拒绝
★ 命令执行高危硬门:命令为破坏性/提权级 → 需授权(逐条确认,不受任何授权豁免)
白名单命中(custom 步骤 / 任务策略闸门 / 子 agent) → 放行
显式授权(会话 / 角色) → 放行
「始终需授权」清单命中 → 需授权
三档文件规则(仅文件操作或外部工具的系统路径调用) → 见下表
命令执行(非高危,只读/写入级) → 严格/宽松需授权;放行模式放行
其余(非文件操作) → 原风险裁决:安全工具放行;放行模式放行;否则需授权
```

> **为什么命令级硬门排在「显式授权」之前**：`bash` 是**单一工具名**，工具级授权
> （白名单 / 会话授权 / 角色授权）无法区分「同一工具这次跑的是 `ls` 还是 `rm -rf`」。
> 若让工具级授权先放行，用户一旦授权过 `bash`，高危命令就会**静默执行**
> （2026-09-13 冒烟实测复现过该缺口，已修复并有回归测试锁死）。

| 模式 | 读文件 | 写文件(沙箱内) | 删文件(沙箱内) | 写/删系统路径(含 C 盘) | 其他工具 |
|---|---|---|---|---|---|
| 严格 `strict` | 需授权 | 需授权 | 需授权 | 需授权 | 原风险裁决 |
| 宽松 `loose`(默认) | 放行 | 放行 | 需授权 | **需授权** | 原风险裁决 |
| 放行 `bypass` | 放行 | 放行 | 放行 | **需授权** | 放行 |

要点：

- **系统路径的写/删是三档的硬底线**，任何模式下都需授权。
- **文件规则只作用于文件目标**。`write(target=bubble)` 写对话正文不受影响——否则严格模式下
  Agent 每写一段正文都要弹授权，产品不可用。
- `read` 仅当查询 `type=file` 时算「读文件」；查世界书 / 技能 / 角色提示词 / 子任务结果属「其他工具」，
  严格模式下不拦截。
- 「删」包含**清空文件内容**（`replace action=delete`）与**删除文件本身**（`replace action=remove`）两种。

### 三、操作与区域如何识别

`server-rs/src/tools/action_class.rs`：

- **操作类型** `ToolOp`：`ReadFile` / `WriteFile` / `DeleteFile` / `Exec` / `Other`
  （危险度序 `Other < ReadFile < WriteFile < DeleteFile < Exec`）。
  - `read`：`queries[].type=file` → 读文件。
  - `write`：`target=file` → 写文件；`target=bubble` → `Other`。
  - `create` → 写文件。
  - `replace`：`target=file` 且 `action ∈ {delete, remove}` → 删文件；其余 `target=file` → 写文件；
    纯 bubble 操作 → `Other`。混合操作取最高危项（删 > 写 > 读）。
  - `bash` → `Exec`；同时按 `tools/command_risk.rs` 计算**命令级风险**（`exec_risk`），
    供硬门判定与审计记录使用（见下节）。
- **路径区域** `PathZone`：
  - `Sandbox`：内置文件工具。其路径经 `safe_rel_path` 收口在 `data/character_files/{角色}/`，
    物理上无法触达 C 盘或任意系统路径。
  - `SystemPath`：插件 / MCP 工具参数中出现盘符（`C:\`）、UNC（`\\`）、Unix 绝对路径（`/`）
    或上级目录逃逸（`..`）时命中。
  - `Opaque`：外部工具但未识别出路径。

> 说明：内置工具没有「删除系统文件」「读写任意路径」的能力，所以「C 盘」规则实际约束的是
> **插件与 MCP 工具**（它们把参数转发给外部进程）。沙箱内路径的写/读/删由三档矩阵管控。

### 三·五、命令执行（bash 工具，阶段 E）

工具 `bash` 让 Agent 执行 shell 命令。四道闸：

1. **总开关** `exec_enabled`（默认关）：关闭时一律拒绝并留审计。
2. **工具级**：风险恒 `Dangerous`；任务模式默认策略（`deny_dangerous`）按**工具名**对 `bash` / `fs_write` / `fs_edit` / `fs_patch`
   开例外下发（任务模式需具备命令执行能力；`fs_patch` 另受**编码包闸门**——关包时不下发，见下方任务策略表），聊天模式走三档授权。注意「下发工具」≠
   「放行危险命令」——命令级硬门排在任何自动放行之前，见下。
3. **命令级**（核心）：`tools/command_risk.rs` 把命令分四级——

   | 级别 | 判定依据(摘要) | 处置 |
   |---|---|---|
   | `safe` | 只读检视(`ls`/`cat`/`grep`/`git status` 等) | 三档矩阵 |
   | `sensitive` | 工作区内写(`mkdir`/`cp`/`sed -i`/`>` 重定向等) | 三档矩阵 |
   | `destructive` | `rm -rf`/`dd`/`mkfs`/`shutdown`/`chmod 777` 等 | **逐条确认,不受任何豁免** |
   | `admin` | `su`/`sudo`/`systemctl`/`pm`/`am`/包管理等 | **逐条确认,不受任何豁免** |

   多命令串联（`&&` `||` `;` `|`）逐段判定取最高危，避免「安全命令 && 危险命令」被降级放行。
4. **执行级**：强制超时（默认 60s，上限 300s）+ 超时强杀；stdin 置 null 禁交互；输出截断 32K 字符。
   桌面直派进程；Android 经 Kotlin 桥按 ROOT → Shizuku → 沙箱档执行（见下）。

**缺省工作目录（任务模式 D1，2026-09-26）**：绑定了工作区的任务在该工作区内执行；
未绑定工作区的任务在**任务级 scratch 目录**（`<DATA_DIR 同级>/task_scratch/<task_id>`，可用
`KEDAI_TASK_SCRATCH_DIR` 覆盖根）内执行；只有聊天路径仍回落到应用数据目录。显式 `cwd`
在任务里必须落在作用域内（`safe_workspace_path` 闸门，越界拒绝）。

**自描述结果头（任务模式 D4，2026-09-26）**：结果首行 `$ {命令}`，次行
`(执行器:{档位};shell:{cmd|sh};cwd:{实际目录};退出码:{})`；描述串与失败提示都写明
「Windows 下由 cmd 解释：不支持 `;` 分隔、`/d/` 路径、`md5sum` 等 GNU 工具，多命令用 `&&`」。

**审计**：每次尝试（含被拒绝的）落 `exec_audit` 表（命令原文/风险级/等级/裁决/退出码/输出摘要），
经 `GET /api/exec/audit` 查询。root/ADB 级命令不可逆，这是唯一回溯依据。
`risk_flag` 列（2026-09-26 新增）标 `''` / `data_dir_touch`（命令文本含数据目录绝对路径）/
`parent_climb`（含 `..` 路径段）——**只标记不拦截**，供事后筛查「模型是否在动用户真实数据」。

**任务模式**：无 UI 确认通道（`no_ui_authorization=true`），高危命令**直接拒绝**而非静默放行——
不能「假装问过」。非高危命令仍按 `task_tool_policy` 与白名单决定是否下发。

**Android 执行层**：三档按 ROOT(su) → Shizuku(ADB shell，UID 2000) → 沙箱(应用自身 UID)探测；
需用户逐档放行（`exec_allow_*`）。Shizuku 经反射调用，未安装时静默降级，不崩溃。
沙箱档用系统自带 `sh -c`，不依赖额外二进制。

### 四、任务模式

任务模式没有 UI 授权上下文，不能走「等待授权」（会空等超时）。因此任务侧一律：

- 未放行工具**立即拒绝**并回灌 `{"error": ..., "code": "tool_policy_denied"}`，不产生授权等待。
- 工具集合由 `task_tool_policy` 决定：

| 策略 | 含义 |
|---|---|
| `all` | 全量 − 元工具（`META_TOOLS` 三员：`get_state` / `apply_patch` / `run_flow`）− 平台与工作区闸门剔除项（无 Android 沙箱档时剔 `submit`；无作用域时剔 `fs_*` 族；关包时剔包专属工具 `fs_patch`）。**不等于**改造前的全放行 |
| `deny_dangerous`(默认) | 全量 − 元工具 − 危险级工具 + **例外 `bash` / `fs_write` / `fs_edit` / `fs_patch`**（危险级见 permissions.rs 的 `default_risk`；例外按**工具名精确匹配**，理由见 `task_engine/tool_policy.rs` 文件头：bash 因任务模式需命令执行能力，工作区写/改/补丁工具因绑定工作区后需落盘能力，其路径由 `workspace_guard` jail 在作用域内；危险命令仍由命令级硬门拦截。**`fs_patch` 另过编码包闸门**——关包时先被 `coding_pack_gate` 整族剔除，例外只在开包时生效） |
| `allowlist` | 仅 `task_tool_allowlist ∩ 已注册` |

custom 步骤的步骤白名单在此基础上**取交**（只能收窄，不能突破任务策略放行危险工具）。
子智能体沿用 `tool_sets::SUBAGENT` 只读白名单。

### 五、设置字段

| 字段 | 默认 | 说明 |
|---|---|---|
| `authorization_mode` | `loose` | 三档：string 枚举 `strict` / `loose` / `bypass`；非法值 400 |
| `bypass_blacklist` | `[]` | 「始终需授权」清单；名单内工具在三档下都需授权 |

| `bypass_mode` | `false` | **已废弃**，仅读兼容；`true` → `bypass`，`false` → `strict` |
| `exec_enabled` | `false` | 命令执行总开关（阶段 E）。关闭时 bash 工具一律拒绝并留审计 |
| `exec_allow_root` | `false` | Android 允许 ROOT 档（su 提权） |
| `exec_allow_shizuku` | `false` | Android 允许 Shizuku 档（ADB shell 权限，无需 root） |
| `exec_allow_sandbox` | `false` | Android 允许沙箱档（应用自身 UID） |
| `session_token_budget` | `0` | 单次生成 token 预算（HB-1）：`0` = 关闭；否则 `1024..=1e9`。工具循环累计 prompt+completion 达到即按 `session_budget_action` 处置；扁平字段（聊天与任务共用） |
| `session_budget_action` | `warn` | 预算超限动作（HB-1）：`warn` 只提示一次后继续 / `stop` 提示并停止本轮工具循环（产出与用量照常保留） |
| `loop_guard_semantic_window` | `16` | 语义熔断窗口（HB-2，`4..=64`）：近 W 次工具调用内做「同工具 + 输出无实质变化」判定 |
| `loop_guard_semantic_min_calls` | `12` | 语义熔断同工具次数下限（HB-2）：`0` = 关闭本闸门，否则 `4..=64` |
| `loop_guard_semantic_max_distinct` | `2` | 语义熔断输出指纹去重上限（HB-2，`1..=8`）：窗口内同工具输出去重后不超过该值即判空转 |
| `task_step_budget_secs` | `1200` | **任务侧**：单步工具循环的墙钟上限（秒，`0` = 关，否则 `1..=86400`；建议 ≥300）。到点**带着已有产出收尾**（步骤照常记 `done`，不判失败），事件文案「步骤墙钟预算用尽」。不设下限是刻意的：`1` 秒合法（低于单次调用 300s 看门狗 = 「第一轮结束就收尾」的合法语义，测试也靠它触发） |
| `task_idle_timeout_secs` | `900` | **任务侧**：运行中任务连续该时长既无模型调用行、也无事件心跳时，由看守以 stop 同源路径收尾（终态 `ended`，原因写 `error`「空闲超时自动收尾」）。`0` = 关，否则 `601..=86400`——下限 = bash 单命令 300s + 单次模型调用 300s + 1，取 600 会误杀正常长命令 |
| `mvu_model` | `null` | 变量两步生成的独立模型（HB-7）：`null`/空串 = 与正文共用；非空 = 覆盖（≤200 字符，PATCH 空串 = 清除） |
| `mvu_temperature` | `null` | 变量两步生成的独立温度（HB-7）：`null` = 内置 `0.3`；`0.0..=2.0` = 覆盖（PATCH 负值 = 清除） |

## 配置与数据目录契约

### 项目范围与目录归属

- Rust 后端：`server-rs/`
- Vue 前端：`web/`
- 桌面壳：`src-tauri/`
- 数据目录(运行时，不进仓库)：`DATA_DIR` 环境变量 > `%APPDATA%\com.kedai.app\data\`(已含用户数据时)
  > 项目根 `data\`；解析逻辑见 `server-rs/src/config.rs`。
- 产品运行时主 Agent 提示词统一保存在 `DATA_DIR/AGENTS_RUNTIME.md`，由后端文件服务、Engine
  与设置页共用同一路径。

### DATA_DIR 解析规则（完整版）

`AppConfig::from_env` 的顺序是 `DATA_DIR` 环境变量 > 用户级统一目录 > 项目根 `data\`
（`server-rs/src/config.rs:138-144`）：

```rust
// 数据目录解析顺序(2026-09 统一):DATA_DIR 环境变量 > 用户级统一目录
// (%APPDATA%\com.kedai.app\data,已有用户数据时) > 项目根 data/。
// 背景:桌面版(Tauri)强制 %APPDATA%,而直接跑 kedai-server.exe / start.ps1 曾用
// 项目目录,两套库并行分叉——一边写的聊天记录另一边不可见(「重进后记录丢失」主因)。
```

- **第三级判据（用户级统一目录是否抢占）**：`%APPDATA%\com.kedai.app\data`
  **仅在该目录已含用户数据时才被采用**（`canonical_user_data_dir`，`config.rs:73-83`）。
  非 Windows 或无用户数据时返回 `None`，回退项目根 `data/`。
- **`canonical_user_data_dir` 实现要义**：读 `APPDATA` 环境变量（空值视为无）→
  `PathBuf::from(appdata).join("com.kedai.app").join("data")` → 若 `dir_has_user_data(&dir)`
  为真返回 `Some(dir)`，否则 `None`。注释原文：「仅当该目录已含用户数据时才返回 Some——
  空壳目录(曾启动过一次但没真正用过)不抢占。」
- **`dir_has_user_data` 判据**（`config.rs:85-105`）：`settings.json` 存在（存过设置即生成），
  或 `kedai.db` 里有**非内置角色**（`SELECT EXISTS(SELECT 1 FROM characters WHERE id <> 'builtin-system')`）
  / **任何会话**（`SELECT EXISTS(SELECT 1 FROM sessions)`）；以只读方式打开库，表可能尚不存在
  （全新库）：查询失败按 `false` 处理。
- **桌面版（Tauri 壳）无条件指向 `%APPDATA%`**：`app_data_dir()` = `%APPDATA%\com.kedai.app`，
  再 `.join("data")`（`src-tauri/src/lib.rs:176`；identifier `com.kedai.app` 见
  `src-tauri/tauri.conf.json:5`），即 `%APPDATA%\com.kedai.app\data\kedai.db`；
  桌面壳启动时把该路径注入 `DATA_DIR`（`src-tauri/src/lib.rs:188`）。
- **Android**：`app_data_dir()` 映射到应用私有目录 `/data/data/<pkg>/files`
  （`src-tauri/src/lib.rs:170-171`，注释明示），无 `%APPDATA%`，解析失败直接报错退出。
- **后果（两版共用同一库）**：桌面版用过的机器上，测试版随后启动会命中「已有用户数据」→
  也切到 `%APPDATA%`，两版即共用同一库，**同一时刻只能跑一个**（第二个实例要么被健康检查
  判定为「已在运行」而复用，要么抢端口/抢写锁）。
- **双库分叉与合并**：在桌面版从未用过的机器上先跑测试版，它会用项目根 `data\` 建库；
  之后跑桌面版会把项目数据**拷贝**（非移动）到 `%APPDATA%`，源目录保留。磁盘上出现两份库时，
  手工合并工具是 `server-rs/src/bin/kedai-data-merge.rs`，用法
  `kedai-data-merge <基线数据目录> <源数据目录> <工作目录>`，入口 `migration::merge_data_dirs`
  （`server-rs/src/migration/merge.rs:54`）；这是**离线 CLI**，需显式传三个目录，
  **不删源数据**，产出写在工作目录。两端数据不自动同步。
  另一支开发/评测 CLI `kedai-agent`（headless 单次任务入口，2026-10-01 HARNESS3-5）与之并列：
  进程内直跑一个 solo 任务、不起 HTTP 服务、不依赖 web/dist；读取同一 `DATA_DIR` 的
  settings.json，但**不写用户设置文件**（命令执行开关只在本进程内存态启用）。用法见 `MAINTENANCE.md`。

### 自定义流程（`agent_flows.json`）与静态子图契约（二维批次 6b）

**运行态映射契约（2026-09-22 加，遗留.md IFW-5）**：`TaskStep.node_id: Option<String>`
（`models/types.rs`），`#[serde(default, skip_serializing_if = "Option::is_none")]`——
**None 时整键省略**，故 legacy/solo/multi/plan/team 与存量 custom 任务的 plan JSON 逐字节不变
（由 `task_step_node_id_is_additive_and_omitted_when_none` 锁定）。口径与降级：

- **仅 custom 模式填**该行对应的流程节点 id（`PlanStep.id`），其余模式恒 `None`
  （`task_engine/custom.rs` 构造 plan 处是唯一写入点）。
- **必须按 id 映射，不能按下标**：plan 行由**过滤后的启用步骤**构造，故 `plan 下标 ≠ 流程数组下标`
  ——停用中间步骤后按下标对齐会整条串位（`tests/task_custom_node_id.rs` 用「停用中线」的流程
  锁定：plan 只含启用节点的 id，停用节点完全缺席且不留调用行）。
- **前端降级三档**：`utils/flowNodeBadges.ts::planRowBadges` 对「流程库未加载 / 行上无 `node_id`
  （旧任务）/ `node_id` 指向的节点已删」一律返回空徽标，**宁缺勿错**。
- **徽标语义**：`第 N 层`（按 `effectiveLevels` 的执行器视角，线性兼容流程也算隐式串联）/
  `严格` / `子流程`（**挂子流程的节点报「子流程」而非档位**——档位被旁路，报它是误导）/
  `成果`（`is_output` 显式优先，否则无后继汇点）/ `已停用`（任务跑过后流程又被改过的情形，
  如实标出当下状态）。
- **数据源（2026-09-22 二维批次 5a 起）**：徽标与详情「流程:X」读**任务自己的流程快照**
  （任务详情顶层 `flow_snapshot`，见下文「任务绑定流程与流程快照契约」），没有快照的旧任务
  才回退「当前流程库」——故「跑完任务后改流程 / 换当前流程」不再让徽标漂移
  （此前那条已知边界由 5a 收口）。降级仍取三档：两个数据源都没有 / 行上无 `node_id` /
  `node_id` 在数据源里找不到 → 空徽标。

**线字段**：`PlanStep.sub_flow_id: Option<String>`（`models/types.rs`），
`#[serde(default, skip_serializing_if = "Option::is_none")]`——**未挂载时整键省略**，

**记账契约**：子图节点在自己的那一层各记一行 `task_llm_calls` + 一行 `task_usage`，
`phase = subflow.<父节点下标链>`、`step_index` = 该节点在**本层**数组中的下标（0 起，展示 +1）。

- **硬约束：phase 不含冒号**。前端流式缓冲 key 是 `${phase}:${step_index ?? ''}` 且按**首个**
  冒号切分（`CallTracePanel.vue`、`stores/task.ts` 的 `liveKey`）——phase 里出现冒号会让
  phase 与步骤号解析错位，嵌套调用的缓冲互相覆盖。故路径分隔符取点号（`subflow.1.0`）。
- **挂载节点自身不记 usage**（子图各层已记），否则同一批 token 父子各记一次，破坏
  「`/calls` 各行 token 求和 == 详情 `usage_total`」不变量（由 `tests/task_custom_subflow.rs` 断言）。

**四类引用校验**（`validate_sub_flows`，保存期 400）：

1. 悬空引用：被引用的流程必须在本库内存在；
2. 自引用与跨流程环（A → B → A；图内环检测挡不住跨流程环，按调用链判）；
3. 嵌套深度 ≤ `MAX_SUB_FLOW_DEPTH`（=3，即链上最多 4 个流程）；
4. **被引用流程按「启用态」复用 `validate_flow` 的结构规则**（启用步骤非空 / 有生成步 /
   图无环 / 工具已注册）。

**校验分层**：保存（`set`）在**候选库**上全库遍历（编辑 B 可能让引用 B 的 A 变深/成环）；
执行只校验**以入口流程为起点的可达链**——库里无关流程的脏数据不拦本次执行
（未绑定任务：`AgentFlowService::current_snapshot` → `validate`；绑定任务：`validate_snapshot`
只看快照自身，见下文）；运行期另有调用链守卫兜底（`custom.rs::run_sub_flow`）。

**被引用流程的 `enabled` 口径**：该开关只决定一个流程能否作为**当前流程**直接执行，
**不影响它能否被别的流程当子流程引用**（辅助流程无须保持启用）；但被引用时一律按「启用态」
做结构校验。同理，**停用步骤**的挂载既不参与执行也不参与校验（`sub_flow_edges` 只看启用步骤，
删除保护与前端警示均同此口径）。

**相关实现**：`agent_flow_service/`（`MAX_SUB_FLOW_DEPTH`/`validate_sub_flows`/
`walk_sub_flows_from`/`expand_sub_flows`/`chat_flow_steps`/`FlowSnapshot`/
`sub_flow_closure`/`validate_snapshot`）、`task_engine/custom.rs`
（`run_sub_flow`/`phase_for_path`/`child_path`/`GraphCtx.flows`）、
`task_service`（`resolve_task_flow` 是执行前解析的单一出处）、`utils/flowNodeBadges.ts`
（运行态徽标，纯函数 `badgeFlowSource` 择数据源）。

**节点契约的机检**：`PlanStep ↔ AgentFlowStep`、`AgentFlowConfig`、`AgentFlowLibrary`
三组映射已于 2026-09-22 登记进 `tools/check-contract.mjs`（同批补登记
`TaskStepStatus` / `TaskSubtaskStatus` 两个枚举，核销此前的「已登记缺口」）；
二维批次 5a 再登记 `FlowSnapshot ↔ TaskFlowSnapshot`（任务流程快照）——
此后「后端加字段、前端漏加」由门禁拦截，不再靠人核对。

### 流程搬运契约（bundle 导出 / 导入，二维批次 7a,2026-09-23）

**导出**：`GET /api/agent-flows/export?id=<flow_id>` → `{ok, bundle}`；`id` 缺省 = **全库**。
bundle 形状 `{ kedai_flow_bundle: 1, exported_at, root_id, flows: [AgentFlowConfig…] }`，
`flows` = 该流程 + 其**可达子流程闭包**（`sub_flow_closure`，与任务快照、删除保护同一条
「什么算被引用」的判定——三处不可能分叉）。

- 给 `id` 时只校验**结构 + 可达引用链**（`validate`），**不看 `enabled`**：草稿与停用的
  辅助子流程同样要能带走（这是与 `snapshot_for` 的关键差别，后者是任务绑定路径，要求启用）；
- 缺省（全库）**只读不校验**：手改脏库也导得出来——**导入才是写路径**，校验在那边把关；
- **不含连接定义与密钥**（D7 口径）；节点级 `connection_id` 原样保留，跨机导入后编辑期显示
  「(引用已失效)」、运行期该节点明确报错（5b 口径，不静默回退默认连接）。

**导入**：`POST /api/agent-flows/import`，body `{flows: [AgentFlowConfig…], root_id?}` →
`{ok, report, library, config}`；校验失败 400 且**库与磁盘逐字节不变**
（全部校验在**候选库**上做完才换库——旧的逐个 PUT 路径做不到：先导的已落盘，后面的引用校验才失败）。

判定顺序（逐条处理；判定基准是**不含 id 的内容指纹** `flow_fingerprint`）：

1. **内容已存在**（本库或本批已有逐字节相同的流程）→ **跳过**；跳过且本库那份 id 与文件不同时，
   批内对它的引用**改指向本库那一份**（否则「入口被导入、子流程被跳过」会留下悬空引用）；
2. 文件 id 本库没有 → **沿用原 id**（跨机搬运 id 稳定，也是重复导入幂等的前提）；
3. 同 id 异内容 → 分配新 id 并登记重映射，批内 `steps[].sub_flow_id` 按映射表改写
   （**绝不覆盖**本机既有流程）；
4. id 为空 → 分配新 id。

**版本与旧格式**：文件里的 `kedai_flow_bundle` 存在且 ≠ 1 → 前端明确拒绝（提示升级 Kedai），
不静默丢字段；缺该键按旧格式容忍——单流程 `{name,steps}` / `{config:{…}}` 包装 /
库格式 `{flows,current_flow_id}`（**整库**导入，不再只取当前流程；`current_flow_id` 作入口）。
`root_id` 经重映射解析后作为新的 `current_flow_id`；一条都没导入（全部跳过）时不动当前选择。
**导出以服务端已保存的版本为准**（端点只认 id）；前端在有未保存修改时先确认，不静默给出旧版。

**id 保留段**：`export` / `import` / `select` 是 `/api/agent-flows/{…}` 的静态路径段，而 axum
静态段优先于 `/{id}`——id 恰为它们的流程**删不掉**（`DELETE /api/agent-flows/export` 命中静态
路由后按方法不匹配回 405）。导入是唯一能引入任意 id 的入口（旧路径恒分配 UUID），故这类 id
在导入侧**一律重映射**（计入报告的 `renamed`），库里不会出现「建得出来、删不掉」的流程。

**搬运包结构体**：`FlowBundle { kedai_flow_bundle, exported_at, root_id, flows }`
（`agent_flow_service/`）——**具名结构体**而非 `json!` 手拼，才能与前端 `AgentFlowBundle`
一起登记进 `check-contract`（本批新增，2026-09-23 共 21 组）；字段名即线格式键，
`kedai_flow_bundle` 与常量 `FLOW_BUNDLE_KEY` 的一致性由单测锁定。

**导入报告**：`FlowImportReport { imported, skipped, renamed: [FlowIdRemap{old_id,new_id,name}] }`
（与 `web/src/api/types.ts` 同形；2026-09-23 登记进 `check-contract`）。

**与任务侧的关系**：搬运只动流程库（`data/agent_flows.json`）；已冻结的任务快照
（`tasks.flow_snapshot`，二维批次 5a）**不受影响**——搬运不是「改流程」，不会让已跑过的任务漂移。

**相关实现**：`agent_flow_service/`（`export_bundle` / `import_bundle` / `flow_fingerprint` /
`FLOW_BUNDLE_KEY` / `FLOW_BUNDLE_VERSION`）、`api/agent_flows.rs`（两个 handler）、
`api/routes/agent.rs`（路由；静态段 `/export`、`/import` 优先于 `/{id}`）、
`composables/useAgentFlow.ts`（`normalizeFlowFile` / `importReportMessage`）。


#### 覆盖模式（A 批 B4，2026-09-24）

导入请求新增可选 `on_conflict: "rename" | "replace"`（缺省 `rename` = 上文全部语义，逐字节不变；
**未知取值一律 400**——覆盖不可逆，静默回退到 rename 会让用户以为已覆盖）。

`replace` 只影响**文件里出现过的同 id 流程**：内容不同 → 覆盖本库那一份（**id 不变 ⇒ 引用不破**，
这正是覆盖模式的价值）；内容相同 → 仍走指纹跳过；保留段 id（`export`/`import`/`select`）与空 id →
仍走重命名（那类没有「本库同一份」可言）。**库中其它流程一律不动**（绝不「导入即清库」）。候选库仍
照常做全库 `validate_sub_flows`，失败则整批拒绝、库逐字节不变（原子性与上文一致）。

报告新增 `replaced: [{ id, name }]`（仅 `replace` 模式非空）。`imported` 的语义为「**写入库**的条数
（新增 + 覆盖）」——7a 时代它等于新增数，加覆盖后仍成立（覆盖也是「写进库」）。前端契约同步：
`FlowImportReport.replaced` / `FlowReplacedFlow`（`tools/check-contract.mjs` 已登记该组）。

### 任务绑定流程与流程快照契约（二维批次 5a,2026-09-22）

**绑定**：`tasks.flow_id TEXT`（可空,**无 DEFAULT**,旧库经 `migration::ensure_tasks_flow_columns`
幂等补列）。NULL = **跟随当前流程**（旧客户端行为不变）；有值 = 创建时选定的流程。
`POST /api/tasks` 的 `flow_id` 为**可选**字段，且**只允许 custom 模式**给出
（其余模式给了即 400「只有自定义流程模式可以绑定流程」——不接受「字段存在但静默无效」）。

- **创建期校验**：流程存在 + `enabled` + 结构 + 从入口起可达的引用链
  （`AgentFlowService::snapshot_for`，与 `current_flow` 同一套 `validate`），失败 400 且**不建行**。
- **不可改绑**：绑定即冻结,本批不提供改绑接口——要换流程就新建任务。

**快照**：`tasks.flow_snapshot TEXT`（可空）存 `FlowSnapshot { root_id, flows }` 的 JSON
——**入口流程 + 其可达子流程闭包**（闭包口径复用 `sub_flow_edges`，与保存期校验、删除保护同源）。

- **冻结时机**：绑定任务**创建时**冻结（此后改那份流程、改当前流程、甚至删除它都不影响该任务）；
  未绑定任务**执行开始时**按当时的当前流程捕获并覆写（语义仍是「跟随当前流程」，重跑跟随新的当前流程）。
- **运行期解析**（`TaskService::resolve_task_flow`，单一出处）：有绑定 → 用快照
  （`validate_snapshot` 只校验快照自身，**不看流程库**）；无绑定 → 当时的当前流程；
  有 `flow_id` 却无快照 → 明确中文报错，**不静默回退**。
- **子图解析域**：`custom.rs::run_sub_flow` 只在快照闭包内按 id 取子流程
  （`GraphCtx.flows`），取不到即报错——「改一个被挂载的子流程」不再影响已冻结任务。
  为此**退役**了两处运行期回读：`TaskFlowAccess::flow_by_id` 与
  `AgentFlowService::validate_structure`（唯一调用点随 5a 消失）。
- **下发形态**：只在 `GET /api/tasks/{id}`（详情）顶层下发 `flow_snapshot`，**列表不下发**
  （快照是 O(流程库) 体积，列表每次事件刷新都会拉）；它在 `tasks` 表里也**不进** `TASK_COLS`。
- **兼容**：`TaskRecord.flow_id` 为加性字段（`skip_serializing_if`，None 整键省略），
  旧任务 JSON 逐字节不变；详情新字段对旧前端是 optional（缺失/为 null 时回退当前库，零噪音）。
- **已知边界**：未绑定且**从未跑过**的任务没有快照，其徽标仍读当前库（与 5a 之前相同）。


#### 任务级连接与改绑编排（A 批 B1/B3，2026-09-24）

**任务级连接**：`tasks.connection_id TEXT`（表尾追加；旧库经 `migration::ensure_tasks_flow_columns`
幂等补列，列序在 `flow_ids` 之后——schema 归一化比对依赖追加顺序）+ `TaskRecord.connection_id`
+ `CreateTaskBody.connection_id`（均 `Option`，缺键 = 沿用旧行为）。
语义 = 该任务**所有** LLM 调用的**缺省连接**（`ConnectionProfile.id`；指向 `settings.json` 的
`connections[]`），**六种任务模式通用**（绑 provider 不绑编排）；节点级 `PlanStep.connection_id`
仍然优先。创建期**校验引用存在且启用**（400 点名）——与流程库「保存期不校验引用」的差异是刻意的：
流程可跨机搬运（本机连接名不成立），任务不可搬运（IFW-11 边界 3），即时校验更友好；运行期引用被删 /
停用仍按 5b 口径**明确报错、不静默回退默认连接**。缺省（缺键）= 跟随设置的默认连接，零行为变化。

**改绑**：`POST /api/tasks/{id}/bind`，体 `{ flow_id: string|null, flow_ids: string[] }`，
**全量替换**语义——`flow_id: null` = 跟随当前流程（解绑，快照清空，下次执行重新捕获）、

### 对比模式契约（`flow_ids` + `run_flow`，二维批次 7b,2026-09-23）

**语义**（D9 取甲）：custom 任务在**根流程照常执行**的前提下，把一份**流程名单**里的流程作为
工具释放给根流程内的**宽松节点**——模型在工具循环里自主调用某套流程、取回其成果。

**线字段**：
- `tasks.flow_ids TEXT`（可空，JSON 字符串数组，NULL = 强制模式），随
  `migration::ensure_tasks_flow_columns` 同批幂等补列（第三列，同为表尾追加）；
- `POST /api/tasks` 的 `flow_ids: string[]`——仅 custom 模式可给，**给了空数组（含全空白项）即
  400**（空名单 = 名存实亡，要跑强制模式就别带这个键）；非 custom 给了即 400；
- `TaskRecord.flow_ids` 为加性字段（`skip_serializing_if`，None 整键省略），旧任务 JSON 逐字节不变；
  它**进** `TASK_COLS`（列表也要显示「可调用 N 个流程」），且**不进** `flow_snapshot` 那条单列查询。

**创建期校验**（`TaskService::create`，全部在写库之前）：名单成员必须**存在 + 启用 + 结构合法**
（`AgentFlowService::validate_members`，逐项点名报错）；**名单不得包含根流程**（显式绑定的
`flow_id` 出现在名单里即 400——它正在执行，被调用必然撞调用链环守卫）。

**冻结域**：`closure_from_roots` 把快照**起点集**由 `{root}` 扩为 `{root} ∪ 名单`（入口恒为首个，
名单按声明顺序紧随其后，子流程仍按发现顺序）——被调流程与静态子流程同一条纪律：
「快照外的一律取不到」。运行期（未绑定任务的「当时的库」）对名单成员取**宽松**口径
（不可用即剔除并 warn，不阻断根流程执行），严格口径只属于创建期与绑定路径。

**工具面**：单一内置工具 `run_flow`（`tools/run_flow.rs`），启动时注册一次；
参数 `{flow, input}`（`flow` 接受流程名或 id，重名报错并列出候选 id；`input` 缺省 = 任务目标），
**描述按本任务名单动态生成**（由 `custom.rs` 逐节点改写 `params.tools` 里的那份定义）。
它进 `tool_sets::META_TOOLS`：聊天与 solo/multi/team/plan 一律看不到；只有对比模式的宽松节点
被显式下发（闸门名单由 `tools` 派生，无第二份判定）。CFG-2 六处登记结果：注册定义 ✅、
`default_risk` = `Sensitive`、`tool_sets::META_TOOLS` ✅、`tool_when` ✅、`render_kind_for` = generic ✅、
前端流程白名单为**自由文本框**（无候选清单，故该处对本工具不适用——用户手写也拿不到它，
策略编译集已剔除元工具）。

**调用点注册表**（进程内，key = `ToolContext.session_id`）：`custom.rs` 在节点工具循环**前**登记、
守卫 Drop 时注销（节点 future 被丢弃即取消时也不留陈旧条目）；处理器查不到即
`run_flow 只能在自定义流程的对比模式节点内调用`。tools 层因此不认识「任务/流程」，
名单/预算/环与深度守卫全在 `task_engine/flow_call.rs`。

**三道闸（缺一条就是烧钱事故；判定顺序 = 拒绝代价从低到高，全在任何模型调用之前）**：

1. **名单内解析**（`resolve_flow_ref`）：解析范围**限于可调用集**（= 名单 ∩ 冻结闭包 − 根流程），
   名单外/不存在的流程一律拒绝且**不产生任何调用行**；
2. **调用链环**（`check_call_guards`，先于深度判）：`chain` 是**流程 id 调用链**，静态子图与动态
   调用共用同一条链——「静态挂载回入口」与「动态调用回入口」由同一处拦下；
3. **动态嵌套深度** `MAX_FLOW_CALL_DEPTH = 2`：与静态子图深度（`MAX_SUB_FLOW_DEPTH = 3`）
   **两条独立轴**（动态层不并入 `g.depth`，被调流程内部那套静态子图从 0 层重新起算）；
   不复用 `subagent_max_depth`（那是子智能体设置）；
4. **每任务预算** `MAX_FLOW_CALLS_PER_TASK = 8`：进程内按任务计数（`run_inner` 建，随 run 起止），
   同一计数器兼作 `d<序号>` 来源；超限的调用消耗序号但不留痕迹。

常量与 `MAX_SUB_FLOW_DEPTH` 同处声明（`agent_flow_service/`，单一出处）。

**记账**：动态调用层顶层 `phase = call.d<序号>`（嵌套 `call.d1.d2`），其内部静态子图仍是
`subflow.<路径>`（即 `subflow.d1.2`）；`step_index` = 节点在该层内的下标。被调流程**逐节点各记
一行调用 + 一行 usage**，调用它的宿主节点自有 usage **不含**这些 token——
「`/calls` 各行求和 == 详情 `usage_total`」不变量因此不破。phase 仍**不含冒号**
（前端流式缓冲 key 按首个冒号切分）。**被调流程内部降级**（有失败/空产出但成果仍选得出）不污染
回灌文本，只把任务置 `partial`（与 6b 静态子图降级同语义）。

**被调流程的呈现口径（2026-09-24 收口）**：

### 节点级连接与工具轮次上限契约（二维批次 5b,2026-09-23）

**线字段（两个加性字段，None 时整键省略 → 存量 `agent_flows.json` 逐字节不变）**：

- `PlanStep.connection_id: Option<String>`（`models/types.rs`）——该节点走哪一套 API 连接
  （`ConnectionProfile.id`）。缺省 = **默认连接**（与 5b 之前一致）。空白串按「未设置」处理
  （`PlanStep::connection_ref`，与 `sub_flow_ref` 同口径）。
- `PlanStep.max_tool_rounds: Option<u32>`——节点级工具循环轮次上限，缺省 = 沿用全局
  `settings.max_tool_rounds`。

**语义：节点级模型 = 选连接。** `ConnectionProfile` 自带 `model`，provider 与模型随该连接，
故**不另引** `PlanStep.model`（`with_model()` 对 mock 是 no-op，节点级 model 会在演示连接上静默失效）。
想在同一 provider 上跑不同模型 → 建两条连接（同地址/密钥、不同 model）。

**运行期解析（单一出处）**：`AgentEngine::resolve_connector(connection_id)`
（`agents/engine/mod.rs`）——`None` → `engine.connector` 读锁快照（**行为与 5b 之前逐字节一致**）；
`Some(id)` → 设置快照里按 id 找连接，命中且 `enabled` → 连接器池取实例、模型取**该连接器真实值**；
未命中 → 明确报错「引用的连接「X」不在设置里」；`enabled=false` → 「已停用」。
**不静默回退默认连接**（与 5a「有 flow_id 却无快照」、6b「子流程不在快照内」同口径）。

- **三条消费路径**：`agents/engine/executor.rs::execute_generation`（工具循环内层，读
  `GenerationParams.connection_id`）、`services/task_service/executor.rs::generate_text`（纯生成）、
  聊天侧 `agents/engine/messages/steps.rs::step_params_for`（把 `step.connection_id` /
  `step.max_tool_rounds` 带进本步参数）。自定义流程的聊天入口因此与任务侧**共享同一分流**。
- **连接器池**：`services/settings_service/connector_pool.rs` 的 `ConnectorPool`——缓存键 = profile id，
  值带构建指纹（`connector_type|base_url|api_key|model`），指纹不一致即重建；条目上限 32（超限清空）。
  池子在 `AppState::new` 建一次、经 `EngineCore` 注入引擎；**`TaskService` 不再自持连接器字段**
  （计划改动点 1：不在 TaskService 里另建缓存，否则「改设置 → 谁生效」有两个数据源）。
  失效**不靠写路径挂钩子**：PUT 保存路径不需要知道池子存在。
- **调用追踪**：`task_llm_calls.model` 记该节点连接的**真实模型**（工具路径此前恒取全局模型，
  节点绑了别的连接就会记错 provider）；解析失败发生在**发起调用之前**，故该节点**不留调用行**，
  错误只落 plan 行文案（记账不变量「`/calls` 求和 == `usage_total`」因此不受影响）。
- **保存期不校验连接引用**：流程库可导出/跨机导入，而连接是**本机**设置（`settings.json`）——
  保存期拒绝会把可移植流程变成本机绑定。故保存期放行（`validate_flow` 只校验 `max_tool_rounds`
  的 1-200 区间，与设置项同范围、错误点名步骤），运行期报错，编辑期由前端选择器保位显示
  「(引用已失效)」并说明后果。
- **挂载子流程的节点**：`connection_id` 被**旁路**（子图各节点各自解析自己的连接），配置保留
  ——与 6a/6b 的「配置保留、切回即生效」同一纪律；`max_tool_rounds` 在严格档下同样不生效、
  配置保留（编辑区随之收起）。
- **已知边界**：聊天侧自定义流程的**调用追踪/用量展示**仍按默认模型名记录（`task_llm_calls` 是
  任务侧口径）；即「聊天里跑 custom 且节点换了连接」时，实际调用走该连接，而聊天侧的可观测面板
  不会体现模型差异（见 `遗留.md` IFW-10）。

### 节点级超时 / 重试与调用闸设置契约（A 批 A1/A2/A3/A4,2026-09-24）

### 五之二、任务侧工具循环的四道闸（提交 3，2026-09-26）

任务模式的工具循环同时受四道闸约束，**前两道任务侧专属、后两道与聊天共用但任务侧更紧**：

| 闸门 | 取值来源 | 到点行为 |
|---|---|---|
| 轮次上限 | `max_tool_rounds`（默认 32） | 停止发起新请求，输出当前结果（步骤照常 `done`） |
| **步骤墙钟预算** | `task_step_budget_secs`（默认 1200s；`0` = 关）→ 经 `task_engine::task_loop_limits` 装配进 `GenerationParams.step_budget` | 同上，事件文案「步骤墙钟预算用尽:已用 Ns / 预算 Ms(第 K 轮)」 |
| **语义熔断（任务侧钳制）** | 用户三值经 `utils::loop_guard::clamp_for_task` **收紧**：窗口 ≤8 / 同工具次数 ≤4 / 去重 ≤2（`0` = 关闭位原样保持） | 第 4 次同工具输出无实质变化即熔断，事件文案「重复空转熔断」 |
| token 预算（HB-1，聊天共用） | `session_token_budget` / `session_budget_action`（默认 0 = 关） | `warn` 提示一次 / `stop` 收尾并留痕 `extra.budget_exceeded` |

- **钳制只收不放**：用户把三值设得比上限更紧时按用户的（合法的收紧请求），更松时按上限；引擎**不做**
  `task:` 前缀嗅探，模式由调用方（`task_loop_limits` 的两处装配：solo 主循环与 custom 工具节点）显式传值。
  聊天路径 `GenerationParams.semantic_guard = None` → 用扁平快照值，行为逐字节不变。
- **四道闸都是「带着产出收尾」而非失败**：步骤记 `done`、正文与用量照常保留——失败会把已完成的工作一起丢掉（提交 2 的教训）。
- **不覆盖**：agentgo 子 agent 的工具循环（`tools/agent_tools_agent.rs`，聊天 AGENT 模式与任务 multi/team 共用）
  不套步骤预算与任务侧钳制，缺口登记在 `docs/遗留.md`。

**任务级空闲看守（提交 3 · D7）**：`task_service/idle.rs` 常驻 tick(60s)扫描 `running`/`planning`
且**既无模型调用行、也无事件心跳**超过 `task_idle_timeout_secs`（默认 900s）的任务，走与用户 `stop`
**同一条** `finish_ended` 路径收尾（终态 `ended` + `error` 写「空闲超时自动收尾:最近 Ns 无模型调用或事件」）。
活动信号 = 进程内心跳（`register_cancel` 登记、`emit_event`/`emit_llm_call` 刷新）优先、库时间戳兜底——
只看库会误杀：`task_llm_calls` 行是**整轮工具循环结束后**才落的，一次十分钟的循环期间库里没有任何新行。
看守**只在 `run_server` 挂载**（`build_test_app` 不挂，测试 app 不该带常驻定时器）。

## 平台分支契约

> 状态：**生效中**（2026-09-13 建立；2026-09-28 增第 4 条「分支创建纪律」）。适用读者：开发 agent 与维护者。禁止注入聊天模型。
> 本节是分支模型的**单一事实来源**：改分支策略、新增平台专属目录时同步更新。
> 原文：`archive/2026-09-16-consolidation/平台分支说明.md`。

### 一、为什么是同源，而不是两套代码

Kedai 是**单一代码库、两个交付平台**：Rust 后端（`server-rs/`）、Vue 前端（`web/`）与
共享工具链在两端完全复用，只有平台能力层与打包发布层不同。平台差异用编译期与运行期
开关隔离，而非复制代码：

- **Rust 侧**：`#[cfg(target_os = "android")]` / `#[cfg(not(target_os = "android"))]`
  门控平台模块。例：`server-rs/src/services/exec/mod.rs:144-148` 桌面走 `desktop.rs`、
  Android 走 `android.rs`；`server-rs/src/services/mod.rs:16-25` 的 `keystore_android` /
  `jni_bridge` / `native_bridge_android` 仅 android 目标编译。
- **前端侧**：`web/src/platform` 的 `isAndroidTauri` 运行期判据。例
  `web/src/components/settings/AndroidExecSection.vue:54` 用
  `showAndroidTiers = isAndroidTauri` 决定 ROOT/Shizuku 等级条是否显示，
  桌面端自动隐藏但**文件仍在共享树中**。

**结论：平台专属文件必须留在主干。** 它们要么被共享代码 import（如
`AndroidExecSection.vue` 被共享的 `AgentSettingsSection.vue:11` 引入），要么被共享脚本
引用（如 `build.ps1`、`tools/bump-version.ps1`、`tools/check-lock-sync.mjs` 都读
`launcher/`）。把它们从主干剥离会直接打断主干构建与 CI，而不是“清理”。

### 二、分支拓扑

```text
main ────────────── 主干:全量共享代码 + cfg/运行期门控的平台代码
  ├── kedai-Win      平台分支 = main + Windows 发布清单(平台发布元数据)
  └── kedai-Android  平台分支 = main + Android 发布清单(平台发布元数据)
```

三个分支的**设计目标**是源码同源、平台分支只在各自的发布清单文档上分叉——理由不是“没分成”，
而是“代码本来就同源，强行切成两份反而制造双向 cherry-pick 漂移”。
> **2026-09-28 实测**：平台分支**尚未随主干同步**，当前落后 `main` **21 个提交**（差异含源码与门禁），
> 下次同步前它们**不代表最新主干**；查法 `git rev-list --count kedai-Win..main`。
>
> **追注 2026-09-29**：两个平台分支已用 `git merge main` 同步，上条实测的「落后 21 提交」随之归零。
> 该数字是**当时快照**、不是常态——它与主干每前进一次就再次变大，**判断现状一律现取**
> （`git rev-list --count kedai-Win..main`），不要引用本段的历史值。

### 三、四条规则

1. **共享改动一律落 `main`。** 后端逻辑、前端组件、协议、共享工具链的任何改动先在
   `main` 提交并通过门禁（`tools/check-all.ps1`；云端 CI 档 2026-09-29 起停用，见 §七），再向下游平台分支合并。
2. **平台专属改动落平台分支。** 指打包配置、签名、发布清单、平台限定文档。若某改动
   同时影响两侧（如 `tauri.conf.json` 的版本号），在 `main` 改，由平台分支合并吸收。
3. **合并方向：`main` → 平台分支。** 平台分支不向 `main` 反向合并平台发布元数据
   （避免两份清单在主干预架）；确需回流共享逻辑时，先在平台分支验证，再手动摘取到 `main`。
4. **不得随意新建分支（2026-09-28 增）。** 长期分支只有上述三条；其余分支一律是
   **一次性临时分支**，仅在 PR 流程需要时创建（非琐碎改动走 PR，见「文档与提交纪律契约」§七），
   并受三条约束：
   - **一事一分支**：命名用 `feat/` / `fix/` / `docs/` / `ci/` / `release/` 前缀 + 语义化短名；
     已有能承载当前改动的分支时复用它，不重复开分支。
   - **不以分支替代主干**：共享改动必须在 `main` 上完成并过门禁；不得用临时分支长期承载开发，
     也不得为绕开门禁或让 CI「看不到」而另开分支（平台分支刻意不触发 CI，见 `.github/workflows/ci.yml`；
     两档 2026-09-29 起服务端停用）。
   - **合并即删**：PR 合并（或该分支废弃）后即刻删除本地与远端同名分支；删除用 `git branch -d`
     （已完全并入才可通过，`-D` 仅在确认无需保留时使用）。
   创建前先 `git branch -vv` 看清现状；推送前先 `git branch --show-current` 确认分支。

   > 依据：2026-09-28 分支收敛（`功能-变更史.md`「2026-09-28 分支收敛」章）——临时分支堆积
   > 曾导致「按 `main` 编译看不到改动」、改动归属不可追溯；本条把该次教训固化为常驻纪律。

## 构建与发布契约

### 一、单二进制原理

`kedai-server.exe` 通过 `include_dir!` **内嵌** `web/dist`（编译期快照，见
`server-rs/src/api/static_files.rs`）。运行时默认只服务内嵌版本；仅显式设置环境变量
`KEDAI_WEB_DIST` 指向磁盘目录时才用磁盘版覆盖（开发调试用，见 `server-rs/src/config.rs`）。

因此**每次改前端后必须重新构建 exe** 才会带上新界面；`server-rs/build.rs` 的
`rerun-if-changed=../web/dist` 保证 cargo 感知前端变化，构建脚本另有 mtime 兜底检测。

> 由此推出一条推论（源文档 §二 场景 D）：前端已被 `include_dir!` **编译期嵌入二进制**，
> 运行期磁盘上的 `web/dist` 不参与服务，改它无效果。

### 二、构建流程

```powershell
.\build.ps1          # 默认双端同步:前端 + cargo build --release + 便携版
.\build.ps1 -TestOnly  # 快速迭代:只产出测试版(结尾会警告便携版未同步)
```

- **本机环境提示（2026-08 批次构建时验证）**：裸 shell 里没有 cargo——MSVC toolchain 需先
  `call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat"`，
  再在同一 shell 里执行 `build.ps1`（脚本内部直接调 cargo/npm，继承环境）。
  Git Bash 里用 `cmd //c "<包装.bat>"` 嵌套调用。另外：构建只跑 debug 不代表 exe 版已更新，
  交付前必须跑 `.\build.ps1`。
- **产物**：`dist\kedai-server.exe`（测试版）+ `dist\Kedai-portable\Kedai.exe`（便携版），
  各自约 20~30MB。双端全量构建约 5~10 分钟（便携版含 Tauri 全量编译）；快速迭代用
  `-TestOnly` 或 `-Dev`。

### 三、两版同步机制（构建指纹）

测试版与便携版是两条独立编译链，各自把编译那一刻的 `web/dist` 冻结进二进制——分开构建必然漂移。
根治手段是「默认双端同步 + 指纹可查 + 启动对齐」三层：

1. **构建层**：`build.ps1` 默认一次产出两端；每个 dist 产物旁边写 `<exe>.build.json`
   （`{version, build_time, dist_hash}`，算法见 `tools/Write-BuildStamp.ps1`）。
2. **运行时层**：`server-rs/build.rs` 把 `KEDAI_DIST_HASH`/`KEDAI_BUILD_TIME` 编进二进制，
   `GET /api/health` 返回 `{ok, ts, version, build_id, build_time, data_dir, dependencies:{db}}`；
   设置中心底部常驻显示「版本 · 构建时间 · 指纹前 8 位」，两端各开一次对比即可肉眼确认同步。
3. **启动层**：`start.ps1` 与图形启动器（`Kedai.exe`，源码 `launcher/`）启动前比对两端
   sidecar 的 `dist_hash`，不一致自动执行 `build.ps1` 双端重建；`Kedai.lnk` 指向图形启动器，
   双击自带过期/漂移检测（直接双击 dist 里的裸便携版 exe 没有这层保障）。

### 四、两套指纹算法（构成与差异）

| 维度 | sidecar 侧 `dist_hash` | 二进制内嵌 `KEDAI_DIST_HASH` |
|---|---|---|
| 实现 | `tools/Write-BuildStamp.ps1::Get-KedaiDistHash`(L8–L30) | `server-rs/build.rs::fnv_hash_dir`(L38–L60) |
| 算法 | SHA256(`Get-FileHash`，聚合再取一次 SHA256) | FNV-1a 64-bit（零依赖手写） |
| 输入集合 | `web\dist` 递归全部文件(L12) | `../web/dist`（**同一目录**，L24–L25） |
| 排序 | 小写**完整绝对路径**(L13 `$_.FullName.ToLowerInvariant()`) | `Vec<PathBuf>` **相对路径**原生序(L41 `files.sort()`) |
| 单文件序列化 | `rel:UPPERHEX\n`，其中 `rel` 由 `Substring($dist.Length)` 得到，**带前导 `/`**(L20–L22) | `rel`（无前导 `/`）+`0x00`+**原始内容字节**+`0xFF`(L52–L57) |
| 输出形态 | 64 位小写 hex(L26) | 16 位小写 hex(L26 `{hash:016x}`) |
| 落点 | `<exe>.build.json` 的 `dist_hash` 字段(L46–L48) | 编译期 `cargo:rustc-env`(L26)，经 `env!` 进二进制 |
| 实测 | `dist/kedai-server.exe.build.json` = `eb949437…efd4bc22`(64 hex) | `/api/health.build_id`(`server-rs/src/api/mod.rs:70`) |

> 已实测确认的两处细节（任何「要复刻对端算法」的方案必须处理的坑）：
> - `Get-ChildItem …` 后 `$f.FullName.Substring($dist.Length)` 结果形如 `/assets/AboutSection-BwBiPNMC.js`
>   ——**前导斜杠**；而 Rust 侧 `strip_prefix` 得 `assets/AboutSection…`，**无前导斜杠**。
> - `Get-FileHash` 返回**大写** hex，PowerShell 写入 `rel:HASH\n`（LF，非 CRLF）；Rust 侧是裸字节流，
>   两者序列化格式整体不同。
> - 两侧排序键也不同（小写绝对路径 vs 相对路径原生序），路径大小写与非 ASCII 时可能次序不一致。

#### sidecar 文件格式

```json
{"version":"<package.json 版本>","build_time":"<UTC 构建时间>","dist_hash":"<聚合 SHA256>"}
```

- `dist_hash` 的算法：对 `web\dist` 全部文件按「小写完整路径 + 单文件 SHA-256」排序后再做一次
  聚合 SHA-256（`tools/Write-BuildStamp.ps1:8-30`）。两台机器用同一份 `web\dist` 会得到同一个值。
- **测试版与便携版的 `dist_hash` 必须一致**（`build.ps1:403-410` 会在构建收尾断言，不一致打印
  红字「严重」并提示重跑）。两者是两条独立编译链，各自冻结编译那一刻的前端，指纹一致才说明同源。
- 查看方法（PowerShell）：

```powershell
Get-Content .\dist\kedai-server.exe.build.json
Get-Content .\dist\Kedai-portable\Kedai.exe.build.json
```

- 本次核查（2026-09-13，版本 `0.3.0-A-beta`）两份 sidecar 的 `dist_hash` 均为
  `eb9494373580…`（前 12 位），即两端同步；该值随每次构建变化，仅作示例。

#### 写入点与消费点

**写入**：

- `build.ps1:282` → 测试版 `dist\kedai-server.exe` 的 sidecar
- `tools/build-portable.ps1:93` → 便携版 `dist\Kedai-portable\Kedai.exe` 的 sidecar
- `server-rs/build.rs:17–32` → 每次编译 `kedai-server` crate 时把 FNV 注入二进制
  （测试版 exe、便携版 Tauri 内嵌 lib、Android `libkedai_desktop_lib.so` 都走这条）

**消费**：

| 消费者 | 位置 | 比对对象 | 缺失/异常时行为 |
|---|---|---|---|
| `start.ps1` 漂移检测 | `start.ps1:82–90`、`:155` | **两个 sidecar** 的 `dist_hash` 互比 | 返回 `$false`，交由 mtime 兜底(L88) |
| launcher 漂移检测 | `launcher/src/main.rs:533–552`、`:658` | **两个 sidecar** 的 `dist_hash` 互比 | 视为「无法判定」不误报(L540–541) |
| `build.ps1` 收尾自检 | `build.ps1:404–411` | 同上 | 红字报警「两端指纹不一致或缺失」 |
| 设置中心展示 | `web/src/components/SettingsHub.vue:31` | 人眼看 `build_id` 前 8 位 | 显示 `--------` |

**没有任何代码把「二进制内嵌 `build_id`」与「sidecar `dist_hash`」做过比对**；
`/api/health.build_id` 目前只被前端当只读文本展示（`web/src/api/health.ts:11`、
`SettingsHub.vue:31`）。这就是 D2 所谓「链未闭环」的字面含义，也是「两套算法不可直接比对」的实际后果。

关键观察：**两条支路的输入都是 `web/dist`；exe 自身字节不在任一哈希的输入集合内。**

#### 范围声明与平台约束

- **launcher 零依赖**：`launcher/Cargo.toml` 的 `[dependencies]` 为空，自述「零第三方依赖」，
  故 launcher 只能做字符串比较，不能在自身内计算哈希（除非新引入/内联哈希实现）。
- **src-tauri 壳无指纹逻辑**：`grep build_id|dist_hash|build.json src-tauri/src` 无命中。
- **Android 天然不在闭环内**：Android 只经 `libkedai_desktop_lib.so` 内嵌 `build_id`，
  APK 内没有也没有 sidecar 可比。无论选哪套方案，**Android 都拿不到闭环校验**。
- **范围声明（须落到 `../MAINTENANCE.md` 同步机制小节与两处脚本头注释）**：
  「本机制用于**两版同源一致性**检查，不构成对 exe 的完整性/防篡改保证；后者需代码签名。」

### 五、结论：指纹链不闭环（D2）的处置与重新评估触发条件

1. 现状的两张指纹**输入都是 `web/dist`，都不覆盖 exe 自身字节**。它们回答的问题是
   「两个 exe 是否由同一份前端构建而来」，而非「这个 exe 是否被人换过」。
2. 现有比对只发生在**两个 sidecar 之间**（测试版 vs 便携版），没有任何代码比对「二进制内嵌
   `build_id`」与「sidecar `dist_hash`」；且未来即便闭环，比对的一方（`build_id`）也由**被检 exe
   自己经 `/api/health` 报出**，无签名/信任根。故闭环对「手工替换 exe」的防护增益有限。
3. **推荐：维持现状 + 补文档**。理由：收益（仅能发现「配错包」这一窄场景，且可被受限
   攻击者伪造）低于成本（动发行链路、双端内嵌值全变、Android 受影响、需新增消费者与重建
   启动器、PS 侧算法复刻脆弱）。
4. 若主智能体判定「运行中的后端必须与 sidecar 可机检同源」这项发布 QA 收益必须落地，则
   **fallback 选方案②（sidecar 增 FNV 字段），不选方案①（`build.rs` 改算 SHA256）**。
5. 评估中发现一条对「防手工替换 exe」**严格更优且更便宜**的第三案：sidecar 改存
   `exe_sha256`（exe 字节的哈希），由持有 `Get-FileHash` 的 `start.ps1` 校验。它超出当初
   二选一范围，仅登记供决策，本轮不实施。

#### 实际防护强度（目标威胁：手工替换 exe）

前提：攻击/误操作者能写 `dist\` 目录（本地桌面应用，exe 与 sidecar 同目录、无签名、无 ACL 隔离）。

| 场景 | 现状能否发现 | 闭环(①或②)后能否发现 | 说明 |
|---|---|---|---|
| A. 只替换 `Kedai-portable\Kedai.exe`，不动 sidecar | **否** | **可能**（若加消费者） | 现有：两 sidecar 不变→不漂移；mtime 只比源码新，不比完整性→不拦。闭环后：若替换成**另一次构建**的 exe，其内嵌 `build_id` 与本地 sidecar 值不同→可发现；若攻击者让新 exe 的 `/api/health` 照抄 sidecar 值，则**仍漏** |
| B. 同时替换 exe 与 sidecar | 否 | **否** | 比对双方都在攻击者控制下；无签名/信任根，任何基于这两个文件的比对都无效 |
| C. 替换项目根 `Kedai.exe`（启动器本体） | 否 | **否** | 根 `Kedai.exe`(260KB，`find` 确认无 sidecar)就是校验逻辑的宿主；换掉它即绕过全部校验。「校验者必须比被校验者更受信」在此不成立 |
| D. 替换/篡改 `web/dist` 磁盘文件 | 不适用 | 不适用 | 前端已被 `include_dir!` 编译期嵌入二进制，运行期磁盘上的 `web/dist` 不参与服务，改它无效果 |
| E. exe 复制损坏/半截文件 | **是**(粗粒度) | 是 | launcher 启动后 `try_wait` 检测秒退并弹窗报错(`launcher/src/main.rs:728–745`)；无需指纹 |
| F. 配错包：把另一次构建的便携版盖到 `dist\Kedai-portable\` | **否** | **是** | 这是闭环唯一真实的净增益：能发现「包内容与 sidecar 不同源」 |

**要害结论**：

1. 哈希的对象是前端资产，不是 exe；所以「替换 exe 字节」这一威胁**根本不在指纹的覆盖面内**。
2. 闭环后新增的比对，其一端由**被检 exe 自己**产出（`/api/health`）。可信度不高于被检对象，
   可被伪造。这不是安全边界，只能算「发布一致性自检」。
3. 若要真正防替换，方向是签名/信任根，或至少校验 **exe 字节**（`exe_sha256` 第三案），
   而非前端哈希。

#### 两案对比（若必须落地机检同源）

| 评估维度 | 方案① `build.rs` 改算 SHA256 | 方案② sidecar 增 FNV 字段 |
|---|---|---|
| 改动面 | `server-rs/build.rs` 重写哈希 + 更新其 2 个单测；`server-rs/Cargo.toml` 新增 `[build-dependencies] sha2`；`server-rs/Cargo.lock` 变化；文档/注释同步 | 仅 `tools/Write-BuildStamp.ps1` 新增 FNV 计算与 `fnv` 字段；`build.ps1`/`build-portable.ps1` 无需改（继续 dot-source 同一函数） |
| 需重建什么 | 桌面双端 exe + **Android `.so`**（build.rs 变更 → 内嵌值格式全变）；launcher（若要加消费者） | 桌面双端（仅为刷新 sidecar）；**Rust 侧零变更，Android 无需因本项重建**；launcher（若要加消费者） |
| 防护强度提升点 | 内嵌值与 sidecar **同算法同输入**，可字符串全等比对；算法统一、无「双算法并存」 | 保留原 SHA256 `dist_hash`（现有漂移检测零影响），另加同输入 FNV 供比对；算法仍双套 |
| 算法复刻风险 | **高**：需精确复刻 PS 的「小写绝对路径排序 + 前导 `/` + 大写 hex + `\n` 序列化」；任一处不同即永远不相等 | **中高**：需在 PS 内复刻 Rust 的「相对路径原生序 + `\0` + 裸内容 + `0xFF`」字节流；PS 侧 64 位乘法溢出（PowerShell 会把 Int64 溢出提升为 double 丢精度），须用 `BigInteger` 或 `Add-Type` 内联 C# 的 `unchecked` 实现 |
| `sha2` build-dep 影响 | `sha2 0.10.9` 已在 `src-tauri/Cargo.lock:3625` 收录，理论上可通过 `check-lock-sync`（规则：server-rs 锁的 (name,version) 须被 src-tauri 锁覆盖）；传递依赖解析版本须一致，否则触发锁同步门禁 → 需实跑 `npm run check:lock` 验证 | 无依赖变化，**不动任何 Cargo.lock**，锁同步/审计门禁零影响 |
| Tauri Android 构建 | 受影响：`build.rs` 变更进入 Android `.so`，内嵌 `build_id` 形态由 16→64 hex；无对端可比，纯属被动变更 | **不受影响**：`build.rs` 不动，Android `.so` 内嵌值保持 16 hex FNV |
| 双端产物指纹变更 | 是：两个 Windows exe + Android `.so` 的内嵌值全部变化 | 否：内嵌值不变，仅在 sidecar 追加字段，旧产物仍可被现有逻辑读取 |
| launcher 零依赖约束 | 不破坏：闭环只需字符串比较(64 hex vs 64 hex) | 不破坏：字符串比较(16 hex vs 16 hex) |
| 「重建 launcher」是否真为必需 | **不是硬性必需**：现有 launcher 读 `sidecar.dist_hash` 的逻辑在两案下都不坏；只有**要新增闭环消费者**时才需要，消费者也可放进 `start.ps1`（有 `Get-FileHash`/HTTP 能力） | 同左 |

**两案共同成本**（与选案无关）：要真正产生收益，都必须新增一个「比对 `/api/health.build_id` 与
sidecar 对应字段」的消费者，并处理「不一致时拒绝启动 / 仅告警」的产品决策；否则只是改了值、
链路依旧无人消费。

#### 方案②最小落地步骤与验收断言（fallback，本轮不实施）

**最小步骤**：

1. `tools/Write-BuildStamp.ps1` 新增 `Get-KedaiDistFnv`：`Add-Type` 内联一小段 C# 实现
   FNV-1a 64（`unchecked` 乘法，`ulong`，offset `0xcbf29ce484222325`、prime `0x100000001b3`），
   与 Rust 完全同序：相对路径→`\`换`/`→`0x00`→裸内容→`0xFF`，按**相对路径序数序**遍历；
   输出 16 位小写 hex。
2. `Write-KedaiBuildStamp` 的 `[ordered]@{…}` 增加 `fnv = Get-KedaiDistFnv -Root $Root` 字段
   （保持扁平紧凑 JSON；launcher 的 `extract_json_string` 按 `"key":"` 子串提取，新增字段不影响
   `dist_hash` 读取）。
3. 新增消费者：在 `launcher/src/main.rs`（或 `start.ps1`）服务就绪后请求 `/api/health`，
   取 `build_id`，与对应 exe 的 sidecar `fnv` 比对；不一致→弹窗/报错并按产品决策拒绝启动或仅告警。
4. 更新 `../MAINTENANCE.md` 同步机制小节与 D2 行，说明新增字段与语义。

**验收断言（可测）**：

- B1（正常同源）：一次 `build.ps1` 双端构建后，启动任一 exe，`GET /api/health` 的 `build_id`
  必须**字符串全等**于该 exe 同名 `.build.json` 的 `fnv` 字段。
- B2（拒绝替换，核心断言）：把 `dist\Kedai-portable\Kedai.exe` 替换为「**另一次构建**的 exe」
  （其内嵌 FNV ≠ 当前 `Kedai.exe.build.json.fnv`），双击 launcher 后，**启动器必须报告指纹不一致
  并拒绝启动**（非零退出或明确弹窗），而不是照旧启动。
- B3（不误伤缺失）：删除或清空 sidecar、或字段缺失时，消费者按「无法判定」处理，
  **不得拒绝启动**（与现有 drift 语义 `launcher/src/main.rs:540–541`、`start.ps1:88` 一致）。
- B4（不误报重复）：同一次构建的产物，连续多次启动不触发重建、不报不一致。
- B5（跨端一致）：`dist\kedai-server.exe` 与 `dist\Kedai-portable\Kedai.exe` 的 `fnv` 相等；
  `build.ps1:404–411` 的既有 `dist_hash` 一致结论仍为绿。

> 说明：断言 B2 可检出「换了另一份 exe」，但**检不出**「攻击者同时伪造 `/api/health` 或替换
> sidecar」（场景 B），这属于方案②能力边界，交付时应连同文档一并声明。
> 方案①（`build.rs` 改算 SHA256）**明确不推荐**：需复刻上列三处序列化细节、新增 `sha2`
> build-dep 并实跑 `npm run check:lock`，成本最高、收益与②持平。

#### 第三案（供决策，超出原二选一范围）

- 让 `Write-KedaiBuildStamp` 额外写入 `exe_sha256 = (Get-FileHash -Algorithm SHA256 $ExePath).Hash`
  （哈希对象是 **exe 字节**，不是前端）。
- 由已持有 `Get-FileHash` 的 `start.ps1` 在启动前重算 exe 哈希并与 sidecar 比对；不一致即拒绝启动。
- 优点：真正覆盖「exe 被替换」；无需 Rust/build-dep/锁变更；不触碰内嵌指纹与 Android；
  launcher 零依赖约束不需要动（校验放在 PS 侧）。
- 缺点：仍需信任 sidecar（攻击者同时换两者可绕过），且对「校验者自身被替换」无效；
  本质是把「前端同源自检」升级为「exe 字节完整性自检」，仍非签名级安全边界。
- **重要限定**：本仓既有做法是「用户从**可信渠道**取到公布哈希，再 `Get-FileHash` 逐字比对」。
  信任根来自**带外公布**的哈希，不是本机 sidecar。上述自动化只是把「配错包/本机被换」的
  自检工程化，**不能替代带外核验，更不替代 Authenticode**。

#### 未决问题（源文档列出，本文件不代裁）

1. **收益定性**：「防手工替换 exe」是否被列为正式安全需求？若仅是发布 QA 的「同源自检」，
   维持现状即可；若是安全需求，方案①② 都不满足，应转向第三案或代码签名。
2. **消费者归属**：闭环校验放 `launcher`（双击主入口，需重建）还是 `start.ps1`（零重建，
   但命令行用户才经过）？
3. **Android 是否纳入**：两案都无法覆盖 Android（无 sidecar）。是否接受「Android 不做指纹闭环」？
4. **不一致时的产品行为**：拒绝启动 / 仅告警 / 自动重建？影响验收断言 B2 的措辞。

> **重新评估触发条件**（D2 登记口径）：①引入代码签名；②出现真实「替换 exe」威胁场景；
> ③需要发布 QA 同源机检（届时优先第三案 `exe_sha256`，次选方案②，不选方案①）。

### 六、版本单源（8 处声明）

- 修复的真实漂移（两次）：①`package-lock.json` 曾停在 **0.2.0**，其余 6 处声明为 0.2.1；
  ②0.3.0-B-beta 升版时漏改两处——`AboutSection.vue` 的 `FALLBACK_VERSION` 停在
  `0.3.0-A-beta`（离线/后端不可达时关于页显示旧号，且该值已编进 `web/dist` 与 exe），
  `package-lock.json` 的 `packages["web"]` 自身版本因脚本按位置只改前 2 处而滞留在旧号
  （会被 `npm ci` 判为 lock 与 `web/package.json` 不同步）。两处均于 0.4.0-alpha 批次修复：
  前者纳入脚本覆盖 + 构建断言，后者改为**按值精确匹配全部自身版本**。
- `tools/bump-version.ps1` **纳入** `package-lock.json` 的**全部自身版本**（现 3 处：顶层 +
  `packages[""]` + `packages["web"]`；按值匹配、不碰依赖版本）与
  `web/src/components/settings/AboutSection.vue` 的 `FALLBACK_VERSION`。
- `build.ps1` 开头 `Assert-VersionConsistency`：校验 8 处声明一致，不一致即 `throw`
  并列出差异（已实测通过/失败两条路径）。

**8 处声明（`Assert-VersionConsistency` 的 `$declared` 顺序）**：

| # | 文件 | 取法 |
|---|---|---|
| 1 | `package.json` | JSON：`"version"\s*:\s*"([^"]*)"`（第一处） |
| 2 | `web/package.json` | 同上 |
| 3 | `package-lock.json` | 同上（不用 `ConvertFrom-Json`：PS 5.1 解析 `package-lock.json` 会因依赖键名报错） |
| 4 | `server-rs/Cargo.toml` | TOML：`(?m)^version\s*=\s*"([^"]*)"` |
| 5 | `src-tauri/Cargo.toml` | 同上 |
| 6 | `launcher/Cargo.toml` | 同上 |
| 7 | `src-tauri/tauri.conf.json` | JSON（第一处） |
| 8 | `web/src/components/settings/AboutSection.vue` | Vue：`const FALLBACK_VERSION = '([^']*)'`（关于页兜底版本常量，会经 vite 编进 `web/dist` 与 exe） |

- 统一口径：取文件**第一处** `"version"` 字段（与 `tools/bump-version.ps1` 同语义）。
- 另：`MAINTENANCE.md` 版本行与 `package-lock.json` 的其余自身版本由 `bump-version.ps1`
  同步，不入断言（文档行与 lock 位置语义不适合做硬门禁）。
- 异常取值：文件不存在 → `(缺失)`；正则不匹配 → `(解析失败)`。
- 不一致输出：`[FAIL] 版本号不一致,构建中止。请跑 npm run version:bump -- <x.y.z> 统一:`
  并逐行打印各文件取值，随后 `throw`；一致则输出
  `版本一致性校验通过:<版本>(8 处声明)`。

**产物签名状态（2026-09-13 逐项实测）**：

| 便携版桌面应用 | `dist\Kedai-portable\Kedai.exe` | **无签名**(NotSigned) | 首选交付形式（见 `../README.md:86`、`../README.md:89`） |

上述 Windows 三份 exe 的「无签名」为实测结论（对当前工作区产物执行
`Get-AuthenticodeSignature` 返回 `NotSigned`）。它们**没有**任何受信任 CA 颁发的代码签名证书。

> 注：便携版目录内另有 `dist\Kedai-portable\README.txt`（由 `tools/build-portable.ps1:96-104`
> 生成），内容为启动与数据目录说明，不涉及签名。

#### 为什么不签

- **代码签名证书是付费产品**，且需以真实主体实名申请、按年续费。是否购买属产品决策，
  当前未购买，故本轮只补文档。
- **自签名证书解决不了 SmartScreen**。SmartScreen 只认可受信任 CA 链上的证书；自签证书
  与「未签名」在用户侧表现一样都会告警，还会额外增加密钥保管负担，因此**不做自签的
  Authenticode**。
- **当前分发定位为内测/自用**，使用者在可核对的渠道拿到产物，接受「未知发布者」的一次性
  确认成本；配合下「可信性自查」即可确认来路。

### 八、用户侧：首次运行遇到 SmartScreen 如何安全继续

#### 什么时候会触发

从浏览器 / 网盘 / 聊天工具**下载**再解压的产物，ZIP 与解压出的 exe 会带上 Windows 的
「网络来源」标记（Mark of the Web / Zone.Identifier），双击时可能弹出：

> **Windows 已保护你的电脑**
> Windows Defender SmartScreen 阻止了无法识别的应用启动。运行此应用可能会导致你的电脑存在风险。

在项目目录内**本地构建**（`.\build.ps1`）的产物通常不带该标记，一般不会弹窗。

#### 安全继续步骤（确认来源后）

1. **先核对来源**（本地构建可跳过；下载分发的 zip 请先做「可信性自查」的哈希核对）。
2. 在蓝色弹窗中点 **「更多信息」** → 展开后出现 **「仍要运行」** → 点「仍要运行」。
3. 若整个 ZIP 被拦、或「仍要运行」不可点：**先解除 ZIP 的锁定再解压**——右键下载的
   `.zip` → **属性** → 勾选底部 **「解除锁定」** → 确定，然后重新解压并运行。已解压出的
   单个 exe 也可同样在「属性」里「解除锁定」。
4. 程序启动后，在应用**设置中心底部**核对「版本 · 构建时间 · 指纹前 8 位」是否与预期一致。

> **不要**为了省事全局关闭 Defender / SmartScreen，或对整个下载目录永久放行。只对**已核对
> 哈希的单个文件**放行；来源不明时不要以「仍要运行」强行启动。

### 九、可信性自查：确认产物来路

1. **构建指纹 sidecar**（`<exe>.build.json`）：见上「sidecar 文件格式」。测试版与便携版的
   `dist_hash` 必须一致，指纹一致才说明同源。
2. **直接核对 exe 哈希**：若要确认拿到的 exe 与构建方公布的一致，对 exe 本身算 SHA-256：

   ```powershell
   Get-FileHash .\dist\Kedai-portable\Kedai.exe -Algorithm SHA256
   ```

   把结果与构建方/发布方公布的十六进制串逐字比对。**建议只从你信任的渠道取哈希值。**
3. **运行时复核**：二进制内嵌 `KEDAI_DIST_HASH` / `KEDAI_BUILD_TIME`，`GET /api/health`
   返回 `build_id` / `build_time`，可与 sidecar 相互印证。

#### Android APK 的签名与覆盖安装约束

APK 与 Windows exe 走不同的签名体系：APK 用 release keystore 自签，构建即签名。

**核验命令**（需本机 `D:\kedai-android\` 工具目录，仅用于核验，不参与运行）：

```bat
cmd /c "D:\kedai-android\bin\apksign.bat verify D:\kedai-android\artifacts\<apk>"
```

**期望结果**（2026-09-13 实测 `Kedai-0.3.0-A-beta-arm64-release.apk`）：

- `Verified using v2 scheme (APK Signature Scheme v2): true`
- `Signer #1 certificate DN: CN=Kedai, OU=Kedai, O=Kedai, L=Unknown, ST=Unknown, C=CN`
- `Signer #1 certificate SHA-256 digest: 19d79a89d87473d286b1ab4d5a45defceae70efe65fa2de0369c1de25f2f062f`

**覆盖安装约束（重要）**：Android 要求**同包名 + 同签名密钥**才能覆盖升级。

- 用**同一密钥**（SHA-256 `19d79a89…`）签的新版 → 可直接覆盖安装，**保留应用数据**。
- 换了密钥 → 必须先卸载旧版才能安装，会**丢失应用数据**。

因此发布 APK 必须始终坚持用 `D:\kedai-android\keystores\kedai-release.jks`（别名 `kedai`），
口令配置在 `src-tauri\gen\android\keystore.properties`（已被 `src-tauri/gen/android/.gitignore`
忽略，不入库）。**切勿重新生成密钥。**

#### 指纹能证明什么、不能证明什么

**能**：证明某份产物由本仓库构建链产出、测试版与便携版同源同步、给你的哈希与公布值一致。

**不能**（诚实标注，勿据此宣称「防篡改」）：

- sidecar（`.build.json`）**未与 exe 做密码学绑定**，可被一并替换，属一致性辅助而非信任根。
- `dist_hash` 只覆盖 **`web/dist` 前端资源**，**不是 exe 二进制自身的哈希**；
  exe 二进制哈希须用 `Get-FileHash` 单独核。
- 二进制内嵌指纹用 FNV-1a，与 sidecar 的 SHA-256 **算法不同、不可直接比对**——此「指纹链不闭环」
  已登记为残余风险 D2。

真正防冒充需要 Authenticode 签名（下节）。

### 十、后续：若要正式签名（只列要点，不实施）

1. **证书类型**
   - **OV 代码签名证书**：成本较低，但 SmartScreen 信誉需**时间与下载量积累**后才逐步消除告警，
     非即时生效。
   - **EV 代码签名证书**：首装即获 SmartScreen 信任，但成本更高，且私钥必须存于硬件令牌或云 HSM。
2. **私钥保护**：2023 年起主流 CA 要求 OV/EV 私钥存硬件令牌或云 HSM（如 Azure Trusted Signing、
   DigiCert KeyLocker），不能再以文件形式保存；需为签发环境与持有者建立流程。
3. **构建/发布改动点**（均为「新增签名步骤」，不改现有构建逻辑）：
   - 每个 exe 产出后执行 `signtool sign /fd SHA256 /td SHA256 /tr <RFC3161 时间戳服务>`；时间戳
     **必须加**，否则证书过期后已签文件随之失效。
   - 接入 `build.ps1` 的三处产物（`dist\kedai-server.exe`、`tools/build-portable.ps1` 产出的
     `dist\Kedai-portable\Kedai.exe`、项目根 `Kedai.exe`）。
   - NSIS 安装包（可选交付形式）可在 Tauri 的 Windows signing 配置中声明证书，或构建后补签。
   - `.github/workflows/ci.yml` **已落盘**（2026-09-26 激活、**2026-09-29 服务端停用**，见本文「构建与发布契约」§七 CI 现状）；若将来把签名步骤并入 CI，需设计签名密钥在 CI 中的安全注入。
4. **预期效果与边界**：EV 可即时消除 SmartScreen 告警；OV 仍需信誉积累。签名无法覆盖
   「用户从不可信渠道取得被替换产物」的场景，来源核对仍是必要环节。
5. **决策归属**：是否购买、买 OV 还是 EV，属产品决策。

### 三、任务模式机制要点（2026-08-28 重构后）

- 后端任务引擎分两层：`server-rs/src/services/task_service/`（任务 CRUD/状态/取消/事件）与

  统一派发点见 `task_engine/mod.rs`）；任务状态为枚举 `TaskStatus`/`TaskStepStatus`/`TaskSubtaskStatus`，
  运行模式为 `TaskRunMode`（`models/types.rs`，serde snake_case 字符串，落盘与 API 线格式不变）。
- 数据流：DB 写入成功后 `TaskService` 经 broadcast 通道发射 `SseEvent::Task`，
  `GET /api/tasks/events` 转发为 SSE；前端 `web/src/stores/task.ts` 事件驱动精确刷新
  （无轮询；断线指数退避重连 + 5s 兜底轮询）。**新增事件 kind 需前后端四处同步**
  （枚举 `TaskEventKind` / 发射点 / `web/src/api/types.ts` 的 TS union / store 刷新映射；
  末项由 `stores/task.ts` 的 `never` 穷尽断言兜底——漏改会在编译期失败，不会静默丢事件）。
- 提示词共享原语在 `server-rs/src/services/prompt_kit.rs`（世界书过滤/注入合成/占位符渲染/
  `untrusted_boundary`），引擎与任务双侧调用，**勿在任一侧复制实现**。
- 双模式提示词隔离由类型承载（`RoleplayPromptConfig`/`TaskPromptConfig`，settings.json
  线格式不变）；新增涉及双模式的设置字段时，继承/隔离规则先读「双模式提示词边界」一节。
- **终态 `result` 契约（2026-09-26 提交 2）**：`tasks.result` 在**任何终态**下都可能是
  「已完成步骤的确定性拼装」——汇总/审计调用失败、取消（`ended`）、失败（`error`）、服务重启
  中断四条路径都经同一拼装器 `task_core::assemble_from_plan` 兜底（落库经
  `db::set_result_only`：**只更新 result 列，不动 status/error**）。判定规则：**能拼出
  「已完成且产出非空」的步骤即 `partial`（result=拼装文本，error=失败原因），一步都没有才
  `error`/`ended` + 空 result**（不伪造成果）。`POST /api/tasks/{id}/approve` 在置 planning 时
  **清空 planned 态的预览 result**（`db::clear_result`，只清 result 列、不发事件）——预览只在
  planned 态有语义，留着会让「result 为空才兜底」失效、把计划当成成果展示。
  前端 `TaskBoard` 对 `error`/`ended` 且 result 非空的展示加「任务未完成，以下为已完成部分的
  成果」标注；plan 续跑 result 只放汇总文本（批次 R1 的「## 最终计划」段已移除，步骤信息由
  `task.plan` 结构承载，前端对旧任务 result 里的该段仍做拆卡兼容），team 的「## 审计结论」段保留。
