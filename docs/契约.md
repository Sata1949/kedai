## HTTP API

> 本节是 `archive/2026-09-16-consolidation/API.md` 的**逐端点全文移植**。字段名、类型、取值域、默认值、状态码、错误语义、示例一律按原文；本节末尾另附 `MAINTENANCE.md` §6「维护红线路由总表」（含 API.md 未列的若干事实，如 `/api/token/count` 的「每条 +4、末尾 +2」）。

### 通用约定

- 基地址：开发模式 `http://127.0.0.1:3001`（前端经 Vite 代理 `/api`）；生产模式同域。
- 所有请求/响应均为 `application/json`（除文件上传与 SSE 流）。
- 除 `/api/health`、`/api/bootstrap` 与 `/api/avatars/*` 外，API 请求必须携带服务启动时生成或由 `KEDAI_API_TOKEN` 固定配置的 Bearer token；非 loopback 监听还必须显式设置 `KEDAI_ALLOW_REMOTE=1`，且固定 token 至少 32 字符。
- 运行时主 Agent 提示词统一来自 `DATA_DIR/AGENTS_RUNTIME.md`，不是仓库开发用 `AGENTS.md`。
- 全部时间字段为 ISO 8601 字符串。

### 聊天

#### POST `/api/chat/send` — 发送消息，触发 Agent 全流程

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `message` | string | ✅ | 用户消息（去空） |
| `session_id` | string | 条件 | 目标会话；与 `character_id` 二选一（缺省时取该角色首个会话/自动创建） |
| `character_id` | string | 条件 | 目标角色 |
| `agent_mode` | `"fast" \| "deep" \| "agent" \| "custom"` | 否 | 默认 `fast`；`deep` 启用完整计划-执行-反思；`agent` 同 deep + 工具循环；`custom` 按「Agent 执行流程」配置的步骤序列执行（需先在设置中启用并保存，否则 400） |
| `temperature` | number | 否 | 默认取运行期设置（初始 0.8） |
| `top_p` | number | 否 | 默认取运行期设置（初始 0.9） |
| `max_tokens` | number | 否 | 默认取运行期设置（初始 1024）；simple 字数注入启用且字数要求更高时自动上调（需 = min(字数×2+512, 8192)） |
| `resend_message_id` | integer | 否 | 编辑后重发锚点；服务端仅接受当前会话最后一条、角色为 `user` 且正文与 `message` 一致的消息，否则返回 409 |

**响应**：`text/event-stream` SSE。事件类型：

| 事件 | 负载 | 说明 |
|---|---|---|
| `step` | `{step, detail?}` | Agent 步骤（计划中/执行中/生成中/反思/出错…）；custom 模式额外携带 `{index, total}`（第几步/共几步），fast/deep/agent 不带 |
| `token` | `{text}` | 文本片段（逐字渲染） |
| `tool_call` | `{name, input}` | 工具调用预告 |
| `tool_result` | `{name, output}` | 工具结果 |
| `vars` | `{stat_data}` | 酒馆助手变量树同步：模型回复中的 `<UpdateVariable>` 补丁被应用后推送最新 `stat_data`（仅变量更新时出现，先于 `finish`） |
| `interrupted` | `{}` | 被停止 |
| `finish` | `{usage, content}` | 结束，含 usage（`prompt/completion/total/context_tokens`）；`content` 已剥离 `<UpdateVariable>` 协议块 |

**错误**：400 消息为空；404 会话不存在；409 会话正在生成中；400 custom 模式未启用/流程未保存或非法。

> **对账提示**：`types.rs` 的 `SseEvent` 另有 `error` / `tool_authorization_required` / `task` 三个变体与 `finish.finish_reason` 字段，本表（API.md 原文）未列出——完整清单见「SSE 线格式」一节。

#### POST `/api/chat/stop` — 停止当前生成

请求：`{ "session_id": string }` → `{ "ok": true }`

#### GET `/api/chat/history?session_id=…` — 消息历史

响应：`{ "messages": [{ id, session_id, role, content, extra, created_at }] }`

> 酒馆助手：assistant 消息 `extra.mvu = { stat_data }` 携带当轮更新后的变量树快照（仅变量更新时），前端按消息顺序回放即可得到会话最新状态；`content` 为剥离 `<UpdateVariable>` 块后的干净文本。**纯变量更新消息（正文为空）同样落库**（带快照），保证刷新/回放不把变量树回滚到更新前。

#### PUT `/api/chat/messages/:id?session_id=…` — 编辑消息

请求：`{ "content": string }` → 更新后的消息

#### DELETE `/api/chat/messages/:id?session_id=…` — 删除消息

成功 → `204`

#### POST `/api/chat/clear` — 清空会话（保留角色定义）

请求：`{ "session_id": string }` → `{ "ok": true }`

### 角色卡

#### GET `/api/characters` — 列表（摘要，不含 data_raw）

#### POST `/api/characters/upload` — 上传角色卡

### Agent 执行流程（custom 模式）

流程为**全局流程库**（持久化 `data/agent_flows.json`）：可保存多个流程、切换当前选中、导入导出。所有响应统一携带：

- `library`: `{ current_flow_id: string|null, flows: [流程…] }` — 完整流程库
- `config`: 当前选中流程（无选中时为 `null`，兼容旧调用方）

单个流程：`{ id, name, description?, enabled: bool, max_parallel_nodes?, steps: […] }`；步骤字段：`{id, name, enabled, goal, action, generates?, system_prompt?, temperature?, max_tokens?, tools?, tool_choice?, tool_choice_function?, parallel_tool_calls?, inputs?, is_output?, x?, y?, kind?, sub_flow_id?, connection_id?, max_tool_rounds?, max_context?, call_timeout_secs?, max_retries?}`（末两项为 A 批 A1/A2，2026-09-24 加：单次调用超时 30..=3600 秒、空产出重试次数 1..=5，均加性省略、挂载子流程的节点旁路，契约全文见 `契约-协议与配置.md`「节点级超时 / 重试与调用闸设置契约」）。

`tools` 语义：`null`/缺省 = 该步不使用工具；`[]` = 全部工具；`[name…]` = 白名单（按注册名过滤）。

二维依赖字段（2026-09-19 二维批次 1/2）：

- `inputs: [步骤 id…]`（缺省省略）= 该步的**上游**；全部步骤都不填 = **线性兼容模式**（按数组顺序串联，等价旧的一维流程，生成消息格式逐字节不变）；任一步填了即二维流程，此时 `inputs` 为空的步骤是**源节点**（只用任务目标）。
- `is_output: true`（缺省省略）= 显式标注最终成果节点；未标注时按**无后继汇点**自动判定。
- `x`/`y` = 画布坐标（2026-09-20 二维批次 3 起由画布的显式动作写入：拖动节点或点「重新布局」；**后端只透传不解释**，列表视图不写。缺省 = 未手工布局，画布按依赖层级自动排布）。
- `kind`：`loose`（缺省）= 允许多轮工具自循环；`strict` = **单次模型调用、不下发任何工具**（2026-09-21 二维批次 6a 起支持）。**档位优先于 `tools`**：严格节点即使配了工具也不下发，工具配置保留在流程里（切回宽松即生效，编辑器按此提示）；其余取值保存期 400 拒绝。
- `connection_id`（2026-09-23 二维批次 5b）：该节点走哪一套 API 连接（`ConnectionProfile.id`）；缺省 = 默认连接。**provider 与模型随该连接**，故「节点级模型」= 选连接（不另设节点级 model）。空白串按未设置处理。引用**不做保存期校验**（流程可导出/跨机导入，连接是本机设置）：运行期若该连接已删除/已停用，该节点**明确报错、不回退默认连接**；挂载子流程的节点上本字段被旁路（子图各节点各自解析）。
- `max_tool_rounds`（2026-09-23 二维批次 5b）：该节点工具循环的轮次上限（1–200），缺省 = 沿用全局 `settings.max_tool_rounds`；严格档下不下发工具、该配置保留但不生效（编辑器在严格档收起该输入）。
- `max_parallel_nodes`（流程级，缺省 2、范围 1–8；`1` = 完全串行）：同一层的节点最多同时执行几个。

#### custom 模式执行语义

- 步骤按 `enabled=true` 顺序执行；每步 `system_prompt` 经酒馆宏展开后追加 `[本步指令]` 到 system 末尾（独立消息视图）。
- `{{setvar}}`/`{{addvar}}` 在每步生成后持久化到会话变量，后续步骤可用 `{{getvar}}` 读取（跨步骤状态传递）。
- 步骤级 `temperature`/`max_tokens` 覆盖全局参数；`tools` 决定该步工具可见性（agent 模式整体下发全部工具，custom 按步控制）。
- `POST /api/agent/plan` 支持 `agent_mode=custom`：返回流程摘要「自定义流程：共 N 步」与各步骤名称。
- **任务侧二维执行**（`POST /api/tasks/{id}/run`，`task_mode=custom`）：
  - 执行顺序 = **拓扑序**（Kahn，就绪节点按数组下标升序出队）；线性兼容流程因此等于数组顺序，行为与一维版一致。
  - 节点输入 = 上游产出按**上游在数组中的下标升序**拼接进 user 消息：单上游沿用 `上一步「X」产出:` 格式；多上游用 `上游节点产出:` + 逐段 `【节点名】`；上游失败或产出为空时该段留空（不写占位词）。
  - 下游只在其**全部上游结束**（无论成败）后才启动；节点失败只影响自身行，不阻塞后继。
  - **并行**：就绪节点同时最多跑 `max_parallel_nodes` 个（缺省 2）；并行会成倍消耗 token。
  - **成果**：显式 `is_output` 节点产出优先；为空则按数组下标降序回退到上一个非空「生成正文」步骤产出；全流程无有效产出 → 任务 `error`（「自定义流程未产出任何成果…」）。含失败节点但成果已产出 → `partial`。
  - **档位**（2026-09-21 二维批次 6a）：`kind=strict` 的节点**单次模型调用**、不下发任何工具（`tools` 配置保留但不生效）——模型即便返回工具调用也不执行；缺省/`loose` 按 `tools` 三态走工具自循环。判定为 `PlanStep::is_strict`，任务侧与聊天侧同一出处。
  - **节点级连接**（2026-09-23 二维批次 5b）：节点可用 `connection_id` 指定**自己走哪一套 API 连接**（provider + 模型随连接）——同一任务内不同节点因此可以走不同 provider。解析收在 `AgentEngine::resolve_connector`（单一出处）：缺省 → 默认连接（行为与 5b 之前逐字节一致）；引用的连接**已删除/已停用** → 该节点 error、**不静默回退默认连接**、其余节点照跑（解析失败发生在发起调用之前，该节点不留调用行）。调用追踪的 `model` 列记**该节点连接的真实模型**。聊天侧 `agent_mode=custom` 与任务侧共享同一分流。边界：聊天侧的可观测面板不会体现模型差异（见 `遗留.md` IFW-10）。
  - **节点级工具轮次上限**（2026-09-23 二维批次 5b）：`max_tool_rounds`（1–200，缺省沿用全局）限制本步工具循环轮数；任务侧与聊天侧同口径，严格档下配置保留但不生效。
  - **取消**：`POST /api/tasks/{id}/stop` 中止全部在飞分支（未启动节点保持 `pending`），任务收口为 `ended`；在飞分支的中断留痕（调用行 `生成已中断`）按设计保留，供前端「已中断」徽标展示。
  - **静态子图**（2026-09-21 二维批次 6b）：节点可用 `sub_flow_id` 挂载**库内另一套流程**，该节点自己不发起模型调用，改为把被引用流程当子图跑一遍，**子图成果即本节点产出**并流向下游。
    - **被旁路但配置保留**的字段：`goal` / `action`（reflect 除外，保存期直接拒）/ `kind` / `tools` / `system_prompt` / `temperature` / `max_tokens`——清空 `sub_flow_id` 即恢复生效（与 6a「档位优先于 `tools`」同一纪律，编辑器按此提示）。
    - **仍生效**的字段：`name`（展示）/ `generates`（成果选拔）/ `inputs`（决定子图在拓扑序中的插入位置）/ `is_output`（成果标注）。
    - **子图源节点的输入 = 挂载节点收到的输入消息**（即「任务目标 + 上游产出」）：上游数据照常流进子图，子图不是孤岛；**成果**取子图自身的成果节点选拔（`output_index` + 空产出兜底）。
    - **plan 不展开子图**：`plan` 恒为**外层**流程的节点列表，挂载节点占一行、子图内部节点不占行；子图进度体现在挂载行的 running 态与调用追踪的 `subflow.<路径>` 行（记账与守卫口径见 `docs/契约-协议与配置.md`「自定义流程与静态子图契约」）。
    - **降级**：子图内有失败/空产出节点但成果仍选得出 → 挂载行标 `done` 并在 result 前缀「(子图内有失败节点)」，任务收 `partial`；**该标注只改展示，不污染下游提示词**（下游拿到的仍是纯子图成果）。
    - **并行**：子流程按**它自己的** `max_parallel_nodes` 并行，嵌套时并发**按层数相乘**（token 消耗随之增加）。
  - **聊天侧差异**：`POST /api/chat/send` 的 `agent_mode=custom` **不并行**，二维流程按拓扑序**线性化**后逐步执行（分支结构在该路径被忽略）；**档位语义两侧一致**（严格节点在聊天侧同样为单次调用、不下发工具）。**子流程在聊天侧被就地展开**成子图节点序列（名字加 `【子流程「X」】` 前缀），展开时步骤 id 按挂载位置重写以保证全局唯一（同一子流程可被多处挂载、父子流程可撞 id），步骤 `inputs` 一律清空。

#### GET `/api/workspace/profile` — 工作区画像探测（CODE-4）

查询参数 `path`（工作区绝对路径，**必填**；前端用 `URLSearchParams` 编码）。响应 `{ ok: true, profile: WorkspaceProfile }`：

- `WorkspaceProfile`：`{ root, detected: ProjectTypeHint[], scanned_dirs, truncated }`——`root` 是**冻结值原样回显**（Windows 上可能含 `\\?\` 前缀，不做显示变换）；`scanned_dirs` 是实际扫描过的**子目录**数（不含根）；`truncated` 为真表示子目录数超上限（32）而未扫全——**诚实留痕**，前端显式展示「(未扫全)」而不是假装扫完；
- `ProjectTypeHint`：`{ kind, marker, suggested_command, depth }`——`kind` 取 `rust` / `node` / `python` / `go` / `java` / `dotnet`（前端对未登记取值**原样回显**，不假装认识）；`marker` 是证据文件的相对路径（子目录层形如 `server-rs/Cargo.toml`，分隔符统一 `/`）；`suggested_command` 是**常量表文案**（如 `cargo test`），UI 按「建议」呈现，**不宣称已核实可用**；`depth` 为 0（工作区根）或 1（直接子目录）；
- **判定口径**：按固定常量表顺序（rust → node → python → go → java → dotnet）逐类判定，每类**首个命中者胜**（先根后子目录；子目录按名字排序），故同一类型最多一条；只做**文件存在性**判断（含 `*.csproj` / `*.sln` 的扩展名匹配），**不解析 manifest、不执行任何命令**；
- **两条硬边界**：① 只探**根 + 一层子目录**（只探根会对 monorepo 给出错误的验证命令——本仓自身即反例：根只有 `package.json`，`Cargo.toml` 在 `server-rs/` 下）；② 与创建任务**同一把尺**校验路径（不存在 / 非目录 / 与数据目录互相包含 → 400，**文案与创建期逐字一致**，同一函数出的），`path` 缺失或空白 → 400（**该条为本端点独有**：创建期把空串当「不绑定」，探测没有「空」可探）；
- 与任务详情的 `workspace_profile` 是**同一个后端函数**（`server-rs/src/services/workspace_profile.rs::probe`）的两处出口；探测在阻塞线程池执行（目录读取是 IO，不阻塞 async 运行时）。

> 来源：`计划.md`「编码能力包功能扩展（CODE-1~CODE-5）」章 CODE-4 条目（2026-09-30 详细设计定稿；调研报告 `plans/CODING-REPORT.md` §5.4）。

- 非 `approved_plan` 时，已批准计划作为 goal（「目标 + 已批准计划」组合文本）下发给该模式，

- **刻意排除** `legacy`（自带规划会与已批准计划重复劳动）与 `plan`（会再规划回到 planned，

- `flow_id: null` = 跟随当前流程（解绑，快照清空，下次执行重新捕获）；
- `flow_ids: []` = 强制模式（清空名单）；非空即为对比模式的可调用名单（成员须存在 + 启用 + 结构合法）；

解析（对不上即不显示）。成功时推 `flow_bound` 事件。契约全文见 `契约-协议与配置.md`「任务级连接与
改绑编排（A 批 B1/B3）」。

#### POST `/api/tasks/{id}/followup` — 终态追加指令（done/partial/error/ended 可追加，solo 续跑续写成果）

请求体 `{ content, mode? }`：`mode` 缺省/空 = `append`（新产出以「追加 N」段附加进
`result`，保留原文）；`replace` = 用新产出整体替换 `result`（段标「修订 N」，用于
「压缩/重写/改前面」类指令）；未知值 400（VALIDATION）。

**校验顺序与 code（来源：`archive/2026-09-16-consolidation/任务引擎六模式.md` §九）**：
空指令 400（VALIDATION）→ 不存在 404（NOT_FOUND）→ 非终态 409（CONFLICT；仅
`done`/`partial`/`error`/`ended` 可追加，`running`/`planning`/`planned`/`pending` 拒绝）
→ service 层复核（竞态失败同样 409）。

**链路与终态映射**：用户指令落 `task_messages`（kind=followup, role=user）→ 任务回 `running`
→ spawn 续跑（不经 TaskEngine 派发；收尾语义为 append 而非覆盖）→ 产出落 assistant 消息并
append 进 `result`（分隔段 `\n\n---\n\n**追加 N：**指令概要（截 80 字符）\n\n` + 产出；
N = followup 序号，即 kind=followup 的 user 消息计数）→ 终态映射：原 `partial` 保持 `partial`
（失败步骤历史不抹平），`done`/`error`/`ended` 追加成功后回 `done`。取消/失败与 legacy 同款
`finalize_run` 收尾（stop → `ended`，失败 → `error` 文本）。**事件纪律**：消息落库不发射独立
事件，生命周期复用既有 `status` 事件（running → done/partial），前端经事件驱动重拉详情携带
`messages`；**不引入新事件 kind**。

#### POST `/api/tasks/{id}/plan-chat` — 批准环节规划对话（planned 态按反馈修订计划）

请求体 `{ message }`。**校验顺序与 code（来源：`archive/2026-09-16-consolidation/任务引擎六模式.md` §十）**：
空反馈 400（VALIDATION）→ 不存在 404（NOT_FOUND）→ 非 `planned` 409（CONFLICT）→
LLM 上游/解析失败 502（UPSTREAM）；修订期间 stop 竞态中断按 409。

**链路**：用户反馈落 `task_messages`（kind=plan_chat, role=user）→ 规划器修订（同步等待；
`register_cancel` 登记使 stop 可中断）→ `set_plan` 替换（发射 `plan` 事件）→ `planned` 态
`result` 计划清单文本同步刷新（「计划已修订，共 N 步：…」，`set_planned_result`）→ assistant
修订说明落库（「计划已修订，共 N 步：步骤名清单」，名清单截 200 字符）→ **重发
`approval_required` 事件**（前端据此刷新批准区）。与 followup 不同：plan-chat 是同步 handler
（`planned` 态无并发执行，响应直接携带修订后计划），不经 `tokio::spawn` 后台化。

**修订提示词**：system = `PLANNER_PROMPT` + 世界书 + 修订指引段（新常量
`PLANNER_REVISE_GUIDANCE`，含独特词「计划修订指引」，mock 测试据此经 `[[reply_if:]]` 区分
首轮/修订轮）；user = 原始目标 + 当前计划 JSON + plan_chat 对话历史 + 本轮反馈。历史截断参照
`record_llm_call` 摘要口径：每条内容截 800 字符、历史段整体截 4000（多轮体积封底）。

#### GET `/api/tasks/{id}/calls` — 任务 LLM 调用追踪（「调用情况」面板）

响应元素为 `TaskLlmCallRecord`（`GET /api/tasks/{id}/calls`，按 `created_at`, `id` 升序）：
`{ id, task_id, phase, step_index, model, prompt_summary, response_summary, prompt_tokens, completion_tokens, reasoning_tokens, elapsed_ms, status, finish_reason, created_at }`。
`phase`：`planner` | `step` | `summarize` | `agent` | `subagent` | `audit`（另有 `summary` / `final_audit` 等口径见 `types.rs` 注释）；`status`：`ok` | `empty` | `error`；`finish_reason` 为上游 `stop`/`length`/`content_filter` 等，`''` = 未知/未下发（旧行兼容）。

#### 任务文件变更台账（2026-09-30 批次 4 / 4b，PRODCAP-4「交付可审计」；批次 A2 补 CODE-2 两端点）五端点

数据源是新表 `task_file_changes`（`models/db/schema.rs`；`before_blob` 存改动前正文，上限 256KB，
超限置 `truncated=1`；任务删除经外键 `ON DELETE CASCADE` 一并清除）。
扫描缺项另存 `task_scan_marks`（批次 4b；每次「未能完整检出」记一行中文原因，任务删除同样级联清除）。

#### GET `/api/tasks/{id}/changes` — 任务文件变更清单

→ `{ "changes": [TaskFileChangeRecord…], "undected": bool, "undected_reason": string|null }`，
`changes` 按发生顺序（`id ASC`）。元素字段：
`{ id, task_id, path, op, source, before_hash, after_hash, before_bytes, after_bytes, truncated, has_baseline, created_at }`
（`models/types.rs::TaskFileChangeRecord`）。**空清单是空数组**，不是 `null`——「本轮没改文件」由前端显式呈现。
`path` 恒为**工作区内相对路径**；响应不携带基线正文。
`op`：`create` | `modify` | `delete` | `rollback`；`source`：`tool`（`fs_write`/`fs_edit`/`fs_patch` 精确记账）
| `bash`（命令前后树扫描的**启发式**检出，批次 4b 起落地）| `rollback`。

**`undected` 是顶层字段而不是清单里的行**（批次 4b）：`changes` 的一行 = 一个**文件改动**，
而「扫描没扫完」不是改动、且零改动的命令也需要能留痕——混进清单会同时污染长度语义与回滚定位。
`undected=true` 时 `undected_reason` 给出**最近一次**缺项的中文原因（如「后扫描未完成…已省略删除类改动」
「有 N 个超过留存上限(256KB)的改动文件未逐项记账」），前端横幅按它分档显示，不得用固定文案冒充。

**bash 侧扫描的三档预算与声明边界**（批次 4b，实测依据见 `功能-变更史.md` 批次 4b 段）：
条目数 20000 / 单侧时间 10s / 驻留正文 32MB，先到者生效；撞条目或时间 → 记 `undected`（检出缺项），
撞驻留预算 → **不记 `undected`**（那些行仍入账，只是 `has_baseline=false`，属行级基线降级）。
扫描按名称跳过 `EXCLUDED_SEGMENTS`（`.git`/`target`/`node_modules`/`dist`/`.kedai-index`/`data`，
与 `fs_glob`/`fs_grep` 同源）**外加**扫描专用忽略集（`.venv`/`venv`/`site-packages`/`__pycache__`/
`.gradle`/`build`/`out`/`vendor`/`Library`/`Pods`/`.next`/`.mypy_cache`/`.pytest_cache`）——
这是**声明边界**：落在这些目录里的改动**不会被扫描、也不记 `undected`**（与工具族跳过排除表同一体例），
前端不得把它渲染成「没有变更」。

#### GET `/api/tasks/{id}/changes/diff` — 单文件 unified diff

查询参数 `?path=<相对路径>`。三种形态**都返回 200**，靠 `available` 区分：
① 有基线 `{ available:true, path, diff }`——`diff` 是自实现 unified diff，超预算时该字段本身是
「改动过大，不生成逐行 diff…」的说明文本，**不是空串**；
② 新建 `{ available:true, path, note:"…本次为新建…", diff }`（全量新增行）；
③ 无基线 / 不在台账 / `truncated` `{ available:false, path, reason }`。
**绝不返回空 `diff` 来表示「拿不到基线」**——空 diff 会被读成「没改动」，正是本契约要区分掉的歧义。

#### POST `/api/tasks/{id}/changes/rollback` — 单文件回滚

查询参数 `?path=<相对路径>`。成功 `{ ok:true, path, restored_bytes }`，新建的回滚是
`{ ok:true, path, removed:true }`；基线不可用 `{ ok:false, available:false, reason }`（HTTP 200，**不动手**）；
落盘失败 500 + `INTERNAL`（原文只进日志，响应是固定文案）；任务 `running`/`planning` 时
**409 + `CONFLICT`**（模型还在写同一文件时回滚会互相覆盖）。
回滚成功后**再记一条 `op=rollback` 的行**——回滚本身是一次改动，不得在清单里隐身。
新建项的回滚**先取快照再删除**（CODE-2）：回滚行带上被删正文，其本身可再被回滚（重建文件）——
「点错一次文件永久消失」的形态由此关闭，整任务回滚的逐项可逆也由这条成立。

`?path=` 一律经 `tools/workspace_guard::safe_workspace_path` 解析（与 `fs_*` 工具同一个闸门，
不留第二份路径策略）；越界 / 符号链接逃逸 / NUL → 400 + `VALIDATION`，中文原因可纠正。

#### POST `/api/tasks/{id}/changes/rollback-all` — 整任务回滚（CODE-2，2026-09-30 批次 A2）

无查询参数。对本任务台账里的**每个路径**逐项执行与单文件回滚**完全相同**的语义（取该路径最新一行；
`create` → 删除；无基线 → 跳过；每项成功再记一条 `op=rollback`），顺序 = 首次出现在台账里的顺序。
响应 `{ ok, restored, removed, skipped, failed, results:[{ path, result, restored_bytes?, note?, reason? }] }`，
`result`：`restored` | `removed` | `skipped` | `failed`；`ok = failed === 0`。
**逐项报告、不整体否决**（计划 Q2=(a)）：某项无基线（`skipped` + 中文原因）或落盘失败
（`failed`，原文只进日志、响应给固定文案）不拦住其余项。任务 `running`/`planning` → **409 + `CONFLICT`
整单拒绝**（与单文件同口径）；空台账 → 200 空报告（`results` 为空数组，不是 404）。
**可逆**：对同一任务再调一次 = 逐项切回「改动后」状态（取最新一行的自然结果，非新语义）。

#### GET `/api/tasks/{id}/changes/patch` — 整任务 patch 导出（CODE-2，2026-09-30 批次 A2）

文本响应（`Content-Type: text/plain; charset=utf-8`，**非 JSON**），由可 diff 行逐文件拼成
**git 可 apply** 的补丁：修改 = `diff --git` + `--- a/<path>` + `+++ b/<path>` + 单 hunk
（头部计数严格按 unified diff 语义——`git apply` 会按计数校验）；新建 = `new file mode` +
`--- /dev/null` + 全量新增行。拿不到基线的（超留存上限 / 读取失败 / 已删除）与
「改动过大 / 无逐行变化 / 路径含空格或引号」**不进正文**，统一在头部注释区列明
（`# 未包含 N 个文件:` + 逐条原因）——半截 patch 在 git 眼里是坏补丁，静默丢失的文件
又会被读成「没改过」，两头都不接受。空台账 → 只有头部注释的文本。
**诚实边界**：按行文本生成（行尾统一 LF），不含 `\ No newline at end of file` 标记处理——
无尾换行的文件可能被 `git apply` 拒绝（该文件仍会出现在补丁里，失败由 git 报出）。

行类型 `TaskFileChangeRecord` ↔ 前端 `TaskFileChange` 已登记进 `check-contract.mjs` 的 MAPPINGS
（2026-09-30 批次 4c，第 22 组；2026-09-30 CODE-4 起全表为 24 组）；前端文件变更区块在 TaskBoard 内嵌渲染
（`web/src/components/FileChangesPanel.vue`，四态文案纪律见组件头注释与上文「顶层字段」段）。

**本批刻意不发 `file_changed` 事件 kind**（PRODCAP-1 的 `task_events` 回放表未落地，
先发即明知会丢帧）：前端在打开任务详情与任务进终态时各拉一次。回补路径见 `计划.md` PRODCAP-4 条目。

#### GET `/api/tasks/events` — **任务事件 SSE 流**
取代前端 REST 轮询；事件 `kind` 取值：`created` | `status` | `plan` | `subtask` | `usage` | `llm_call` | `deleted` | `agent_status` | `approval_required` | `delta` | `flow_bound`（`delta` 为流式正文增量暂态事件，不落库；权威数据以 `llm_call` 落库行 / `calls` 端点为准；`flow_bound` 为改绑编排事件，前端按 `status` 同款刷新）。

**预算与截断自愈**（常量见 `server-rs/src/api/chat.rs`）：

- 未显式指定 `max_tokens` 时取「用户设置 vs 8192（`GENERATE_RAW_MIN_TOKENS`）」的较大者
  ——结构化输出下限：卡片要求「整个回复有且仅有一个 JSON」，1024 默认值会把 JSON 腰斩
  （2026-09-13 Android「掉格式」根因）；显式值原样尊重并钳在 `1..=131072`，
  `max_tokens: 0` 返回 400 `VALIDATION`；
- 上游 `finish_reason=length` 时预算翻倍重发（封顶 32768，最多 2 次）；
- **重发失败或自愈用尽时仍返回 200 + 最后一次（半截）文本**：卡片自带解析器可从半截
  文本尽力提取，整体报错反而更无用；此时错误只留服务端日志
  （`generate_raw_retry_failed_fallback_partial` / `generate_raw_still_truncated`）。

**已知限制**：客户端断开不取消在途重发（最多 3 次上游调用）；本端点不落 usage/审计，
重发消耗只能从服务端日志统计。

### 契约引擎 HTTP 出口（方案 A）

供 ST 前端与外部工具调用同一契约引擎（与 Agent 多步工具 `apply_patch` 共用同一管线，单库无分叉）。契约不存在时补丁原样放行（存量卡零行为变化）。

> **并发语义**：本出口与 Agent 生成共用存储；外部更新应避免与进行中的生成并发调用，并发时运行态快照以引擎收尾为准（变量表不丢，快照可能短暂回退）。`writer` 是子系统标识而非身份认证——持有 bearer token 的调用方可任意声明 `writer`（含 `"agent"`）；所有权校验防的是「子系统误写」，认证边界在 token（与前端同级信任）。

#### POST `/api/variable/update` — 契约引擎统一写入

请求：`{ session_id, patches: [{ op, path, value?, from?, confidence? }], writer? }`

- `patches`：JSON Patch 子集（replace/set/insert/delta/remove/move）；`confidence` 可选（"low"/"medium"/"high"，非法值按 low 处理——不写入、进待复核队列）；
- `writer`：写者子系统 id，缺省 `"external"`；契约 `updateRules` 的 `ownership.writers` 须包含该 id 或 `"*"`（默认 `[agent, manual]`），否则 `not_owner` 拒绝；
- 门控：未声明字段 `unknown_field` 拒绝、低置信入 pending、契约生效时逐 op 留痕（kaleido_changelog）并维护 meta.pending。

响应（部分被拦仍 200，已生效部分生效）：`{ ok, stat_data, entries, warnings?, breaker_hashes? }`；`ok=false` 表示全部被拦（树未变；低置信场景提议已入队，全部被拒场景无任何写入）。请求体结构不符 → 422。

#### GET `/api/variable/state?session_id=…` — 契约运行态整行

`{ session_id, contract_version, stat_data, meta, revision_seq, revision_hash, updated_at }`；尚无契约运行态 → 404。

#### GET `/api/variable/changelog?session_id=…&limit=50` — 逐 op 变更流水

`{ entries: [ChangelogEntry] }`（最新在前，limit 夹取 [1, 1000]）。

#### GET / PUT / DELETE `/api/characters/{id}/contract` — 角色卡内嵌契约（编辑面板出口）

读 / 写 / 移除角色卡**内嵌契约**（存于 `data_raw.extensions.nlkaleido`）；`PUT` 带陈旧哈希时走 409 分支。与上文的运行态出口（`/api/variable/*`）不同层：这一组改的是**卡上的契约定义**，那一组改的是**会话的运行态变量树**。

#### GET `/api/characters/{id}/contract/history` — 契约变更历史

`{ entries: [...] }`（最新在前）。历史来源与 `kaleido_changelog` 同族，但按角色卡维度聚合。

#### POST `/api/characters/{id}/contract/rollback` — 按 `seq` 回滚契约

请求带目标 `seq`；语义校验不通过返回 422。回滚改的是卡上的契约定义，不回滚会话运行态。

### 命令执行（exec 端点）

来源：`archive/2026-09-16-consolidation/命令执行层与Android三档执行器-变更说明.md` §一「新增 API」；实现 `server-rs/src/api/exec.rs`。该批次**不改既有 API 线格式**（仅新增 exec 端点）、**不改既有 DB schema**（仅新增 `exec_audit` 表）。

| 端点 | 说明 |
|---|---|
| `GET /api/exec/tier?refresh` | 当前执行器等级 + 中文标签 + Shizuku 环境；`refresh=1` 强制重探 |
| `GET /api/exec/audit?limit&source&risk` | 审计列表（时间倒序，limit 上限 500） |
| `DELETE /api/exec/audit` | 清空审计 |

**`GET /api/exec/tier` 响应**：`{ tier, label, shizuku_installed, shizuku_granted, refreshed }`。等级取值 `root` / `shizuku` / `sandbox` / `disabled`（`ShellTier::{Root,Shizuku,Sandbox,Disabled}` 的 `as_str`）；中文标签分别为 `ROOT 提权` / `Shizuku(ADB 权限)` / `沙箱(应用自身权限)` / `已禁用`。前端授权面板据此展示「等级可见」并可提示用户开启通道；`shizuku_installed` / `shizuku_granted` 让面板区分「未安装」(引导安装)与「已安装未授权」(引导授权)。

`refresh=1`（或 `true`）时清 Android 侧探测缓存**强制重探**：`detectTier` 带进程内缓存（避免每次 exec 都跑 `su`），用户新装 Shizuku / 刚授权 / 刚装 Magisk 后不重探永远拿到缓存旧值。设置页「刷新」按钮走 `refresh=1`，其余读取（如启动探测）走缓存。桌面端无缓存语义，两者等价。

**`GET /api/exec/audit` 响应**：`{ "entries": [ExecAuditEntry…] }`。query 参数全部可选：`limit`（缺省 100，实现侧 `clamp(1, 500)`）、`source`（`chat | task | android`）、`risk`（`safe | sensitive | destructive | admin`）；过滤值空串视为不传。排序 `ORDER BY ts DESC, id DESC`。

**`ExecAuditEntry` 字段**（线格式与前端 `web/src/api/exec.ts` 对齐，机检映射 7）：
`{ id, ts, source, task_id, session_id, command, shell, tier, risk, decision, exit_code, stdout_summary, stderr_summary, risk_flag }`；
其中 `task_id` / `session_id` / `exit_code` 可为 null；`decision` ∈ `allowed` / `denied`；
`risk_flag` ∈ `''` / `data_dir_touch` / `parent_climb`（2026-09-26 D1 批新增，**只标记不拦截**：模型有 shell 就能读进程可读的任意路径，cwd jail 只约束相对路径与缺省目录，标记的价值是让「把数据目录当草稿纸」这类行为在审计表里可筛可查）。

**`DELETE /api/exec/audit` 响应**：`{ "ok": true, "deleted": N }`；DB 失败 → `{error, code: DB}` + 500。

**审计写入纪律**（同源文档「审计」段）：`exec_audit` 表字段为
`id, ts, source(chat|task|android), task_id, session_id, command, shell, tier, risk, decision, exit_code, stdout_summary, stderr_summary, risk_flag`；
**每次尝试都落一行，含被拒绝的**——「有人试图跑 rm -rf」同样要留痕；输出摘要截断 2000 字符，避免审计表被长输出灌爆。

**工具面契约（同源文档「新增工具」段）**：工具名 `bash`，参数 `command`（必填）/ `cwd` / `timeout_ms`；平台默认 shell：Windows 用 `cmd /c`，其他平台用 `sh -c`；风险恒 `Dangerous`；**不加入任何只读白名单**（READONLY_SCOUT / SUBAGENT / REFLECT）。

**自描述结果头（2026-09-26 D1 批）**：每次返回首行为 `$ {command}`，次行为 `(执行器:{档位};shell:{cmd|sh};cwd:{实际工作目录};退出码:{退出码})`——工具名叫 `bash` 但 Windows 实际是 `cmd`，原先前只回档位与退出码，模型按 bash 语法写命令（`;` 分隔、`/d/` 路径、`md5sum`）后只看到「退出码 1」，无从纠正假设；描述串同批写明 cmd 的语法边界，非零退出码时追加一行同样提示。命令分级四级 `safe` / `sensitive` / `destructive` / `admin`，多命令串联逐段判定取最高危；`destructive`/`admin` 命令**逐条确认，不受任何授权豁免**（判定链最前）。

**`submit` 工具（2026-09-17 新增）**：把最终产物作为文件交付到设备下载位置。

- 参数：`filename`（必填，含扩展名；路径分隔符会被拍平为 `_`）、`content`（必填，上限 8MB）。
  文件名上限 120 字符（超出截断但保留扩展名）；空名/纯点名/空内容/超限内容一律拒绝。
- 返回值：**实际落盘位置的可读描述**——API≥29 为 `下载/<文件名>`（MediaStore.Downloads，
  免存储权限）；API 24-28 回退写入应用外部目录 `Android/data/<pkg>/files/Download/<文件名>`
  并返回绝对路径（本项目**不申请任何存储权限**，故低版本拿不到系统下载目录的写入权）。
- **可见性（双重门）**：工具始终注册，但只在 **Android 且执行档位为沙箱**（非 ROOT / 非 Shizuku）
  时下发给模型——过滤点在 `task_engine/tool_policy.rs::platform_gate`（defs 与 allowed 同源剔除），
  执行期 `tools/submit.rs` 再复核一次可用性（用户可能在任务途中改档位）。
  非 Android、或 Android 的 ROOT/Shizuku 档下，模型看不到该工具（那两档 `bash` 本就能写任意路径）。
- **风险级 `Sensitive`**（非 `Dangerous`）：目标路径由应用决定、不接受任意路径参数；
  按危险级登记会被任务模式默认策略（deny_dangerous）整体剔除，工具将形同不存在。
  三个只读白名单（READONLY_SCOUT / SUBAGENT / REFLECT）均**不含**该工具。
- 桥接：`KedaiNative.saveToDownloads`（入参 `文件名␟内容`，与 `shareFile` 同编码约定），
  经 `native_bridge_android::save_to_downloads` 调用；方法名与参数个数由
  `tools/check-arch.mjs` 规则 L 把关（Android cfg 代码在 Windows 上不编译，只能脚本守）。

### 健康检查

#### GET `/api/health`

`{ ok: true, ts }`

**完整响应形状（源：`server-rs/src/api/mod.rs:110-153`；`archive/2026-09-16-consolidation/MAINTENANCE.md` §4/§6）**：

```
{ ok, ts, version, build_id, build_time, data_dir, dependencies: { db } }
```

- `ok` **恒 true（liveness 冻结点）**：`src-tauri` 的 `health_ok()` 以此字段判定「已有实例在运行」，用于单实例复用/端口竞态，**不得改为依赖态**。
- `ts` 为 `chrono::Utc::now().timestamp_millis()`。
- `version` = `CARGO_PKG_VERSION`；`build_id` = 编译期注入的 `env!("KEDAI_DIST_HASH")`；`build_time` = `env!("KEDAI_BUILD_TIME")`。
- `data_dir` 供桌面壳/启动器复用已运行实例前校验指向同一数据目录，防止静默挂到另一套库。
- `dependencies.db`：db 不可用时置 `"error"`，但 `ok` 仍为 true（依赖降级 ≠ 进程不活）。
- 查询参数：`?deep=1`（或 `deep=true`）触发整库 `PRAGMA quick_check`（大库代价高，仅显式触发；跑在 `spawn_blocking` 里，避免阻塞 tokio worker）；缺省走轻量探测。
- 设置中心底部常驻显示「版本 · 构建时间 · 指纹前 8 位」，两端各开一次对比即可肉眼确认同步。

**构建指纹 sidecar 契约（源：`archive/2026-09-16-consolidation/MAINTENANCE.md` §4「两版同步机制（构建指纹）」）**：
每个 dist 产物旁边写 `<exe>.build.json`（`{version, build_time, dist_hash}`，算法见 `tools/Write-BuildStamp.ps1`）；
`start.ps1` 与图形启动器（`Kedai.exe`，源码 `launcher/`）启动前比对两端 sidecar 的 `dist_hash`，不一致自动执行 `build.ps1` 双端重建。

> **注意（不要直接比对）**：二进制内嵌的 `build_id`（`KEDAI_DIST_HASH`）与 sidecar 的 `dist_hash` **算法不同，不可直接比对**——前者为 FNV-1a 64-bit，后者为聚合 SHA256（见 `契约-协议与配置.md`「二进制内嵌 `build_id`」条）。

#### SSE 事件格式（chat/send）

```
data: {"type":"step","step":"计划中…","detail":"..."}\n\n
data: {"type":"token","text":"片"}\n\n
data: {"type":"tool_call","name":"calculator","input":{...}}\n\n
data: {"type":"tool_result","name":"calculator","output":{...}}\n\n
data: {"type":"interrupted"}\n\n
data: {"type":"finish","usage":{prompt_tokens,completion_tokens,total_tokens,context_tokens},"content":"..."}\n\n
```

- 格式：`data: {json}` + 空行，`type` 编码在 JSON 内，无 `event:` 字段

- 客户端断开时自动中断生成（engine 检测 mpsc send 失败）

- 错误响应统一 `{"error":"消息"}`；已接入结构化错误码的端点附带 `"code"`（如 `{"error":"会话不存在","code":"NOT_FOUND"}`，码表见 `server-rs/src/api/errors.rs`：VALIDATION/UNAUTHORIZED/NOT_FOUND/CONFLICT/DB/UPSTREAM/INTERNAL，前端按 code 分类提示）

- 全部时间字段为 ISO 8601 字符串

## SSE 线格式

### 帧格式（两条流共用）

- 格式：`data: {json}` + 空行（`\n\n`）。
- 事件类型（`type`）**编码在 JSON 体内**，**无 `event:` 字段**；SSE 规范中的 `event:` 行从不出现。
- 前端按 `type` 分派；`kind`（任务流内层分类）与 `type` 是两个层级：任务流的 `type` 恒为 `task`，分类在 `kind`。
- 客户端断开时自动中断生成（engine 检测 mpsc send 失败）。

### 聊天流（`POST /api/chat/send`）

`SseEvent` 的 serde 属性为 **`#[serde(tag = "type", rename_all = "snake_case")]`**（`server-rs/src/models/types.rs::SseEvent`），因此每个变体名折算为 snake_case 后即 `type` 字面值（共 11 个）：

| `type` 字面值 | Rust 变体 | 负载字段 | 说明 |
|---|---|---|---|
| `token` | `SseEvent::Token` | `text: String` | 文本片段（逐字渲染） |
| `step` | `SseEvent::Step` | `step: String`；`detail?: String`；`index?: usize`；`total?: usize` | Agent 步骤；`detail`/`index`/`total` 均 `skip_serializing_if = "Option::is_none"`（None 时字段整体省略）。`index`/`total` 为 custom 模式步骤进度，其余模式不携带 |
| `tool_call` | `SseEvent::ToolCall` | `name: String`；`input: Value`；`call_id?: String`；`render_kind?: String` | 工具调用预告；`render_kind` 为「工具展示意图（render intent）」，前端据此分派渲染，缺省走 JSON 直出 |
| `tool_authorization_required` | `SseEvent::ToolAuthorizationRequired` | `name: String`；`risk: ToolRisk`；`reason: String`；`run_id: String`；`call_id: String` | 工具未获授权因而**没有执行**；前端据此提供会话/角色授权入口。全部字段必填（无 skip_serializing_if） |
| `tool_result` | `SseEvent::ToolResult` | `name: String`；`output: Value`；`call_id?: String`；`render_kind?: String` | 工具结果 |
| `vars` | `SseEvent::Vars` | `stat_data: Value` | 酒馆助手变量树同步（每次应用 `<UpdateVariable>` 补丁后推送最新 `stat_data`；仅变量更新时出现，先于 `finish`） |
| `interrupted` | `SseEvent::Interrupted` | 无 | 被停止 |
| `retry` | `SseEvent::Retry` | `attempt: usize`；`max: usize`；`reason: String` | 上游请求**重试中**提示（HB-4，2026-09-18）：连接器在等待重试前发出，用户不再面对「界面停几十秒然后报错」的无解释等待。**非终态**——成功后照常继续 `token`/`finish`，失败时仍以 `error` 收尾 |

| `finish` | `SseEvent::Finish` | `usage: TokenUsage`；`content: String`；`finish_reason?: String` | 结束；`content` 已剥离 `<UpdateVariable>` 协议块。`finish_reason` 为上游 `finish_reason`（`stop` / `length` / `content_filter` 等），`length` = 输出被 `max_tokens` 截断；`None` 时序列化省略（旧客户端忽略未知字段即可，线格式向后兼容） |

**`TokenUsage` 线格式**（`server-rs/src/models/types.rs:247-260`）：

```

  prompt_cache_hit_tokens, prompt_cache_miss_tokens }
```

`prompt_tokens` / `completion_tokens` / `total_tokens` / `context_tokens` 为 `i64`（必填）；`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 带 `#[serde(default)]`，无缓存字段的提供商恒为 0。`MAINTENANCE.md` §6 的示例帧只列前四个键（`prompt/completion/total/context_tokens`），后两个为后续新增且缺省有值——旧客户端按前四键读取不受影响。

**`SseEvent::Error.code` 五个冻结值**（来源：`archive/2026-09-16-consolidation/工程韧性修复-变更说明.md` §2.4「验收证据」）：

```
request_timeout / rate_limited / auth_failed / upstream_error / generation_failed
```

### 任务事件流（`GET /api/tasks/events`）

任务事件由 `TaskService` 的 broadcast 通道推送，该端点转发为 SSE，取代前端 1s REST 轮询。
`SseEvent::Task` 的**全部字段除 `task_id` 外均为可选**（`#[serde(default, skip_serializing_if = "Option::is_none")]`），旧客户端缺字段即忽略（向后兼容）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `task_id` | String | 必填 |
| `kind` | `TaskEventKind`（可选） | 事件分类（见下表） |
| `title` | String（可选） | 任务标题 |
| `status` | `TaskStatus`（可选） | 任务状态 |
| `detail` | String（可选） | 简短中文说明（供前端事件监控面板展示）；`kind=delta` 时为攒批后的正文增量文本 |
| `finish_reason` | String（可选） | 上游 `finish_reason`（仅 `kind=llm_call` 且成功调用携带；`"length"` 即 max_tokens 截断标记）；None = 不适用/未知，序列化时省略 |

- `TaskRunMode`：`as_str` 与 serde 输出一致；**DB 读取**走 `from_str_lossy`（未知值记 warn 回退 `legacy`，不 panic 不丢行）；**API 入参**走 `from_str_strict`（未知值返回 `None`，由调用方回 400「未知任务模式」）。

- `TaskRecord` 结构体字段：`{ id, title, status, plan, result, error, character_id?, created_at, updated_at, task_mode, executor_id?, workspace?, flow_id?, flow_ids?, connection_id? }`；`status` 缺省 = `pending`，`task_mode` 缺省 = `legacy`（旧 JSON 无此字段即 legacy），各 `Option` 字段均带 `skip_serializing_if = "Option::is_none"`（None 时整体省略，前端须标为可选）。

  - `flow_id`（2026-09-22 二维批次 5a 加）：**任务绑定的自定义流程 id**，空 = 跟随当前流程。绑定即冻结——创建时按该流程落一份快照（`tasks.flow_snapshot`，见「任务绑定流程与流程快照契约」），此后改流程 / 换当前流程都不影响该任务；**仅 custom 模式可给**（其余模式给了即 400）。加性字段，旧任务 JSON 逐字节不变。
  - `flow_ids`（2026-09-23 二维批次 7b 加）：**对比模式的可调用流程名单**（`Option<Vec<String>>`，JSON 字符串数组）。非空 = 根流程照常执行 + 名单内流程作为 `run_flow` 工具释放给宽松节点，模型自主调用并取回成果；与 `flow_id` 相互独立（后者仍是根流程），**名单不得包含根流程**（创建期 400）；`POST /api/tasks` 给了空数组（含全空白项）即 400（空名单 = 名存实亡），非 custom 给了即 400；成员须存在 + 启用 + 结构合法（逐项点名 400）。同样 `skip_serializing_if`，None 整键省略。契约全文见 `契约-协议与配置.md`「对比模式契约（`flow_ids` + `run_flow`）」，口径见 `计划.md` §九 裁定 24。

## 错误体与状态码契约

### 结构化错误体

已接入结构化错误码的端点响应形状为：

```
{ "error": "消息", "code": "<SCREAMING_SNAKE 码值>" }
```

未接入处仍是**裸** `{"error": "消息"}`（历史形态，前端按无 `code` 兜底处理）。`error` 字段保持不变的目的是向后兼容（`server-rs/src/api/errors.rs:1-3`）。

### 七个 `code` 取值（`server-rs/src/api/errors.rs:17-56`）

`ErrorCode` 的 `as_str()` 返回值即线格式字面值（SCREAMING_SNAKE，**属对外稳定契约**）：

| `code` | Rust 变体 | 语义与配套 HTTP 状态 |
|---|---|---|
| `VALIDATION` | `Validation` | 参数缺失 / 校验失败（HTTP 400）；「contract 回滚的 422 语义校验也归此码」 |
| `UNAUTHORIZED` | `Unauthorized` | 未认证 / token 失效（HTTP 401；预留给鉴权出口接入） |
| `NOT_FOUND` | `NotFound` | 资源不存在：角色 / 会话 / 消息 / 历史记录等（HTTP 404） |
| `CONFLICT` | `Conflict` | 状态冲突：会话正在生成中、重发/重生成锚点失效等（HTTP 409） |
| `DB` | `Db` | 数据库 / 阻塞任务失败（`db_call` / `db_read` / `db_write` 的 Err 出口，HTTP 500） |
| `UPSTREAM` | `Upstream` | 上游 LLM 连接器错误（预留，供 connectors 错误出口接入） |
| `INTERNAL` | `Internal` | 未归类的服务端内部错误（HTTP 500） |

**码与状态码必须匹配**——`err_with_code(code, msg, status)` 的调用方勿跨档使用（`errors.rs:50-56`）；
另有「按 HTTP 状态码推断默认错误码」的辅助路径（「供仅知状态码的旧辅助函数平滑迁移」）：
`400 → VALIDATION`、`401 → UNAUTHORIZED`、`404 → NOT_FOUND`、`409 → CONFLICT`（其余映射见该文件）。

### 状态码语义

| 状态码 | 语义 |
|---|---|
| `201` | 创建成功（如 `POST /api/chat/sessions`、`POST /api/characters/upload`、`POST /api/world-books/upload`） |
| `204` | 删除成功（如 `DELETE /api/chat/messages/:id`、`DELETE /api/chat/sessions/:id`、`DELETE /api/characters/:id`、`DELETE /api/world-books/:id`、`DELETE /api/memory/:id`）。`DELETE /api/memory/{id}` 为「204 无正文」 |
| `400` | 缺参 / 校验失败（含非法 `authorization_mode`、`agent_mode=custom` 未启用/流程未保存或非法、`followup`/`plan-chat` 空指令与未知 `mode`、`max_tokens: 0`、覆盖层非法值） |
| `404` | 资源不存在（含 `GET /api/variable/state` 尚无契约运行态） |
| `409` | 状态冲突（会话正在生成中；`resend_message_id` 锚点失效；`followup` 非终态；`plan-chat` 非 `planned`；plan-chat 修订期间 stop 竞态中断） |
| `413` | **已知例外**：`DefaultBodyLimit` 在提取器执行前由 tower 层拒绝，**形状不统一**（统一 413 形状需自定义层拦截 body `Frame` 错误，成本远高于收益——已在 `json_body.rs` 头部写明原因） |
| `422` | 请求体结构不符（`POST /api/variable/update`）；contract 回滚的语义校验归 `VALIDATION` |
| `405` | 方法不允许（如 `DELETE /api/health`）：由 `method_not_allowed_fallback` 返回 JSON + `code`（此前为**空 body**） |
| `500` | `DB` / `INTERNAL`；固定文案 + `tracing::error!` 记原文，**不泄露内部细节**（`DB_ERR_USER_MESSAGE`） |
| `501` | `POST /api/agent/execute` 固定桩未实现 |
| `502` | 上游失败（`plan-chat` 的 LLM 上游/解析失败为 `UPSTREAM`；`api/resource.rs` 出口为 `{error, code}` + 原有真实状态码 400/500/502） |

### 错误面收口纪律（来源：`archive/2026-09-16-consolidation/工程韧性修复-变更说明.md` §2.1）

- **提取器统一**：`api/json_body.rs` 的 `JsonBody<T>` 薄包装把 `JsonRejection` 收口为 `{error, code: VALIDATION}` + 400（不新增第三方依赖）。已接入：`chat`(5)、`tasks`(5)、`settings`(3)、`characters`(1)、`sessions`(8)、`task_executors`(1)、`agent_flows`(1)。畸形 JSON → `400 application/json` + `code: VALIDATION`（此前 `text/plain`）。
- **未知 `/api/*`** 由 `spa_fallback` 给出 `404 application/json` + `code: NOT_FOUND`（此前 404 无 `code`）。
- **假成功封堵**：`api/static_files.rs:34,48`（目录穿越拒绝 / 头像不存在）由「错误体 + 200」改为真实 `404` + `code: NOT_FOUND`。
- **泄露封堵**：`api/util.rs:21 db_err`（真正的活泄露出口）原文改由 `tracing::error!` 记录，响应统一为固定文案 `DB_ERR_USER_MESSAGE` + `code: "DB"`；签名不变。
- **正常业务上报不改为非 2xx**：`api/settings.rs:766`（embedding 测试）**保留 200 + `ok:false`**，仅补 `code`/`error`（「改非 2xx 会把『测试未通过』变成异常弹窗」）。
- **反馈业务数据与 `code` 并存**：`api/plugins.rs:82` **保留** `ok`/`loaded`/`errors` 业务数据，补 `code`/`error`；`errors` 逐项文案属用户排障必需，保留透出。
- **真实状态码判定**：前端 `web/src/composables/useResourceFrames.ts` 同步改为**按 HTTP 状态判成败**（原按 `body.ok` 分支会把后端 `code`/错误文案丢掉）。
- **测试断言辅助**：`assert_error_shape`（真实状态码 + `code`）与 `assert_no_internal_leak`（`tests/api_errors_codes.rs`）。

### 时间字段

**全部时间字段为 ISO 8601 字符串**（`MAINTENANCE.md` §6「约定」）。例外/特例须显式标注：`GET /api/health` 的 `ts` 为 Unix 毫秒整数（`timestamp_millis`），**不是** ISO 8601 字符串【待核实】——该事实出自 `server-rs/src/api/mod.rs:143` 的实现，与本条「全部时间字段为 ISO 8601」的表述不一致（见文末「源文档之间的不一致」第 4 条）。

### 1. `tools/check-contract.mjs` —— 前后端类型契约快照

**定位**：前端 `web/src/api/types.ts` / `web/src/api/memory.ts` 的类型是手写的，与 Rust 后端契约逐字对齐靠人；本脚本把「已知高变更面」的字段集合做差集比对，漂移即非零退出，纳入 `tools/check-all.ps1` 门禁（stage `contract: check-contract`）。

**判定规则（刻意宽严有别）**：

| 情形 | 判定 |
|---|---|
| 后端有字段、前端缺 | **FAIL**（真漂移，前端会读到 undefined） |
| 前端有字段、后端无 | **FAIL**（前端在臆造契约） |
| 后端可选、前端非可选 | WARN（后端可能省略该字段） |
| 前端可选、后端非可选 | 容忍（前端放宽类型是安全的） |

**解析口径**：`rustFields` 按顶层逗号切分字段（`<> () []` 内逗号不算分隔符），处理多行类型、`serde(rename)`、`serde(skip)`；`Option<T>` 本身**不算可选**（序列化为 null），只有 `skip_serializing_if` 才让字段在 None 时整体省略、前端才应标为可选。`rustVariants` 按 `rename_all = snake_case` 折算变体名为线格式文本。
