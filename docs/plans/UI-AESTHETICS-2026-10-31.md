## 一、总评：这套 UI 的底子是好的

在给问题之前先说结论：**Kedai 的视觉体系不是「丑」，而是「不均匀」**。

好的部分（这些不要动）：

- **设计令牌体系完整**：4px 步进间距、8 档字阶、4 档字重、硬阴影梯度、`z-index` 唯一阶梯，
  全部收敛在 `tokens.css`。这在中型前端项目里属于上游水平。
- **构成主义语言执行得彻底**：纯直角（`--radius: 0`）、2px 印刷黑描边、硬投影（无模糊）、
  红黑三原色 + 淡粉画布。一致性很强，没有半吊子的"现代感"混入。
- **消息区排版质量高**：代码块、引用块、列表悬挂缩进、表格、删除线，Markdown 全要素渲染正确。
  正文行宽约 42 个汉字（`max-width: 820px`），正好落在舒适阅读区间。
- **彩窗主题是认真做的**：整窗环境层 + 半透明面板，实测文本对比度 17.07:1 / 7.21:1，**远超 AA**。

问题集中在**三类不均匀**：
① 同一排控件的**规格不一致**；② 同一表单的**对齐不严格**；③ 内容少时的**空白失衡**。

## 二、问题清单（按「改完后观感提升幅度」排序）

### 美感-A1 顶栏三个开关规格不一致 ★★★★★

**当前实测**（1440×900）：

| 控件 | 形态 | 宽 | 高 | 基线 y |
|---|---|---|---|---|
| `HTML` | 裸开关（浅色方块 + 文字） | 81 | **22** | 36 |
| `JS 禁用` | **白底 2px 黑框按钮** | 67 | **34** | **30** |
| `AGENT` | 裸开关（浅色方块 + 文字） | 87 | **22** | 36 |

**这就是最刺眼的一处**：三个并列的同类开关，中间那个长得完全不一样——它是唯一带边框、带白底的，
高度比左右各高出 12px，顶边高 6px、底边低 6px，**在一条水平线上形成视觉鼓包**。

**试改验证（已实测）**：把 `JS 禁用` 拉齐到 22px 裸开关（透明底、无边框、前缀方块与另两个同构）：

```
试改前：三个控件 y = 36 / 30 / 36，高度 22 / 34 / 22
试改后：三个控件高度统一 22px，同一基线
```

截图对比：`shots/p01-topbar-try.png`。

**改动点**（`web/src/components/ChatTopbar.vue` + 对应 CSS）：

```css
/* 顶栏三开关统一为「裸开关」规格，JS 禁用不再单独做成按钮 */
.sv-topbar-render .sv-btn.ghost.sv-btn-sm {
  height: 22px; min-height: 22px;
  padding: 0; border: 0; background: transparent; box-shadow: none;
  font-size: var(--text-base); font-weight: 400;
}
```

> **设计判断**：`JS 禁用` 之所以被做成按钮，可能是因为它是"危险操作/需要强调"。
> 但它与 `HTML`、`AGENT` 同属**渲染管线开关**，语义同级。强调应由**状态文案**承担
> （禁用时文字变红或加粗），而不是靠改变控件形态——后者破坏了这一排的节奏。

**验收断言**：顶栏 `.sv-topbar-right` 内三个开关的 `getBoundingClientRect().height` **全部相等**；
`top` 值极差 **< 1px**。

### 美感-A2 表单标签列宽不固定，输入框左缘参差 ★★★★★

**当前实测**：

```
标签宽度随文字自适应：
  "BASE URL" → 79px   → 控件左缘 x = 542
  "API KEY"  → 72px   → 控件左缘 x = 535
  "MODEL"    → 72px   → 控件左缘 x = 535
  "CONN"     → 72px   → 控件左缘 x = 535

控件左缘的取值集合：{542, 535}   ← 同表单内出现两种左边界，差 7px
```

同时 `BASE URL` 因为 79px 装不下 `BASE URL`（含字距 `0.96px`）而**折行**。

**为什么这很刺眼**：人眼对**竖直线**极其敏感。三个输入框左边缘差 7px，在视觉上就是
「一个稍微往右缩了」，整块表单看起来像没对齐的胶水稿。

**试改验证（已实测）**：

```css
.sv-inp-tag { width: 88px; min-width: 88px; flex: 0 0 88px; white-space: nowrap; }
.sv-inp-row { display: grid; grid-template-columns: 88px 1fr; align-items: center; gap: 12px; }
```

结果：

```
修改前：控件左缘 {542, 535}（2 种）；标签折行 —— BASE URL 占 2 行
修改后：控件左缘 {553}（1 种）；标签行数全部 = 1
```

截图对比：`shots/p09-label-align.png`（可清楚看到三个输入框左缘笔直对齐）。

**改动点**：`web/src/styles/panels.css` 的 `.sv-inp-tag` / `.sv-inp-row`，
或落到 `web/src/components/settings/*.vue` 的共享字段行组件。

**验收断言**：设置页所有输入控件的 `getBoundingClientRect().x` **取值集合大小 = 1**；
所有 `.sv-inp-tag` 的 `Range.getClientRects()` 行数 **= 1**。

### 美感-A3 任务台空态内容压在顶部，底部空出 43% ★★★★☆

**当前实测**（1440×900）：

```
.sv-task-empty   高 790px，y = 76
  └ .sv-task-start  高 383px，y = 130
底部剩余空白 = 866 - 513 = 353px   ← 占可用高度的 44.7%
内容起点距容器顶 = 130 - 76 = 54px
```

即：**上方留 54px、下方留 353px**，重心严重偏上。这不叫留白，叫没排完。

**试改验证（已实测）**：给容器加 `justify-content: center`：

```
修改前：topGap 54  / bottomGap 353   （比例 1 : 6.5）
修改后：topGap 230 / bottomGap 176   （比例 1.3 : 1，视觉均衡）
```

截图对比：`shots/p08-task-centered.png`。

> **注**：第一次用 `<style>` 注入 `justify-content: center` 没有生效（被更高优先级覆盖），
> 改用内联样式才量到效果——说明**实际改的时候要确认那条规则的选择器权重够**，
> 不能只写一条 `.sv-task-empty { justify-content: center }` 就以为改完了。

**改动点**（`web/src/components/task/TaskBoardEmpty.vue` 或 `task.css`）：

```css
.sv-task-empty {
  display: flex;
  flex-direction: column;
  justify-content: center;   /* 内容在可用高度内垂直居中 */
}
```

若不想纯居中（会让内容离顶部太远），可用**上偏置居中**：

```css
.sv-task-empty { justify-content: center; }
.sv-task-start { margin-bottom: 8vh; }  /* 视觉重心略微上移，符合"从上方开始"的阅读习惯 */
```

**验收断言**：`.sv-task-empty` 内唯一子元素的上下 gap 比值 ∈ [1, 2]（不再出现 1:6.5 这种失衡）。

### 美感-A4 侧栏角色区空出一半以上，装饰方块孤悬 ★★★★☆

**当前实测**：

```
.sv-side-head    高 192（品牌 + 统计卡）
.sv-appmode      高  44（模式切换）
角色区（flex:1）  高 508  ← 实际只有一张角色卡（约 56px）
.sv-side-foot    高 114（导入 + 设置 + 退出）

角色区空白 ≈ 508 - 56 = 452px，占角色区 89%
```

侧栏中段因此是一大片**没有任何内容的粉色空地**，只有一张孤零零的「系统助手」卡片贴在顶部。

而**任务历史空态**里那个装饰性红色斜线 + 黑方块（`sv-supreme` 组合）却出现在角色区空地的中间，
因为它在 `.sv-task-empty` 内部，视觉上像是「飘在侧栏半空」。

**改动点**（按性价比排序）：

1. **推荐：给角色区加空态引导**（而非留白）——角色数据少时在列表下方显示
   一条低调的提示：「还没有更多角色 · 导入角色卡开始」，用 `--sv-ink-faint` + 12px，
   与任务历史空态的 `01 写目标 · 02 展开执行设置 · 03 创建并执行` 形成对称的三步引导语言。
2. **或：让角色卡列表垂直居中**（`justify-content: center`），至少消灭「贴在顶部」的失重感。
3. **不要做**：把侧栏宽度收窄。320px 是模式切换按钮（两个 132px 按钮 + 边框）的刚好宽度，
   收窄会触发 UI-A5 的折行问题。

**验收断言**：角色区可用高度与实际内容高度差 > 200px 时，必须有可见的空态提示元素
（`document.querySelector('.sv-char-empty')` 非空）。

### 美感-B1 消息表格宽度随内容收缩，三列宽度不匀 ★★★★☆

**当前实测**：

```
表格外框宽 228px（气泡宽 588px，表格只占 39%）
三列实际宽：112 / 57 / 58   ← 最宽列是最窄列的 1.96 倍
无表头底色
```

表格缩在气泡左侧，右边空一大片，而且列宽被最长的单元格绑架（`较长的一格内容` 撑宽第一列）。

**试改验证（已实测）**：

```css
.sv-msg-bubble table { width: 100%; table-layout: fixed; }
.sv-msg-bubble thead th { background: var(--sv-pink-light); }
```

结果：

```
修改前：表宽 228，列宽 112 / 57 / 58
修改后：表宽 548，列宽 182 / 182 / 182   ← 三列均分，占满气泡
```

截图对比：`shots/p06-table.png`。

**注意**：`table-layout: fixed` 会让**长内容强制换行**而不是撑宽列。对表格来说这是对的
（列宽稳定可预测），但如果单元格里有不可断的长串（URL、长英文单词），需要配
`overflow-wrap: anywhere` 或 `word-break: break-word`，否则会溢出。

**改动点**：`web/src/styles/` 下的消息 markdown 样式（`.sv-msg-bubble table` 一族）。

**验收断言**：渲染一个 3 列表格，三个 `th` 的宽度极差 **< 2px**；表格外框宽度 ≥ 气泡内容宽度的 95%。

### 美感-B2 发送按钮禁用态几乎不可见 ★★★★☆

（上一份报告已列为可用性缺陷 UI-A1，此处从**美感**角度补充试改验证）

**实测**：禁用态底色与输入区背景对比度 **1.03:1**——按钮的「形体」完全消失，只剩下一团颜色。

**试改验证（已实测两个方案）**：

| 方案 | 边框 | 对比度 | 观感 |
|---|---|---|---|
| 虚线 + `--sv-line-strong` | `2px dashed #d8c3cb` | **1.61:1** ❌ | 仍然太淡 |
| **实线 + `--sv-ink-faint` + 55% 不透明** | `2px solid #5f6166` | **5.46:1** ✅ | 轮廓清晰，仍是禁用观感 |

截图对比：`shots/p04-send-disabled.png`（虚线，失败）、`p05-send-disabled2.png`（实线，成功）。

**推荐**：

```css
.sv-btn-send:disabled {
  background: transparent;              /* 去掉浅粉填充，形体由边框承担 */
  border: var(--bw) solid var(--sv-ink-faint);
  color: var(--sv-ink-faint);
  box-shadow: none;
  opacity: .55;                          /* 补足"不可用"的语义 */
}
```

> **为什么不用虚线**：本案实测虚线 1.61:1 不达标；而且硬边体系里虚线是「占位框」语义
> （用于尚未确定的区域），用在按钮上会读成「这里将来会有东西」。实线 + 降透明度更准确。

### 美感-B3 附件按钮与输入框右缘不对齐 ★★★☆☆

**当前实测**：

```
输入框 textarea 右缘 = 1346
「快速回复」        = x 1208, w 89 → right 1297
「选择文件」        = x 1305, w 89 → right 1394
音频浮钮            = x 1384, w 40 → right 1424
```

三个右缘（1346 / 1394 / 1424）互不相同，形成一条**锯齿状的右边界**。

**试改验证（已实测）**：给输入区加右侧安全边距后：

```
footer.sv-inputbar { padding-right: 64px }
→ 音频浮钮与「选择文件」重叠面积：170 → 0
→ 「选择文件」右缘 1394 → 1346，与输入框右缘对齐
```

截图对比：`shots/p03-pad-try2.png`。

**改动点**：

```css
/* web/src/styles/shell.css 或 content.css */
footer.sv-inputbar { padding-right: 72px; }  /* 40(浮钮) + 16(右距) + 16(呼吸) */
```

**一个设计层面的建议**：如果保留音频浮钮，它本质上和「快速回复 / 选择文件」是同一层级的

三者从左到右严格递增（无交叉、无重叠）。

### 美感-C1 字号出现令牌外的档位 ★★★☆☆

**实测字号分布**（可见文本节点）：

```
11px × 22    12px × 22    13px × 18    14px × 2     15px × 1
16px × 2     18px × 5     38px × 1     9px  × 6
```

`tokens.css` 定义的合法档位是：`11 / 12 / 13 / 14 / 15 / 18 / 24 / 30`。
实际出现了 **9px**（6 处）与 **38px**、**16px** —— 三者都不在令牌里。

逐一核查：

| 值 | 位置 | 判断 |
|---|---|---|
| `9px` | `panels.css:568` 的 `.sv-hub-nav-idx`（设置导航序号 01~06） | **应改**。9px 中文环境下接近不可读，且与 12px 标签比例失衡 |
| `38px` | `ChatWindow.vue:762` / `TaskBoardEmpty.vue:137` 的 `clamp(28px, 3.4vw, 38px)` | **可保留**。这是 hero 标题，用 `clamp` 做响应式是合理例外；但建议把上限收进令牌（如新增 `--text-hero`） |
| `16px` | `mobile.css:216` 的 textarea | **必须保留**。iOS Safari 对 <16px 的输入框会强制页面缩放，这是刻意的平台适配 |

**试改验证（已实测）**：`.sv-hub-nav-idx` 从 9px 提到 11px：

```
修改前：9px，序号宽度 15px，与 12px 标签比例 0.75
修改后：11px，序号宽度 16px，与 12px 标签比例 0.92   ← 视觉上终于"站住了"
```

截图对比：`shots/p10-nav-idx.png`。

**改动点**：

```css
.sv-hub-nav-idx { font-size: var(--text-2xs); letter-spacing: 0.08em; }  /* 9px → 11px */
```

**验收断言**：全站 `getComputedStyle(el).fontSize` 的取值集合 ⊆
`{11, 12, 13, 14, 15, 18, 24, 30}` ∪ **白名单**（`clamp()` hero 标题、`mobile.css` 的 16px 输入框）。

### 美感-C3 设置页按钮主次权重几乎无差别 ★★☆☆☆

**实测**：

```
「保存 API 设置」   黑底白字  x 453, w 357, h 40
「从 API 加载模型列表」白底黑框 x 820, w 357, h 40   ← 完全等宽等高
```

两个按钮**宽度完全相同（357px）**，一个纯黑、一个白底，视觉上是 50:50 的兄弟关系。
但从语义看，「保存」是主操作、「加载模型列表」是辅助操作，应该 2:1 或 3:1 的权重。

**改动点**：主按钮保持 `flex: 2`，次按钮 `flex: 1`（或次按钮改 `sv-btn-sm` 尺寸）：

```html
<div style="display: grid; grid-template-columns: 2fr 1fr; gap: 12px">
  <button class="sv-btn primary sv-btn-fill">保存 API 设置</button>
  <button class="sv-btn ghost sv-btn-fill">从 API 加载模型列表</button>
</div>
```

**验收断言**：主按钮宽度 / 次按钮宽度 ≥ 1.8。

### 美感-C4 页签下划线被过渡类吃掉（疑似） ★★☆☆☆

**观察**：设置弹窗左侧导航的 active 项有红色斜线标记；但主界面模式切换（`01 角色扮演` / `02 任务`）
的 active 态是**整块黑底**，没有使用同一套「红色标记」语言。

**这是设计选择还是遗漏？** 从令牌体系看，`.sv-hub-nav-item.active` 与 `.sv-mode-nav active`
都是 `background: var(--sv-ink)`，风格一致。**此项列为「需确认」，不建议擅自改。**

## 三、建议的批次划分

建议新 ID 前缀 **`UIPOL-`**（UI polish；`UIFIX-` / `UIP-` / `ANDUI-` / `UIVIS-` 均已占用）。

| 批次 | 包含 | 预估 | 理由 |
|---|---|---|---|
| **UIPOL-1 对齐与规格** | A1 顶栏开关、A2 表单标签、B3 右缘对齐、C2 内边距 | 半天 | 全是「把已有的东西对齐」，零新增组件，风险最低，**观感提升最大** |
| **UIPOL-2 布局均衡** | A3 任务台居中、A4 侧栏空态、B1 表格整宽 | 半天~1 天 | 涉及 flex 布局调整，需要多分辨率回归 |
| **UIPOL-3 视觉权重** | B2 发送按钮、C1 字号收口、C3 按钮主次 | 半天 | 涉及状态样式与令牌调整，需同步检查有无其他组件受影响 |

**强烈建议先做 UIPOL-1**：它只改 4 处 CSS，但能一次性消灭「顶栏鼓包」「表单参差」「右下角锯齿」
这三处最容易被第一眼注意到的不均匀。

## 四、需要裁决的 2 个点

### R-UIPOL1 音频浮钮是「保留为浮层」还是「收进工具栏」？

- **选项 a（推荐）**：收进输入区工具栏，作为第三个附件按钮。语义统一、彻底消灭重叠、
  不用担心任何分辨率下的位置冲突。
- **选项 b**：保留浮层，只加右侧安全边距（`padding-right: 72px`）。改动更小，
  但浮层在 768 及以下会隐藏（`mobile.css:234`），行为不一致。

### R-UIPOL2 任务台空态是「垂直居中」还是「上偏置居中」？

- **选项 a**：纯居中（gap 比 1.3:1），干净但可能显得内容"浮"在中间。
- **选项 b（推荐）**：居中 + `margin-bottom: 8vh`（gap 比约 1.8:1），保留「从上方开始阅读」的方向感。

## 五、确认「不用改」的部分（避免过度设计）

| 项 | 实测 | 结论 |
|---|---|---|
| 消息正文行宽 | 820px ≈ 42 汉字 | 落在舒适阅读区间（中文建议 35~45 字） |
| 正文行高 | `line-height: 24.5px / 14px` = 1.75 | 长文阅读的标准值 |
| 代码块 | 纯黑底 + 等宽字体 + 圆角 0 | 与硬边体系一致，可读性良好 |
| 彩窗主题对比度 | 17.07:1（正文）/ 7.21:1（说明） | **远超 WCAG AA**，不需要调 |
| 侧栏宽度 320px | 模式切换按钮刚好放下 | 不要再收窄 |
| `mobile.css` 的 16px 输入框 | iOS 防缩放 | **刻意设计**，不要"统一"掉 |
| 字号 38px hero | `clamp()` 响应式 | 合理例外，建议收进令牌而非改值 |
| 红色斜线装饰 | 构成主义标识 | 既有设计语言，**不是错位** |
