# KedaiAgent 任务模式实测问题分析与修复方案

> 报告日期：2026-10-19
> 实测模型：commandcode 网关 + `deepseek/deepseek-v4.1-flash-fast`（真实模型）
> 实测任务：我的世界风格悬浮空岛（单文件 HTML + Three.js）
> 证据：`D:/kedai-bench-run/mcisland-evidence/`

## 一、实测现象

| 轮次 | 编排 | 关键结果 |
|---|---|---|
| 第 1 轮 `5d6aba28…` | team，3 主/8 步，默认 32 轮上限 | 主 1/主 2 在写 `10-world`/`30-atmosphere` 前耗尽 32 轮；代码只留在结果正文且被截断；主 3 拒绝伪造，验收 3 PASS / 22 FAIL |
| 第 2 轮 `5a9cc199…` | team，2 主/6 步，80 轮上限 | 仍在第 1 个子目标耗尽 80 轮；90-main 未被修改；正文留下完整 10-world 代码与 90-main 补丁说明 |
| 第 3 轮 `102d5823…` | solo，窄题面 + 首次必须 `fs_write` + 16 轮 | 67 秒写出 15.8KB 大气分片，总装成功 |

## 二、根因分析

### 1. 轮次上限是“全局默认”，不是任务级策略

任务模式 `solo` / `multi` / `team` / `plan` / `followup` 共用 `solo.rs::run_agent_loop`，
参数里写死 `max_tool_rounds: Some(settings.max_tool_rounds)`；`custom` 节点缺省也回退到同一个全局值。
执行器 `run_tool_loop` 把 `None` 当默认 32、`Some(n)` 当硬上限（`executor.rs` 的 `max_rounds`）。
因此“改设置到 80”只是把同一个硬墙推远，不改变“到墙即停”的语义。

### 2. 硬上限的收尾语义是“输出当前文本”，不是“保证产物落盘”

到上限时执行器只做一件事：本轮工具执行完后停止发起下一轮模型请求，把当前 `result.content`
作为产出返回。它不会检查工作区里是否真的存在目标文件，也不会要求模型先写盘。
于是模型可以“读了 80 轮、代码都在正文里、文件一个没写”，任务仍以 `done`/`ended` 结束，
只是验收脚本发现 `index.html` 缺失。

### 3. 模型在“先理解再动手”上会无限探索

第 1/2 轮的主 agent 把绝大多数轮次花在 `fs_read`/`fs_grep`/`bash` 查看已有分片与 API 上，
真正 `fs_write` 只发生在开头（00-core、20-house、40-ui）或从未发生（10-world、30-atmosphere）。
在 32/80 轮两种预算下都复现，说明不是“预算不够”，而是**缺少写盘优先级约束**。

### 4. team 的审计/终审/汇总没有工具

team 的规划、审计、终审、汇总都是纯文本 `generate_text` 调用，不挂工具。
审计 agent 只能读主 agent 的自述，无法检查 `index.html` 是否存在、是否能通过 `node --check`、
是否包含 6 个 PART。第 1 轮主 3 的“拒绝伪造”是正确兜底，但这是主 agent 的自觉，不是系统强制。

### 5. 并行主 agent 共用一个工作区，缺少“文件级交接”约束

team 规划器自动拆 2~4 个主 agent，各主并行跑自己的子目标。shared workspace 下：
- 没有文件所有权/锁；
- 没有“分片 ready 才能总装”的运行时校验；
- 总装依赖某个主 agent 自觉等待和拼接；
- 只要一个主 agent 没落盘，总装就只能拒绝执行。

### 6. 轮次上限之外已有其他安全阀

`task_step_budget_secs`（默认 1200s，单步墙钟）、`task_idle_timeout_secs`（默认 2400s）、
`session_token_budget`（默认 0=关）、语义熔断（同工具输出无变化）、重复调用熔断、
取消通道与任务级总预算（默认 0=关）。因此“取消轮次上限”不等于“允许无限失控”，
但仍应保留这些安全阀，并在文档中明确它们的兜底关系。

## 三、修复方案

### 本次立即修复（P0）：取消任务模式轮次限制

1. `executor.rs` 引入显式哨兵：`max_tool_rounds = Some(0)` 表示 **不限轮次**；
   `None` 仍表示聊天/旧调用方的默认 32；`Some(n>0)` 仍是显式上限（聊天/节点级）。
2. `solo.rs`（覆盖 solo/multi/team/plan/followup）改为 `Some(0)`，任务模式默认不再有轮次上限。
3. `custom.rs` 改为 `Some(step.max_tool_rounds.unwrap_or(0))`：
   - 未配置节点级上限 → 不限轮次；
   - 节点作者显式配置 `max_tool_rounds` → 仍按该值生效（这是显式节点预算，不是系统性默认墙）。
4. `max_tool_rounds` 设置项继续供聊天 AGENT 使用；前端文案改为“聊天 AGENT 工具轮次上限”，
   避免任务模式用户误以为该设置仍生效。
5. 保留并强化注释：轮次上限取消后，单步墙钟预算/空闲超时/语义熔断/取消仍生效。

### 后续方案（P1/P2，不在本次提交）

| 编号 | 问题 | 建议 |
|---|---|---|
| R-1 | 先探索后写盘 | 任务提示词加“写盘优先”：首个工具调用应写目标文件骨架；大文件分片先落盘再自检 |
| R-2 | 审计无工具 | 给 team 审计/终审挂只读工具，或强制读取 `index.html` + `evidence/verify.txt` |
| R-3 | 总装依赖自觉 | 任务侧加“产物清单/必需文件”字段；终态前检查必需文件存在，缺失判 `partial`/`error` |
| R-4 | 并行覆盖 | 分片文件所有权/锁；或强制“每主只写自己的 parts/ 文件”，总装由确定性脚本执行 |
| R-5 | 探索空转 | 增加“连续 N 轮只读无写”检测，提示或中止；与语义熔断互补 |
| R-6 | 任务结果不可见 | 任务详情返回工作区产物清单；前端成果卡展示文件与验收摘要 |
| R-7 | 成本护栏 | 保留 `task_total_budget_secs` 作为可选总墙钟；默认仍关，长任务显式开启 |

### 验收计划

1. 单元测试：`resolve_max_rounds(None)=32`、`Some(0)=None`、`Some(n)=n`。
2. 真实模型：把 `max_tool_rounds` 设为 5，运行一个必须 >32 轮的单文件任务
   （逐轮读取 40 个文件、禁止 bash/glob 批量），任务仍应完成；证明设置不再限制任务模式。
3. 回归：`cargo test`、`cargo fmt --check`、`node tools/check-arch.mjs`、
   `node tools/count-tests.mjs --check`。
4. 真实模型冒烟：任务模式一次小任务 + 聊天 AGENT 一次工具调用，确认聊天侧仍受 32 轮默认限制。

## 四、边界与已知取舍

- 本次不实现 R-1~R-7；它们需要产品面决策（尤其是审计工具与产物清单字段）。
- “彻底取消”在本次实现中覆盖任务模式的**默认全局上限**；`custom` 节点显式配置的
  `max_tool_rounds` 仍作为节点作者主动设置的预算保留。若产品要求连节点级也取消，
  只需把 `custom.rs` 改为 `Some(0)` 并移除/禁用流程编辑器中的该字段（另开一批）。
- 轮次上限取消后，任务的实际停止条件变为：模型不再调用工具、步骤墙钟到点、
  空闲超时、语义/重复熔断、用户取消、或任务总预算（若开启）。这些条件都应在 UI 与文档中可见。

## 五、本次验证记录（2026-10-19 晚）

### 单元与门禁
- 新增 3 例（`agents::engine::executor::round_limit_tests`）：`None→32`、`Some(0)→None`、
  `Some(n>0)→n`；定向测试 3/3 通过。
- 后端全量 `cargo test -j 8`：**1843 个测试（1413 单测 + 430 集成），0 FAILED，EXIT 0**。
- 前端 `npm test -w web`：**1671/1671 通过（155 文件）**。
- `cargo fmt --check`、`node tools/check-arch.mjs`、`node tools/count-tests.mjs --check` 全绿；
  `MAINTENANCE.md` 计数已同步为 1843/1413。

### 真实模型验证（commandcode + `deepseek/deepseek-v4.1-flash-fast`）
把任务模式 `max_tool_rounds` 故意设为 **5**，用 40 个文件的链式读取任务验证：

1. 任务 `352dd1e0…`：**读完全部 40 个文件**（a01→a40，最后内容 DONE），
   SSE 中无「达到工具调用轮次上限」。该次模型在**一次响应里并发 40 个 fs_read**，
   所以它证明了“工具调用数不再被 5 限制”，但没有单独证明“跨 5 轮”。
2. 任务 `96655278…`（同名链、语义熔断关闭）：28+ 次 fs_read 后仍在运行，
   无轮次上限事件；人工停止。
3. 任务 `2a67729f…`（41 文件随机名链）：76 次 fs_read 后仍未收敛，人工停止；
   无轮次上限事件。
4. 任务 `aca590e8…`（8 文件随机名链）：40 次 fs_read 后仍未收敛，人工停止；
   无轮次上限事件。
5. 其中一个任务在**未关闭语义熔断**时于第 4 次 `fs_read` 被误判：
   `NEXT=a02.txt` / `NEXT=a03.txt` 经 `normalize_tool_output` 把数字归一成同一指纹，
   报「输出实质无变化(去重后 1 种)」。这是独立缺陷（R-5），本轮不修；
   验证时用 `loop_guard_semantic_min_calls=0` 关闭该闸门。

**结论**：轮次上限在代码/单测层面已彻底取消（`Some(0)` 不再产生 `last_round`），
真实模型任务中也不再出现「达到工具调用轮次上限」。模型侧仍可能因
**并行工具调用**（一轮发出几十个 fs_read）或**语义熔断误判**而不收敛，
这两项分别对应后续 R-4/R-5，不是轮次上限本身。
