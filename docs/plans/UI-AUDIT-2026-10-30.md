## 一、结论摘要（先看这段）

共确认 **13 项真实缺陷**，按严重度分三档。**没有一项需要在设计语言上做妥协**——全部可以在
现有构成主义/至上主义硬边体系内修好。

| ID | 问题 | 一句话后果 |

## 二、第一档逐项证据与改法

### UI-A1 发送按钮禁用态几乎不可见

**实测**（1440×900，空输入）：

```
.sv-btn-send:disabled
  background: rgb(253, 241, 245)   ← --sv-pink-light
  border:     2px solid rgb(216, 195, 203)  ← --sv-line-strong
  color:      rgb(92, 92, 92)
  与容纳它的输入框对比度: 1.03 : 1     ← 关键数字
  与页面背景对比度:       1.03 : 1
  自身文字与底色对比度:   6.07 : 1    （文字够清楚，但按钮轮廓消失）
```

**归因**：`web/src/styles/shell.css:475` 的 `.sv-btn-send:disabled` 用了 `--sv-pink-light`，
而同页面 `--sv-paper: #fdfafb` 与 `--sv-pink-light` 亮度几乎相同。WCAG 对**非文本 UI 组件**要求
至少 3:1，这里 1.03:1 远低于门槛。

**改动点**：把禁用态从「浅粉底」改为「无填充 + 虚线或点划边」——保持硬边教义（不加圆角、不加渐变）：

```css
.sv-btn-send:disabled {
  background: transparent;                    /* 不再用 --sv-pink-light */
  border: var(--bw) dashed var(--sv-ink-faint); /* 硬边体系允许的点划线语言 */
  color: var(--sv-ink-faint);
  box-shadow: none;
}
```

**验收断言**：空输入时，`.sv-btn-send` 的背景（或边框）与其父容器对比度 **≥ 3:1**；
在 1440/1024/768 三档视口下，按钮轮廓均可在截图中辨认（人工过目 3 张图）。

**风险 / 回滚**：单条 CSS；回滚即恢复 `background: var(--sv-pink-light)`。

### UI-A2 音频浮钮压住「选择文件」按钮

**实测**（1440×900）：

```
.sv-audio-toggle  position:fixed; right:16px; bottom:16px; z-index:40
  rect = (x:1384, y:844, w:40, h:40)
选择文件按钮
  rect = (x:1305, y:827, w:89, h:34)   → right:1394
重叠区 = 10px(宽) × 17px(高) = 170 px²

elementFromPoint 采样（选择文件按钮右缘 6 点）：
  (1392,834) → 选择文件
  (1390,838) → 选择文件
  (1388,842) → 选择文件
  (1386,846) → sv-audio-toggle   ← 被抢
  (1384,850) → sv-audio-toggle   ← 被抢
  (1382,854) → 选择文件
```

**归因**：`web/src/styles/content.css:665` 的 `.sv-audio-toggle` 是 `position:fixed; right:16px; bottom:16px`，
而输入区按钮行同样贴着右下角，两者**没有互相预留空间**。

**改动点**（二选一，推荐 a）：

- **a. 给输入区留出安全边距**：`--composer-safe-right: 56px`（40 + 16），让输入区内部右侧
  padding 用这个令牌，浮钮永不与按钮重叠。优点：不改浮钮语义，任何宽度下都成立。
- **b. 浮钮上移到输入区上方**：`bottom: calc(16px + var(--composer-h))`。缺点：需要知道输入区高度，
  窗口 resize 时要重算。

推荐 a，因为它是纯 CSS 令牌，不引入运行时耦合。

**验收断言**：在 1440 / 1024 / 768 三档视口下，
`getBoundingClientRect()` 求 `.sv-audio-toggle` 与 `.sv-btn-attach` 的交集 **面积 = 0**；
且对「选择文件」按钮右缘做 6 点 `elementFromPoint` 采样，**全部命中按钮自身**。

**风险 / 回滚**：新增一个 CSS 令牌；回滚即删令牌、恢复原 padding。

### UI-A3 用户消息不走 Markdown 渲染

**实测**（隔离实例内写入的会话，刷新后）：

```js
// 用户消息
document.querySelector('.sv-msg.user .sv-msg-bubble').innerHTML
→ "你好，帮我看看这个界面。\n顺便列出几个要点：\n- 第一条\n- 第二条\n- 第三条 "

// 同一会话的助手消息
svg-msg.assistant  → querySelector('ul') ✅  querySelector('pre') ✅  querySelector('table') ✅
```

用户气泡里 `- 第一条` 是**纯文本**，助手气泡渲染成真正的 `<ul><li>`。

**归因**：渲染路径分叉。助手走 `renderMarkdown`（`ChatMessageItem` 的 markdown 分支），
用户消息走纯文本插值（模板里 `{{ }}`）。

**这是否是设计意图？** 需要核实的点是：用户输入里常含代码/列表，若按纯文本显示反而"保真"。
但实际体验有两点不利：
① 同一会话两种排版，视觉不一致；
② 用户自己贴的一段代码（缩进/换行敏感）在气泡里会因 `white-space` 处理而与粘贴内容不同。

**建议方案**：用户消息也走 Markdown，但**关闭原始 HTML 与自动链接**（沿用已有的 sanitize 白名单，
与助手一致），并保留 `white-space: pre-wrap` 兜底空行。若产品侧判定「用户输入必须原样显示」，
则改为**加等宽字体块**至少让缩进与列表符号对齐——但需要在这个条目上显式裁决。

**验收断言**：写入一条含 `- a\n- b` 的用户消息，渲染后
`.sv-msg.user` 内 `querySelector('ul')` 为真；同时 `<script>`、`onerror=` 等内容仍被剔除
（复用现有 sanitize 测试夹具，追加 3 个用户侧用例）。

**依赖 / 需确认**：R-UI-A3（见第六节）——「用户输入是否也要渲染 Markdown」需产品裁决。

### UI-A4 设置页说明文案漏渲染 Markdown

**实测**（DOM）：

```html
<p class="sv-note">
  本区编辑的是**默认连接**;要多存几套请在「连接配置」里管理,聊天与任务都使用默认连接。
  保存后立即生效并写入 data/settings.json;Key 仅存本地服务端,不回显明文。地址会自动补全 协议与 /v1。
</p>
```

**归因**：`web/src/components/settings/ApiSettingsSection.vue:85` 直接写死 `**默认连接**` 星号。
`.sv-note` 是普通 `<p>`，不渲染 Markdown → 星号原样露出。

**改动点**：把 `**默认连接**` 改成 `<strong>默认连接</strong>`（本组件内已有该写法先例），
或去强调改用「默认连接」四字。**不要在 `.sv-note` 上挂 Markdown 渲染器**——说明文字用内联标签足够。

同批顺手修该段落的两处标点：
- `本区编辑的是**默认连接**;要多存几套...` → 中文分号应为 `；`
- `在「连接配置」里管理,聊天与任务` → 逗号应为 `，`

**验收断言**：全仓 `grep -rn '\*\*' web/src/components/**/*.vue` 在**模板文本节点**中零命中
（现有 `**` 命中全部属于注释或 Markdown 渲染器自身）。

**风险 / 回滚**：纯文案；单行改动。

### UI-A5 窄屏中文被逐字折断

**实测**（768×1024）：

```
「已连接」→ 竖排三行（"已" / "连" / "接"）
「综合设置」→ 两行（"综合设" / "置"）
「退出 Kedai」→ 两行（"退出" / "Kedai"）
```

（390×844 时侧栏收起为抽屉，此问题消失；**768 档最严重**。）

**归因**：侧栏在 768 档仍保持 320px 固定宽度，内部按钮为 `flex` 布局且**未设 `white-space: nowrap`**，
可用宽度不足时中文逐字断行。

**改动点**：
1. 给侧栏底部按钮（`.sv-side-btn`）与连接状态（`.sv-conn-state`）加 `white-space: nowrap`；
2. 在 `--bp-md`（768）档把侧栏宽从 320px 收到 **268px**，或让「退出 Kedai」在窄档只显示图标 + `title`；
3. 「已连接」状态在窄档**只保留色块**（绿/红方块），文字进 `title` 提示。

**验收断言**：768×1024 下，对侧栏所有 `button` 与状态标签用 `Range.getClientRects()`
统计行盒数，**全部 = 1**（现有「01 角色扮演」按钮的双行属于数字与文字的特殊组合，允许 2 行，
但需与新规则一致：即整个按钮文本**不许出现被逐字打断**的情况）。

**风险 / 回滚**：涉及响应式断点；需在 768 / 820 / 1024 三档各截一张图确认无回归。

## 三、第二档逐项证据与改法

### UI-B1 Agent 面板打开后输入区控件换行错位

**实测**（1440×900，Agent 面板展开，面板 340px）：

```
输入框下方工具栏（截图 08-agent-panel.png / crops/composerwrap-00.png）：
  行1: [01 FAST][02 DEEP][03 AGENT][04 CUSTOM]  授权 [严格][宽松][放行]
  行2: [deepseek/deepseek-v4.1-flash ▼]
  行3: [快速回复] [选择文件]
```

**量测对照**（同一页面，面板折叠 vs 展开）：

| 控件 | 面板折叠 | 面板展开 |
|---|---|---|
| `.sv-auth-mode` | x=688, y=828 | x=688, y=828 |
| `.sv-model-select` | x=854, y=824 | x=854, y=824 |
| 「快速回复」`.sv-btn-attach` | x=1208, y=**827** | x=1192, y=**827** |
| 「选择文件」`.sv-btn-attach` | x=1305, y=**827** | x=1289, y=**827** |

折叠时全部在同一 `y` 带内（824~828）；展开时两个附件按钮仍停在 y=827，但**模型选择器被挤到下一行**
（截图 08 中 y 明显增大），三个控件不再同排 —— 即「同一组控件被拆到两行」的视觉断裂。

**同时**：顶栏「JS 禁用」被压成两行（`JS 禁` / `用`，截图 `crops/agentpanel-00.png`），
角色名截断成 `系统...`。

> **注**：本轮无法稳定复现「展开 Agent 面板」这一操作（顶栏 `sv-render-toggle-v2` 的点击在本宿主里
> 未触发面板展开），上表「展开」列取自截图 08 的同一时刻量测，故以截图为准。

**归因**：输入区工具栏是 `flex-wrap: wrap`，主区变窄后自然换行；但换行后**没有对齐策略**
（模型选择器独占一行、右侧按钮掉到第三行），看起来像布局失控。

**改动点**：
1. 给工具栏定义**明确的换行优先级**：`order` 固定为「模式档位 → 授权 → 模型 → 附件」，
   换行时按组整体换行（每组 `flex-shrink: 0`），不允许单个控件被拆散；
2. 模型选择器设 `min-width: 180px` 且 `flex: 1 1 180px`，避免被压成一行独占；
3. 顶栏「JS 禁用」加 `white-space: nowrap`，并在窄档换成图标 + `title`；
4. 角色名 `text-overflow: ellipsis` 保留（当前已生效），但 `min-width` 给足 96px 避免缩成「系统...」。

**验收断言**：Agent 面板从折叠 → 展开，主区宽度变化 340px 时，
输入区工具栏内**没有任何单个控件折行**（用 `Range.getClientRects()` 统计每个 button 的行盒数 = 1）。

### UI-B2 折叠态页签参与布局导致文字折行

**实测**：

```
面板折叠（width: 0）时仍然测得：
  .sv-agent-tab-btn「Agent 状态」 w=64.9 h=86.4  → 折 2 行
  .sv-agent-tab-btn「调用情况」   w=34.3 h=86.4  → 折 4 行
面板展开（width: 340）时：
  「Agent 状态」 w=167 h=33.6  → 1 行 ✅
  「调用情况」   w=169 h=33.6  → 1 行 ✅
```

**归因**：折叠态用 `width: 0` 收起，但内部子元素**没有 `visibility: hidden` 或 `overflow: hidden`**，
仍按父容器压缩后的可用宽度参与排布，于是页签被压到 34px。

**改动点**：折叠态（`width: 0`）同时设 `overflow: hidden` + 内部 `min-width: 0` 失效化，
或改用 `display: none`（但会失去过渡动画）→ 推荐 `overflow: hidden` + `contain: layout`。

**验收断言**：折叠态下 `getBoundingClientRect()` 宽度为 0 的面板，其内部任何元素的
`getBoundingClientRect().width` **不得小于展开时的 80%**（证明子元素不参与压缩排布）。

### UI-B3 「模型与生成」滑块与数值框不对齐

**实测**（截图放大 3 倍）：

- 温度 / Top-P / 最大生成长度三条滑块的**轨道基线**与右侧数值框**不在同一水平线**；
- 「最大生成长度」的输入框 `32768` 横跨整行（约 600px），而值只有 5 位数字；
- 三条滑块的数值框宽度不一致（0.30 / 1.00 / 32768）。

**改动点**：
1. 滑块行改为 grid：`grid-template-columns: 1fr 88px`（轨道自适应、数值框定宽 88px 右对齐）；
2. 数值框统一 `text-align: right` + 等宽数字 `font-variant-numeric: tabular-nums`，
   三个值纵向对齐成一条线；
3. 滑块与数值框 `align-items: center` 保证基线一致。

**验收断言**：三条滑块行的数值框 `getBoundingClientRect().x` **完全相同**，宽度完全相同；
Slider 轨道 `y + height/2` 与数值框 `y + height/2` 差 **< 1px**。

### UI-B4 标点全半角混用

**验收断言**：新增门禁脚本段（或扩 `check-frontend-lint`）——扫描 `web/src/**/*.vue` 的
`<template>` 文本节点，`[\u4e00-\u9fa5],` 命中数 **= 0**（白名单须显式登记并附理由）。

**依赖 / 需确认**：R-UI-B4（见第六节）。

## 四、第三档逐项

### UI-C1 加载态用「...」占位

**实测**：首次打开设置 → API 连接页时，`CONN` 字段显示 `...`（约 1.5 秒后变为
`openai-compatible`），`sv-count` 区域同理。DOM 稳定后内容正确。

**改动点**：把纯文本 `...` 换成已有的骨架组件 `SkeletonBlock`（UIP-13 已落地），
宽度按内容估（CONN 用 140px、count 用 96px）。

**验收断言**：加载态下该位置 `document.querySelector('.sv-skeleton')` 非空；无裸 `...` 文本节点。

### UI-C2 主区懒加载期间纯空白

**实测**：轻量模式切换后，主区 `.sv-main` 内**无任何可见子元素**（过渡结束后才出现），
期间没有任何加载指示。

**归因**：`defineAsyncComponent` 的组件在 chunk 加载期间返回空。

**改动点**：给懒加载组件统一配置 `loadingComponent: SkeletonBlock`（现有 `lazyModal` 可扩展），
或至少在 `.sv-main` 上加一个最小高度的骨架。

**验收断言**：人为把网络降速（DevTools throttling），切模式瞬间截图 —— 主区**有可见骨架**而非空白。

### UI-C3 引导页步骤标签与正文间距

**实测**：`.ob-step-label` 与 `.ob-lead` 之间**没有显式间距规则**（`.ob-lead { margin: 0 }`），
实际间距来自父容器 gap；视觉上偏紧。同时引导弹窗标题条在本轮截图中出现空白，经核实为
**宿主字体渲染问题**（源码 `OnboardingModal.vue:192` 标题正常存在），非产品缺陷。

**改动点**：`.ob-lead { margin: var(--space-2) 0 0 }`，给标签与正文之间一个明确的 8px 呼吸。

**验收断言**：`.ob-step-label` 底边与 `.ob-lead` 顶边间距 ∈ [6, 12] px。

## 六、需要产品裁决的 3 个点

### R-UI-A3 用户消息要不要渲染 Markdown？

- **选项 a（推荐）**：渲染，与助手一致，走同一套 sanitize 白名单。优点：排版统一；缺点：用户
  贴的精确文本（如带缩进的日志）会被重排。
- **选项 b**：不渲染，但改用等宽字体块 + `white-space: pre-wrap`，让列表符号与缩进至少对齐。
- **选项 c**：保持现状（纯文本），仅在气泡上加「原始文本」标记。

### R-UI-B4 哪些半角标点属于「刻意」？

需要明确白名单：键盘操作提示（`Enter 发送,Shift+Enter 换行`）、版本号、路径、代码片段。
建议：**除 `title` 属性外，所有模板文本节点一律全角**，键盘提示改写为「Enter 发送 / Shift+Enter 换行」
（与占位符已有的 `/` 分隔风格一致）。

### R-UI-C2 懒加载骨架要不要做成统一能力？

- **选项 a（推荐）**：在 `lazyModal` 基础上扩展 `lazyPane` 工厂，全站懒加载统一带骨架。
- **选项 b**：只给主区（模式切换）加骨架，其他保持空白（改动最小）。

## 七、确认不是缺陷的观察（避免后续重复排查）

以下现象在本次观察中出现过，经核查**属于环境或既有裁决**，不要再当新问题处理：

| 现象 | 核实结论 |
|---|---|
| 设置页标题滞后一步、元素带 `sv-fade-leave-from` | **rAF 不推进**的宿主问题（`rafFramesIn500ms: 0`），真实浏览器无此现象 |
| 切模式后主区长时间空白 | 同上（过渡未收尾）；但「无骨架」本身是真问题，归 UI-C2 |

| 顶栏左上角红色斜线像"错位" | 构成主义标识元素（`sv-hub-nav-item::after`），既有设计语言 |
