### 经验 E95 —— 「先清空再逐条写」的替换类接口：失败路径的原子性必须靠「预校验 + 单事务」，逐条服务方法拼不出事务（2026-10-15 代码审查修复批 A）

- **现象**：`import_chat` 先 `clear_messages` 再「校验一条、`add_message` 一条」。第二条 role 非法时
  返回 400——但旧消息已被删、第一条新消息已落库：**报错与数据损坏同时发生**（隔离实例端到端复现：
  400 之后历史只剩「新消息一」）。同类形态：任何「替换语义」的写入口（导入、覆盖、整树回写）
  若把「清旧 + 写新」拆成多次独立调用，失败就停在半截。
- **根因（两层）**：① 校验散在写入循环里——先改库后校验，失败时已无退路；② 逐条走 `add_message`
  这类**自取写锁**的服务方法，天然进不了外部事务（Rust 侧会嵌套 `Mutex` 等待，SQLite 侧
  `MutexGuard<Connection>` 又拿不到 `&mut` 开 `transaction()`）——「贴合现有方法」的写法恰好把
  原子性做没了。
- **做法**：① 全量**预校验**（白名单归一化 / 非空 / 子结构预序列化）全部通过后才碰数据库；
  ② 取**唯一写连接**开 `conn.transaction()`，在事务内发原生 SQL（删旧 → 插新 → 更新时间），
  不调用任何自取锁的方法；任一步 `?` 传播 → `Drop` 回滚。既有事务范式可直接抄
  （`world_book_service::update_raw`，c388fb9）。
- **两处易漏细节**：**清理副作用也要进事务且错误要传播**——被替换行关联的旁支数据
  （message 作用域变量）若走「失败只记日志」的宽松清理，会出现「变量已清、消息未换」的第三种状态；
  宽松语义（单条删除/截断/清空）与严格语义（替换）应共用同一 SQL 文本、只分叉错误处理。
  另外**空集合语义要显式钉住**（本处 = 清空），修复不得顺手改语义。
- **可复用结论**：判断一个替换接口是否安全，看三件事——校验发生在写之前吗？清与写在同一个事务吗？
  清理副作用失败会被忽略吗？三条任一为否即是 KEDAI-01 同族缺陷。测试判据不能只看状态码：
  要断言「失败后原数据逐字段不变（含 id 与关联变量）」。
- **来源**：2026-10-15 审查修复批 A（`fix/review-01-02`）；代码 `services/session_service.rs::import_chat`；
  回归 `server-rs/tests/api_character_session.rs` 三条用例；证据 `revfix-0102-evidence/`。

### 经验 E96 —— 子进程输出管道「先 wait 后 read」是互相等待：排空必须**并发**、保留必须**有界**、收尾必须**有界**（2026-10-15 代码审查修复批 B）

- **现象**：桌面执行器 spawn 后**先** `child.wait()`、**再** `read_to_end`。输出超过管道容量
  （Windows ≈64 KiB）时子进程阻塞在 write、父进程阻塞在 wait——大输出命令（构建/测试日志）
  永远跑不到头，只能等超时误杀；且超时路径完全不读管道，已写出的输出全部丢弃。
  独立探针：不排空 1 MiB → 1.5s 仍阻塞；并发排空 → 65ms 退出。**抬高超时值不解决**——
  等待关系本身是死的。
- **做法（三层，缺一层都留坑）**：① **并发排空**：spawn 后立即 take 管道起读任务，进程运行期间
  持续消费（不能等退出）；② **有界保留**：读任务边读边截（头/尾字符窗口 + 中间只计数），
  内存上界与输出量解耦——但**达到上限后必须继续读并丢弃**，停止排空 = 退回死锁；
  UTF-8 要按块边界增量解码（残片缓冲 + 非法字节按 lossy 语义），否则多字节字符会被块边界切坏；
  ③ **有界收尾**：子孙进程可能持有管道写端导致 EOF 永不到来（Unix 无作业对象；Windows 靠
  `JobTree::terminate()` 关继承写端）——读任务收尾给宽限、超宽限放弃并**保留已捕获部分**
  （不能为「完整」无限等，也不能白丢已读输出）。
- **诚实边界**：宽限放弃意味着「宽限后到达的输出会丢」（有界性的代价，登记遗留）；进程树清理
  本身仍是 EXEC-TREE-1 的登记限制，修复管道不等于修好进程树。
- **顺手抓到的失实文案**：「输出超上限」说明里的「完整内容见审计日志」——审计表经
  `audit::summarize` 只存摘要，全链路根本不存在完整副本。**教训**：截断说明里承诺的落点
  （审计/文件/其它入口）必须核实真的存在；文案单处维护（`truncation_marker`）便于随实现一起改。
- **来源**：2026-10-15 审查修复批 B（`fix/review-01-02`）；代码
  `services/exec/desktop.rs`（`PipeCapture`/`drain_pipe`/`finish_reader`）；回归 5 例
  （stdout/stderr/双通道各 ≈1 MiB、超时预算内返回、Unix 子孙持写端有界收尾；修复前实测
  「阻塞到超时(20000 ms)已终止」）；证据 `revfix-0102-evidence/`。

### 经验 E97 —— 「按名字 + 时间近似匹配」的绑定在同名/并发场景必然选错：身份必须由产生侧一次生成、处处贯穿（2026-10-16 审查修复批 C/D）

- **现象**：KEDAI-04——前端 `pickUndoSnapshot` 只按 `tool_name` + 全局 max 消息 id 选快照：
  点击较早一次同类写工具调用，「回退到此处」恢复的是**最新一次**同类快照；无同名快照时还会
  退到其他工具的快照（函数级实测复现）。误回退方向是「悄悄改了别处的数据」，用户无从察觉。
- **根因**：快照与工具调用两侧**各自独立产生**，中间没有任何共同标识——快照 id 直到 commit
  才生成（消费端拿不到），工具调用记录也不存快照 id（历史重载后拿不到）。匹配只剩下猜。
- **做法**：① **id 前移**——快照 id 在「执行前」生成，commit 用同一 id 落库并把 id 回传执行侧；
  ② **身份贯穿**——执行侧（run_id/call_id 的源头）把调用身份随快照落库、把快照 id 随工具结果
  事件透出并随工具调用落库：同一次执行的三处（快照行 / SSE 事件 / tool_calls 落库）共用同一 id；
  ③ **消费端只按 id 恢复**——身份缺失（旧记录/开关未开）即禁用按钮并解释；快照失效即标记，
  **回退到启发式匹配是禁止项**（宁可不可用，不可猜错）。
- **通用判据**：凡「A 端产生、B 端需要找到它」的绑定，匹配键必须由产生侧一次生成、随两条路径
  各自传递到消费端；「按名字/时间/位置近似」在同名与并发下必然歧义。同族先例：WBCONC 的
  显式 `removed` 集合（不再靠全量覆盖猜删）、PLGM 的注册表注入（不再靠顺序猜装配）。
- **来源**：2026-10-16 审查修复批 D-1；回归 `tests/undo.rs::snapshot_binds_to_tool_call_event_and_trace`
  + 前端 `AgentPanel.undo.test.ts` 点击链路；对旧代码红证 6/6。

### 经验 E98 —— 清单式恢复（undo）的正确骨架：批内逆序 + 全批预检 + 失败零删除 + 幂等重试；顺序一律用持久序号，不用毫秒时间戳（2026-10-16 审查修复批 C/D）

- **现象**：KEDAI-05——`restore` 只逆操作所选一条快照，却按 `created_at >= 目标` 删除全部
  后续快照：数据没回到所选时点，后续恢复依据却已消失；同毫秒的多条快照被一并误删。
- **根因（两条独立缺陷叠加）**：① **删除范围与恢复范围不同源**（purge 用时间扫，apply 只做一条）；
  ② **毫秒时间戳当顺序依据**——同毫秒并列后位置不可复现，「目标及其后续」界定不了。
- **做法（四件套 + 一把锁）**：① 快照表加**持久单调 `seq`**（写锁内 `max+1`；旧行按 `rowid`
  回填=当时真实执行顺序）；② 恢复集合 = 目标及后续（`seq >= 目标`），**逆序（新→旧）逐条应用**；
  ③ **全批预检**在前（payload 可解析 / 类型合法 / 路径合法 / 截断标志 / 必要字段 / JSON 基线），
  任一条不通过即整批拒绝、**零改动零删除**；④ 全部成功才按**精确 id 列表**清理（不再时间扫删，
  批外新快照不受影响）；中途失败**保留全部快照**——逆操作各自幂等，重试=原样重放；
  ⑤ 恢复入口进程内**串行化** + 关联实体运行中（生成）直接拒绝（README/契约写明边界）。
- **通用判据**：「部分失败后还能不能重试」取决于逆操作是否幂等 + 记录是否保留；「同毫秒/同秒」
  这类并列在实践中必然出现，凡是「界定先后」的地方都要持久序号，时间戳只做展示。
- **来源**：2026-10-16 审查修复批 D-2；回归 `tests/undo.rs` 六条新用例（含中途 IO 失败保留
  快照后重试、同毫秒按 seq 确定性处理、预检拒绝零副作用）；对旧代码红证 6/6。

### 经验 E100 —— 本机 Clash 的 fake-ip DNS 会让「域名不存在 → 校验拒绝」类断言失效：`.invalid` 也被解析成假 IP（2026-10-16 审查修复批 C/D 收口时发现）

- **现象**：全量 `cargo test` 中 `tests/api_errors_codes.rs::resource_proxy_errors_carry_code_without_leaking_upstream_detail`
  红：期望 `.invalid` 保留域在 SSRF 解析阶段被拒（400 VALIDATION），实际走到「连接上游失败」（502 UPSTREAM）。
- **根因（环境而非代码）**：本机装了 Clash（2026-10-15 为 codex 登录安装），其 fake-ip DNS 对本机

### 经验 E101 —— 建表批里引用「本批次才补的列」= 旧库升级炸弹（索引/触发器同理）；fail-fast 的全量跑会把这类缺陷藏在后续 target 里（2026-10-16 审查修复批 C/D 实测抓出）

- **现象**：批 D 给 `undo_snapshots` 加了 `seq` 列 + `(session_id, seq)` 索引。索引顺手写进了
  `schema.rs` 的建表批（`CREATE INDEX ... ON undo_snapshots(session_id, seq)`）——**新装全绿、
  既有全部测试全绿**；但 `tests/schema_migration_meta.rs`（旧库升级路径）6/6 红：
  `建表失败: no such column: seq`。
- **根因（执行顺序）**：`Db::open` 的升级链是「**建表批**（`CREATE_TABLES`）→ **ensure_* 补列**」。
  旧库的 `undo_snapshots` 不带 `seq` 列，`CREATE TABLE IF NOT EXISTS` 整表跳过、而紧跟的
  `CREATE INDEX` 引用不存在的列 → **升级事务直接回滚，旧用户库打不开**。也就是说：凡是
  「引用本批次新加列」的语句，只要落在建表批里就是一颗旧库炸弹（`IF NOT EXISTS` 只保护表/索引
  自身的存在性，不保护列）。
- **正确做法**：此类索引/触发器**只放在对应的 `ensure_*` 里**（它必然在补列之后执行），并在
  `schema.rs` 原位置留注释钉住原因；fresh 与升级两条路径于是走**同一函数**产出同一 schema，
  `schema_migration_meta` 的逐表指纹（列 + 索引集合）把两侧一致性钉死。
- **为什么没被早发现（测试方法论）**：`cargo test` 默认 **fail-fast**——前一个 target 一失败，
  后面的 target **根本不会执行**（也不是「编译了整个 workspace」就等于「跑了」）。本批一次
  fail-fast 全量恰好停在前面的环境红上，把这个真实缺陷藏了两轮；换 `--no-fail-fast` 后立即
  现形。**收口全量必须 `--no-fail-fast`**，否则「其余全绿」是抽样幻觉。
- **来源**：2026-10-16 批 C/D 收口；修复 commit + `tests/schema_migration_meta.rs` 12/12 复绿；
  红证 `revfix-0305-evidence/cargo-test-no-fail-fast.log`、终态 `cargo-test-nff2.log`。

### 经验 E102 —— 有「第二个接入点」的变更清单最易漏：`ensure_*` 迁移必须同时接入 `Db::open` 与 merge 两侧预补（2026-10-16 批 C/D 的 codex 复审实测抓出）

- **现象**：批 D 新增两个幂等迁移（`ensure_undo_snapshots_restore_columns` /
  `ensure_tool_calls_snapshot_id_column`）只接进了 `Db::open` 的升级链；`merge_databases`

### 经验 E103 —— 「先查标志位再执行」的并发预检有 TOCTOU 窗口：把互斥做成**双侧 try-lock 同一把会话锁**，让锁的持有期天然覆盖副作用（2026-10-16 批 C/D 的 codex 复审实测抓出）

- **现象**：回退（restore）与同会话生成之间用「API 先查 `is_active` 再执行」协调——检查与
  「生成注册」之间是窗口，且 `commit_staged`（快照落库）不在任何协调范围内，理论上可交错。
- **做法（本批落点）**：`UndoService` 持每会话 `tokio::sync::Mutex`——生成侧在其异步任务内
  `try_lock_owned`（guard 随任务存续，持有期天然覆盖 snapshot_before/commit 等全部副作用）；
  restore 在阻塞上下文 `try_lock`，失败返回固定文案、API 映射 409。双侧都是 **try 语义**
  （不排队不等待），任一侧持有时对侧立刻可见拒绝；无需证明两个「检查-注册」序列的偏序。
- **通用判据**：并发互斥优先「同一把锁 + try-lock + 持有期=副作用窗口」，而不是「读标志位→
  执行→写标志位」的双向检查（后者总要论证 TOCTOU 上界）；锁的**持有期**就是正确性声明。
- **边界**：只覆盖同一把锁的持有者集合（本批 = 聊天生成与回退）；跨会话同角色文件写、任务
  会话写入不在其内（遗留 UNDOFIX-L1），不越界声称。

### 经验 E106 —— 有上限的响应读取必须「边读边计数」：先缓冲后校验 = 峰值内存失守，「等读完再判」会把超限响应拖成完整下载（2026-10-17 代码审查修复批 E）

- **现象**：代理类端点先用 `resp.bytes()` 全量缓冲、事后比较上限——上限对**峰值内存**为零约束。
  且即使改成流式读取，若判定条件是「读完后看总长度」而不是「越限即停」，超限响应仍会被
  完整下载（拒绝得晚，资源先花掉）；提高超时值不改变等待关系。
- **三律**：① **先计数后复制**——追加前用 `checked_add` 累计实际字节，超限分块不复制进缓冲，
  越限即返回并丢弃响应；② 声明长度（`Content-Length`）只用于**预拒**（声明超限直接不读）与
  预分配，**不替代**实际计数（缺失/失真/分块传输照实算）；③ 扩容以上限**封顶**——几何增长
  不得让缓冲容量越出约定上限。边界一律取「恰好通过」（`n <= limit`），改语义前先与旧判据对表。
- **测试布点**：在**传输层**注入，不为测试放开生产校验（SSRF 拒私网 → 测试不经端点，直接把
  响应喂给读取函数）；用**原始 TCP 上游**给出完全可控的帧（缺声明长度 / chunked / 截断）。
  「超限即停」的判据是**挂住连接不关**（实现若等 EOF 会超时失败）；「预拒」的判据是
  **体一个字节都不发**；慢响应用客户端短超时 + 外层 `timeout` 双保险断言「及时失败而非挂死」。
- **来源**：2026-10-17 批 E（KEDAI-06）；证据 `D:\kedai-bench-run\revfix-06-evidence\`
  （`red-compile.log` / `green-resource.log`）。

### 经验 E107 —— 「执行后补记写入行」不能靠 `MAX(id)`/时间窗猜：让写入工具回传真实 id + 是否新建；去重命中是正常路径，不是异常（2026-10-17 回退快照硬化批）

- **现象**：`memory_write` 的逆操作需要在**执行后**知道「刚插入哪一行」。旧实现执行前记
  `max_id_before`，执行后取「本角色 id 大于该值的第一行」。这条猜法在四种情况下都错：
  ① 窗口期另一会话/蒸馏先插入 → 绑到别人的行；② 去重命中原有记忆（本工具**没有插入新行**，
  属正常路径）→ 绑到任意旧行；③ 基线读取失败被 `unwrap_or(0)` 吞掉 → 从 0 起找；
  ④ 并发下 id 顺序不等于执行归属。后果不是统计偏差，而是回退按 id 删除，**删错持久记忆**。
- **做法**：把「是否新建、真实 id」变成工具输出契约——`MemoryService::insert_with_status` 返回
  `(entry, created)`，工具输出 `id`/`created`；快照 `commit_staged` 只认输出，`created=false`
  直接丢弃快照。基线类读取（如变量树）改成可失败的 `try_*`，读失败**不产快照**（fail-closed），
  不要用空值继续。
- **通用判据**：凡「执行前快照 + 执行后补记」的两段式，补记字段必须来自**执行结果本身**，
  不能用全局 max、时间窗、行数差等间接信号猜；「没有发生写入」必须是显式的正常返回（如
  `created=false`），否则快照层无法区分「没写」与「找不到」。
- **测试布点**：单测直接构造「快照后先插入别人的行，再提交目标行输出」的确定性交错，断言
  `inserted_id` 是目标而非较小 id；另测去重 `created=false` 零快照。端到端再加一条
  `memory_write → 快照 → restore → 记忆行消失`。
- **来源**：2026-10-17 独立复审 P1-1；证据 `D:\kedai-bench-run\undo-hardening-evidence\`
  （`red-undo.log` / `green-undo.log`）。

### 经验 E108 —— 「回退成功」必须由每一步逆操作被证实：宽松删除吞错 + 随后清快照 = 假成功且不可重试（2026-10-17 回退快照硬化批）

- **现象**：恢复批次逐条应用逆操作，失败即返回并保留快照——设计正确；但气泡/记忆逆操作走的是
  宽松删除 API（SQL 错误被 `unwrap_or(false)` 吞掉、只返回 bool），`apply_inverse` 忽略返回值，
  于是「删除失败」被当成「行本来就不存在」的幂等成功；整批走完后清理事务删除全部快照并返回
  200。用户看到「已回退」，数据没恢复，恢复依据也被删掉。同类问题还有：UPDATE 不检查 affected
  rows，行在预检与更新之间消失会被静默当作成功。
- **做法**：为「删除必须被证实」的调用方提供**严格变体**（`try_delete_message` / `try_delete`：
  `Ok(false)` 仍表示本来不存在，SQL 错误 `Err`），逆操作用严格变体；UPDATE 分支检查
  `affected == 0` 并报错（保留快照，重试走「不存在 → 插入」分支）。宽松 API 保留给主流程
  （不让清理失败阻断消息删除），但回退路径不能用。
- **通用判据**：只要后续动作会**删除恢复依据**（清快照/清日志/推进 checkpoint），之前每一步都
  必须是「被证实成功」，不能是「没报错」。把「幂等成功」与「执行失败」在返回类型上分开
  （`Result<bool>`），不要用一个 bool 同时承载两种语义。
- **测试布点**：用 SQLite `BEFORE DELETE` 触发器 `RAISE(ABORT)` 确定性阻断删除（不依赖磁盘满/
  权限等环境故障），断言 restore 返回错误、行仍在、快照仍在；旧实现会返回回执并清快照，测试
  判别力真实。
- **来源**：2026-10-17 独立复审 P2-1；证据 `D:\kedai-bench-run\undo-hardening-evidence\`
  （`red-undo.log` / `green-undo.log`）。

### 经验 E109 —— Vue scoped CSS 不会穿透 `v-html`：结果卡样式“写了但没生效”只能靠截图发现（2026-10-17 UIQ-4）

**现象**：任务成果卡明明写了 `.sv-task-result h1/p/table/th` 等规则，构建产物里也有这些选择器，
但页面上的标题仍是 UA 默认字号，表格无边框、无左右对齐；所有规则“静默失效”。

**根因**：scoped 样式会被编译成 `.sv-task-result h1[data-v-xxx]`，而 `v-html` 注入的节点**不带**
组件的 scope 属性，因此后代选择器永远不命中。它不会报错、不会让 typecheck/单测变红——只有真实
渲染截图或计算样式能发现。

**做法**：所有面向 `v-html` 内容的 scoped 规则一律用 `:deep()`，例如
`.sv-task-result :deep(table) { ... }`；组件自身模板内的节点仍用普通 scoped 选择器。
**检查法**：`getComputedStyle(document.querySelector('.sv-task-result table')).border` 为空/0 即命中本坑；
截图与计算样式都要看，不要只看“CSS 文件里有这条规则”。

**来源**：UIQ-4 任务成果卡（代码提交 `b38af66`）；证据 `D:\kedai-bench-run\uiq4-evidence\after\desktop-task-done-result.png`。

### 经验 E112 —— 主题透明度是 alpha 叠乘 + 特异性 + 图层数量的合成结果（2026-10-18 GLASS-1）

**现象**：彩窗主题名义上有 `rgba(...,.86)` 面板和 12 条 `backdrop-filter`，用户看到的却是
完全不透明的拼片印刷面；同时「切主题/打开设置」明显卡顿。

**根因（四层叠加）**：
1. **alpha 叠乘**：面板 = 底色 .86 × 白玻璃芯 .84 × grisaille 拼片 .4 × mosaic 拼片 .86，
   有效透过率只剩约 0.19%；铅条还是全不透明。单看任意一层都像“半透明”，叠起来就是实色。
2. **backdrop-filter 打错位置**：顶栏/侧栏顶/模态头底色是 `#0e2a5f` 全不透明；面板又被拼片
   盖住。模糊只作用于元素背后，不会模糊自己的 `background-image`，这些声明视觉上等于没加。
3. **特异性**：主题规则 `html[data-theme] .sv-canvas`（0,2,1）高于 scoped 的
   `.sv-canvas--ambient[data-v]`（0,2,0），而且只清 `background-color`、没清 `background-image`，
   所以“透明画布”被主题的拼片背景反压，环境层只剩约 8% 可见度。
4. **backdrop 的可达性**：stage 级 canvas 在 `.sv-main` 内部，不可能成为侧栏/主栏的 backdrop；
   面板背后只有不透明石壳。要让面板真透明，必须把环境层提到 App 级，或让外壳彩色光透上来。

**性能判据（不要只看 CSS 文件和体积）**：
- 用 `PerformanceObserver({entryTypes:['longtask']})` 记录主题切换/设置打开；
  UIQ-4 基线首次切玻璃 **288ms + 53ms**。18px 模态 `backdrop-filter` 在“设置打开 + 切主题”
  场景单独制造 **159ms**；inline 禁用后同场景降到 **60ms**，最终移除模态实时 blur 后为 **0**。
- 用 `WebGLRenderingContext.prototype.drawArrays` 计数验证暂停：空闲 **28/s**；移动抽屉打开
  先补 2 帧后 **0**；关闭恢复 **28/s**。只看 `data-webgl="ready"` 无法证明循环已停。
- 大面积实时 blur + 30fps 画布是持续成本；把模糊从大面板/模态移到“背景已暂停”的小面积，
  比调小 blur 半径更有效。

**启动判据**：`App.vue` 的 `SplashScreen v-if / 主界面 v-else` 会让主界面在 splash 的 1.6s 内
**完全不挂载**，揭幕瞬间才首次挂载整套重型图层。改为主界面常驻 + splash 覆盖 + `inert`，并让
Splash 等待主题 CSS（上限 3s）后，揭幕不再产生首次挂载重绘；主题 CSS/字体再拆开加载，
CSS 就绪即可切主题，字体由 `font-display: swap` 接管。

**来源**：GLASS-1（`c2313a5` / `9d6d5e7` / `fe4eef1`）；证据
`D:\kedai-bench-run\glass1-evidence\{baseline,after}\metrics.json` 与同目录截图。

### 经验 E113 —— 全量 PUT 的“删除”必须显式表达；并发新增的 uid 撞车不能靠“不存在”推断（2026-10-18 WBCONC）

**现象/根因**：
- 旧 `PUT /entries` 以“视图内的 uid”为保留集合，未列出的条目一律删除。前端打开编辑器取快照、
  分钟级后保存；窗口期内模型归档步/卡脚本写入的条目被静默删除（不是理论风险：角色档归档默认开）。
- 只把删除改成显式 `removed` 还不够：本地新增行 id = 草稿 max+1，窗口期模型也从同一 max 出发。
  保存时 raw 里已有同号条目，服务端若按“uid 已存在 = 更新”推断，会把模型新条目覆盖掉。

**做法**：
- 保存语义 = **叠加 + 显式 `removed` 删除**；未列出且未 removed 的条目保留（对象 map 与数组两种
  形态同口径；角色卡内嵌书常为数组，不能只修对象形态）。
- 前端用“打开时基线 id 集”同时算出 `removed` 与 `added`；服务端在写锁事务内对 `added` 中的行
  **无条件重分配**当前 max+1，不看 uid 是否已存在。
- 响应返回**提交后合并视图**，前端据此刷新草稿与基线；服务端 GET 会过滤空条目，前端要保留本地
  空白行（仍属于基线的空行留在基线里，避免下次被当成 added 反复换 uid）。

**判据/测试（三者缺一不可）**：
1. 旧快照 PUT（不带 removed）后，窗口期新增条目仍存活且响应含它；
2. `removed` 里的条目真删除；
3. 本地新增 id 与窗口期条目撞号 + `added` 时，两者都存活，本地行 uid = max+1。
并发正确性不能只靠“最后再读一遍”证明——需要真实线程（提交 1 的 80 次并发 create）或端点级探针
（`wbconc-evidence\probe-result.json`，25 项断言）。

**来源**：WBCONC 提交 1/2（`ad0f0cf` + `fe6bc96`）；残余（同 uid 字段级 LWW、同轮契约双版本、
内嵌书双份）登记 `遗留.md` §二十七。

### 经验 E114 —— GUI 启动器的阻塞提问要同时管「并发实例」与「一次启动的提问次数」（2026-10-19 启动器双重弹窗）

**现象/根因**：
- 同一份 `main()` 里先 `confirm()` 端口接管、再 `msgbox()` 构建决策：两者同时成立时单次启动
  必出两个窗；用户只会描述为「检测到增量更新时有双重弹窗」，不会拆分两次提问各自的来源。
- 启动器没有单实例守卫：检测要递归扫 `web/src`、`server-rs/src` 与产物 mtime，窗口出现前的
  第二次双击会起第二份进程，两份进程各弹一个同样的窗。

**做法**：
- 阻塞交互的最外层加命名互斥体（`CreateMutexW` + `ERROR_ALREADY_EXISTS`），第二实例静默退出。
- 同一次启动的多个前置条件（端口接管 / 构建方式）合并进一个决策弹窗；把「会先结束旧实例」
  写进文案，而不是在决策前再弹一次确认。
- 失败校验（产物是否齐全、端口是否被非 Kedai 程序占用）前移：能直接报错的场景不要先提问。

**判据**：
- 纯决策函数单测（`needs_port_confirmation` / 接管文案）锁定「最多一次提问」的边界；
  互斥体用测试专用名字验证「第二持有者被拒」，避免依赖真实单实例环境。
- GUI 弹窗本身在无桌面会话或受防护环境可能无法脚本复现。本机实测：直接 `Start-Process`
  根 `Kedai.exe` 会被宿主/安全防护连进程树一起清理（exe 同时消失）；改走
  `Shell.Application.ShellExecute`（委托资源管理器，等价双击）即可正常枚举原生弹窗。
  复核判据：400ms 连发两次启动 → 6 秒后进程数 1、`#32770` 弹窗数 1。
- 仍不可测时以单元测试 + 代码路径审查为准，并在台账如实登记「人工实测未做」，
  不要用「测试全绿」冒充 GUI 实测。

**来源**：2026-10-19 launcher 修复批（单实例守卫 + 端口接管并入启动决策）。

### 经验 E115 —— 取消轮次上限 ≠ 产物保证（2026-10-19 TMR 批）

**现象/根因**：
- 真实模型实测里，team 主 agent 在 32/80 轮两种预算下都把绝大多数轮次花在 `fs_read`/`fs_grep`/`bash`
  上，代码只留在结果正文且被截断，工作区一个文件没写；执行器仍以 `done` 收尾。
- 根因不是「预算不够」，而是**终止条件只管轮数、不管产物**：`run_tool_loop` 到上限/熔断/墙钟时
  只返回当前 `result.content`，从不检查目标文件是否存在。取消轮次上限只是把墙推远。
- 提示词层面还有反向推力：`EXECUTOR_PROMPT` 写「写入文件不替代正文」、`capability_note` 写
  「文件只是过程物」——对编码任务，这会把模型推向「攒在正文里」。

**做法**：
- 提示词加**条件段**（仅本轮真正下发工作区写工具时）：「写盘优先」——最小骨架/首个分片先落盘，
  最多先读 3 个直接相关文件就落第一版，大文件逐片落盘，文件是主交付、正文给摘要与验收要点。
- 运行时加**连续只读守卫**：任务路径按工具调用数累计，连续 8 次只读先提醒「先落盘」，再次 8 次
  熔断并保留已有正文；任一写类工具清零并重置提醒。它抓的是「一直读、不落盘」，与语义熔断
  （输出不变）互补。
- 终态加**文件交付门槛**：绑定工作区 + 允许写工具 + Solo/Multi/Team（含批准后续跑）时，本次执行
  必须至少一次非回滚文件变更（台账执行前后差值）；否则 `Done` 降 `Partial`，`tasks.error` 写明原因。
  未绑定工作区/legacy/custom/followup 不强制——它们可能是纯文本任务。

**判据**：
- 提示词单测防回退（「写盘优先」「最多先读 3 个」「文件是主交付」）。
- `task_loop_budget::readonly_streak_nudges_then_breaks`：第 8 次提醒、第 16 次熔断并保留第 16 轮正文。
- `task_loop_budget::{workspace_task_without_file_changes_is_partial, workspace_task_with_file_change_stays_done,
  workspace_task_with_bash_file_change_stays_done}`：零产物降级、fs_write/bash 产物流通。
- 不要只用「测试全绿」当验收：mock 只能证明闸门接线，是否真的先落盘必须看真实模型实测
  （审计文档 §五 的 40 文件链式读取形态）。

**来源**：`docs/plans/TASK-MODE-ROUNDS-AUDIT.md`（2026-10-19）；TMR-1/TMR-3/TMR-5 落地。

### 经验 E116 —— 只读空转检测必须与语义熔断分开（2026-10-19 TMR 批）

**现象/根因**：
- 任务侧语义熔断把输出里的**任意连续数字**折叠成 `#`，于是 `NEXT=a02.txt` 与 `a03.txt` 指纹相同；
  任务侧门槛是「同工具 4 次」，链式 `fs_read` 读到第 4 个文件就被误判「输出实质无变化」。
- 这不是「熔断太松/太紧」的调参问题：语义熔断看的是**输出内容是否变化**，而探索空转的判据是
  **动作类型是否只有读**；用前者代替后者，必然把「正常读不同文件」和「反复读同一内容」混在一起。

**做法**：
- 归一化只折叠 **≥3 位**连续数字：时间戳/耗时/计数/四位路径仍是噪声，`a02/a03`、`v1/v2` 可区分。
  保留「只差 3 位以上数值视为同构」的已知取舍，并在遗留 TMR-L5 登记 `part-001.md` 类残留。
- 单独实现连续只读守卫（`ToolBudget.readonly_streak_limit`）：按**工具调用数**累计（单轮并发 40 个
  `fs_read` 也算 40 次），只读探测工具计数、写类/编排类清零、中性工具不增不减；仅在本轮闸门名单
  含工作区写工具时启用（聊天/审计/子 agent 的只读面不会误触发）。
- 顺序放在 token/墙钟预算之后、语义熔断之前：预算是更明确的终止条件，只读守卫先给「先落盘」
  的可操作提醒，语义熔断仍管「输出不变」。

**判据**：
- `loop_guard::output_fingerprint_keeps_short_numeric_identifiers`：`a02/a03` 不同、三位耗时仍同。
- 只读判定单测：只读/写类互斥，`todo/sleep/calculator` 中性，前缀同名不误伤。
- 集成测试关闭语义熔断（`loop_guard_semantic_min_calls=0`）后只读守卫仍按 8/16 生效——证明两者独立。

**来源**：TMR-5 实现与审计文档 §五 的误判记录。

### 经验 E117 —— 审计 agent 不看文件就是自述审查（2026-10-19 TMR 批）

**现象/根因**：

### 经验 E118 —— 声明式文件所有权：声明路径与运行期路径必须同一把尺（2026-10-20 TMR2 批）

**现象/根因**：
- 审计 R-4 的形态是：多个主 agent 共享工作区并行写，没有文件级约束，谁后写谁覆盖。
- 只给提示词「各写各的」不够：模型会写 `./parts/a.js`、`parts/a.js`、`parts\a.js` 等不同拼法，
  也会写规划器根本没想到的共享文件。
- 只在运行期按「当前调用路径」登记也不够：声明归属若与运行期键不是同一套归一化，
  声明给主 1 的文件会被主 2 当成「未声明」抢走。

**做法**：
- 声明侧（`normalize_workspace_rel`）与运行期（`ExecScope::reserve_write`）**共用同一函数**：
  相对路径、拒 `..`/绝对路径/通配符/NUL、分隔符统一 `/`、Windows ASCII 小写化、长度/数量上限。
- `WriteOwnership` 两张表：不可变的**声明表**（规划器指定 owner）与互斥的**认领表**（未声明路径首写者）。
  `reserve` 在同一把锁里完成「声明归属检查 + 认领」，避免两个主同时通过检查后各自落盘。
- 认领放在**写入之前**；写失败不回滚——失败方向是「仍归本主」，不会造成跨主覆盖。
- 拦截点选在工具层（`fs_write/fs_edit` 落盘前、`fs_patch` 整批落盘前），而不是提示词或后置扫描；
  错误文案必须列出该主负责哪些文件，否则模型只会反复重试。

### 经验 E119 —— 交付摘要读时合成；必需文件门槛要读「最终 plan」（2026-10-20 TMR2 批）

### 经验 E120 —— 语义熔断按 basename 保留文件名，不要按整条路径（2026-10-20 TMR-L5）

**现象/根因**：TMR-5 把数字折叠阈值收窄到 ≥3 位后，`a02/a03` 已可区分，但

  第 4 次熔断。

### 经验 E123 —— `task_llm_calls` 的 agent 行是「整轮累计」，不是单次调用；推理内容必须计入估算（2026-10-23）

### 经验 E127 —— 交付物的「接线正确」要机器判定；单文件是目标级约束，补做复查必须前移（2026-10-24）

**做法**：把「读分片 + 替换槽位 + 写入口」做成确定性工具 `fs_inline_html`：

- 无模板模式：模型给 `sources` 顺序，引擎生成经典 `<script>` 外壳；ESM 分片要求模型
  提供模板控制边界；
- 落盘前用 `wiring::single_file_text_issues` 拒绝本地外链/相对 import，失败不落盘；
- 工具进工作区写族、`deny_dangerous` 按名例外，提示词明确「优先用该工具，不要手写」。

**判据与反例**：`task_inline_tool`（两主链 + 一次 `fs_inline_html`）能装配出含两个分片的
自包含 `index.html`，`delivery.missing=[]`、`content_issues=[]`、步骤 done。**不要**让模型
自己写 inline 构建脚本再 exec——槽位名错配（`@@TEX@@` vs `@@TEXTURES@@`）正是 SKY-4 的
原始形态；也不要只靠事后审计发现 `@@`。

**边界**：只做文本装配，不执行 JS、不解析完整语法；ESM `export` 重写未做；模板里的
`@@` 一律视为槽位；入口运行期自检仍需模型/审计（SKY-1 残余）。
**真实模型**：窄探针 A（任务 `494631ec-…`）`done` 347s，`fs_inline_html` 实际调用，
`index.html` 259B 自包含，`missing=[]`/`content_issues=[]`。
**来源**：`docs/计划.md` SKY-8；`docs/遗留.md` §三十一 SKY-8；相关 [[E124]] [[E127]]。

### 经验 E132 —— 运行期自检用 headless `--dump-dom` + 虚拟时间，不要先引 CDP；rAF 不推进（2026-10-25 SKY-9）

**背景**：SKY-1 要求「入口运行自检的机器闸门」，审计只能把 `window.GameMain.ready`、
`scene.children`、`BlockEngine.map.size` 标「待验」。仓库没有任何浏览器自动化依赖，
引 Playwright/CDP 要新增依赖、端口与生命周期管理。

**做法**：Chromium 系的 `--headless=new --virtual-time-budget=15000 --dump-dom` 会把
**虚拟时间推进到预算后**的序列化 DOM 打到 stdout。把交付 HTML 复制一份，头部插入
error/unhandledrejection/console.error/资源失败捕获，尾部插入采样脚本（读 `window`
上的 `ready`/`scene.children`/`map.size`/`renderer`/`getState()`），结果写进
`data-kedai-probe` 属性；Rust 从 stdout 取属性、百分号解码、`serde_json` 解析。
无端口、无 WebSocket、无新依赖，单次 3~6 秒。

**三个必须知道的坑**：
1. **`requestAnimationFrame` 在无头环境不推进**（最小矩阵实验：`setTimeout` 写入的
   属性出现，`rAF` 回调里的不出现）。采样只能用 `setTimeout`；同理 `fps`/`draws`
   不能当判据，渲染循环没跑不等于装配失败。
2. **`load` 事件在虚拟时间下可能等不到**；`DOMContentLoaded` + 兜底 `setTimeout`
   可靠（应用 boot 通常也挂 DCL）。采样要做两次（1.2s/3.2s），容纳异步初始化。
3. **file:// 与 HTTP 都会把跨域脚本错误抹成 `Script error.`**（不带 filename/line）。
   这是浏览器同源策略，不是探针缺陷；判据仍成立（`ready=false`/空场景），但不要把
   错误位置当可靠信息，也不要把临时探针副本路径写进用户可见错误。

**边界**：只采信装配完成后的同步状态；不测交互/帧率/视觉；外部 CDN 加载失败只记
提示（离线不是代码缺陷）；没有浏览器时跳过而不是判失败。
**来源**：`docs/计划.md` SKY-9；证据 `D:\kedai-bench-run\sky9-evidence\`；
相关 [[E124]] [[E131]]。

### 经验 E133 —— 全局命名接线要静态比对「生产者/消费者」，别等运行期空场景（2026-10-25 SKY-9）

**背景**：第三轮全题复跑里，入口 `requireGlobal('BlockEngine')` 与上游
`window.MC_BLOCK_ENGINE` 的命名风险只能靠审计自由文本指出；最终文件其实两处都导出了，
但静态检查没有任何判据，审计只能标「待验」。

**做法**：`wiring::global_wiring_issues` 收集两类信号：生产者（`window.X =` /
`global.X =` / `globalThis['X'] =`，排除 `==`）与消费者（`requireGlobal('X')`、
`window.X` 读取，排除赋值）。`requireGlobal` 未导出即报（这是模型自己写的查找助手，
返回 null 必然启动失败）；普通读取只在「未导出、但与某个已导出名规范化后相近」时报
（去 `_`/`-`/大小写、允许去 `MC` 前缀、包含匹配限 ≥6 字符），避免把 `UI`/`GameUI`
当错配。注释先剥离，CDN 全局（THREE 等）与浏览器内置属性在白名单。

**为什么不能只做运行期**：运行期失败只告诉你「空场景」，不告诉你「哪个全局名错了」；
静态命名检查在落盘后、终审前就能点名两侧名字，成本近乎为零。两者互补：静态抓
名字，运行期抓「名字对但装配没跑完」。

**边界**：不解析完整 JS 语法；字符串里碰巧像赋值的文本可能误报（概率低）；无法判定
参数顺序/签名（仍靠运行期与审计）。**来源**：`docs/计划.md` SKY-9；
`docs/遗留.md` §三十一 SKY-9；相关 [[E127]] [[E132]]。

### 经验 E134 —— 批量删除重复代码块：行锚正则的 `\s*` 会吞换行，相邻删除区间会重叠（2026-10-25 C-2E）

- **现象**：用脚本把 75 个测试文件里的本地夹具删掉、改为 `mod common;` 后，`cargo check` 报若干「unclosed delimiter」，且被删函数后面的第一个函数名少了两个字符（`fn temp_workspace` → `mp_workspace`）、闭括号也丢了。
- **根因**：① 行锚正则写成 `^(\s*)...fn`，`\s*` 匹配换行，导致 `m.index` 落在函数上一行甚至更早，删除起点前移；② `removalEnd` 在删完函数后又吞掉后随空行，相邻两个夹具的删除区间因此重叠；脚本按字节从后往前应用时，前一个删除已经改变了后一个区间的偏移，最终把下一个函数的开头和结尾各削掉一截。
- **做法**：行锚只允许水平空白（`[ \t]*`，不要 `\s*`）；删除区间不吞后随空行（留给 rustfmt）；批量改动后用「括号深度与 HEAD 对比」做结构体检（HEAD 本身因字符串内大括号也可能非零，不能只看绝对值），再跑 `cargo check --tests`；未使用导入交给 `cargo fix --tests` 后仍要复查（本次 cargo fix 后还剩 31 处 `BodyExt`/`ServiceExt`，按编译器行号精确删除）。
- **复用判据**：任何「按函数/块批量删除 + 多处相邻」的机械重构，都要先在小样本上验证删除边界，再全量执行；不要用 `\s` 跨越行边界。

### 经验 E135 —— 读时合成的摘要不要跑昂贵探针：运行期结论写库、按轮次清空（2026-10-25 SKY-9-L1）

**背景**：SKY-9 的终态运行期自检要起一次无头浏览器（3~6 秒），结果此前只写
`tasks.error` 与 Status 事件；详情 `delivery` 是每次 SSE 刷新都会重算的静态摘要，
于是错误条点名「页面没有 canvas」、成果卡却 `content_issues=[]`。

**做法**：加一列 `tasks.runtime_issues`（JSON 字符串数组），把生命周期钉在四个点上：
① 写——终态门槛 `runtime_check::probe` 后唯一写入（通过也写空数组）；
② 读——详情只查单列（**不进 `TASK_COLS`**，列表接口零成本），**绝不把 probe 放进
`summarize`**；③ 清——`reset_task` / `approve` / `followup` 起跑时清空，上一轮结论
不得挂到新一轮；④ 展示——`delivery.runtime_issues` 与静态 `content_issues` 分列，
前端各占一行警示。迁移按既有 `ensure_*` 模式补列，双库合并两侧同补。

**为什么不能偷懒**：把 probe 塞进 `summarize` 会让每次详情请求（SSE 高频）都可能起浏览器；
用内存缓存则要处理多任务并发与进程重启，比一列 SQLite 的维护成本高得多。反过来，只改
错误条文案而不持久化（原「方案 c」）仍是两套事实来源，测试也钉不住。

**边界**：无浏览器/未选中入口时自检不执行，列保持空数组——与「自检通过」在展示上同形，
区别只在 Status 事件；需要区分时应另加 verified 位，本批不做。**来源**：`docs/计划.md`
SKY-9 追补；`docs/遗留.md` §三十一 SKY-9-L1；相关 [[E132]] [[E133]]。

### 经验 E136 —— 产品边界要落成「确定性拒绝 + 可执行下一步」，静默跳过是缺陷（2026-10-26 SKY-10）

**背景**：SKY-8/SKY-9 的残余一直写「ESM 单文件支持仍开放」。真实缺陷不是「引擎不会打包」，
而是模型选了 ESM 后：`fs_inline_html` sources 模式硬拒绝、预置骨架静默跳过、全 ESM 时
`assemble_pre_seed` 返回 `Err` 又被调用方 `.ok()?` 吞掉——入口不存在，模型既没有入口也
不知道原因，只能重新规划或空转。

**做法**：先把边界定死（单文件交付不建立本地模块图；分片必须经典脚本；引擎不打包 ESM、
不重写 export；最终入口只允许远程 ESM/importmap），再把边界落成三件可执行的东西：
① 预置结果结构化（`PreSeedOutcome { html, inlined, skipped_esm, reason }`），成功/失败
都把跳过的分片逐一点名并给改写指令；② 四类静态判定（经典 script 的 import/export、
importmap 本地目标、未映射裸说明符、`/...` 本地绝对路径）进入落盘前与终态 `content_issues`；
③ 提示词删掉「确需 ESM 可提供 importmap/模板」的例外——留着例外，模型就会走例外。

**为什么不做 bundler**：相对 import 拓扑排序 + 去 export 看着简单，实际要处理循环、
默认导出、重导出、命名冲突、live binding 与求值顺序；本仓库没有 JS AST 解析器，手写
文本子集会在「看似成功、语义已变」处出问题——这比诚实 partial 更糟。若未来重启，先引入
真实解析/打包依赖并先写循环/重导出/命名冲突用例，不要继续加行级启发式。

**2026-10-26 复测**：新 key 到位后三连窄探针——模型在题面明确要求 `import/export` 时仍按
引擎提示改写成经典脚本（边界生效）；healthy 与 THREE 两题入口运行期自检通过。两个
`partial` 分别来自既有团队 900s 预算与重复 bash 守卫，不是 ESM 边界缺陷。
**How to apply**：看到 ESM 相关 `partial` 先分三类——预置/装配是否点名了 ESM 分片（本批
新增回路）、终态是否只是预算/守卫收尾、运行期自检是否通过；不要把所有 `partial` 都归到
ESM 边界。

**边界**：文本判定不覆盖动态 `import()` 的本地路径与 `import.meta` 资源解析；`</script>`
转义仍未做。**来源**：`docs/计划.md` SKY-10；`docs/遗留.md` §三十一 SKY-4/8/9；
相关 [[E129]] [[E131]] [[E135]]。

### 经验 E137 —— 改任务缺省输出上限必须同批校准 mock 截断门限（2026-10-27 TPROF-1；2026-11-05 TPROF-2 再校准）

**现象**：任务向缺省输出上限从 8192 抬到 32768 后，`connectors/mock.rs` 的
`TOOL_RAW_MIN_BUDGET` 若仍是 16384，首轮 32768 已高于门限，`[[tool_raw:]]` 会直接返回
完整 tool_call。表现不是编译错误，而是四个「截断自愈」集成用例静默失去首轮截断：
`tasks_modes_solo_multi` / `tasks_modes_plan` / `tasks_crud` / `task_self_heal_usage_on_failure`
要么调用行数变少，要么找不到「截断自愈」error 行。TPROF-2 把缺省再从 32768 抬到 65536，
门限必须同步从 49152 抬到 98304，否则同一形态会再次出现。

**Why**：mock 钩子用「当前 max_tokens 是否低于固定门限」区分首轮与自愈重发轮。
门限是测试脚手架常量，不随产品默认值自动更新；它必须严格落在「任务首轮预算」与

只改默认值或只改门限，都会让两轮形态消失（引擎同一轮只自愈一次，不会自动补第三轮）。

**How to apply**：改 `TASK_DEFAULT_OUTPUT_TOKENS` 时同批检查
`TOOL_RAW_MIN_BUDGET`，并保留/扩充 `connectors::mock` 的常量关系单测
（首轮 < 门限 ≤ 首轮×2）。当前值：首轮 **65536** / 门限 **98304** / 翻倍 **131072**。
看到自愈用例变绿但调用行数减少时，先检查门限，不要改断言。
相关 [[E76]] [[E86]]。

### 经验 E138 —— 人称约束要作为「最后一层强指令」独立存在，不能写进任何会被 recency 盖过的地方（2026-10-28 POV-1）

**现象**：角色扮演的「第三人称」设置长期漂移成第一人称。逐层排查发现五处叠加：

① system 静态层最后一条是不是它？② 步骤指令/工具指南之后有没有更强的人称句？
③ 反思模型看得到它吗？④ 上文/摘要/文学段里有没有「与上文一致」把它粘住？
四处都过一遍，再做真实模型实测（至少第一人称、第三人称 deep、视角关闭、对话、转述五形态）。

### 经验 E140 —— 编译效率的瓶颈在「调试信息体积」与「单 crate 无边界」，不在链接器或 build.rs（2026-10-31 编译效率批）

**现象**：`server-rs/target` 一次调查时达 **82 GB**，D 盘只剩 13 GB。构成：`deps/` 69 GB、
`incremental/` 12 GB；其中 **272 个 `.pdb` 合计 53 GB**（单个测试二进制的 PDB 约 300 MB），
`libkedai_server-*.rlib` 单份 912 MB（历史上同时存在 2 份 900 MB 级副本）。
单文件增量（改一个 `.rs` 后 `cargo build`）实测 **15.6 s**。

**Why**：
1. **PDB 是体积大头且纯属调试产物**——它只被调试器消费，删除不影响任何编译产物、
   增量缓存或运行行为。删完 target 从 82 GB → 28 GB，零改动构建仍 0.39 s（缓存完好）。
2. **链接器不是瓶颈**：换 `rust-lld`（工具链自带）与 MSVC `link.exe` 实测 15.3 vs 15.6 s，
   无差别；不值得为它引入工具链可移植性成本。
3. **`build.rs` 的 `rerun-if-changed=src` 也不是主因**（假设被实验证伪）：临时移除后
   `touch src/config.rs` 仍 11.6 s——cargo 自身按 mtime 判定就会重编。
   11~15 s 是 **136K 行单 crate 的固有编译成本**，没有 crate 边界可分。
4. **真正的杠杆是 `debug` 级别**：dev 档 `debug = 1`（line-tables-only）把增量降到
   13.3 s、rlib 降到 294 MB，而 **panic 仍带 `文件:行:列`**，故 dev 不能降到 0。
5. **三个 bin 各链一次**：`kedai-server` / `kedai-agent` / `kedai-data-merge` 共享 lib
   但独立链接，占去约 6 s。日常只起主 bin 时可用 `watch.ps1 -MainBinOnly`。
6. **dev 与 test 两档要分别定，且结论相反**（这一点反直觉，别类推）：
   - dev 取 `debug = 1`：rlib 912→294 MB、增量 -15%，**并保留 panic 行号**
     （实测 `panicked at src\config.rs:336:23`），排障刚需，不能降到 0。
   - test 取 `debug = 0`：`debug = 1` 对测试 PDB **几乎无瘦身**
     （131 MB vs 完整档 127 MB——行号表本身就占绝大部分），
     而 0 档让 89 个测试 PDB 从 11 GB 降到 3.2 GB、**编译还快 28%**（91 s → 66 s）。
     测试档丢掉行号不要紧：失败断言由 libtest 直接打印 `tests/xxx.rs:123`
     与断言消息，不依赖 PDB 符号化；偶需行号时临时 `RUSTFLAGS=-Cdebuginfo=1` 覆盖即可。

**How to apply**：
- 磁盘告急且不宜全量重编时，**先删 PDB**：`find server-rs/target/debug -name '*.pdb' -delete`
  （先确认没有 `kedai-server` 在跑）。当前 bin 的 PDB 会在下次构建时按需重生，属正常。
- 判断「编译慢」先分层量：`cargo build --timings` 看编译 vs 链接，别一上来换链接器。
- `[profile.dev] debug = 1` 已固化在 `server-rs/Cargo.toml`。**`profile.dev` 不作用于
  `cargo test`**（它用 `profile.test`），故测试栈回溯不受影响；若将来要压测试 PDB，
  另加 `[profile.test]`，但一次只改一处，便于归因。
- 别为了「让 build.rs 少跑」而动 `rerun-if-changed`——它不是主因，改了也白改。
- 实测矩阵与证据：`D:\kedai-bench-run\compeff-evidence\01-profile-matrix.md`。
  相关 [[E17]]（1455 内存耗尽）[[E29]]（rlib 缺失先降并发）——两者都因 debuginfo 巨大而加剧，
  本条把它们的内存侧压力一并降低。

### 经验 E141 —— 观感类「对齐」改造：改对了位置比改对了值更关键（2026-10-31 UIPOL 批）

**背景**：审美审计报告（`docs/plans/UI-AESTHETICS-2026-10-31.md`）给出 7 条「不均匀」问题
与逐条 CSS 建议。本批复核时发现，其中两条的**建议本身不足以达成它自己写的验收断言**——
照抄建议会对不上验收标准，而且不容易察觉。

**两条实例（都是「改对了值、改错了位置」的变体）**

1. **A3 任务台空态居中**：报告建议改 `task.css` 的 `.sv-task-empty { justify-content: center }`，
   且注明「注入 `<style>` 不生效」。真实原因是**组件 scoped 规则的 specificity 更高**
   （`TaskBoardEmpty.vue` 的 `.sv-task-empty.fill` = 0-2-0 压过全局的 0-1-0），改全局那条
   永远无效。更要紧的是：**只加居中也不够**——`.sv-task-start` 自带
   `margin-top: clamp(24px, 6vh, 72px)`，会把居中后的内容继续下推。本批首轮只改居中、
   保留 `margin-bottom: 8vh`，实测上下比 0.69（162 : 234），**仍在报告自己的验收区间
   [1, 2] 之外**；把 margin 一并归零后才是 1.00。

2. **A2 表单标签列**：报告建议 `88px`。实测存在「剧情推演同步全局词条」这类十余字标签，
   88px 会多截 3 个；且**定宽必然引入截断**，而报告没提 title——补 title 是这条改动的
   必要组成部分，不是加分项。此外 `flex: 0 0 96px` 必须配 `min-width: 0`：flex 项的
   `min-width` 默认是 `auto`（= min-content），`white-space: nowrap` 的长标签会**顶破定宽**，
   定宽形同虚设。

3. **B3 输入区右缘**：报告建议 `padding-right: 72px`（40 浮钮 + 16 右距 + 16 呼吸）。
   实测 64px 即可让重叠归零（`--space-4 + 48px`），72px 只是把输入区白缩 8px。

**How to apply**

- 观感类建议里的**具体数值一律当假设**，落地前先在真实页面量一遍几何（本批用
  `getBoundingClientRect` + `elementFromPoint` + `Range.getClientRects()` 三件套）。
- 改「对齐/居中」类问题时，同时检查**同类规则的 specificity 与同级 margin/padding 短路**：
  scoped 块常比全局域更具体；`margin` 与 `justify-content` 会互相抵消。
- 定宽列 + `nowrap` 的固定搭配：**必须**同时写 `min-width: 0`（或 `min-width: <定宽>`）
  与 `text-overflow: ellipsis`，并给所有会超长的实例补 `title`。漏一项就是「定宽了但没截」
  或「截了但看不全」。
- 观感类批次无法用 jsdom 断言尺寸，落**源码级契约测试**（本批 `components/uipolVisual.test.ts`
  8 例）守关键声明，注释里写清「修前的值」——下一轮最容易被反问的就是这个。
- 相关 [[E74]]（视觉能力包模拟器全链验证）[[E109]]–[[E111]]（UIQ-4 前端观感实测）。

### 经验 E142 —— 「只扫模板」的文案门禁会漏掉常量表；「改了渲染路径」的批次要单独证渲染行为（2026-10-31 UIVIS 批）

**背景**：缺陷审计报告要求把模板里的半角标点统一（实测 **327 处**），并把这条做成门禁。
本批按报告口径写了「只扫 `.vue` 的 `<template>` 文本节点」的扫描器，清零后跑通、写进门禁，
**却在真机复核时发现下拉框里仍是半角**。

**两条教训**

1. **模板扫描漏「常量表」这一整类**：`web/src/api/labels.ts` 的 `MODE_OPTION_LABELS` /
   `FLOW_MODE_OPTION_LABELS` 被模板以 `{{ TABLE[x] }}` 的形式原样渲染成 `<option>` 文本。
   模板里只有表达式、没有字面文案，所以扫描器看不见——但**用户看到的就是半角**。
   同类的还有能力位 `tip`（`CONNECTION_CAPABILITIES`）与教程文案 `utils/tutorialCopy.ts`。
   修法：扫描器除模板外，**再显式登记「展示标签常量表」清单**逐文件扫字符串字面量
   （注释先剥掉，否则说明文字会被误算）。

2. **扫「全部 .ts 字面量」会造出大批假阳性**：本批先试了全量扫描，命中 **537 处**——
   绝大多数是错误信息、日志与注释，而错误信息里常嵌着代码原文
   （如 `Chat Completions: response_format;Responses: text.format`），强行全角会**改坏语义**。
   故门禁必须「白名单式登记」，不能全域开扫。

3. **判据要严到不误报**：只认「**汉字**紧邻半角标点」，并且排除①标签属性
   （`title` / `placeholder`，含「Enter 发送, Shift+Enter 换行」这类刻意半角）、②`{{ }}`
   表达式内（代码）、③HTML 注释。少了任一条，门禁要么误报一片、要么漏掉 `{{ TABLE[x] }}`
   这种「模板里看不见、界面上看得见」的路径。

4. **改了渲染路径的观感批次，不能用「源码契约通过」代替行为证据**：本批 A3 把用户消息
   从纯文本插值改成 markdown（新增 `renderUserMarkdown`）。这类改动**源码断言只能锁声明，
   锁不住行为**——必须真的渲染一条含 `ul` / `pre` / `blockquote` / 原始 `<img>` / 裸 URL 的
   用户消息，逐一断言「哪些成了元素、哪些仍是文本」。无模型可用的场景下，往隔离实例的
   `messages` 表直插一条即可（等价于查看历史会话）。

5. **懒加载骨架的「没看到」不等于「没生效」**：`lazyMain` 刻意设 `delay: 180ms`
   （缓存命中时瞬时闪一块骨架比不闪更差）。本地起服务时 chunk 在 180ms 内就位，骨架
   **永远不会出现**——此时正确的证据是三合一：① chunk 独立且按需请求（`performance` 资源条目）；
   ② 骨架的 scoped 规则确实随包下发（遍历 `document.styleSheets` 找 `data-v-*` 选择器）；
   ③ 结构由 jsdom 断言。别因为「截不到骨架」就判定功能没做。

**How to apply**

- 写「文案/排版」类门禁时，先问一句：**这些字是写在模板里，还是写在某个常量表里？
  渲染时会不会经插值进来？** 后者必须显式登记，否则门禁给的是假绿灯。
- 门禁的**排除面**要和命中面一样明确（属性 / 表达式 / 注释 / 代码原文），并把排除理由写进脚本头。
- 改渲染分支的批次，验收要「源码契约（锁声明）+ 真实渲染（锁行为）」两条腿；
  只有前者时，务必在提交正文写明「行为证据缺位」及其原因。
- 与 [[E141]]（观感类对齐改造：改对位置比改对值更关键）同族：都是「报告的建议不等于
  验收断言」的变体——一个在 CSS 层，一个在文案与门禁层。

### 经验 E143 —— 机械门禁全绿 ≠ 台账语义正确：收口要对照验收断言、模块路径与门禁覆盖（2026-10-31 SUBFIX 批）

**背景**：对 2026-10-31 当日 7 批做代码 + 文档审计。check-docs / check-doc-claims /
text-punct / count-tests 等机械门禁全绿，但逐条对照代码与文档后仍发现：

1. **「已完成」不等于原验收达成**：计划 4.7 取元测试路线后，登记点并未收敛，
   原验收「新增哑工具只需改 1–2 处」实际未满足；状态只写了「已完成」，没有标注差异。
2. **模块路径会随重构漂移**：台账把 `explicit_risk` 写在 `permissions.rs`、把
   `tool_when_for_test` 写在 `registry.rs`，实际已拆到 `tool_risk.rs` / `tool_meta.rs`。
3. **门禁声明要覆盖实际登记面**：变更史说 text-punct 覆盖「两张表」，脚本只登记了

**How to apply**

- 批次收口时把「原验收断言」逐条对照实现，未达成的写进状态/边界，不要用「已完成」一笔带过。
- 台账写模块路径前，先在当前 HEAD `grep` 一次函数定义位置；重构批尤其容易漂。
- 声明门禁覆盖 N 张表时，核对脚本里的登记数组长度；只扫模板的门禁天然漏常量表。
- 自维护的 IANA/白名单表定期与上游 registry 对差；补表时同时补表驱动用例，
  否则「补了代码没补测试」仍可能漏段。
- 机械门禁保证「字面一致」，语义正确（验收、路径、覆盖、上游事实）仍需人审；
  审计批应把这两层分开写结论。


### 经验 E144 —— Windows CI 的钱花在「不缓存」而不是「编译慢」：先量 step 级耗时，再动刀（2026-11-01 CI 提效批）

**背景**：仓库长期记着「Windows 权威档单次 30~50 分钟」（E66、ci-linux.yml 头注释）。
2026-11-01 从 GitHub API 取三次真实 run 的 **step 级**计时，实际是 **12.9~19.2 分钟**：

| step | PR 成功 run 41307800763 | main 成功 run 41302465747 | main 失败 run 41309317403 |
| --- | --- | --- | --- |
| Cache cargo | 72s | 84s | 73s |
| **Install cargo-audit** | **196s** | **342s** | **364s** |
| Install npm deps | 31s | 52s | 52s |
| Build web | 7s | 12s | 10s |
| Local gates | 431s | 620s | 461s（红） |
| **合计** | **770s** | **1148s** | 995s |

**三条可复用结论**：

1. **「安装工具」是隐形大头**。`cargo-audit` 每次现编占 25%~37%——因为 `Get-Command` 的判断
   恒为假（`~/.cargo/bin` 不在缓存路径里）。给工具二进制单独一条 `actions/cache`，key 用
   **固定字面量 + 版本号**（不用 hashFiles：它与依赖树无关），并给安装加 `--version` 钉死。
   版本号与缓存 key 必须同源（本仓用 job 级 `env.CARGO_AUDIT_VERSION`），否则缓存里的旧二进制
   会顶掉新版本、审计口径静默漂移。同款写法可参照 ci-linux 对 cargo-ndk 的处理。
2. **同一份代码波动 6 分钟 = 缓存命中率不稳，不是机器慢**。PR 431s vs main 620s 的 Local gates
   差，根子在精确 key「全有全无」：改一次 Cargo.toml 就零复用、整轮冷编。三处修法——
   ① 排除 `target/debug/incremental`（本机实测 23 GB，占整个 target 56%，CI 一次性编译复用它收益近零）；
   ② key 里**只留真正会被编译的清单**（此前混入 `src-tauri/Cargo.toml`，改一次 Tauri 依赖就让
   server-rs 的缓存整份作废；而 `src-tauri/target` 在 CI 里根本不存在——check-all.ps1 从不碰它）；
   ③ 加 `restore-keys` 前缀回退，把命中率从二值变成「总有部分复用」。
3. **单仓缓存配额是 10 GB，会按 LRU 淘汰**。实测该仓库已用 11.59 GB、其中 cargo 条目 5 条各约
   2.1 GB（同名 key 因不同 scope 各存一份）。**缓存不是越大越好**：超配额后新缓存会挤掉旧缓存，
   表现为「有时命中有时不命中」的随机慢。查配额：`GET /repos/{owner}/{repo}/actions/caches`。

**另一个容易搞反的点**：`-SkipWeb` 并不等于「只跳过前端编译」。check-all.ps1 历史上把 11 段
纯 Node 的契约/架构/计数/ratchet 检查与前端编译归在同一守卫下，`-SkipWeb` 会连带跳过它们，
轻量档只剩文档三段与审计。需要「跳编译、保静态口径」时，应新增一个显式挡位（本批加了
`-StaticOnly`，它优先于 `-SkipWeb`），而不是复用 `-SkipWeb` 并假设语义。改开关语义前先 grep
它在 pre-push / build.ps1 / 文档里的全部调用点。

**How to apply**

- 动 CI 之前先取 step 级耗时（`GET /repos/{owner}/{repo}/actions/runs/{id}/jobs`），
  不要按总时长猜瓶颈；仓库文档里的区间值可能已过期数周。
- 判断「缓存有没有用」看**同一份代码两次 run 的差值**，而不是看缓存步骤自身耗时。
- 排除 `incremental` 只对「一次性热态编译」成立；本地内循环（`watch.ps1`）仍依赖它，别全局删。
  **但在 GitHub Actions 上它基本是空操作**：`dtolnay/rust-toolchain` 这个 action 会自动
  设置 `CARGO_INCREMENTAL=0`（其日志里明写 "Disable incremental compilation"），
  CI 因此从不生成 `incremental` 目录。本批实测印证：排除前后缓存条目都是 ~2201 MB。
  **教训：改缓存路径前先看 runner 实际产出了什么，别拿本机 `du` 的数字当 CI 的体积。**
- **改缓存策略后必须回读真实体积**：`GET /repos/{owner}/{repo}/actions/caches` 给出每条
  `size_in_bytes`。本批「缩小 target 缓存」的预期被实测证伪（2.14 GB → 2.15 GB），
  按仓库纪律如实登记为「未达成」，而不是把总时长的偶然波动说成收益。
- 给 main 减负时，先确认有没有**别的会编译的触发源**（schedule）在给 PR 档保鲜：GitHub 的
  缓存作用域只允许 PR 还原「当前分支」或「默认分支」的缓存，**兄弟 PR 之间互相看不见**。
  main 一旦不再编译又不加定时全量，新 PR 会稳定冷编。
- 顺手记：CI 里失败的步骤若把输出 `| Out-Null` 掉，判红时只剩一行 exit code。
  排障价值远大于那几十行噪声——本批的 launcher flaky 就是靠本地按 4 线程复跑才定位的。

### 经验 E145 —— 装饰性纹理的「规整感」来自骨架，不来自不规则；透明度与光泽也只能靠分层叠加（2026-11-02 GLASS-PANE-1）

**背景**：彩窗主题上一轮把「拼接玻璃」整条删掉了（全界面 `pattern: false` 100%）。
本批把它补回来，中间试错四轮，每轮都被真实截图否掉，最后才收敛：

| 方案 | 观感实测 | 结论 |
| --- | --- | --- |
| 48 块完全随机多边形（沿用旧原型） | 碎玻璃／迷彩 | ❌ 缺骨架 |
| 随机多边形 + CSS 叠石棂网格 | 有规整感，但铅条与网格打架 | ❌ 两套结构互斥 |
| 规则菱形，行距 = 全高 | 菱形只在顶点相碰，中间露大片暗格 | ❌ 读作菱格纹地砖 |
| **石棂骨架 + 菱形错缝咬合（行距 = 半高）** | **真彩窗** | ✅ |

**Why**

- **「不规则」不是规整感的来源，骨架才是**。真实彩窗的构造是「刚性石棂（等距竖棂 +
  横档）先切出规则格子，格内才是玻璃片」。只画随机多边形 = 只画了玻璃片、没有骨架，
  必然读作碎玻璃。这条与「装饰要克制」无关，是构造顺序问题。
- **菱形的咬合是纯几何**：菱形总高 = 2×半高，所以相邻行中心距必须是**半高**才能嵌入；
  写成全高就只在顶点相碰。这个错误肉眼看上去像「菱格地砖」，很容易被误认为
  「配色不对」而去改颜色——浪费一整轮。
- **暗色场景下不能靠「盖暗罩」压纹理**。拼片是「浅底 + 黑线」，盖暗罩只会得到一片均匀的
  灰；`background-blend-mode: multiply` 才让浅底变成透光的彩色玻璃、黑线仍然是黑。
  三档实测：0.50 暗罩 = 灰白纸片 / multiply `#1d3a70` = 发乌 / multiply `#4a68a8` = 暗蓝透光。
- **透明感与光泽只能分层做**：玻璃片自身 `fill-opacity` < 1 才有"透"，片内斜边高光 +
  右下暗部才有"厚度"，贯穿式斜向反光才是"镜面"。加白只会得到磨砂灰。
- **横向条带必须单独设计**。顶栏 68px 高，拿 820×560 的竖窗图做极端缩放取样，
  采到的永远是某一块局部。按「一档高 + 两个光窗宽」生成专用周期图，`repeat-x` 平铺，
  尺寸 `auto 100%` 自适应——这一条让顶栏从「一块蓝布」变成「一整条窗」。

**How to apply**

- 做装饰纹理前先问：**骨架是什么**？等距网格、轴网、放射扇——先有骨架再有片。
  只有骨架确定后，「不规则」才是加分项。
- 用「注入 style 做 A/B 对照截图」验证手法，不要凭想象：本批 6 个候选里 4 个一看就否，
  每轮成本约 1 分钟（改 style.textContent + clip 截图），比改代码重编快一个数量级。
- 遮罩浓度、采样位置、混合模式这三件事要**一起**调，单独调任何一个都会得出错误结论。
- **不要拿装饰条填留白**。用户明确否掉了三种装饰条方案（右栏横带 / 两栏竖棂 / 底部窗槛），
  留白的正解是让版式本身撑满并把内容按阅读节奏分散。整块 `space-between` 会把
  标题与描述之间也撑出上百像素的缝——正确做法是只让某一簇 `margin-top: auto`。

### 经验 E146 —— 跨模式共用的「文案」有三种，只有一种该改写，两种该分叉（2026-11-02 RTSPLIT-R3/R4）

**背景**：双模式（角色扮演 / 任务）共享 `tools/` 注册表与 `prompt_kit` 原语。排查「还有哪些
跨模式共用但语义跑偏的东西」时，同一句 `untrusted_boundary` 规则句已在前一批修掉。这一批
剩下两类：**工具 `description`** 与 **世界书段落前缀**。表面上都是"文案"，处置方式却不同：

| 类别 | 例子 | 处置 |
|---|---|---|
| 单模式专属文案，另一侧根本看不到 | `build.rs` 的【创作总纲】 | **不改**（任务链不调用） |
| 双模式共用、两侧语义都成立 | `tool_when("search")` = "需要联网查询…" | **不改** |
| 双模式共用、但一侧语义跑偏 | `read` 的「角色提示词 / 角色文件区」；世界书前缀「设定」 | **按模式分叉** |

**Why**

- **判据是「执行期哪个模式消费它」，不是「读起来像不像创作语言」**。`tool_when` 里
  「需要联网查询」两模式都对，中性化它只是无谓改动；而 `read` 的「角色文件区」在任务侧
  指向一个**不存在的东西**（任务读的是工作区文件），这才是缺陷。
- **分叉点必须在「读取侧 / 出口」，不能在「注册点」**。注册点是聊天链的唯一来源：
  改写它要动 20 余处角色扮演调用点，而「任务侧要什么」只在任务工具面的出口才成立。
  本批做法：新模块 `tools::tool_description` 持两套文案，任务侧出口
  （`tool_policy::compile` / `scout_defs`）调 `with_mode(Task, defs)` 重写；
  角色扮演侧由**逐字节回归锁**看着，谁改注册原文谁红。
- **「未知工具原样返回」比「统一清空」安全**。插件 / MCP 自定义工具没有任务向文案，
  统一清空会让它们在任务侧彻底失去语义——比保留创作措辞更糟。
- **顺手清词面时要先分清「描述现状」与「描述旧机制」**。任务侧有一批注释写着
  「人设 / 升华 / 提示词注入」，看着都像过时残留，但逐条读下来分两类：
  「人设档位已随 TM-SET-2 退役」是**准确的现状陈述**（不能说它过时，改了反而丢信息）；
  而「注入执行者人设 + 世界书 + 提示词注入」是在**用已退役机制描述现行行为**，必须改。
  判据：这条注释在读的人会以为那个机制**还在**吗？

**How to apply**

- 新做「跨模式文案」类修复时，先按上表三分类过一遍：能证明「另一侧看不到」的不要动，
  两侧都成立的中性句不要动，只有语义跑偏的才分叉。
- 分叉照 `untrusted_boundary_for(mode, …)` 的范式：一侧保持原文，新增带 `_task` 语义的
  入口，再补一条**逐字节相等**的兼容性断言锁住旧调用点。
- 判断「这条注释过时了吗」时，问「读者会不会以为某机制还活着」，而不是「里面有没有敏感词」。

### 经验 E147 —— `getComputedStyle` 在过渡期间给的是起始帧：观感量测必须先 `finish()` 动画（2026-11-03 ATTACH-1 观感批）

**背景**：给彩窗主题补侧栏底部三按钮的主题化（ATTACH-1 观感批）。改了 CSS、重新构建、`reload()` 页面，
读到的计算值**永远**是旧值。为定位原因，连续排除了四种假说：

| 假说 | 验证 | 结论 |
|---|---|---|
| 特异性不够 | 注入 `html[data-theme] .sv-sidebar .sv-side-foot .sv-btn.sidebar-exit`（(0,5,0)） | 仍不变 |
| 简写/长写冲突 | 改成与 `panels.css` 同构的简写 `background` | 仍不变 |
| 需要 `!important` | 注入 `…{background:rgb(…)!important}` | **仍不变** |
| 浏览器缓存旧 CSS | 换端口起全新隔离实例 | 仍不变 |

四种都排除后，答案在于**根本没读对**：`el.getAnimations()` 显示该按钮上有 5 个
`transition` 处于 `running`（含 `background-color`），而**侧栏宽度过渡（25px → 296px）尚未结束**。
`getComputedStyle` 在过渡期间返回的是**当前插值**（= 起始帧），所以无论怎么改 CSS 都读到旧值。

**Why**：过渡是「时间上的中间态」，而 `getComputedStyle` 回答的是「此刻的值」。
元素一进入可见状态就开始过渡（本例：侧栏从折叠到展开），量测脚本在过渡早期采样就会拿到起点。
更麻烦的是它的形态像一个**层叠问题**——「我改的规则不生效」，于是人会一路往特异性、
简写、`!important` 的方向走，而那四个方向全都是错的。

**How to apply**：

- 量测**任何**有过渡/动画的元素前，先跑一遍：
  ```js
  for (const el of document.querySelectorAll('*')) {
    if (typeof el.getAnimations === 'function') for (const a of el.getAnimations()) { try { a.finish(); } catch {} }
  }
  ```
  再 `await new Promise(r => setTimeout(r, 100))` 后读取。
- 判据：`el.getAnimations().length > 0` 就**不要相信**这次读数，尤其当值恰好等于「改动前」。
- 看到一个元素尺寸明显异常（本例宽 25px，正常约 296px）时，先怀疑它处于过渡中间态，
  而不是布局缺陷。
- 与 [[E145]] 同族：都是「观感问题要先建立可靠的观感信号，再谈改法」。区别是 E145 讲
  装饰纹理的骨架，本条讲**量测时机**。
- 关联的另一个纯 CSS 陷阱：同一条规则里 `background: var(--x)` 与 `background-image: none`
  混写时，浏览器解析期无法求值 `var()`，会把简写展开成**一串空子属性**
  （实测 CSSOM：`background-color: ;`），整条规则等于没设底色。只写长写即正常。
  这条已写成源码契约（`stainedGlassCss.test.ts` 第 4 条）。

### 经验 E148 —— 窗口化列表的两个承重约束：IO root 要绑真正滚动的容器，占位行必须与真实行共用同一个 `bindRow`（2026-11-04 TMSHOW-4）

**背景**：TMSHOW-2 给任务执行档 2（扁平全消息时间线）接窗口化，复用既有
`composables/useVirtualMessages.ts` 的纯逻辑核心 `createVirtualListState`，把行 id 从
`number` 泛化为 `string | number`。逻辑层单测全绿、320 条轨迹的 DOM 数量也确实是
「42 真实 + 279 占位」，但真实页面滚起来**看不到新条目**。实跑抓出两个必须同时成立的约束：

| 假说 | 验证 | 结论 |
|---|---|---|
| 阈值设太高（`VIRTUAL_THRESHOLD`） | 改到 20 条即触发 | 不是，320 条早就越过了 |
| 纯逻辑算错可见窗口 | 单测直接喂 scrollTop | 不是，逻辑层用例全绿 |
| IO root 绑错元素 | 观察 IntersectionObserver 的 root 是包裹 div | **是** |
| 占位行没登记 ref | 滚动到中段，占位仍占着位置不换真实行 | **是** |

真因两句：**`IntersectionObserver` 的 `root` 必须是真正滚动的那个容器**（本项目是
`.sv-task-detail`，不是外面那层包裹 div——包裹 div 自己不滚，任何行都永远「可见」，
观察器从不触发换页）；**占位 div 也必须挂 `:ref` 走同一个 `bindRow`**，否则它被滚进
视口时没人通知逻辑层「这里该换成真实行了」，条目就停在占位壳里。

**Why**：窗口化的正确性靠「谁滚 → 谁被观察 → 谁负责换成真行」这条链闭合。链上任何一环
指向了**不滚动的元素**，观察器都会静默退化成「全部可见 / 全部不可见」——它不报错、不
告警，DOM 数量统计甚至还是对的（占位确实生成了），只有人眼滚动时才发现空。这也是为什么
「DOM 节点数受控」这条断言不足以证明窗口化生效：**节点数对而内容不换**是典型案例。

**How to apply**：

- 接窗口化时先回答三个问题，写进注释：① 真正滚动的是哪个元素（找 `overflow: auto/scroll`
  的那一层，不是它的父级）？② IO 的 `root` 是否就是它？③ 占位行与真实行是否共用一个
  `bindRow` 登记 ref？
- 判据要落在**内容**上而不是数量上：滚动前后对比「首条可见条目的文本」，或断言
  「滚动后真实行 id 集合发生变化」。只断言「42 真实 / 279 占位」会漏掉本条。
- 已有 300+ 条轨迹的页面做验收更省事：TMSHOW 的实测口径是「初始 42 真实 / 279 占位，
  滚动到中段后 54 / 267」——**两个数字都要动**，只动一个就是本条的症状。
- 与 [[E147]] 同族：都是「量到的信号看起来对，但它描述的不是你以为的那件事」。
  区别是 E147 讲**时间**（过渡中间帧），本条讲**空间**（观察了错误的滚动容器）。

### 经验 E149 —— 旧原语被新用途复用时,必须重审它的隐含假设(2026-11-04 ATTFIX-1)

`api/characters.rs::parse_multipart` 是 2026 年早期为**角色卡上传**写的解析器。当时它的
全部调用方传的都是 UTF-8 JSON——几乎不可能包含 `\r\n--` 这串字节。于是这段代码里有
个当时完全够用的简化:

```rust
// 找内容的结束位置
let Some(next_rel) = find_subsequence(rest, b"\r\n--") else { break };
```

它只匹配 `\r\n--`,**不带 boundary**。协议上正确的终止符是 `\r\n--{boundary}`。
2026-11-03 的 ATTACH-1 把同一个解析器接到了「导入任意附件」上,第一次有用户的文件可能撞上
这个序列。CRLF 换行的 Markdown 就够了——front matter 的 `---` 后面紧跟换行,正文里任意
一处 `\r\n--` 都会让解析器认为「part 到此结束」,把后半截丢掉。实测 28 → 13 字节。

**Why**:这个缺陷之所以能活到被人工发现,是因为它**三层自洽**:

- 解析器截断内容 → 返回的 `Vec<u8>` 就是短的;
- 落盘大小取 `bytes.len()` → 记录的 `size` 也是短的;
- 前端展示读的就是库里的 `size` → 显示「12 B」;

没有任何一层拿真实文件长度去对账,所以没有一处报错、没有一条日志、没有一个测试会红。
用户唯一的信号是「附件内容对不上」,而这个信号要在他真的去读文件时才会出现。更隐蔽的是:
**把旧原语接到新用途上的那次改动,测试是绿的**——因为新用途的测试恰好用了不含该序列的
内容。复用本身没有错,错在没人重新问一遍「它当初为什么可以这么写」。

**How to apply**:

- **复用旧原语前,先找它的隐含输入假设**:写它的时候调用方传的是什么形态的数据?新用途
  会不会打破这个假设?(JSON → 任意文件、ASCII → 任意字节、小文件 → 25MB、单线程 → 并发)
- **解析器类代码的每个「简化匹配」都记着它省掉了什么**:`\r\n--` 与
  `\r\n--{boundary}` 的差异,在注释里写清楚「本解析器假设内容中不含该序列」比省下
  那几行更值钱。
- **边界不可判别时报错,不要截断**:截断产出的是「尺寸自洽、内容残缺」的数据,比 400 难查
  一个数量级。本条的修法里,同一处还补了「分隔符之后只能跟 CRLF 或 `--`」的协议校验——
  它把「内容里出现真实 boundary」从静默截断变成了可重试的 400。
- **测试要用真实形态的内容**:解析器的回归用例如果只用 `"abc"`,就永远测不到本条。按用途
  挑最刁钻的输入——CRLF 文本、含协议标记的字面量、边界长度文件、并发写同一目录。
- 与 [[E28]]（断言要能真的红）、[[E29]]（变异验证）一脉:本条的五条新用例全部做过变异验证,
  其中 ATTFIX-9 在缺陷形态下 8 次并发只落 3 个不同文件——能复现出错误的数量本身就是证据。
