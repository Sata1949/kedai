**修复前的问题（报告发现对应的代码事实）**

1. **KEDAI-03（P1）Windows 删除命令未进高危确认**：`del`/`erase` 落 `SENSITIVE_COMMANDS`
   （而 `rm`/`rmdir` 在破坏性级），命令级硬门只认 Destructive/Admin/ScreenInput → 任务白名单
   （`custom_authorized`）、Bypass 档与工具级显式授权可**静默执行** `del /q x`；`rd`（cmd 的 rmdir
   别名）完全未收录。
2. **KEDAI-04（P1）回退按工具名启发式选快照**：`pickUndoSnapshot` 只按 `tool_name` + 全局 max
   消息 id 选——点击较早一次同类调用恢复的是**最新一次**同类快照；无同名快照时还退到其他工具的
   快照。快照 id 直到 commit 才生成（消费端拿不到）、`tool_calls` 也不存快照 id（重载后拿不到）。
3. **KEDAI-05（P1）回退只逆操作单条却清后续快照**：`restore` 只读目标 payload 并只逆操作它，
   却按 `created_at >= 目标` 删除全部后续快照（同毫秒一并误删）——数据没回到所选时点，后续恢复
   依据却已消失；既有测试把「清后续快照」钉为预期且不断言文件状态。

**改了什么**

1. **KEDAI-03 提级**：`del`/`erase` 移入 `DESTRUCTIVE_COMMANDS` 并收编同族别名 `rd`（保留单一分类
   出处）——命令级硬门、任务模式拒绝、确认卡展示全部自动继承既有链路，未改裁决代码。诚实边界
   不变（词表不是安全边界，`Remove-Item` 等解释器变体不在清单，见遗留 UNDOFIX-L3）。
2. **KEDAI-04 身份绑定（最小方案 + 可匹配标识）**：快照 id **前移**到执行前生成（`SnapshotStager`
   持 id，commit 以同 id 落库并回传）；`undo_snapshots` 加 `call_id`/`run_id`（调用身份，可空
   不回填）；`tool_calls` 加 `snapshot_id`；SSE `ToolResult` 加性字段 `snapshot_id`——同一次执行
   的「快照行 / 事件 / 落库」三处共用同一 id。注册表新增 `execute_with_decision_meta`
   （既有 `execute(_with_decision)` 变薄委托，行为逐字节不变），仅引擎主执行路径走 meta 版；
   身份在 `execute_call`（run_id/call_id 的源头）构造并随快照落库。前端工具卡存 `snapshotId`，
   「回退到此处」只恢复该卡绑定的快照；绑定缺失（旧记录/开关未开）→ 按钮**禁用并解释**；点击时
   核对列表，已失效则不调用恢复 API、**不选替代目标**；`pickUndoSnapshot` 启发式删除。
   历史重载经 `tool_calls.snapshot_id` → `AgentTrace` → `restoreAgentTrace` 映射续上精确匹配。
3. **KEDAI-05 逆序恢复语义**：`undo_snapshots` 加**持久排序 `seq`**（写锁内 `max+1`，迁移对旧行
   按 `rowid` 回填=当时的执行顺序；毫秒时间戳同毫秒并列，不再作界定依据）；`restore` 取目标及
   同会话后续全部快照（`seq >= 目标`）**逆序（新→旧）逐条应用**——数据整体回到目标时点；恢复前
   对**整批预检**（payload 可解析/类型合法/文件路径/256KB 截断标志/气泡与记忆必要字段/变量树
   JSON 基线），任一条不通过即拒绝整批（**零改动零删除**）；全部成功后按**精确 id 列表**清理
   （不再 `created_at >=` 扫删——同毫秒不再误伤、批外新快照不受影响）；中途失败**保留全部快照**
   （逆操作各自幂等，修复原因后可原样重试）。并发：恢复入口进程内串行化；目标会话生成进行中
   → 409「请先停止生成再回退」（前端同款禁用）；跨会话同角色文件写冲突为登记边界（UNDOFIX-L1）。

## 2026-10-17 回退快照硬化批（复审 P1/P2：记忆快照精确绑定 / 恢复失败保留快照 / seq 降级回填）

**来源**：2026-10-17 对 `main = 62866b7` 的独立复审（REVFIX 批收口后）发现 1 条 P1 与若干 P2。
本批先修 P1 与最贴近数据安全的 P2：① `memory_write` 快照仍靠 `MAX(id)` 猜插入行，并发/去重/读失败
时会绑到无关记忆，回退可删错持久记忆；② 恢复的部分逆操作失败被宽松删除吞掉，随后仍清空快照并
返回「成功」；③ `seq` 只在首次补列时回填，用户退回旧版 exe 写入的 NULL 行再升级时永久 NULL；
④ 前端恢复失败不刷新历史、跨会话残留反馈与标记、批量回退只标被点卡片、无全局单飞门。

**P1 记忆快照绑定工具回传的真实行 id**

- 缺陷：`build_payload` 执行前记 `max_id_before`，`commit_staged` 执行后取「本角色 id 大于该值的
  第一行」当作本次插入。窗口期另一会话先插入、或 `MemoryService::insert` 命中去重（没有新行）、
  或基线读取失败返回 0 时，快照都会绑错行；逆操作按 id 直接删除 → 回退删除无关记忆。
- 修复：`MemoryService::insert_with_status` 返回 `(entry, created)`；`memory_write` 工具输出追加
  `id`/`created`（保留 `stored` 兼容）；快照构建不再读 `max(id)`，`commit_staged` 只认输出中的
  `id`，`created=false` 直接丢弃快照。`update_variables` 基线改走
  `SessionService::try_load_assistant_vars`（读失败不产快照），避免把空树写成基线。
- 判据：新增单测两条——窗口期他人先插入时快照 `inserted_id` 必须等于工具回传 id（旧实现实测绑到
  并发行的 1 而非目标的 2）；去重命中 `created=false` 不产快照。新增端到端一例：真实
  `memory_write` → 快照落库 → restore 删除记忆行。

**P2 恢复失败不得清恢复依据**

- 缺陷：`bubble_insert` / `memory_insert` 逆操作调用宽松删除（`delete_message` / `MemoryService::delete`
  吞 SQL 错误只返回 bool），`apply_inverse` 忽略返回值并继续；整批「成功」后清理事务删除全部快照。
  写库失败时用户看到回退成功，消息/记忆仍在，而快照已不可重试。气泡 UPDATE 分支也不检查
  affected rows，行在预检与更新之间消失会被静默当作成功。
- 修复：新增 `SessionService::try_delete_message` / `MemoryService::try_delete`（`Ok(false)` 仍表示
  「本来就不存在」的幂等成功，SQL 错误上抛）；`apply_inverse` 改用严格变体，错误使整批在清理前
  返回；`restore_bubble_row` 检查 `affected == 0` 并报错（重试会走「行不存在 → 插回」分支）。
- 判据：新增两条单测用 SQLite `BEFORE DELETE` 触发器确定性阻断删除——旧实现返回
  `Some(RestoreReceipt)` 且快照被清；修复后返回错误、消息/记忆仍在、快照保留。前端新增失败路径
  刷新断言与 404 中性化断言。

**P2 `seq` 降级写入的 NULL 回填**

- 缺陷：`ensure_undo_snapshots_restore_columns` 用 `had_seq` 门控回填；升级后的库被旧版 exe
  （不认识 `seq` 列）写入新快照时 `seq` 为 NULL，再升级因 `had_seq=true` 跳过回填，
  `COALESCE(seq,rowid)` 把两个 id 域混在一起排序/界定批次。
- 修复：每次迁移都执行 `UPDATE undo_snapshots SET seq = rowid WHERE seq IS NULL`；已有值不重写。
- 判据：扩展现有迁移用例——首次迁移后手工把一行 `seq` 置 NULL，再次 ensure 必须回填为 rowid
  （旧实现保持 NULL）。

**前端：失败态与跨会话状态收敛**

- 恢复失败（含 500「已恢复 X/Y」）也 `loadHistory`，让界面反映后端已应用的部分逆操作；

  `snapshotId`（历史重载后仍稳定）；批量恢复按列表前缀标记同批所有卡片。

## <a id="2026-10-18-glass1"></a>2026-10-18 彩窗主题真透明与性能收口批（GLASS-1）：整窗环境层 + 半透明玻璃面板 + 启动预挂载/主题预载 + 自适应档位

**症状**

- 彩窗主题名义上有半透明面板与多条 `backdrop-filter`，实际观感是完全不透明的拼片印刷面；
  主体边缘看不到外墙的彩色玻璃，WebGL 环境层几乎不可见。
- 启动揭幕、首次切到彩窗、打开设置/抽屉均有明显卡顿；UIQ-4 只做了截图与体积验收，没有
  FPS/long task 基线。

**根因（实测/计算样式）**

- **alpha 叠乘**：面板 = `rgba(...,.86)` × 白玻璃芯 `.84` × grisaille `.4` × mosaic `.86`，
  有效透过率约 0.19%；铅条仍不透明。单层“半透明”叠起来就是实色。
- **backdrop-filter 打在实底上**：顶栏/侧栏顶/模态头是 `#0e2a5f` 全不透明；面板被拼片覆盖。
  模糊只作用于元素背后，不模糊自己的背景图。
- **特异性**：`html[data-theme] .sv-canvas`（0,2,1）压过 scoped `.sv-canvas--ambient[data-v]`
  （0,2,0），且只清 `background-color` 未清 `background-image`，透明画布被主题拼片反压。
- **backdrop 可达性**：stage 级 canvas 在 `.sv-main` 内部，不可能成为侧栏/主栏的 backdrop；
  面板背后只有不透明石壳，必须把环境层提到 App 级。
- **启动**：`App.vue` 的 `SplashScreen v-if / 主界面 v-else` 让主界面在 1.6s splash 内完全不挂载，
  揭幕瞬间才首次挂载整套重型图层。
- **切主题**：`initTheme()` 同步写令牌、异步加载 CSS+字体；首次切玻璃时把主题 CSS/字体与全站重绘
  都压在点击帧。18px 模态 `backdrop-filter` 在“设置打开 + 切主题”场景另造 **159ms** 长任务。
- **持续开销**：大面积实时 blur 叠在 30fps 画布上；面板宽度过渡反复重分配 WebGL drawing buffer；
  遮罩打开时环境层不暂停。

**改了什么**

- **整窗环境层**：`App.vue` 在 `.sv-frame-col` 内、`.sv-body` 之下挂唯一 `AmbientField`（仅彩窗主题）；
  `ChatWindow` / `TaskBoard` 不再挂 stage canvas。`useActiveThemeId` 把主题注册表桥成 Vue ref。
- **真透明层级**：`.sv-main` / `.sv-sidebar` 降至 `rgba(250,246,232,.58)` + 中央 scrim；
  `.sv-canvas` / `.sv-taskboard` / `.sv-stage` 透明；顶栏/侧栏顶/输入区改半透明深蓝/白玻璃；
  模态改 `.68` tint 无实时模糊；大面积 grisaille/mosaic 图层删除，拼片只留外壳/按钮/气泡等小面积；
  玻璃主题关闭 `body::after` 噪点 multiply；移除 `background-attachment: fixed`。
- **动画与暂停**：`uiPrefs.overlayOpen` 汇总任一模态/抽屉；App 级与 stage 级环境层在
  splash/生成/任务执行/遮罩打开时暂停。`ResizeObserver` 尺寸变更 120ms 合并。
- **自适应档位**：新增 `visual/perfTier.ts` 与 `html[data-perf-tier]`；低档关闭全部实时 blur，
  环境层 20fps / 0.45 倍、shader 跳过第三次 fbm；high 档 30fps / 0.6 倍。新增 1.2MP 像素预算、
  `failIfMajorPerformanceCaveat:true`、`alpha:false`。
- **启动/切主题**：主界面在 splash 期间预挂载（`inert` + `aria-hidden`）；Splash 等待主题 CSS
  （3s 上限）；`theme/registry` 新增 `preload(id)`、`init()` 返回 Promise、切换期两帧抑制过渡；
  `builtin` 拆 CSS/字体；`UiSection` 先预载再原子切换并显示「切换中…」；high 档 idle 预载 CSS/环境层 chunk。

**为何这么改**

- 真透明不是把某一层 alpha 调低：必须同时降底色、去大面积拼片、修复特异性，并把环境层放到
  面板的祖先层级；否则面板背后永远没有可见内容。
- 性能优先：大面板/模态的实时 blur 在动画背景上是持续成本；本批把模糊面积缩到“背景已暂停”的
  小面积/抽屉，移动端与低档设备直接关闭。18px 模态 blur 的 159ms 长任务是直接证据。
- 启动卡顿的主因是首次挂载时机，不是 CSS 体积；预挂载 + 等主题 CSS 比单纯压缩 CSS 更有效。

## <a id="2026-10-18-wbconc"></a>2026-10-18 世界书并发收口批（WBCONC）：叠加保存 + 显式删除 + 新增行锁内重分配

**症状**

- 角色扮演进行中修改世界书（尤其 deep/agent 归档步同时写入）：用户打开条目编辑器后保存，
  窗口期内模型/卡脚本新写入的条目被静默删除；角色卡内嵌 `character_book` 的数组形态同样中招。
- 独立世界书并发 `create_trigger_entry` 可撞 uid 并互相覆盖；条目缓存填充与失效交错时，
  旧快照可能被写回刚清空的缓存；保存到已删除的书仍报成功；列表加载失败面板却显示「暂无世界书」。

**根因**

- `merge_entries_into` 以「视图内 uid」为保留集合（对象）或直接整组替换（数组），
  「未列出」被当成「删除」；编辑器快照与保存之间是分钟级窗口。
- 仅把删除改成显式 `removed` 仍不够：本地新增行 id = 草稿 max+1，窗口期模型也从同一 max 出发；
  保存时 raw 已有同号条目，服务端按「uid 已存在 = 更新」推断，会覆盖模型新条目。
- 提交 1 前的独立书写回是 `get → 内存改 → save_data_raw` 三步分离；条目缓存双检无代际；
  `save_data_raw` 不检查影响行数。前端 `resources.loadWorldBooks` 吞异常且不落状态，
  `WorldBooksModal.listLoadError` 因而不可能被触发。

**改了什么**

- 提交 1（`ad0f0cf`）：`WorldBookService::update_raw` 写锁事务收编 `update` / `add_entry` /
  `update_entry_content` / `create_trigger_entry` / PUT entries；`entries_gen` 代际计数拒绝
  写交错期间的旧快照落缓存；`save_data_raw` 对 0 行返回 None。
- 提交 2（`fe6bc96`）：
  - `merge_entries_into(entries, views, removed)`：**叠加视图 + 仅显式 removed 删除**；对象 map
    与数组形态同口径，未列出且未 removed 的条目保留；视图未承载字段（extensions 等）继续保留。
  - `max_entry_uid` / `assign_added_uids` 迁入 `parsing/world_book`；`added` 由前端基线差集给出，
    服务端在写锁事务内**无条件**重分配当前 max+1（不看 uid 是否已存在）。
  - `save_entries_merged` / `save_character_book` 返回提交后的合并视图；`SaveEntriesBody` 加
    `removed` / `added`（serde default，旧调用方向后兼容）；API 响应不再回显请求体。
  - 前端 `WorldBooksModal` / `PromptManager` 记录打开时基线，保存时算 removed/added，用响应刷新
    草稿与基线；本地空白行保留（GET 会过滤空条目）；`resources` store 新增 `worldBooksError`，
    面板加载失败不再误显示空态。
- 本提交（台账）：`功能.md` 补请求级快照 vs 工具实时视图语义、`tools:[]` 含 META 工具；
  `经验.md` E113；`遗留.md` §二十七 WBCONC-L1~L3 与 RL-5 结案；`scriptRunner.ts` 注释对齐
  消息级 lorebook 链路；契约文档已在提交 2 更新。

**为何这么改**

- 删除必须由客户端**显式**表达：服务端无法区分「用户删了」与「用户没加载到」。快照式全量回写
  在并发写入场景必然丢数据，加锁只能保证不互相覆盖，不能恢复被删除的条目。
- 新增行也必须显式：撞号时「存在即更新」的推断与「新行」语义直接冲突；用基线差集把
  用户意图（新增）传给服务端，才能安全重分配。
- 返回合并视图是闭环：用户保存后立即看到窗口期内他人写入，不必关闭再打开编辑器；
  同时前端基线随之刷新，避免下一次保存把新条目当成新增而反复换 uid。

## <a id="2026-10-18-startup-incremental"></a>2026-10-18 启动检测识别增量构建：start.ps1 分源比较 + 图形启动器三选一

## <a id="2026-10-19-launcher-double-prompt"></a>2026-10-19 启动器双重弹窗修复：单实例守卫 + 端口接管并入启动决策

**症状**

- exe 版（项目根 `Kedai.exe`）在「便携版过期 + 增量产物就绪」时连续弹出两个原生弹窗：
  先问端口上的旧实例，再问「启动测试版 / 重建便携版 / 直接启动当前便携版」。
- 双击图标后第一份启动器尚未画出窗口时再点一次，会叠出两份完全相同的检测弹窗。

**根因**

- 端口探测与构建检测是两条独立交互：`main()` 先 `confirm()` 端口接管，再 `msgbox()` 构建决策，
  两者同时成立时一次启动必然两次阻塞提问；且端口对话发生在产物校验之前，产物缺失时会先问一次再报错。
- 启动器没有单实例守卫：检测要递归扫描 `web/src`、`server-rs/src` 并读产物 mtime，
  窗口出现前的重复点击会起第二份进程，两份进程各弹一个窗。

**改了什么**

- `launcher/src/main.rs`：
  - 新增命名互斥体 `Local\Kedai-Launcher-Singleton`；第二份启动器静默退出，不再叠弹窗。
  - 端口只探测不提问（仅「被非 Kedai 程序占用」直接报错）；构建决策弹窗按需追加
    `port_takeover_note`（写明端口号与「会先结束旧实例」），用户选定启动方式后统一接管端口。
  - 只有在「没有构建决策可问」时才保留原来的端口接管确认；一次启动最多一个阻塞弹窗。
  - 产物校验提前到端口探测之前：产物缺失时只出「该跑构建」这一条错误。
- 测试：新增 3 例——互斥体第二持有者必须被拒；`needs_port_confirmation` 只在未展示决策时
  为真；接管说明只在端口忙时出现且含端口号与「先结束」。

**为何这么改**

- 两条路径都靠「同一时刻只允许一个提问者」解决：互斥体挡住并发实例，弹窗合并挡住同一实例
  内的连续提问。
- 端口接管说明并入决策而不是静默杀进程：用户仍能看到「会先结束旧实例」，不会误以为启动器
  在乱结束程序；这也与正式版自身「端口被旧实例占用时先结束再启动」的接管语义一致。

**验证（本机）**

- `cargo test --manifest-path launcher/Cargo.toml`：17 例通过（新增 3 例）。
- `cargo build --release --manifest-path launcher/Cargo.toml` 通过，产物复制到项目根 `Kedai.exe`。
- `tools/check-all.ps1 -LooseAudit`：20 段全部通过（EXIT 0），含 `cargo fmt --check` / clippy /
  workspace 测试、文档与契约/架构/计数门禁、前端 eslint / vue-tsc / vitest / vite build 与体积预算。
- 真实双击复核（2026-10-19 09:55，`Shell.Application.ShellExecute` 委托资源管理器，等价双击）：
  便携版过期 + 增量产物就绪时，400ms 间隔连发两次启动，6 秒后进程数 **1**、可见 `#32770`
  弹窗数 **1**（内容为增量三选一），启动器 exe 复核后仍存在。证据：
  `D:\kedai-bench-run\launcher-double-prompt-evidence\gui-probe.log` 与 `gui-probe.png`；
  `遗留.md` §二十八 LAUNCH-1 已结案。

## <a id="2026-10-24-sky1-deterministic-delivery"></a>2026-10-24 SKY-1 确定性下限 / SKY-4 / SKY-5：静态接线、单文件交付与补做复查

## <a id="2026-10-30-db7-ui-hint"></a>2026-10-30 DB-7 前段：双库分叉的 UI 可见性（提示条）

> 承接 2026-10-29 的「三类静默失败修复」中 DB-7 的**启动期日志告警**一步。该批收尾时
> 明确登记了边界：「`GET /api/bootstrap` 不带该信息，前端无提示」。本章补上 UI 侧。

**改了什么**

- **新端点 `GET /api/diagnostics/data-dirs`**（`server-rs/src/api/diagnostics.rs::data_dirs`）：
  复用既有的 `config::detect_split_data_dirs` 与 `config::split_dir_candidates`，
  响应 `{ data_dir, others: [{ path, evidence }] }`。`others` **恒为数组**（空 = 无分叉）。
  探测含文件系统访问与只读 SQLite 打开，放 `spawn_blocking`；任务失败时回 500 而不是
  返回空列表——把检测失败伪装成「没有分叉」正是本条目要堵的静默。
- **线格式组装抽成纯函数** `split_dirs_payload(selected, found)`：端点与单测共用一份，
  避免「单测验的是一套、端点发的是另一套」。
- **前端 API 层** `web/src/api/diagnostics.ts`：新增 `SplitDataDir` / `DataDirsReport` 类型、
  `getDataDirs()` 与形状闸门 `assertDataDirs`。闸门**先检查再取字段**（不用 `!!v && …` 的
  假值合并式判据），`others` 缺失或 `data_dir` 缺失一律抛错；脏条目（无 `path`）丢弃。
- **状态** `web/src/stores/uiPrefs.ts`：`splitDataDirs` + `setSplitDataDirs` + `dismissSplitDataDirs`。
  载荷用 camelCase 视图模型（`dataDir` / `others`），与线格式解耦——api 层形状演进只改
  `setSplitDataDirs` 一处。
- **展示** 新组件 `web/src/components/SplitDataDirsHint.vue`（`role="status"`，沿用全局
  `.sv-render-hint` 的 info 视觉，仅在其 scoped 块补「允许换行 + 左对齐」两条），
  `App.vue` 启动时调一次 `getDataDirs()` 并在顶部渲染。
- **测试**：后端 2 例单测（payload 保留 path/evidence 且顺序原样、空结果 `others` 为空数组）
  + 1 例集成（端点恒 200、`data_dir` 非空、`others` 恒数组、自身不出现在分叉列表）；
  前端 12 例（api 5 / store 3 / 组件 4）。

**为何这么改**

- **不并入 `/api/bootstrap`**：那条是鉴权握手路径，页面首个请求必走；把文件系统探测塞进去
  会让首屏多一次同步 IO 依赖，且 `bootstrap` 在 `security.rs` 里另有 loopback 校验与令牌桶
  限频语义，混入诊断载荷会把「拿 token」与「探测磁盘」两件事绑在一起。独立端点 + 前端
  并行拉取，检测失败只 `console.warn`、不影响启动。
- **每次请求重探而非缓存**：候选目录内容可能在进程存活期间变化（用户拷库、删掉另一套），
  缓存的提示会停留在过期事实上。代价是几次 `metadata` + 一次只读 SQLite 打开，只在启动调一次。
- **用 info 条而非错误条**：当前这套库本身是好的，分叉不是故障；给「重试」按钮更没有意义
  （没有可重试的动作）。故它可关闭、不重试，关掉即置 null 且不持久化——分叉状态可能变化，
  持久化会让用户永远看不到第二次提示。
- **必须逐条给路径**：「聊天记录没了」是用户看到的现象，「另一套库在 `C:\…\data`」才是能
  据以行动的事实。只显示「检测到多套数据目录」等于把问题原样丢回去。

## <a id="2026-10-31-sdc-residuals"></a>2026-10-31 SDC 批：SSRF 白名单化、孤儿快照清算、两表保留上限、合并逻辑引用重映射

> 承接「处理计划与遗留里的剩余任务」。从 `docs/计划.md`（44 条未启动）与 `docs/遗留.md`
> （约 16 条工程可做项）中挑出**判据已写清、不需产品裁定、不依赖真机**的一组，四项全部是
> 后端 Rust，相互独立、各自可回滚。

**改了什么**

- **3.5/T4 `is_public_ip` 白名单化**（`tools/agent_tools_search.rs`）：黑名单枚举改为
  `IPV4_SPECIAL` / `IPV6_SPECIAL` 两张自维护 IANA 特殊用途段表 + 位掩码判定，语义是
  「默认拒绝、只放行公网单播」。新增 `100.64/10`（CGNAT）、`192.0.0.0/24`、`192.88.99.0/24`、
  `198.18/15`、三段 TEST-NET、`2001::/23`、`3fff::/20`、`5f00::/16` 等段；IPv4-mapped IPv6
  递归走 IPv4 判定。零新依赖（`Ipv6Addr::is_global` 仍是 nightly-only，原方案本就证伪）。
- **UNDOFIX2-L1 孤儿快照**（`services/undo_service.rs` / `task_service/mod.rs` /
  `character_service.rs`）：任务引擎的 `task:{id}` 虚拟会话没有 `sessions` 行，快照写入侧
  直接跳过；`TaskService::delete` 按 `task:{id}` 精确清理，`CharacterService::delete`
  在该角色 sessions 被级联删除**之前**按会话 id 集合清一次。
- **3.8 两表保留上限**（`kaleido_state_service.rs` / `undo_service.rs`）：`kaleido_changelog`
  按会话保留 2000 条（与 `exec_audit`/`cu_audit` 同口径），`undo_snapshots` 按会话保留 200 条
  （回退是交互操作；单条 payload 上限 256KB）。写后裁剪，失败只告警不阻断。
- **UNDOFIX2-L3 剩余项**（`undo_service.rs`）：`replace` 多文件快照补齐**完整内容条目**上限 64 与总字节
  预算 4MB；超预算项标 `truncated:true` 并保留路径条目（restore 侧据此明确报「快照不完整」）。
- **UNDOFIX2-L2 合并逻辑引用**（`migration/merge.rs` / `conflict.rs` 未改）：新增
  `LOGICAL_REFERENCES` 声明两处非外键引用（`undo_snapshots.session_id` →
  `sessions.id`、`tool_calls.snapshot_id` → `undo_snapshots.id`），并入重映射列表；
  `dependency_order` 增加逻辑父表约束；合并事务内 `renumber_undo_snapshot_seq` 按
  `(session_id, created_at, 原 seq, id)` 重排 `seq`。

**为何这么改**

- SSRF 判定用黑名单必然是「补一个漏一个」：CGNAT 段既非 RFC1918 也不触发任何既有判定，
  会被当成公网放行到连接阶段。白名单语义把失败方向倒过来——漏登记的段默认被拒。
- `task:*` 快照是纯负债：restore 以 `sessions` 为权威，这类行永远恢复不了，只会在库里累积
  256KB 级的 payload。跳过快照比事后清理更彻底，删除侧清理覆盖升级前遗留。
- 两张只增表此前只在会话删除时清空（`undo_snapshots` 连这条都没有），长会话会无限增长。
- `replace` 的单文件上限挡不住累加：64 个 256KB 文件就是 16MB 常驻。
- 合并工具的两处逻辑引用是「schema 上不是外键、语义上是引用」的典型：不重映射会让源侧

**为何这么改**

- 旧格式用 US（`\u{1f}`）直接分隔字段，命令原文或命令输出含该字符就会错位。US 是普通控制字符，`printf 'a\x1fb'` 之类完全可以产出来。
- 在「长度前缀」与「base64」两个候选里取 base64：长度前缀只能解决请求侧，回执侧的 stdout/stderr 同样含任意字节，base64 一次把两侧都收掉，且两侧标准库都有现成实现。
- **首字段放版本号**是为了错误可见性：两侧版本不一致时（APK 与后端不同步），旧实现会静默错位解析出乱七八糟的字段，新实现直接报「协议版本不匹配」。这是本次唯一一处取舍——没有做隐式兼容回退，因为静默错位比报错更难诊断。

**验证**

- 桌面侧 `cargo test --lib services::exec`：**42 passed**（含 `wire` 6 例与 `android` 4 例）。
  - 判别性：`exec_request_roundtrips_with_control_characters` 用 `printf 'a\u{1f}b\u{1f}c'` 做往返，修复前该输入会被切成 5 段；`exec_result_roundtrips_with_control_characters` 同理覆盖回执侧。
  - `version_mismatch_is_rejected_loudly`：旧格式入参与旧格式回执都必须报「协议版本不匹配」。
- Android 目标：`cargo check --target aarch64-linux-android`（经 `acargo.bat` 注入 NDK 与 MSVC 宿主环境）**通过**。
- `cargo fmt --manifest-path server-rs/Cargo.toml` 与 `cargo clippy --all-targets -- -D warnings` 通过。
- 真实模型：本批为跨端编解码协议修复，不涉及模型生成链路，按 AGENTS.md 豁免条款执行。

**边界**

- **未做真机验证**：本批只证编译 + 桌面侧对拍。三档执行器的端到端确认仍属 `计划.md` 6.4 / `遗留.md` AND-3（需 root 真机或 Shizuku 设备）。
- **两侧必须同版本发布**：v2 不兼容旧 APK 与旧后端。混合版本会明确报错（而不是静默错位），但 Android 侧的执行能力会整体不可用——发布时前后端必须同批。

## <a id="2026-10-31-pc4-netstat"></a>2026-10-31 PC-4 批：端口接管解析改结构判据（本地化 netstat 不再静默失效）

> 来源：`计划.md` §三 PC-4——`src-tauri/src/lib.rs` 与 `launcher/src/main.rs` 均用 `line.contains("LISTENING")` 解析 `netstat -ano`。非英文 Windows 的 netstat 会把状态列本地化（如「侦听」），该路径下**端口接管静默失效**。

**改了什么**

- 两侧各抽出纯函数 `parse_netstat_listeners(text: &str, port: u16) -> Vec<u32>`
  （`launcher/src/main.rs` 与 `src-tauri/src/lib.rs`），原调用点改为调用它。
- 判据从「匹配 `LISTENING` 字面量」改为**列结构**：
  - 协议列 `TCP`/`TCPv6`/`UDP`/`UDPv6` 不随语言变化，用它剔掉表头与「活动连接」行；
  - 本地地址列以 `:PORT` 结尾（避免 `:13001` 误命中）；
  - **TCP 行显式排除连接态**（`ESTABLISHED` / `TIME_WAIT` / … + 简体中文形态）；UDP 行无状态列，末列即 PID。
- `tools/check-all.ps1` 新增 `cargo test (launcher)` 段（第 24 个 `Invoke-Stage`）。

**为何这么改**

- 本地化失效是这一类缺陷里最隐蔽的：功能在开发者机器上正常，到了中文用户的机器上「点退出后端还在跑」，且**没有任何报错**。
- 没有直接上 `GetExtendedTcpTable`（原计划的备选路线）：它要新增 `windows-sys` 特性面过 `check-lock-sync`，而省下的只是一次 `netstat` 进程派生——这条路径每次只跑一次（关闭时 / 启动接管时）。
- **首版实现踩了自己的坑**：只按协议列筛而不排除连接态，会把占着该端口的客户端短连接一起 `taskkill`。单测 `netstat_parse_ignores_headers_and_dedupes` 第一轮就转红（期望 `[8748]` 实得 `[8748, 12345]`），据此补了 `is_non_listening_state` 排除集。这条经验已写进函数文档。

**验证**

- `cargo test --manifest-path launcher/Cargo.toml` → **22 passed**（新增 5 例）。
- `cargo test --manifest-path src-tauri/Cargo.toml --lib` → **9 passed**（新增 5 例）。
- 两侧用例输入相同（本地化状态列 / 英文回归 / 连接态跳过 / UDP+IPv6 / 空与畸形），确保判据一致。
- `node tools/check-doc-claims.mjs` → OK（阶段数 23→24 已同步 `契约-协议与配置.md`）。
- 真实模型：本批为纯解析逻辑修复，不涉及模型生成链路，按 AGENTS.md 豁免条款执行。

**边界**

- 状态列的**排除集**是枚举：未知语言的本地化文案不在表里时按「监听」处理（与旧行为一致，不会更差）；新增语言若有实测反馈再补。
- 解析失败仍**静默跳过**（不弹「请手动结束进程」提示）：端口接管是兜底路径，弹窗会打扰更常见的「本来就没有残留」情形。该取舍留给后续按实测反馈决定。
- **新发现的缺口**：`launcher` / `src-tauri` 的单测此前从不在任何门禁里跑（`cargo test --workspace` 只在 `server-rs/` 下执行）。本批把 `launcher` 接进了 `check-all.ps1`（热态 1.1s）；`src-tauri` 因会连带重编 Tauri 依赖树仍未接，登记为 `遗留.md` §三 **TESTCOV-1**。
