## <a id="2026-11-01-ci-speedup"></a>2026-11-01 CI 提效批：Windows 档逐 step 量化 + 缓存与触发面重构

### 改了什么

**0. 修 launcher 单测的临时端口竞态（顺带发现的真缺陷）**

`launcher/src/main.rs` 的 `probe_reports_free_for_closed_port` 原实现：`bind(127.0.0.1:0)`
拿端口 → `drop(listener)` → 断言 `probe_port` 判 `Free`。`drop` 后端口立即回到系统临时端口池，
同文件另两个 probe 用例并发的 `bind(:0)` 可能马上拿回同一端口，于是 probe 连上那个监听者、
误判 `Occupied`。

- **实测失败率**：本机 4 个测试线程（对齐 CI runner 4 vCPU）跑 200 轮红 2 次；32 线程 20 轮红 1 次；
  失败点恒为本用例。修复后 4 线程 300 轮 + 32 线程 100 轮，**0 失败**。
- **CI 证据**：run `41309317403`（main push）的唯一红点就是这一步（2.6s 内判红），
  且失败输出被 `2>&1 | Out-Null` 吞掉，只剩一行 `throw 'launcher 单测失败'`。
- **修法**：改为「换端口重试 8 次，任一次判 Free 即通过」，真回归（Free 分支失效）会全红，
  不会因重试蒙混；`tools/check-all.ps1` 的该段**不再吞输出**。

**1. `cargo-audit` 改为缓存二进制 + 版本钉死（省 3~6 分钟）**

`.github/workflows/ci.yml` 新增 `env.CARGO_AUDIT_VERSION: '0.22.2'` 与独立缓存步骤
（`path: ~/.cargo/bin/cargo-audit.exe`，`key: cargo-audit-<版本>-<os>`），安装改带 `--version`。

**2. cargo 缓存瘦身 + restore-keys（稳住那 6 分钟波动）**

同一文件的三处调整：排除 `server-rs/target/debug/incremental`；key 只留
`server-rs/Cargo.lock` + `server-rs/Cargo.toml`（摘掉 src-tauri 两份清单）；
新增 `restore-keys: cargo-<os>-`。

**3. main 只跑轻量档 + 定时全量保鲜 + 超时（每个 merge 省一整轮）**

- `check`（全量）加 `if: github.event_name != 'push'` 与 `timeout-minutes: 45`，
  **job 名保持不变**（分支保护的 required checks 是 `check` / `check-ubuntu`）。
- 新增 `check-main`（`if: push && refs/heads/main`，`timeout-minutes: 20`；稳态约 93s，
  但 cargo-audit 缓存 miss 时要从源码装 376s、npm ci 抖动可达 2~3 分钟，10 分钟余量
  偏紧——一次超时就会把轻量档判红，比它要避免的问题更糟），
  跑 `./tools/check-all.ps1 -StaticOnly`。
- `on:` 新增 `schedule: '0 18 * * 0'`（每周日 18:00 UTC）。

**4. `tools/check-all.ps1` 新增 `-StaticOnly` 挡位**

只跑「与编译产物无关」的检查：文档三段 + 11 段纯 Node 静态检查 + 审计两段；
跳过 fmt/clippy/cargo test 与前端四段。**它优先于 `-SkipWeb`**，且**不改变
`-SkipWeb` / `-SkipRust` 的任何既有语义**（历史行为原样保留）。

**5. 台账**

- `docs/经验.md` 新增 **E144**（step 级数据 + 三条可复用结论）；E66 里过期的「30~50 分钟」加实测修正。
- `MAINTENANCE.md` §2 开关说明补 `-StaticOnly`。
- `docs/契约-协议与配置.md` 机械门禁段补 `-StaticOnly` 与 `check-main` 指向。
- `ci-linux.yml` 头注释里过期的「30~50 分钟」同步修正。
- `ci.yml` 全量档 step 名按**现行**阶段顺序重写（旧名是 2026-10-30 重排前的顺序）。

### 为何这么改

用 GitHub API 取三次真实 run 的 **step 级**计时（见下表），数据与「文档记的 30~50 分钟」
和「凭编译直觉猜的瓶颈」都对不上：

| step | PR 成功 `41307800763` | main 成功 `41302465747` | main 失败 `41309317403` |
| --- | --- | --- | --- |
| Cache cargo | 72s | 84s | 73s |
| **Install cargo-audit** | **196s** | **342s** | **364s** |
| Install npm deps | 31s | 52s | 52s |
| Build web | 7s | 12s | 10s |
| Local gates | 431s | 620s | 461s（红） |
| **合计** | **770s ≈ 12.9min** | **1148s ≈ 19.2min** | 995s ≈ 16.6min |

两条结论直接决定改法：

1. **「安装工具」是隐形大头**——`cargo-audit` 占 25%~37%，因为 `~/.cargo/bin` 从来不在缓存路径里，
   `Get-Command` 在全新 runner 上恒为假。这是唯一「完全消除而非摊薄」的项。
2. **同一份代码两次 run 差 6 分钟（Local gates 431s vs 620s）= 缓存命中率不稳**。
   根子是精确 key 的「全有全无」：改一次 Cargo.toml 就零复用。加 `restore-keys` 把它变成
   「总有部分复用」，同时排除体积占比过半却不被复用的 `incremental`。

缓存配额也查了：GitHub API 显示该仓库已用 **11.59 GB，超过 10 GB 单仓上限**，
其中 cargo 条目 5 条各约 2.1 GB（同名 key 因不同 scope 各存一份），会被 LRU 淘汰——
这正是「有时命中有时不命中」的机制来源。

「main 只跑轻量」的依据：PR 检查跑在 `refs/pull/N/merge` 上，**那棵树就是合并结果**，
全量已在 PR 阶段验过。但**定时全量不能省**——GitHub 的缓存作用域只允许 PR 还原
「当前分支」或「默认分支」的缓存，兄弟 PR 之间互相看不见；main 一旦不再编译又不加定时全量，
新 PR 会稳定冷编。

- **launcher flaky**：修复前 4 线程 200 轮红 2 次；修复后 4 线程 300 轮 + 32 线程 100 轮全绿。
- **云端实测**：改动前三次 run 的 step 级数据即上表（`D:\kedai-bench-run\ci-speedup-evidence\`）；
  改动后的实测见本节末尾「改动后的云端实测」。

### 边界与未做

- **不改** `-SkipWeb` / `-SkipRust` 的既有语义（会动到 pre-push、build.ps1 与既有文档口径）。
- **不做** sccache（计划 C-4 仍未启动，本批不顺手评估）、换链接器（经验 E140 已否决
  rust-lld，实测无差别）、动 `build.rs` 的 `rerun-if-changed`（E140 已证伪）。
- **不改** `check-all.ps1:307` 的 `-j 8`：它属门禁脚本而非 CI 配置，4 核 runner 上的最优并发
  需单独矩阵实验。
- `src-tauri` 单测仍未接入门禁（缺口见 `../遗留.md` §三 TESTCOV-1）。

### 改动后的云端实测（PR #82，run `41318719501`，2026-11-01）

同一个 head commit（`1e2d4ef`）跑了两次：attempt 1 是缓存**首次上传**（必然 miss），
attempt 2 是**稳态**（缓存已就位）。两次都 `success`。

| step | 改前基线（PR run `41307800763`，他人代码） | 改后 attempt 1（首次，缓存未建） | 改后 attempt 2（稳态） |
| --- | --- | --- | --- |
| Cache cargo | 72s | **0s** | 65s |
| Cache cargo-audit | —（无此步） | 1s | 1s |
| **Install cargo-audit** | **196s** | 376s（必然现编） | **1s** |
| Install npm deps | 31s | 50s | 51s |
| Build web | 7s | 10s | 9s |
| Local gates | 431s | 730s（冷编） | 569s |
| Post Cache cargo（上传） | 1s | **188s** | 0s |
| **job 合计** | **770s ≈ 12.9min** | 1391s ≈ 23.2min | **730s ≈ 12.2min** |

**关键结论（诚实口径）**：

1. **`Install cargo-audit` 196s → 1s，是本批唯一确定性的、可复现的大额收益**
   （省 3.25 分钟）。首次运行时它是 376s——因为缓存条目还不存在，这是设计上的必然
   一次性成本，不是缺陷。判据是 attempt 2 的 1s。
2. **总时长只从 12.9min 降到 12.2min（-5%）**，因为 Local gates 从 431s 变成 569s
   （+138s）。**这一项不能归因于本批改动**：`cargo test --workspace` 单段就占 374s、
   clippy 69.7s、vitest 69.8s，都是 Windows 4 核 runner 的固有编译/运行成本；
   基线那次 431s 落在不同的 runner 与负载上。两轮之间 Local gates 的差值（431 vs 569）
   与「缓存命中率」无关——两轮都是**部分命中**（cargo 缓存 65s 的恢复时间即证据）。
3. **`Cache cargo` 从 72s 变成 65s（稳态）**，说明 restore-keys 生效但没有立刻显著
   提速：本分支是首次用新 key 格式，缓存是从旧 key 通过 restore-keys 回退拿到的，
   cargo 仍需按 fingerprint 重编一部分。真正判据要等下一次 PR（那时 restore-keys
   会命中本批新建的完整缓存）。
4. **首次运行的 188s 上传开销**是缓存体积换来的成本。排除 `incremental` 后单条目
   应显著小于改前的 2.1 GB，但要等下一次 run 用真实字节数验证（`GET
   /repos/{owner}/{repo}/actions/caches`）。

**未达成的原始预期**：PR 全量 ≤10min 未达成（实测 12.2min）。原因是原预期把
「Local gates 431s」当作可优化项，而 step 级数据显示它是 4 核 runner 上
374s cargo test + 70s clippy + 70s vitest 的硬成本，与缓存策略无关。要压缩它
需要动测试并行度或缩小测试面，属另一类决策（见本批「明确不做」）。

**第三轮（`14335ae`，run `41324021309`，`success` 801s ≈ 13.3min）——复现性确认**：

| step | 基线 | attempt 2 | 第三轮 |
| --- | --- | --- | --- |
| Cache cargo | 72s | 65s | 78s |
| **Install cargo-audit** | **196s** | **1s** | **2s** |
| Local gates | 431s | 569s | 624s |
| **job 合计** | 12.9min | 12.2min | 13.3min |

第三轮把结论钉死了两件事：

1. **cargo-audit 缓存稳定生效**（1s / 2s，基线 196s、main 上 342~364s）。
2. **Local gates 的波动（431 → 569 → 624）与缓存策略无关**——三轮分别是不同
   runner 与不同时刻的负载。**这是 4 核 Windows runner 的固有编译成本**，本轮
   优化没有、也不打算改变它。任何把这些数字的差异说成「缓存命中率改善」的解读
   都是错的。

**合并后验证 `check-main`（run `41328562978`，main push，`success` 451s ≈ 7.5min）**：

| step | 耗时 |
| --- | --- |
| Set up job / checkout / Node / Rust | 2 / 7 / 9 / 14s |
| Cache cargo-audit | 0s（miss） |
| **Install cargo-audit** | **353s**（缓存 miss，main scope 首次） |
| Install npm deps | 50s |
| **Local gates 轻量档（`-StaticOnly`）** | **11s** |
| **job 合计** | **451s ≈ 7.5min** |

三点确认：

1. **触发面按设计生效**：该 run 里 `check` 为 `skipped`、`check-main` 为 `in_progress→success`。
   合并前实测 12.9min 的全量档不再在 main push 上运行。
2. **`-StaticOnly` 本身只 11 秒**——14 段静态检查 + 两段审计的实际开销，验证了轻量档
   主体极便宜；那 451s 里有 353s 是 cargo-audit 在 main scope 上的首次安装。
3. **把 `check-main` 超时从 10 分钟放宽到 20 分钟是必要的**：本轮 7.5 分钟已接近原
   10 分钟上限，而 main scope 的 `cargo-audit-0.22.2-Windows` 缓存本轮才建立
   （`created_at 2026-11-01T17:00:13Z`），**下一次 main push 起该步应回落到 1~2s，
   整档预计约 100s**。

**判据可复现**：`D:\kedai-bench-run\ci-speedup-evidence\` 存五份 step 级 JSON
（attempt1 / attempt2 / 第三轮 / check-main / 两条基线）与 `caches-after.json`。

## <a id="2026-11-02-glass-pane-1"></a>2026-11-02 拼接玻璃落地批（GLASS-PANE-1）：石棂骨架 + 菱形小片 + multiply 染色

**症状**

彩窗主题「石室与光」（`7a01329`）质感对了，但**把「拼接玻璃」整条删掉了**：
实测全界面 8 个带背景层的元素 `pattern: false` **100%**，没有任何多块玻璃结构，
跟用户要的「教堂拼接玻璃」不再一致。侦查稿 `docs/plans/GLASS-PANE-HANDOFF-2026-11-02.md`
记录了这一点并给出实现路径，但那份路径里的拼片源（48 块随机多边形）本批实测**不可用**。

**根因（两处，且都不是「配色不对」）**

1. **纹理缺骨架**：48 块完全随机的多边形读作碎玻璃／迷彩。真实彩窗的规整感来自
   **刚性石棂**（等距竖棂 lancet + 横档 + 上下窗框）先切出规则格子，格内才是玻璃片。
   只画「不规则」而没有骨架，必然碎。
2. **暗场景下不能靠盖暗罩压纹理**：拼片是「浅象牙底 + 黑铅条」，铺在近黑石梁上
   读作灰白纸片；再盖 0.50 暗罩只会得到一片均匀的灰，彩色感全部消失。

**改了什么**

- 新增 `--kg-panes-band`（560×80，`panes-band.svg` 约 500 节点 / 26 KB raw / 4.8 KB gz 源）：
  一个平铺周期含 **2 个光窗 + 2 条竖石棂 + 上下窗框**，格内是**错缝咬合的菱形 quarry**
  （行距 = 半高，这是咬合的充要条件），玻璃片 `fill-opacity` 0.6~0.7 让底色透上来，
  每片内有斜边高光与右下暗部，条带内嵌两条贯穿式斜向反光。
- **顶栏 → 横向拼片窗楣**：`background-blend-mode: multiply` 与深钴蓝 `#4a68a8` 相乘
  （不是盖暗罩），叠顶部天光 + `inset` 顶/底亮边 + 底部内阴影。
- **第 ⑦ 轮遗留处理**：给 AGENT / HTML-JS / 统计格 / 窄屏溢出菜单各垫
  `rgba(9,14,32,0.72)` 近黑玻璃 + 内侧金边，让控件从拼片里浮起来。
- **角色卡选中态 / 主按钮 → 宝石玻璃**：同一套 multiply 染色 + 四层结构
  （天光 / 柔光垫 / 染色层 / 拼片），主按钮染色用亮酒红 `#a8394f` 保住底色。
- **空态**：曾试三种装饰条（右栏拼片横带 / 两栏竖棂 / 底部窗槛），**均经用户裁定「太丑」撤掉**；
  最终不留任何装饰条，留白由**版式本身**解决——两栏撑满高度，只让「模式行」与
  「右栏页脚」各自 `margin-top: auto`，而不是整块 `space-between`。
- **顺带修掉 4 类真实缺陷**（均为实测抓出，非计划内）：
  1. **空态网格整个空转**：`grid-template-columns` / `gap` 写在 `.sv-start` 上，
     真正的 grid 容器是 `.sv-start-grid` / `.sv-task-start-grid`——4 处声明从未生效。
  2. **顶栏统计区 1.15:1**：`.sv-topbar *` 把文字刷暖白，统计格与溢出菜单底仍是
     `--sv-white`。改暗玻璃内嵌格并逐项翻暖白。
  3. **提示条 1.87:1 / 关闭键 1.16:1**：`.sv-render-hint` 是浅蓝底深蓝字，落到近黑
     石室上只剩 1.87；其 ✕ 还是白底配暖白字 1.16。改暗玻璃 + 透明暗底。
  4. **死选择器与死令牌**：`.sv-topbar .sv-token-cell` 删除（该类只在侧栏头）；
     `--kg-lead-soft` / `--kg-sapphire-lit` / `--kg-emerald` / `--kg-amethyst` 删除，
     `--kg-ruby` 启用为主按钮底色。
- 新增契约测试 `web/src/theme/stainedGlassCss.test.ts`（8 例）：拼片令牌存在性、
  **白名单制**的用点登记、**内容层严禁铺拼片**（本批最关键的回归守卫）、`!important` 为零、
  侧栏 `position` 只在桌面媒体查询内、空态列定义必须在真正的 grid 容器上、
  顶栏统计格必须有暗底、令牌表不留死条目。

**为何这么改**

- 拼片必须**分层使用**：装饰层（顶栏窗楣）与强调层（选中态/主按钮）可以，内容层一律素玻璃。
  只要拼片是背景，文字就必然跨越铅条——这条在侦查稿的七轮原型里被验证过两次。
  白名单制是为了让「以后谁觉得面板空就往上铺」这条路走不通。
- 用 multiply 而不是暗罩，是因为暗罩会同时抹掉彩色；multiply 保留「浅底→彩、黑线→黑」的
  相对关系，这正是暗室里看彩窗的样子。
- 空态不塞装饰条：装饰条只是在填缝，观感仍是「没做完」；撑满 + 按阅读节奏分散才是版式解法。

## <a id="2026-11-04-algo-1"></a>2026-11-04 算法热点优化（ALGO-1）：任务节点预算选择 O(n²)→O(n)

**改了什么**

`server-rs/src/services/prompt_kit.rs::select_segments_within_budget` 的预算判定，由「每推进一段
都对 `segments[keep_from..].kept` 与 `segments[..keep_from].omitted` 各做一次全量求和」改为维护
两个累计量：初始 `kept_total = Σkept`、`omitted_total = 0`，每省略一段即
`kept_total -= kept[i]`、`omitted_total += omitted[i]`。返回值 `keep_from`、两处错误文案、
`SegmentCost` 结构、唯一生产调用点（`task_engine/custom/step.rs`）均未改。

**为何这么改**

旧实现每轮全量求和，`keep_from` 最多推进 n 次即 O(n²)；n 是节点上游产出段数，custom 流程可达
几十~上百段。这是 2026-11-04 只读算法评估中「纯函数、零契约、零裁决冲突」优先级最高的一条：
不在计划「明确不做」，也不在遗留「接受不修」；遗留 PBT-1 实测证伪的是同文件的**链式 replace**
（0.042 ms），与本函数无关。

**验证证据**

- 新增 `budget_selection_matches_reference_implementation`：测试内保留优化前的 O(n²) 参考实现，
  对 `n=0/1/2/10/64/256` × 4 种头部 × 9 种预算 × 4 组确定性伪随机成本逐例比对
  `Ok(keep_from)` 与 `Err` 文本；新增 `budget_selection_keeps_when_exactly_at_budget` 锁 `<=` 边界。
- **变异验证**：把 `<=` 改 `<`、把 `kept_total -=` 改 `+=`，各红 3 例（边界 + 等价性 + 既有
  「最旧先省」），随后还原。
- `cargo test -j 8 --lib` 全绿；`cargo clippy --all-targets -- -D warnings` 通过；计数以
  `../../MAINTENANCE.md` §2 为准。

**真实模型实测**

`POST /chat/completions` 返回 `Invalid 'Authorization' header or token.`），与 TMSHOW-4 / ATTFIX

## <a id="2026-11-04-attfix-1"></a>2026-11-04 后端附件链正确性（ATTFIX 提交 1）：multipart 截断 / 批原子性 / 并发撞名

**需求**：2026-11-04 对同一基线（`13b3504`）做了两轮独立缺陷排查，得出 13 条真缺陷 + 1 条
口径冲突。本提交收掉其中**会损坏用户数据**的五条：ATTFIX-1 / 2 / 8 / 9 / 10。
执行稿 `docs/plans/ATTFIX-BUGFIX-PLAN-2026-11-04.md`，其余三批（轨迹缺口补拉 / 前端附件体验 /
followup 能力位）尚未开工，登记在 `docs/计划.md` 的 ATTFIX 条目里。

**改了什么**

1. **ATTFIX-1（P0）multipart 内容截断**（`api/characters.rs`）：内容终止符此前只匹配
   `\r\n--`、不带 boundary，内容里出现该序列即被静默截断（CRLF 换行的 Markdown front matter
   的 `---` 之后即中招，实测 28 → 13 字节），而落库的 `size` 也是截断后的值——三层自洽，
   无人报错。修法：终止符改为 `\r\n--{boundary}`；并新增协议校验「分隔符之后只能跟 CRLF 或
   `--`」，两者都不是说明内容里出现了真实 boundary，此时**报错**而不是截断。
   `parse_multipart` 由返回 `Vec` 改为返回 `Result<Vec, String>`，五个调用方（角色卡 / 世界书 /
   提示词预设 / 工具插件 / 任务附件）全部改为向上传播为 400。**这是本批唯一影响多端点的改动**，
   四个既有消费方套件全部复跑确认零回归。
2. **ATTFIX-2（P1）上传批次非原子**（`api/tasks/attachments.rs` + `task_service/attachments.rs`）：
   端点侧循环内 `?` 提前返回，已写入的行与文件不回滚，函数文档声称「整批失败」而实现造出
   「400 但已入库前 N 个」。修法：新增 `TaskService::store_attachments`，**先整批校验
   （空 / 25MB / 累计个数）再逐条写入**；个数上限按**整批**算（此前每个 `store_attachment`
   各自查库、批内不累加，一次传 12 个能全进——这是同一条缺陷的附带项）。
3. **ATTFIX-8（P2）legacy 附件段粘连**（`task_service/legacy_attachments.rs`）：
   `legacy_step_user_message` 用 `format!("{}{step_goal}", ...)` 把附件段末行与步骤目标粘成一句。
   修法：改为 `\n\n` 分隔；拼接逻辑提成纯函数 `join_step_user_message` 以便逐例单测
   （`legacy_summary_user_message` 与 `attachment_suffix` 本身无此问题，未动）。
4. **ATTFIX-9（P2）并发上传撞名**（`task_service/attachments.rs`）：`next_seq` 读目录取最大值 +1，
   两个并发请求算出同一 seq，`fs::write` 后者覆盖前者，库里两行指向同一物理文件。修法：新增
   `reserve_seq` 用 `OpenOptions::create_new` **原子占位**，撞名则 seq+1 重试（上限 64），
   拿到独占句柄后再写入。
5. **ATTFIX-10（P2）坏行静默跳过**（`task_service/attachments.rs`）：`list_attachments` 的
   `rows.flatten().collect()` 把读不出的行当不存在。修法：逐行 `map_err` 上抛（与同模块
   `scan_events` / `scan_trace` 同口径）；查询抽成静态 `select_attachments(&Connection)`
   以便内存库单测。

**为何这么改**

- **截断 vs 报错**：截断产出的是「尺寸自洽、内容残缺」的附件，用户唯一信号是「附件内容

## <a id="2026-11-04-attfix-2"></a>2026-11-04 轨迹缺口补拉（ATTFIX 提交 2）：分页拉全 + 游标语义收紧为「已连续覆盖」

**需求**：ATTFIX 执行稿 §二 提交 2。断线重连或 SSE 丢帧后，任务轨迹中间一段会永久消失，
用户切到档 2 / 档 3 时看到的是缺了几百条的断层，且**永远不会自愈**。

**缺陷是什么**（两处叠加，缺一不可）

1. **只拉一页**：`pullTraceGap` 没有 `loadTaskTrace` 那样的 `while` 分页循环，一次最多补 500 条。
2. **游标先推进**：`appendTrace` 在 `void pullTraceGap(...)` 之后同步把游标推到缺口之后那帧的
   seq；`pullTraceGap` 结束时又用合并后末条的 seq 覆盖一次。两处都跨过了尚未拉回的区间。

典型时序（执行稿已用脚本复现）：

```text
已见 seq=11 → 断线 → 收到 seq=700
  补拉只回 12..511(一页上限) → 游标落 700
  512..699 共 188 条永久丢失
  之后 seq=701 相对 700 连续 → 缺口检测再也不触发
```

**改了什么**

- `pullTraceGap` 改成与 `loadTaskTrace` 同构的分页循环：`TRACE_PAGE_LIMIT` 每页 500、
  `TRACE_MAX_ROWS` 总量封顶 2000、末条 seq 不推进即终止（防脏数据死循环）。
- **新增 `coveredSeqByTask`** —— 语义是「1..N 中间没有空洞的最大 N」，与「见过的最大的 seq」
  彻底分离。三条推进规则：`appendTrace` 只在 `trace.seq === covered + 1` 时前进；
  `pullTraceGap` 只按**自己覆盖到的位置**推进；追平后用 `advanceCoveredSeq` 把 `rows` 里
  已存在的大 seq 帧一并吞进来（否则下一帧会再触发一次一模一样的补拉）。
  原 `lastSeqByTask` 的语义已被完全取代，直接删除——**不保留两个游标**，避免以后再分叉。
- **翻页中途失败时保留已拉回的进度**：`collected` 搬到 `try` 之外、并入逻辑挪进 `finally`。
  原实现整批丢弃，一次失败会把已有进度也清掉，用户看到的空洞比失败前更长。

**为何这么改**

- 分页与游标必须**同时**修：只修分页，游标仍会在补拉返回前被推到 700，缺口照样丢；
  只修游标，一次最多补 500 条，超过一页的缺口仍会剩一半。
- 游标语义用独立的 Map 表达而不是在 `appendTrace` 里加分支判断：两个语义（见过 vs 连续覆盖）
  混在一个变量里，正是这条缺陷能长期存活的原因；分开之后每条推进规则都能被单测直接钉住。
- 失败保留部分进度：网络抖动应该是「少拉了一段」，不应该是「把已经拉到的也丢掉」。

**验证证据**

- `useTaskTrace.test.ts` → **27 passed**（新增 4 例）：
  - `缺口跨多页时全部拉回(只拉一页会漏掉中段)`：700 条逐条无空洞，第二页起点必须是 511；
  - `补拉失败时游标不前移`：一次失败后，下一帧仍能凭「已连续覆盖」重新触发，起点是 1 而非 50；
  - `补拉翻到第二页时失败 → 游标停在第一页末尾`：起点是 501，绝不跨到 700；
  - `补拉追平后游标推进到连续覆盖末端`：连续帧不再触发补拉。
- 全量 `npm test -w web` → **1978 passed / 180 文件**；
  `npm run build -w web`（含 vue-tsc 硬门禁）通过，`TaskBoard.js` 51.83 kB 仍在预算内。
- **变异验证（三条全做）**：
  ① 补拉退回只拉一页 → 跨页用例红（700 条只得 512 条）；
  ② 游标改用「合并后末条 seq」→ 第二页失败用例红；
  ③ `appendTrace` 退回「见过的最大 seq」→ 失败后重试用例红。
  第一版的「游标改用末条 seq」变异单独跑没红——因为分页修好后末条恰好等于 cursor；
  为此补了「第二页失败」这条用例才把两个语义真正区分开。这次尝试本身说明：**变异不红不等于
  代码对，可能只是没有用例站在那个分岔点上**。
- 门禁：`count-tests --check` 一致、`check-arch` 无新增违规、`check-file-size` 26 个基线无增长。

**计数回填**：前端 1930 → **1934**（180 文件不变；vitest 运行时 1947 → 1955）。
后端本批未改，2233（1720 + 513 / 88 文件）零变化。

不需要真实模型参与；同时上游凭据仍为 401（同提交 1），无可用的端到端环境。

## <a id="2026-11-04-attfix-4"></a>2026-11-04 followup 能力位（ATTFIX 提交 4）：提示词不再对续跑的 legacy 任务说谎

**需求**：ATTFIX 执行稿 §二 提交 4，也是该批次四提交的收口。

**缺陷**：附件注入的 `tools_available` 从 `task.task_mode` 反推
（`!matches!(task_mode, TaskRunMode::Legacy)`）。但 followup 由 `FollowupExecutor` 执行、
走 `run_agent_loop`，**工具集是完整**的。于是 legacy 任务续跑时，模型收到的附件段写着
「本模式没有文件读取工具,无法打开上述文件;若必须读取其内容,请改用 Solo / 多 Agent /
团队等带工具的模式」——而它其实能读。

这是 ATTACH-1-L2（2026-11-03，legacy 步骤生成说「用 fs_read 读取」但拿不到工具）的
**镜像case**：同一处能力位，同一类「提示词在说谎」，换了个入口重现。上一批修的是
「没工具却说有」，这批是「有工具却说没有」。

**改了什么**

- `spawn_run` / `run_inner` 各加一个 `executor_has_tools: bool`，能力位由**派发点**按
  **实际执行器**传入，不再从 `task_mode` 反推。三个入口的取值：

| 入口 | 值 | 依据 |
|---|---|---|
| `run_mode` | `!matches!(task_mode, Legacy)` | Legacy 是三步纯文本生成；其余五模式走工具循环 |
| `run_followup` | **`true`** | FollowupExecutor 走 `run_agent_loop` |
| `run_approved` | **`true`** | ApprovedPlan 逐步 + Solo/Multi/Team/Custom 整体，全部走 `run_agent_loop` |

- 注释写清「不能从 `task_mode` 反推」的原因（followup / approve 会用别的执行器，而
  `task_mode` 记录的是任务当初怎么跑的），避免下一个人按直觉改回去。
- `run_inner` 参数达到 8 个，加 `#[allow(clippy::too_many_arguments)]` 并注明理由：
  全是「本次派发的事实」，没有可归并的同类项，拆结构体只会把调用点摊得更散。

**为何这么改**

能力位描述的是「**这一轮执行**能不能用工具」，而 `task_mode` 描述的是「任务当初怎么跑的」。
两者在「同一任务换执行器重跑」的路径上必然分叉（followup / approve 都是这种路径）。
把它做成派发点的入参，等于让「谁真正知道答案」的人来回答——这是最不容易再次漂移的形态。

**验证证据**

- `cargo test --test task_attachment_injection -j 8` → **6 passed**（新增 1：
  `legacy_followup_is_told_it_has_read_tools`）。
- 全量 `cargo test -j 8` → **2206 passed / 0 failed**（93 个测试二进制全 ok）。
- `cargo clippy --all-targets` 零告警；`cargo fmt` 干净。

**取证过程中踩的两个坑（都已写进用例注释）**

1. **`prompt_summary` 会截断**：每消息 800 字 / 整体 4000 字，而附件段在 goal 末尾。
   用它断言会得到「根本没有附件段」的假象——第一版用例就是这么红的。改用 mock 的
   `[[floors]]` 钩子，它把**实际收到的完整消息**回显进产出。
2. **followup 的 goal 会拼上轮 result**：legacy 首轮结果里本来就带着一份「本模式无读取工具」
   的附件段（那段是对的）。整串匹配会把上轮的正确文案误判成本轮的错误——必须只对
   **最后一个** `## 附件` 起的片段断言。

这两个坑合起来说明：**断言「提示词里没有什么」时，先确认你断言的是哪一份提示词**。

前端本批未改，1948 / 180 文件零变化。

**真实模型实测**：本批是后端提示词文案的接线修正，正确性由确定性用例覆盖（用例直接

## <a id="2026-11-06-task-auth-tiers"></a>2026-11-06 任务工具三档授权（step / workspace / auto）：裁决、事件、端点、确认卡

### 2026-11-06 热修：Android 退出即 FORTIFY 闪退（0.4.5 发布资产）

**现象**：Redmi/marble（Android 15 / HyperOS 2.0.203.0）打开 Kedai 即闪退；
abort message 为 `FORTIFY: pthread_mutex_lock called on a destroyed mutex`，栈顶为
`libwebviewchromium_plat_support.so onDestroyed` → hwui `WebViewFunctor::~WebViewFunctor`
→ `__cxa_finalize` → `exit`。Android 14 模拟器（WebView 113）复现为 EGL display 析构的
同款 abort，证明根因与具体图形库无关。

**根因**：Tauri/tao 在 Android 事件循环结束时调用 `std::process::exit`；退出会执行 C/C++
静态析构，而 Java 主线程与 WebView 仍存活，hwui 的 `WebViewFunctorManager`（或 EGL display）
析构去锁一个已被 WebView 销毁的互斥量，Android 14/15 的 FORTIFY 直接 SIGABRT。三条路径
都中招：前端返回键退出（`app.exit(0)`）、启动失败（`app_handle.exit(1)`）、数据位置切换
（`AppHandle::restart` → `process::restart` → `exit`）。放大因素：Android 默认公共根
`Download/Kedai-Data` 的可写探针使用**隐藏文件名**，未授予「所有文件访问」时会假阳性，
真正的 `kedai.db` 建不出来 → 启动失败 → `exit(1)` → 崩溃。

**修法**：

- Android 退出统一 `libc::_exit` / Kotlin `Process.killProcess`；`RunEvent::ExitRequested`
  再兜一层，第三方插件调用 `AppHandle::exit` 也不会崩。
- 启动失败改原生 `MaterialAlertDialog` 展示错误；用户点「退出」走 `Process.killProcess`，
  不再由后台任务静默 `exit(1)`。
- 数据位置重启改 `AlarmManager + PendingIntent`，不再走 Tauri `process::restart`。
- 端口被非 Kedai 进程占用时自动改用系统分配的空闲端口。
- 数据根探针改用真实 `data/characters` 下的可见文件 + 真实 `kedai.db`，已有库只读检查、
  不删不改；公共根不可用则回退私有目录 + pending，不再硬选。
- 未授权「所有文件访问」且公共根已有不可读库时：启动日志
  `Android 默认数据根不能承载 SQLite: 已有数据库无法打开 … 回退应用私有目录`，
  服务在私有目录正常启动（PID 存活、无 `FORTIFY`）；授权后 `PUT /api/data-location`
  返回 `{"root":…,"migrated":true,"restart_required":true}`。

**验证**（证据 `D:\kedai-bench-run\android-exit-evidence\`）：

- 修复前（0.4.5 发布资产，SHA `fc725497…`）：正常退出与启动失败均出现
  `FORTIFY` + `Fatal signal 6 (SIGABRT)`；tombstone 保存为 `before-tombstone_06.txt`。
- 修复后：正常退出（返回键 ×4）进程消失，logcat 无 `FORTIFY`、crash buffer 为空；
  人为破坏 `kedai.db` 触发启动失败时，原生对话框显示真实错误，点「退出」后
  `Sending signal. PID: … SIG: 9`，无 abort；端口 3001 被占时日志
  `端口 3001 被占用,改用 36875` 并正常启动。
- 单元测试：`cargo test --lib probe` 8 passed；全量 `cargo test -j 8` **EXIT 0**。
