## <a id="2026-11-01-ci-speedup"></a>2026-11-01 CI 提效批：Windows 档逐 step 量化 + 缓存与触发面重构

### 改了什么

**0. 修 launcher 单测的临时端口竞态（顺带发现的真缺陷）**

`launcher/src/main.rs` 的 `probe_reports_free_for_closed_port` 原实现：`bind(127.0.0.1:0)`
拿端口 → `drop(listener)` → 断言 `probe_port` 判 `Free`。`drop` 后端口立即回到系统临时端口池，
同文件另两个 probe 用例并发的 `bind(:0)` 可能马上拿回同一端口，于是 probe 连上那个监听者、
误判 `Occupied`。

- **实测失败率**：本机 4 个测试线程（对齐 CI runner 4 vCPU）跑 200 轮红 2 次；32 线程 20 轮红 1 次；
  失败点恒为本用例。修复后 4 线程 300 轮 + 32 线程 100 轮，**0 失败**。
- **CI 证据**：run `41309317403`（main push）的唯一红点就是这一步（2.6s 内判红），
  且失败输出被 `2>&1 | Out-Null` 吞掉，只剩一行 `throw 'launcher 单测失败'`。
- **修法**：改为「换端口重试 8 次，任一次判 Free 即通过」，真回归（Free 分支失效）会全红，
  不会因重试蒙混；`tools/check-all.ps1` 的该段**不再吞输出**。

**1. `cargo-audit` 改为缓存二进制 + 版本钉死（省 3~6 分钟）**

`.github/workflows/ci.yml` 新增 `env.CARGO_AUDIT_VERSION: '0.22.2'` 与独立缓存步骤
（`path: ~/.cargo/bin/cargo-audit.exe`，`key: cargo-audit-<版本>-<os>`），安装改带 `--version`。

**2. cargo 缓存瘦身 + restore-keys（稳住那 6 分钟波动）**

同一文件的三处调整：排除 `server-rs/target/debug/incremental`；key 只留
`server-rs/Cargo.lock` + `server-rs/Cargo.toml`（摘掉 src-tauri 两份清单）；
新增 `restore-keys: cargo-<os>-`。

**3. main 只跑轻量档 + 定时全量保鲜 + 超时（每个 merge 省一整轮）**

- `check`（全量）加 `if: github.event_name != 'push'` 与 `timeout-minutes: 45`，
  **job 名保持不变**（分支保护的 required checks 是 `check` / `check-ubuntu`）。
- 新增 `check-main`（`if: push && refs/heads/main`，`timeout-minutes: 20`；稳态约 93s，
  但 cargo-audit 缓存 miss 时要从源码装 376s、npm ci 抖动可达 2~3 分钟，10 分钟余量
  偏紧——一次超时就会把轻量档判红，比它要避免的问题更糟），
  跑 `./tools/check-all.ps1 -StaticOnly`。
- `on:` 新增 `schedule: '0 18 * * 0'`（每周日 18:00 UTC）。

**4. `tools/check-all.ps1` 新增 `-StaticOnly` 挡位**

只跑「与编译产物无关」的检查：文档三段 + 11 段纯 Node 静态检查 + 审计两段；
跳过 fmt/clippy/cargo test 与前端四段。**它优先于 `-SkipWeb`**，且**不改变
`-SkipWeb` / `-SkipRust` 的任何既有语义**（历史行为原样保留）。

**5. 台账**

- `docs/经验.md` 新增 **E144**（step 级数据 + 三条可复用结论）；E66 里过期的「30~50 分钟」加实测修正。
- `MAINTENANCE.md` §2 开关说明补 `-StaticOnly`。
- `docs/契约-协议与配置.md` 机械门禁段补 `-StaticOnly` 与 `check-main` 指向。
- `ci-linux.yml` 头注释里过期的「30~50 分钟」同步修正。
- `ci.yml` 全量档 step 名按**现行**阶段顺序重写（旧名是 2026-10-30 重排前的顺序）。

### 为何这么改

用 GitHub API 取三次真实 run 的 **step 级**计时（见下表），数据与「文档记的 30~50 分钟」
和「凭编译直觉猜的瓶颈」都对不上：

| step | PR 成功 `41307800763` | main 成功 `41302465747` | main 失败 `41309317403` |
| --- | --- | --- | --- |
| Cache cargo | 72s | 84s | 73s |
| **Install cargo-audit** | **196s** | **342s** | **364s** |
| Install npm deps | 31s | 52s | 52s |
| Build web | 7s | 12s | 10s |
| Local gates | 431s | 620s | 461s（红） |
| **合计** | **770s ≈ 12.9min** | **1148s ≈ 19.2min** | 995s ≈ 16.6min |

两条结论直接决定改法：

1. **「安装工具」是隐形大头**——`cargo-audit` 占 25%~37%，因为 `~/.cargo/bin` 从来不在缓存路径里，
   `Get-Command` 在全新 runner 上恒为假。这是唯一「完全消除而非摊薄」的项。
2. **同一份代码两次 run 差 6 分钟（Local gates 431s vs 620s）= 缓存命中率不稳**。
   根子是精确 key 的「全有全无」：改一次 Cargo.toml 就零复用。加 `restore-keys` 把它变成
   「总有部分复用」，同时排除体积占比过半却不被复用的 `incremental`。

缓存配额也查了：GitHub API 显示该仓库已用 **11.59 GB，超过 10 GB 单仓上限**，
其中 cargo 条目 5 条各约 2.1 GB（同名 key 因不同 scope 各存一份），会被 LRU 淘汰——
这正是「有时命中有时不命中」的机制来源。

「main 只跑轻量」的依据：PR 检查跑在 `refs/pull/N/merge` 上，**那棵树就是合并结果**，
全量已在 PR 阶段验过。但**定时全量不能省**——GitHub 的缓存作用域只允许 PR 还原
「当前分支」或「默认分支」的缓存，兄弟 PR 之间互相看不见；main 一旦不再编译又不加定时全量，
新 PR 会稳定冷编。

- **launcher flaky**：修复前 4 线程 200 轮红 2 次；修复后 4 线程 300 轮 + 32 线程 100 轮全绿。
- **云端实测**：改动前三次 run 的 step 级数据即上表（`D:\kedai-bench-run\ci-speedup-evidence\`）；
  改动后的实测见本节末尾「改动后的云端实测」。

### 边界与未做

- **不改** `-SkipWeb` / `-SkipRust` 的既有语义（会动到 pre-push、build.ps1 与既有文档口径）。
- **不做** sccache（计划 C-4 仍未启动，本批不顺手评估）、换链接器（经验 E140 已否决
  rust-lld，实测无差别）、动 `build.rs` 的 `rerun-if-changed`（E140 已证伪）。
- **不改** `check-all.ps1:307` 的 `-j 8`：它属门禁脚本而非 CI 配置，4 核 runner 上的最优并发
  需单独矩阵实验。
- `src-tauri` 单测仍未接入门禁（缺口见 `../遗留.md` §三 TESTCOV-1）。

### 改动后的云端实测（PR #82，run `41318719501`，2026-11-01）

同一个 head commit（`1e2d4ef`）跑了两次：attempt 1 是缓存**首次上传**（必然 miss），
attempt 2 是**稳态**（缓存已就位）。两次都 `success`。

| step | 改前基线（PR run `41307800763`，他人代码） | 改后 attempt 1（首次，缓存未建） | 改后 attempt 2（稳态） |
| --- | --- | --- | --- |
| Cache cargo | 72s | **0s** | 65s |
| Cache cargo-audit | —（无此步） | 1s | 1s |
| **Install cargo-audit** | **196s** | 376s（必然现编） | **1s** |
| Install npm deps | 31s | 50s | 51s |
| Build web | 7s | 10s | 9s |
| Local gates | 431s | 730s（冷编） | 569s |
| Post Cache cargo（上传） | 1s | **188s** | 0s |
| **job 合计** | **770s ≈ 12.9min** | 1391s ≈ 23.2min | **730s ≈ 12.2min** |

**关键结论（诚实口径）**：

1. **`Install cargo-audit` 196s → 1s，是本批唯一确定性的、可复现的大额收益**
   （省 3.25 分钟）。首次运行时它是 376s——因为缓存条目还不存在，这是设计上的必然
   一次性成本，不是缺陷。判据是 attempt 2 的 1s。
2. **总时长只从 12.9min 降到 12.2min（-5%）**，因为 Local gates 从 431s 变成 569s
   （+138s）。**这一项不能归因于本批改动**：`cargo test --workspace` 单段就占 374s、
   clippy 69.7s、vitest 69.8s，都是 Windows 4 核 runner 的固有编译/运行成本；
   基线那次 431s 落在不同的 runner 与负载上。两轮之间 Local gates 的差值（431 vs 569）
   与「缓存命中率」无关——两轮都是**部分命中**（cargo 缓存 65s 的恢复时间即证据）。
3. **`Cache cargo` 从 72s 变成 65s（稳态）**，说明 restore-keys 生效但没有立刻显著
   提速：本分支是首次用新 key 格式，缓存是从旧 key 通过 restore-keys 回退拿到的，
   cargo 仍需按 fingerprint 重编一部分。真正判据要等下一次 PR（那时 restore-keys
   会命中本批新建的完整缓存）。
4. **首次运行的 188s 上传开销**是缓存体积换来的成本。排除 `incremental` 后单条目
   应显著小于改前的 2.1 GB，但要等下一次 run 用真实字节数验证（`GET
   /repos/{owner}/{repo}/actions/caches`）。

**未达成的原始预期**：PR 全量 ≤10min 未达成（实测 12.2min）。原因是原预期把
「Local gates 431s」当作可优化项，而 step 级数据显示它是 4 核 runner 上
374s cargo test + 70s clippy + 70s vitest 的硬成本，与缓存策略无关。要压缩它
需要动测试并行度或缩小测试面，属另一类决策（见本批「明确不做」）。

**第三轮（`14335ae`，run `41324021309`，`success` 801s ≈ 13.3min）——复现性确认**：

| step | 基线 | attempt 2 | 第三轮 |
| --- | --- | --- | --- |
| Cache cargo | 72s | 65s | 78s |
| **Install cargo-audit** | **196s** | **1s** | **2s** |
| Local gates | 431s | 569s | 624s |
| **job 合计** | 12.9min | 12.2min | 13.3min |

第三轮把结论钉死了两件事：

1. **cargo-audit 缓存稳定生效**（1s / 2s，基线 196s、main 上 342~364s）。
2. **Local gates 的波动（431 → 569 → 624）与缓存策略无关**——三轮分别是不同
   runner 与不同时刻的负载。**这是 4 核 Windows runner 的固有编译成本**，本轮
   优化没有、也不打算改变它。任何把这些数字的差异说成「缓存命中率改善」的解读
   都是错的。

**合并后验证 `check-main`（run `41328562978`，main push，`success` 451s ≈ 7.5min）**：

| step | 耗时 |
| --- | --- |
| Set up job / checkout / Node / Rust | 2 / 7 / 9 / 14s |
| Cache cargo-audit | 0s（miss） |
| **Install cargo-audit** | **353s**（缓存 miss，main scope 首次） |
| Install npm deps | 50s |
| **Local gates 轻量档（`-StaticOnly`）** | **11s** |
| **job 合计** | **451s ≈ 7.5min** |

三点确认：

1. **触发面按设计生效**：该 run 里 `check` 为 `skipped`、`check-main` 为 `in_progress→success`。
   合并前实测 12.9min 的全量档不再在 main push 上运行。
2. **`-StaticOnly` 本身只 11 秒**——14 段静态检查 + 两段审计的实际开销，验证了轻量档
   主体极便宜；那 451s 里有 353s 是 cargo-audit 在 main scope 上的首次安装。
3. **把 `check-main` 超时从 10 分钟放宽到 20 分钟是必要的**：本轮 7.5 分钟已接近原
   10 分钟上限，而 main scope 的 `cargo-audit-0.22.2-Windows` 缓存本轮才建立
   （`created_at 2026-11-01T17:00:13Z`），**下一次 main push 起该步应回落到 1~2s，
   整档预计约 100s**。

**判据可复现**：`D:\kedai-bench-run\ci-speedup-evidence\` 存五份 step 级 JSON
（attempt1 / attempt2 / 第三轮 / check-main / 两条基线）与 `caches-after.json`。

## <a id="2026-11-02-glass-pane-1"></a>2026-11-02 拼接玻璃落地批（GLASS-PANE-1）：石棂骨架 + 菱形小片 + multiply 染色

**症状**

彩窗主题「石室与光」（`7a01329`）质感对了，但**把「拼接玻璃」整条删掉了**：
实测全界面 8 个带背景层的元素 `pattern: false` **100%**，没有任何多块玻璃结构，
跟用户要的「教堂拼接玻璃」不再一致。侦查稿 `docs/plans/GLASS-PANE-HANDOFF-2026-11-02.md`
记录了这一点并给出实现路径，但那份路径里的拼片源（48 块随机多边形）本批实测**不可用**。

**根因（两处，且都不是「配色不对」）**

1. **纹理缺骨架**：48 块完全随机的多边形读作碎玻璃／迷彩。真实彩窗的规整感来自
   **刚性石棂**（等距竖棂 lancet + 横档 + 上下窗框）先切出规则格子，格内才是玻璃片。
   只画「不规则」而没有骨架，必然碎。
2. **暗场景下不能靠盖暗罩压纹理**：拼片是「浅象牙底 + 黑铅条」，铺在近黑石梁上
   读作灰白纸片；再盖 0.50 暗罩只会得到一片均匀的灰，彩色感全部消失。

**改了什么**

- 新增 `--kg-panes-band`（560×80，`panes-band.svg` 约 500 节点 / 26 KB raw / 4.8 KB gz 源）：
  一个平铺周期含 **2 个光窗 + 2 条竖石棂 + 上下窗框**，格内是**错缝咬合的菱形 quarry**
  （行距 = 半高，这是咬合的充要条件），玻璃片 `fill-opacity` 0.6~0.7 让底色透上来，
  每片内有斜边高光与右下暗部，条带内嵌两条贯穿式斜向反光。
- **顶栏 → 横向拼片窗楣**：`background-blend-mode: multiply` 与深钴蓝 `#4a68a8` 相乘
  （不是盖暗罩），叠顶部天光 + `inset` 顶/底亮边 + 底部内阴影。
- **第 ⑦ 轮遗留处理**：给 AGENT / HTML-JS / 统计格 / 窄屏溢出菜单各垫
  `rgba(9,14,32,0.72)` 近黑玻璃 + 内侧金边，让控件从拼片里浮起来。
- **角色卡选中态 / 主按钮 → 宝石玻璃**：同一套 multiply 染色 + 四层结构
  （天光 / 柔光垫 / 染色层 / 拼片），主按钮染色用亮酒红 `#a8394f` 保住底色。
- **空态**：曾试三种装饰条（右栏拼片横带 / 两栏竖棂 / 底部窗槛），**均经用户裁定「太丑」撤掉**；
  最终不留任何装饰条，留白由**版式本身**解决——两栏撑满高度，只让「模式行」与
  「右栏页脚」各自 `margin-top: auto`，而不是整块 `space-between`。
- **顺带修掉 4 类真实缺陷**（均为实测抓出，非计划内）：
  1. **空态网格整个空转**：`grid-template-columns` / `gap` 写在 `.sv-start` 上，
     真正的 grid 容器是 `.sv-start-grid` / `.sv-task-start-grid`——4 处声明从未生效。
  2. **顶栏统计区 1.15:1**：`.sv-topbar *` 把文字刷暖白，统计格与溢出菜单底仍是
     `--sv-white`。改暗玻璃内嵌格并逐项翻暖白。
  3. **提示条 1.87:1 / 关闭键 1.16:1**：`.sv-render-hint` 是浅蓝底深蓝字，落到近黑
     石室上只剩 1.87；其 ✕ 还是白底配暖白字 1.16。改暗玻璃 + 透明暗底。
  4. **死选择器与死令牌**：`.sv-topbar .sv-token-cell` 删除（该类只在侧栏头）；
     `--kg-lead-soft` / `--kg-sapphire-lit` / `--kg-emerald` / `--kg-amethyst` 删除，
     `--kg-ruby` 启用为主按钮底色。
- 新增契约测试 `web/src/theme/stainedGlassCss.test.ts`（8 例）：拼片令牌存在性、
  **白名单制**的用点登记、**内容层严禁铺拼片**（本批最关键的回归守卫）、`!important` 为零、
  侧栏 `position` 只在桌面媒体查询内、空态列定义必须在真正的 grid 容器上、
  顶栏统计格必须有暗底、令牌表不留死条目。

**为何这么改**

- 拼片必须**分层使用**：装饰层（顶栏窗楣）与强调层（选中态/主按钮）可以，内容层一律素玻璃。
  只要拼片是背景，文字就必然跨越铅条——这条在侦查稿的七轮原型里被验证过两次。
  白名单制是为了让「以后谁觉得面板空就往上铺」这条路走不通。
- 用 multiply 而不是暗罩，是因为暗罩会同时抹掉彩色；multiply 保留「浅底→彩、黑线→黑」的
  相对关系，这正是暗室里看彩窗的样子。
- 空态不塞装饰条：装饰条只是在填缝，观感仍是「没做完」；撑满 + 按阅读节奏分散才是版式解法。
