## 聊天主链路

角色扮演(文学创作)会话的主链路是「一次发送 → 上下文装配 → LLM 流式生成 → 落库 → SSE 回推」,
`/api/chat/send` 是唯一入口,一次请求走完 Agent 引擎全流程。

**现状能力**

- **端点与分支**:`POST /api/chat/send` 解析请求体(空消息 400)→ 无 `session_id` 时
  `ensure_session` + `seed_first_message` 补开场白 → 引擎并发预检(`engine.is_active`,冲突 409)
  → 生成参数组装(请求体优先、回退运行期设置;`max_tool_rounds` 默认 32)
  → `pending_runs` 原子占位(先于任何消息写入)→ 三路分支:**重生成锚点**(校验末条 assistant)、
  **重发锚点**(校验末条 user 且正文一致)、**常规落 user 消息**(`extra` 带 ts 与 prompt_tokens)。
- **模式归一**:`agent` / `deep` / `custom`,缺省 `fast`;`custom` 分支取当前启用流程、
  `validate`、过滤 disabled 步骤后快照下发。
- **参数安全上限**:请求体参数有硬上限校验(65536 / 1048576 两档),越界拒绝而非截断。
- **字数注入联动**:简单模式「字数」项启用时自动上调 `max_tokens`(`output_budget_for_word_count`),
  防思考模型把正文预算烧在思考上。
- **占位生命周期**:`pending_runs` 的登记与清理由 `PendingRunGuard`(drop 守卫)承担,
  引擎 panic 也会清理——不再出现「一次 panic 后该会话永久 409」。
- **SSE 管线**:handler 建 `mpsc::channel::<SseEvent>(1024)`,`tokio::spawn(engine.run(..))`,
  SSE 响应以 `KeepAlive 30s` + `no-cache` 输出。事件类型:
  `token`(文本片段)、`step`(Agent 步骤)、`tool_call` / `tool_result`、
  `tool_authorization_required`、`vars`(变量树同步)、`interrupted`、`retry`(上游重试中提示,
  携带本次尝试/上限/原因,非终态)、`error`(含 code/retryable)、
  `finish`(含 usage)、`task`(任务模式事件,前端仅透传)。
- **中断与抢占**:同会话旧 run 在引擎入口先 `abort()`,再登记新 run;中断通过
  `watch::channel<bool>` 中止标志贯穿全链路;`finish_run` 按 run_id 清理登记(旧 run 不删新 run)。
- **收尾顺序纪律**:assistant 消息落库**必须先于** `Finish` 事件(消除前端 `loadHistory` 竞态);
  随后依次是角色卡后端脚本执行、其余作用域落盘、契约运行态提交、`Finish{usage, content}`、
  用量统计(`session_usage` + `global_usage`)。
- **swipes 版本**:重生成走 `upsert_regenerated_message`,版本数组落 `extra.swipes`,
  `POST /api/chat/messages/{id}/swipe` 切换版本;历史投影取当前版本进入上下文。
- **配套端点(已实现)**:`/api/chat/stop`、`/api/chat/history`、会话 CRUD、
  `sessions/{id}/truncate`(保留锚点删其后)、`sessions/{id}/regreet`(重生成开场白)、
  `/api/chat/clear`、`/api/export/chat` 与 `/api/import/chat`(SillyTavern 兼容)、
  `/api/chat/generate-raw`(角色卡资源页作者脚本的一次性非流式生成桥,不写会话)、
  `/api/chat/sessions/{id}/undo` + `/api/undo/{id}/restore`(快照回退)。

**权威来源**:`server-rs/src/api/chat.rs`(`send` / `generate_raw_budget` / `PendingRunGuard`)、
`server-rs/src/agents/engine/mod.rs`(主流程与收尾)、`server-rs/src/agents/engine/run_finish.rs`;
文档小节 [优化实施方案-2026-09](archive/2026-09-16-consolidation/优化实施方案-2026-09.md) 第一篇第 2 章

## 上下文工程与压缩

上下文装配是「每轮重新算前缀、但前缀逐字节稳定」的设计,压缩在装配之前发生。

**现状能力**

- **装配顺序(函数级)**:`collect_context` 阻塞池读角色卡/历史/压缩摘要 → 历史投影
  (重生成取当前 swipes 版本)+ snip → 世界书条目收集/分离/分组/渲染 → mvu 状态块生成 →
  产出只读 `CollectedCtx`;`finalize_messages` 做
  `build_llm_messages_with_position` 六层拼装(系统提示 / 世界书常态位 / 注入 / 历史 /
  GENERATE 位 / @INJECT)→ 运行时主提示词前置 → **摘要槽 → 记忆槽 → 召回槽**
  (`insert_summary_slot` → `insert_memory_slot` → `insert_recall_slot`,后者**有命中才插**)插入 →
  `trim_to_context` 按预算裁剪 → 发送统计落宏变量。
- **前缀分层**:消息组装固定为「system(静态)→ 摘要槽 → 记忆槽 → 召回槽 → 尾部历史(只追加)」;
  同会话两次构建的公共前缀逐字节一致(有回归测试护航),使 provider 侧前缀缓存可命中。
  概率门控与随机命中不扰动该前缀(构建侧有不变式测试锁定:常驻条目进 system 前缀且不参与概率,
  触发条目进尾部注入区)。
- **缓存感知压缩**:每轮 LLM usage(含 DeepSeek `prompt_cache_hit_tokens` / OpenAI
  `cached_tokens`)落 `llm_requests` 表;`GET /api/diagnostics/cache` 报告命中率、费用估算与
  **四级水位**(soft / snip / compact / force);前端「优化」弹窗内 `CacheHealthPanel` 展示。
- **压缩本体**:`agents/engine/compaction.rs` 做**可逆投影 + LLM 摘要**——原文消息永不删除,
  摘要落 `session_compactions` 表,删摘要行即恢复完整历史。触发方式:
  manual(`POST /api/chat/compact`,清除走 `/api/chat/compact/clear`)或 auto(历史 token 超阈值
  时在 plan 之后、`collect_context` 之前执行);设置项 `compaction_mode` / `compaction_threshold`。
- **阶梯压缩(snip)**:LLM 摘要前先做零成本 snip——陈旧超长工具结果压成占位符、
  错误特征保留、尾部原文保留;`compaction_keep_recent`(默认 4)与 `compaction_snip_bytes`
  (默认 8192)可配置。
- **摘要槽增量化**:摘要改追加式增量(旧摘要字节冻结),压缩后缓存只 miss 尾部。
- **工具历史裁剪**:`run_tool_loop` 每轮 `execute_generation` 前执行 `trim_tool_history`——
  按「assistant(带 tool_calls)+ 后续连续 tool 消息」分轮,keep-recent + 预算双闸门在**轮**粒度操作:
  超出 `tool_history_keep_rounds`(默认 4,钳 1..=32)的最老轮工具结果原地替换为短摘要
  (幂等标记,已摘要轮凭前缀跳过、不占 keep 名额),该轮 assistant 的 `reasoning_content` 一并清空;
  估算总 token 超 `tool_history_budget_tokens`(默认 16384,0 = 禁用预算闸门)时继续摘要至达标;
  保底最近 1 轮始终完整;`tool_calls` 与 `tool_call_id` 全部保留以维持严格后端要求的配对。
- **token 计数口径**:`count_message_tokens` 计入 `tool_calls` 的 name/arguments
  (新增 `count_single_message_tokens` 统一口径),token 计数按 (编码, 文本哈希, 长度) 缓存;
  裁剪侧配套 `reclaim_round_arguments` 回收参数占位(占位保持**合法 JSON**,id/name 保留);
  `trim_tool_history` 返回 `ToolHistoryTrimOutcome`,未达标记走 warn 而非静默。
- **工作状态锚点**(2026-09-30 批次 3,HARNESS3-3):写类与命令类工具(`fs_write`/`fs_edit`/
  `write`/`replace`/`create` 取 `path`,`bash` 取 `command` 首行)被摘要化或被回收参数时,
  **锚点留在占位里**——长任务跨压缩后模型仍知道「改过哪些文件、跑过什么命令」,不会重复读、重复改;
  名单与键名的单一出处在 `tools/tool_sets.rs::state_anchor_arg`(见本文件「十九」)。
  锚点不豁免摘要:整轮结果与参数照旧回收,否则重开历史无界膨胀的口子。
- **裁剪兜底**:压缩后仍超预算时 `trim_to_context` 从最早历史向前裁剪,系统层与世界书常态层不动;
  极端兜底分支按「1 token ≈ 2 字符」保守起步 + 真实 tokenizer 复测,仍超预算则按比例收缩一次。
- **跨会话记忆蒸馏**的注入侧在本章(记忆槽),蒸馏本体见「记忆」章。

**权威来源**:`server-rs/src/agents/engine/compaction.rs`(`maybe_compact` / `snip_tuples` / `should_snip`)、
`server-rs/src/agents/engine/messages/{build,trim,inject}.rs`(`trim_tool_history` /
`reclaim_round_arguments` / `insert_summary_slot` / `insert_memory_slot` / `protected_head_len`)、
`server-rs/src/services/cache_diagnostics.rs`、`server-rs/src/services/token_service.rs`;
文档小节 [优化实施方案-2026-09](archive/2026-09-16-consolidation/优化实施方案-2026-09.md) 第一篇第 3、4 章、
第 23 步链路,`../MAINTENANCE.md` §14「上下文压缩」「缓存感知压缩管线」,
[perf-baseline](archive/2026-09-16-consolidation/perf-baseline.md) §五(P0-1 两项与 P1-2)。

## 世界书与提示词注入

世界书(World Info)、正则脚本与三层注入位(@INJECT / GENERATE / RENDER / 楼层)构成提示词注入面。

**现状能力**

- **来源两类**:独立上传世界书(SillyTavern 导出格式,顶层 `entries` 对象或数组,可绑定角色、空=全局)
  与角色卡内嵌 `character_book.entries`(兼容 V2 顶层与 V3 `data.character_book` 两种布局)。
  原始 JSON 无损保留在 `world_books.data_raw`。
- **匹配算法**:扫描池只取 `role=="user"` 的历史消息(assistant 文本不触发);逐条目
  disabled 跳过 → `@@` 装饰器(`@if`/`@unless` 用 EJS 白名单求值,失败容错为照常注入;
  `@var`/`@set` 解析存 `decorators`)→ `constant` 恒注入;
  **正则优先**(`use_regex` 且编译成功),否则 `keys` + `keys_secondary` 并列子串匹配
  (大小写按 `case_sensitive`);`use_probability` 时按纳秒 `%100 < probability` 门控。
- **扫描窗口 `scan_depth`**:关键词匹配只扫最近 N 条用户消息(0/负 = 全部历史);
  SillyTavern 语义正确落地——**`scan_depth` 是独立字段**(`extensions.scan_depth`),
  与「插入深度」`depth`(position=atDepth 用)语义分离,两条路径收敛到共享函数
  `scan_window_len`(优先 / 兜底 / 0 / 封顶四态);显式 `scanDepth` 覆盖 `depth` 兜底。
- **注入位置**:`WorldText{constant, triggered}` 两组——常态并入 system(显式 `role` 则作独立消息);
  激发默认追加**最新 user 消息尾部**(前缀缓存友好),`role=assistant` 作独立消息,
  `role=system` 钳制为 user。排序 `position → order → id` 稳定升序。
- **条目内容渲染**:每条命中 content 过一遍 EJS 渲染(`render_assistant_content_with`),
  渲染为空不注入。
- **上传自动规范化**:兼容酒馆变体——关键词字段名 `keys/key/keywords/keyword` 与逗号分隔字符串、
  `constant` 兼容字符串/数字并支持缺失时自动判定(无关键词无正则 → 常驻)、
  `role` 缺失即「自动」(常驻→system、激发→user);上传响应附转换统计 `conversion`。
- **机制自检**:世界书窗口「检查自动分配机制」按钮 / `GET /api/world-books/auto-assign-check`
  一键验证条目解析、属性自动分配、转换链路。
- **条目编辑与缓存**:条目编辑视图(含正则标记)、全量回写、新增空条目、角色卡内嵌条目读写;
  世界书条目按 character_id 缓存,5 条写路径全部失效;`save_data_raw` 随内容重算 `entry_count`。
- **@INJECT**:消息级精确插入(`pos` / `target` / `regex`),实现于 `messages/inject.rs`,
  协议见 [inject-protocol](archive/2026-09-16-consolidation/inject-protocol.md)。
- **GENERATE / RENDER 内容注入**:`[GENERATE:BEFORE/AFTER]`、`{idx}`、`REGEX` 三种内容注入,
  已在引擎挂载并有测试覆盖,协议见 [generate-render-protocol](archive/2026-09-16-consolidation/generate-render-protocol.md)。
- **EJS 兼容**:世界书条目中的 `<% %>` / `<%= %>` / `<%_ _%>` 按当前变量状态渲染;
  内建 `getvar/setvar/addvar`、`Math`、数组/字符串方法、if/for/箭头函数等 JS 子集;
  `<#escape-ejs>` 块用控制字符占位符转义;自研解释器带循环步数/墙钟预算与解析深度守卫。
- **正则脚本(`regex_scripts`)**:AI 输出中的占位符/变量标记替换为显示 HTML(如状态栏卡片),
  前端可开关;匹配与转义顺序为「先在原文匹配脚本 → 对 AI 输出整体 HTML 转义 →
  仅把命中片段还原为脚本自带内容(作者可信)」,`<script>` 源码提取后由沙箱 iframe 执行并受授权门禁。
- **提示词注入(三层)**:简单模式四项(字数 / 转述 / 对话 / 视角,按可调顺序合成一条拼入 system 末尾,
  支持酒馆宏);禁词库(自由编辑「禁词 → 替换词」映射,替换词留空 = 删除);
  复杂模式**楼层系统**(仿 SillyTavern Prompt Manager:角色/位置/深度/拖拽排序,
  可导入酒馆预设)。配置持久化 `<数据目录>/prompt_floors.json`。
- **LAST_SEND / LAST_RECEIVE 统计变量**:引擎收尾写入会话宏,模板可读;
  `POST /api/settings/prompt-preview` 可预览最终提示词(不发请求)。

## 角色卡兼容

SillyTavern 生态原生兼容是**解析层(L1)**的硬承诺:既有酒馆资产(角色卡 / 世界书 / 变量与输出协议)原样可用。
它不构成产品定性——Kedai 定性为通用 LLM 智能体 harness,角色扮演(文学创作)与任务工作台是它的双顶层模式。

**现状能力**

- **角色卡**:支持 V2/V3 规范(`.png` tEXt 内嵌 或 独立 `.json`),**未知字段无损保留**
  (原卡存 `data_raw`);上传 **30MB** multipart(外层 body 上限 35MB);列表接口不返回 `data_raw`;
  `tools/inspect-card.mjs` 提供结构检查。
- **开场白**:`first_mes` 自动识别,「编辑提示词」弹窗可编辑,随卡保存在 `data_raw` 中,
  新建会话时作为角色第一句话;留空表示无开场白;`sessions/{id}/regreet` 可重新生成开场白。
- **角色卡内嵌世界书**:兼容 V2 顶层与 V3 `data.character_book`;条目编辑与回写有专用端点。
- **对话互操作**:消息数组与 SillyTavern 完全一致,导入/导出无障碍(SillyTavern 兼容 JSON)。
- **酒馆助手(SillyTavern-Assistant)兼容**:
  - **EJS 模板渲染**:见「世界书与提示词注入」章(同一渲染器)。

## Agent 引擎

Agent 引擎是**双顶层模式共享**的编排核心(角色扮演会话与「六模式任务引擎」章同源),与连接器、工具、契约系统共享同一批底座。

**现状能力**

- **状态机**:`idle → planning → executing ⇄ tool_call → reflecting → finished`,可 `interrupted` / `error`;
  中断通过 `watch::channel<bool>` 中止标志贯穿全链路;失败回退经 `retreat_to_generating_step`
  有界重试(不无限自我修复)。`agent_sessions` 表持久化 plan / state / steps。
- **四种模式**:
  - `fast`:单步直接生成;
  - `deep`:计划 → 执行 → 反思,质量更高(主生成不启用工具,反思轮已放开 `read`);
  - `agent`:工具自循环(`run_tool_loop`);
  - `custom`:自定义流程(`AgentFlowConfig` + 流程库)。
- **规划与反思**:`planner.rs` 产出 fast/deep 计划并识别算式;`reflector.rs` 质量反思三规则
  (空 / 截断 / 未答疑问);反思步剥离 `<UpdateVariable>` → 禁词 `censor_text` →
  `reflect_with_tools`(LLM 双轨)或机械 `reflect` → 通过则 `idx+1`,失败则回退重生成。
- **工具循环 `run_tool_loop`**:生成 → 响应含 `tool_calls` 则 `decide_with_policy` 裁决 →
  按风险分组执行(**Safe 级并发**,其余串行且含最长 300s 的用户授权等待,
  SSE `tool_authorization_required` 驱动前端授权卡)→ 回填 assistant(`tool_calls`)+ tool 结果 →
  再生成;上限 `max_tool_rounds`(默认 32)。循环带**重复调用熔断**
  (`utils/loop_guard.rs`:FNV 指纹 + 环形窗口 N=8/K=3,中止理由经 step 事件透出)与
  **工具历史裁剪**(见「上下文工程与压缩」章)。任务模式在此之上另加两道闸——**步骤墙钟预算**
  与**语义熔断任务侧钳制**(见「六模式任务引擎」章第十五节),聊天路径两者皆不生效。
- **截断自愈**:单轮生成被 `max_tokens` 截断到不可用(空正文且 `finish_reason=length`,
  或任一 tool_call 参数 JSON 非法 / 连接器流尾 flush 报错)时,该轮 `max_tokens` 翻倍原样重发一次
  (上限 8192),重发仍失败才透出原错误;普通文本截断(非空正文)维持「截断仍 `done`」语义;
  触发记录经 `ExecutorResult.self_heals` 透出。**推理感知自愈**:识别「推理耗尽预算」并一次给足预算
  (不再盲目翻倍);四路截断重试统一收敛为 `utils::retry` 纯函数。
- **三层 JS 能力分级**(对用户/卡片作者提供的可执行内容按信任度分层,**全部刻意回避 eval 与任意代码执行**):

  | 层 | 载体 | 实现 | 能力边界 | 资源限制 |
  |---|---|---|---|---|
  | 渲染期模板 | 角色卡/世界书 EJS | 自研解释器 `parsing/assistant/ejs/`(lexer→parser→ast→exec) | 60+ 封闭内建枚举(`value.rs::Builtin`),无 IO/网络/动态求值 | 调用深度 128,`evalTemplate` 嵌套 16(线程局部 `EVAL_TEMPLATE_DEPTH`) |
  | 脚本期 | 角色卡/全局 tavern_helper 脚本 | rquickjs 沙箱 `scripts/` | TavernHelper 兼容桥(见「角色卡兼容」章),桥外无能力 | 每次执行独立 Runtime;合作式超时 1s + 内存 64MB;经 `spawn_blocking` 串行 |
  | 工具期 | `<数据目录>/plugins/tools/*.json` | 白名单表达式求值器 | 必须以 `return/result =` 开头,唯一变量 `args`;白名单函数(JSON/String/Math)+ 成员方法;无循环、无函数定义、无环境 | 注册进 `ToolRegistry` 后受统一权限层与单工具超时约束 |

- **EJS 解释器容错纪律**:模板编译为单一 JS 程序(文本段→`__kedai_out__`,`<%= %>`→`String(...)`,
  `<% %>` 原样拼接,大括号跨标签配对);parser 语句级容错(错误收集后跳到下一语句边界恢复);
  Env 作用域链 `Vec<Rc<RefCell<HashMap>>>`(闭包捕获可写回外层);
  **逐语句容错 + 整体失败回退原文**;「无上下文容错」横切原则:读类函数缺上下文返回默认值,绝不 panic。
- **运行时主提示词**:`DATA_DIR/AGENTS_RUNTIME.md` 由后端文件服务、Engine 与设置页共用同一路径;
  内置默认回退(含角色扮演默认提示词 `from_config` + `load` 空值回填,修复空版本首装提示词为空)。
- **提示词共享原语**:`services/prompt_kit.rs` 承载世界书过滤 / 注入合成 / 占位符渲染 /
  `untrusted_boundary`,引擎与任务双侧调用,不在任一侧复制实现。
- **双模式提示词隔离**:由类型承载(`RoleplayPromptConfig` / `TaskPromptConfig`),
  settings.json 线格式不变;继承/隔离规则见
  [模式提示词边界](archive/2026-09-16-consolidation/模式提示词边界.md)。
- **可观测**:推理链经 SSE 流式推送前端;`/api/agent/plan` 可预览行动计划(不执行);
  `/api/agent/interrupt` 等价 stop。

**权威来源**:`server-rs/src/agents/{state_machine,planner,reflector}.rs`、
`server-rs/src/agents/engine/{mod.rs,executor.rs,run_loop.rs,run_finish.rs}`、
`server-rs/src/services/prompt_kit.rs`、`server-rs/src/tools/registry.rs`、
`server-rs/src/utils/loop_guard.rs`;
文档小节 [优化实施方案-2026-09](archive/2026-09-16-consolidation/优化实施方案-2026-09.md) 第一篇第 2、5、7 章,

## 六模式任务引擎

任务模式是与角色扮演**平级的第二顶层模式**(`appMode`)。本节为
[任务引擎六模式](archive/2026-09-16-consolidation/任务引擎六模式.md) 的全文移植(该文档原为
`services/task_engine/` 的设计依据,此处按能力现状收录;未实现项已改记为交叉引用)。

分层归属:契约在 L1(`models/`),引擎在 L2(`services/task_engine/`),六模式执行器
(含 legacy/followup)全部驻 `task_engine`,模式选择 UI 在 L3。

### 一、六模式语义

| 模式 | 语义 | 执行路径 |
|---|---|---|
| `legacy`(默认) | 三段式:规划 → 逐步执行 → 汇总。**行为逐字节不变** | `task_engine/legacy.rs`(`LegacyExecutor`,自 `task_service/executor.rs` 机械搬迁) |
| `solo` | 单主 agent 工具自循环:目标直接进 run_tool_loop,工具集按 `task_tool_policy` 编译(默认 `deny_dangerous`:危险级与元工具除外、bash 例外),步数上限 `max_tool_rounds` | `task_engine/solo.rs` |
| `multi` | solo + 子 agent 工具化:主 agent 可经 `agentgo` 派子 agent(走 run_tool_loop + 工具白名单,`agent_depth+1` 深度守卫生效) | `task_engine/multi.rs`(复用 solo 主循环 + `tools/agent_tools_agent.rs` 的工具化子任务路径) |
| `plan` | 只规划不执行:产出计划进 `planned` 待批准态,零副作用;`POST /api/tasks/{id}/approve`(可携修改后计划)批准后消费已批准计划逐步骤续跑(每步独立 agent 调用 + 汇总);放弃 = stop | `task_engine/plan.rs` |
| `team` | 规划器拆子目标(全局上限 15)并归并为 2~4 个主 agent,每主领 1~4 个子目标;首版仅自动拓扑(规划器动态决定);各主并行跑 solo 循环(主内按子目标逐个独立执行)并可派子 agent;末段审计 agent 做一致性/质量/覆盖度审查(缺漏打回指定主 agent 补做,最多 1 轮;补做后追加一次终审,只产出结论文本不再打回),再升华整合输出最终结果 | `task_engine/team.rs` |
| `custom` | 复用 `AgentFlowConfig` / `validate_flow` / 流程库(L2 既有资产),配轻量 step 执行器:只吃 steps+goal,不依赖角色卡/聊天历史;每步按 `step.tools` 白名单走 `execute_generation` 或 `run_tool_loop` | `task_engine/custom.rs` |

> `tools` 三态(易误配,2026-09-10 实跑修复 F8):`None` = 不使用工具,**`Some([])` = 全部工具**,
> `Some(list)` = 白名单。前端已在「全部工具」及「不生成正文 + 全部工具」组合下加警示文案。

**custom 的流程模式(二维批次 7b,2026-09-23)**:任务在「强制」(老行为:只跑绑定/当前流程)
之外可选「**对比**」——根流程照常执行,另把一份**流程名单**(`tasks.flow_ids`)里的流程作为
单一内置工具 `run_flow` 释放给根流程内的**宽松节点**,模型在工具循环里自主调用某套流程、
取回其成果。三道成本闸(名单 / 调用链环与动态嵌套深度 / 每任务调用预算)在任何模型调用之前
判定,被拒的调用不产生任何调用行;动态层的调用行记账为 `call.d<n>` 前缀。三个闸门的取值与语义见
`契约-协议与配置.md`「对比模式契约（`flow_ids` + `run_flow`）」与 `计划.md` §九 裁定 24;
**后两闸的阈值自 2026-09-24 起可配**(任务侧设置项「流程调用深度」「每任务调用上限」,
默认 2 / 8,取任务开跑时的设置快照——见「前端」章的「任务侧流程调用闸与节点默认上下文」)。

#### 工具可用性矩阵(2026-09 授权改造后)

任务模式工具集合由 `task_tool_policy` 编译(见 [授权模式](archive/2026-09-16-consolidation/授权模式.md) 第四节),
且**恒不等待授权**(未放行工具立即拒绝为 `tool_policy_denied`)。默认策略 `deny_dangerous` 对
`bash` / `fs_write` / `fs_edit` **按工具名精确匹配**开例外下发(bash 因任务模式需命令执行能力;
两个工作区写/改工具因绑定工作区后需落盘能力,其路径由 `workspace_guard::safe_workspace_path`
jail 在作用域内),但破坏性/提权命令仍由命令级硬门统一拒绝。
各模式实际可用工具:

| 模式 | 规划/编排阶段 | 执行阶段 |
|---|---|---|
| `legacy` | 只读侦察(`tool_sets::scout_tools`:4 个基础 + **有作用域时**并入 `fs_read`/`fs_glob`/`fs_grep`,≤2 轮) | **无工具**(纯生成) |
| `solo` | 无规划 | 按 `task_tool_policy` 编译的集合(默认 `deny_dangerous`:危险级与元工具除外、`bash`/`fs_write`/`fs_edit` 例外) |
| `multi` | 无规划 | 同 solo(主循环逐字节复用);子 agent 用 `tool_sets::SUBAGENT` 只读白名单 |
| `plan` | 只读侦察(同上,`scout_tools`) | 批准后逐步执行,每步按 `task_tool_policy` |
| `team` | 规划/审计/汇总均无工具 | 各主 agent 按 `task_tool_policy` |
| `custom` | — | 按 `task_tool_policy` 编译后再与步骤 `PlanStep.tools` 取交(只能收窄);**对比模式**的宽松节点额外获得 `run_flow`(见下) |

共享白名单常量集中在 `server-rs/src/tools/tool_sets.rs`(单一出处):
`META_TOOLS`(`get_state` / `apply_patch` / **`run_flow`**,永不进正文列表)、`READONLY_SCOUT`、
`SUBAGENT`、`REFLECT`。

> `run_flow`(二维批次 7b)进 `META_TOOLS` 的理由与前两者同型:它是**按任务名单释放**的工具
> ——名单是运行期数据,全局可见毫无意义(聊天与 solo/multi/team/plan 都不该看到它);
> 真正用得着它的那条路径由 `task_engine/custom.rs` 显式把定义塞进 `params.tools` 并进闸门名单,
> 不依赖本清单。

> **闸门名单的空集语义(2026-09-24 修正)**:任务侧闸门名单由「本轮下发的工具集」派生,
> **空名单 = 拒绝一切**(旧语义「空名单 = 全量放行」已删除)。触发场景:某节点的 `tools` 白名单
> 只写了被任务策略剔除的工具名(如默认 `deny_dangerous` 策略下的 `write`),交集为空——此时该节点
> 下发的工具清单为空,模型**臆造**的工具调用也必须被拒(修前会被 `custom_authorized = true`
> 放行执行)。`solo` 与 `custom` 走同一判定;策略 `all` 时下发集本身非空,不受影响。

> 说明:`multi` 与 `solo` 的主循环参数相同,差异仅在「子 agent 链路」由 `agentgo` 提供——
> 而 `agentgo` 在 solo 的策略编译集中同样可用。两者的实质区别是模式语义标注与团队协作预期,
> 执行器层面等价。`legacy` 与其余模式的差异则远大于「有无规划阶段」:其执行步骤完全不启用工具。

### 三、引擎复用路径(关键设计决策)

任务模式复用聊天引擎的 `execute_generation` / `run_tool_loop`
(`agents/engine/executor.rs`),**不建影子 sessions 行**。

决策依据(2026-08-29 代码实测):

- `PRAGMA foreign_keys = ON`,`agent_sessions`/`llm_requests`/`messages` 等表全部
  FK 到 `sessions(id)`;影子行方案需贯穿多张表造影子数据,且 `sessions` 表会混入任务行
  (聊天列表污染面大);
- `run_tool_loop` 对 `agent_session` 的依赖仅为状态落库调用,可 `Option` 化;
- runs 互斥登记只在 `AgentEngine::run()` 内,直接调 `run_tool_loop` 天然绕开,
  任务级互斥由 `task_service/cancel.rs` 的 token 机制承担(既有)。

最小改动清单:

1. 可见性:`pub(super) mod executor` → `pub(crate)`;`execute_generation` /
   `run_tool_loop` / `ExecutorResult` / `AbortFlag::new` → `pub(crate)`;
2. `run_tool_loop` 的 `agent_session: &AgentSessionRecord` 参数改为
   `Option<&AgentSessionRecord>`(内部 `update`/`add_tool_call` 调用点改 `if let Some`),
   任务模式传 `None`,聊天路径传 `Some`(行为不变);
3. `llm_requests` 落库(`execute_generation` 内的 `save_llm_request` / `save_llm_cache_usage`)
   对 `task:` 前缀 session_id 跳过——任务侧调用追踪走 `task_llm_calls`,llm_requests 仅聊天链路,
   避免 FK 失败告警刷屏;
4. 构造顺序:`app_state` 先建 `AgentEngine`,再以 `Arc<AgentEngine>` 注入 `TaskService`
   (engine 不依赖 tasks,无循环);
5. 事件通道:task_engine 自建 mpsc,起 drain 任务把引擎事件映射为 `SseEvent::Task`
   (kind=agent_status 等)经 broadcast 转发,并落 `task_llm_calls`(phase=agent/subagent/audit);
6. 工具授权:任务模式无 UI 授权上下文,`run_tool_loop` 的 `step_whitelist` 恒传

   策略已编译的可下发集合由 `params.tools` 给出,不经白名单放行)或显式白名单(multi 子 agent),
   避免危险工具 300s 授权等待;`TaskService` 的 bypass 设置语义不变。

### 七、2026-08-31 / 09-02 实测修复(截断自愈 / 规划器侦察 / 错误文本 / 孤儿恢复 / 工具历史回灌上限)

五项真实模型实测驱动的行为变化(均带集成测试,`tests/tasks.rs`):

1. **截断自愈(问题①)**:`run_tool_loop` 单轮生成被 `max_tokens` 截断到「不可用」
   (空正文且 `finish_reason=length`,或任一 tool_call 参数 JSON 非法/连接器流尾
   flush 报「arguments 不是合法 JSON」)时,该轮 `max_tokens` 翻倍(上限

   错误。普通文本截断(非空正文)不算,维持「截断仍 done」语义。触发记录经
   `ExecutorResult.self_heals` 透出,任务模式(solo/multi/team/plan 续跑/custom/
   子 agent)补落 `task_llm_calls` 标注行(status=error,response_summary 含
   「(截断自愈)…重发」),调用情况面板可见完整链路。legacy 路径的空输出分级
   重试(plan/step/summary 无工具纯生成)是既有同问题不同层机制,不受影响。
2. **规划器只读侦察(问题②)**:legacy 与 plan 共用的 `plan_task` 在产出计划 JSON

   随后最终轮不带工具强制产出计划 JSON(计划契约不变);模型幻觉白名单外工具
   名时回填拒绝错误 JSON 不执行;侦察轮失败(如协议异常)回退无工具直接规划,
   不沉任务。侦察轮与计划轮均经 `generate_text` 统一出口落 `task_llm_calls`

   team 规划器(`plan_team`)维持无工具单次生成,未启用侦察。
3. **步骤 error 文本落库(问题③)**:步骤失败时失败原因与 status=error 同一次

   重开库 → 断言终结」。

### 八、批次 R2a:终态追加输入(followup,2026-09-03)

### 十、team 纯生成点截断自愈(2026-09-03 真实模型复验驱动)

实测 team 全链路(DeepSeek 推理模型,`default_max_tokens=1024`)发现:审计
agent 的 reasoning 烧光预算,`finish_reason=length` 产出腰斩 JSON
(`{"通过":false,"打回":[{"main":2`),腰斩原文直接进最终 result 的
「## 审计结论」卡——既难看又误导(`parse_audit` 虽按通过兜底不沉任务,
但结论=原文的旧语义把协议残片暴露给了用户)。

根因:solo/custom 的截断自愈在 `run_tool_loop` 层,而 team 的审计/终审/汇总
是 `generate_text` 直调点,不在自愈覆盖内。修复(`team.rs`):

1. **`generate_text_healed` 包装**:审计/终审/汇总三处统一走新出口——先按
   原预算调 `generate_text`,`finish_reason=length` 时预算翻倍重发一次
   (纯函数 `trunc_heal_budget` 决策,封顶 `TEAM_RETRY_MAX_TOKENS_CAP`)。
   两次调用均经 `generate_text` 落 `task_llm_calls`,调用情况面板可见
   「截断 → 提高预算重发」链路;token 用量与 `record_usage` 两次都入账
   (与 solo 自愈留痕同口径),并发 `agent_status` 事件告知前端。
2. **腰斩 JSON 末层兜底**:`parse_audit` 对「以 `{` 开头但解析失败」的
   截断形态不再把原文塞进结论段,改为干净说明「(审计输出不完整,按通过
   兜底)」,原文前 120 字符记 warn 日志备查;纯文本回复维持旧语义
   (结论=原文)。

测试:`team.rs` 的 `trunc_heal_budget_only_on_length`(仅 length 触发/翻倍/
封顶/越顶不触发)、`audit_truncated_json_fallback_clean_conclusion`
(腰斩 JSON 兜底通过、结论段不含 `{`)。

### 十一、2026-09-10 六模式实跑修复(F1~F8)

隔离数据目录 + 真实 `deepseek-flash` 对六模式各跑「创建 → run → 多轮 followup」,
plan 补跑 plan-chat → approve → followup,依据实测暴露的 8 个问题修复:

1. **F1 custom 非生成步骤产出正文**(`custom.rs`):`generates=false` 的 direct 步骤
   此前复用 `EXECUTOR_PROMPT`(「直接输出最终结果」),无视步骤自身「只做内部规划」
   而吐出完整正文,并被下一步原样回显。现改用新常量 `TASK_INTERNAL_PLAN_PROMPT`
   (只做分析规划、不产出正文),其产出加「(内部规划)」标注、仅供后续步骤参考、
   不计入最终成果(`draft` 仅由 `generates=true` 步骤产出)。
2. **F2 任务模式注入污染**(`task_prompt_inject_enabled`,默认 false = 隔离):

3. **F3 记账缺口**(一致性口径):凡落 `task_llm_calls` 的调用都补落 `task_usage`——
   规划器侦察轮、截断自愈 heal 行、规划失败重试轮、步骤/汇总首调空输出轮次。

4. **F4 plan 续跑步数矛盾**:approve 组 goal 追加约束句「步骤数量与内容一律以本
   清单为准」,修用户经 plan-chat 改步数后汇总仍沿用原始目标旧步数的矛盾

5. **F5 followup 重写模式**(`mode: append|replace`,缺省 append 向后兼容):
   append 无法表达「压缩/重写/改前面」;replace 用新产出整体替换 result

7. **F7 legacy 前端子任务区重复**(`TaskBoard.vue`):legacy 的 subtasks 与计划步骤

### 十三、2026-09-26 D1 批:任务可写面收敛(scratch 工作区 / 规划器能力段 / 侦察放开 / bash 自描述 / 审计标记)

来源:真实模型 12 轮实测(六模式 × 写作/编程,隔离数据目录 + 沙箱)暴露的
「未绑定工作区的任务把用户数据目录当草稿纸」缺陷——plan/写作一轮跑了 77 条 shell 命令、
在数据目录留下 12 个垃圾文件、写 python 脚本去 `open('kedai.db-wal','rb')`、15 分钟不收敛。
修复分五件事(证据与对照值见 `功能-变更史.md` 收口章):

1. **任务级 scratch 作用域**:未绑定工作区的任务不再「没有作用域」——执行前在
   `<数据目录同级>/task_scratch/<task_id>` 内建目录并绑定为任务作用域(`KEDAI_TASK_SCRATCH_DIR`
   可覆盖根;刻意与数据目录同级,放在其内会被 `safe_workspace_path` 的 data_dir 二次防线
   整体判为冲突)。目录建不出来 → 任务以明确错误终止,**不降级回数据目录**。
   由此 `fs_*` 工具族对所有任务下发(`workspace_gate` 仍按「作用域是否存在」求值,
   只是任务恒有作用域),bash 缺省 cwd 从数据目录改为该 scratch;聊天路径逐字节不变
   (无 scope 的第四分支只服务于它)。
2. **规划器能力段**:`plan_task` / `plan_team` 的 system 追加「【本轮可用能力(执行阶段)】」段
   (单一出处 `task_core::prompt_consts::capability_note`)——legacy 的步骤**没有任何工具**,
   该段明说「交付物必须是正文,禁止把交付物规划成文件」;plan/team 的步骤走工具循环,
   该段给出文件工具清单、**文件根绝对路径**、bash 的 cmd 语法边界,并声明
   「交付物正文必须由执行者直接产出,文件只是过程物」。规划器不知道执行者能做什么,
   就必然规划出做不到的步骤(实测它的计划原文就写着 `constraints.md`/`draft.md`)。
3. **侦察轮放开只读工作区工具(D5)**:任务有作用域时把 `fs_read`/`fs_glob`/`fs_grep`
   并入规划侦察白名单(`tool_sets::scout_tools(true)`,仍禁写),`plan_scout_loop` 以该作用域
   作为路径闸门根——规划器终于能看见工作区里的真实文件(此前 `read` 走角色扮演文件区语义,
   实测报「读取文件 package.json 失败:系统找不到指定的路径」后盲规划)。无作用域保持旧白名单。
4. **`bash` 自描述(D4)**:结果头改为 `$ {命令}` + `(执行器:…;shell:{cmd|sh};cwd:{实际};退出码:…)`,

5. **审计风险标记**:`exec_audit` 新增 `risk_flag`(`''` / `data_dir_touch` 命令文本含数据目录
   绝对路径 / `parent_climb` 含 `..` 路径段),**只标记不拦截**——模型有 shell 就能读进程可读的
   任意路径,cwd jail 只约束相对路径与缺省目录,假装封堵比不封堵更糟;标记让这类行为事后可筛。

### 十四、2026-09-26 提交 2:部分成果兜底(终态不再丢已完成的工作)

来源:同批真实模型实测的第二类缺陷——**已完成的工作被丢弃**。legacy/写作的 4 个步骤全部
`done`(plan 各步 result 累计约 3900 字),最后汇总撞 300s 看门狗 → 任务 `error`、
`tasks.result` 为空,用户只看到「出错」;team/写作 9 个子目标完成 6 个(2 个 300s 超时)→
同样无最终结果。根因三段:终态枚举 `TaskTerminal::Failed` 没有部分成果字段、落库侧
`finalize_run` 的 error/ended 分支只写 status/error **不碰 result**、前端成果卡只对
done/partial 渲染。修复分六件事:

1. **单一出处的拼装器**(`task_core::assemble.rs`):`assemble_from_plan(&[TaskStep])` 把
   「已完成且产出非空」的步骤确定性拼成 `## 步骤名` 段(按 plan 顺序;名称折叠换行防假标题;
   有失败步骤时另起一行「> 未完成的步骤:…」),**不调 LLM、不读库**;
   `fallback_terminal(plan, reason)` 一处判定:**能拼出成果 → `Complete{status=partial,
   result=拼装文本, error=原因}`,拼不出才 `Failed`**——四模式与两条兜底路径共用,禁止各写一份。
2. **四模式降级**:legacy 与 plan 的汇总失败、team 的审计/终审/汇总调用失败与汇总空产出、
   custom 的运行失败与「未产出任何成果」,都改走上述判定;取消路径仍返回 Err,交由引擎按
   `ended` 收尾(避免把「已停止」误报成 partial)。
3. **终态兜底落库**:`finalize_run` 写终态**前**、以及 `stop()` 置 ended **之前**都调用同一个
   兜底函数(`salvage_partial_result`):若 `tasks.result` 仍为空而 plan 里已有已完成步骤的产出,
   先补写结果(`db::set_result_only` 只更新 result 列,不动 status/error)再照旧写 ended/error
   ——取消与失败两条路径都不再丢工作,且「已停止」一出现就带成果。
   选「读库兜底」而非给 `TaskTerminal::Failed` 加字段:改动面更小,且一并覆盖引擎 Err 兜底
   (`task_engine/mod.rs` 的 Err 分支)与模式自报 Failed。
   **配套:`approve` 在置 planning 时清空 planned 态写入的预览 result**(`db::clear_result`)——
   那条 result 是「待批准的计划清单」,只在 planned 态有语义;留着会让兜底的「result 为空才
   补写」判据整条跳过,成果卡里就只剩一份**计划**被当成「已完成部分的成果」(2026-09-26
   真模型 plan/写作 实测命中:某步已完成 560 字,result 里仍是计划清单)。清空后:续跑成功由
   汇总文本落 result,失败/取消由兜底写已完成步骤的产出,两侧都是真产出。
4. **重启中断同样兜底**(`recover_orphan_tasks`):服务启动把 running/planning 置 ended 时,

### 十五、2026-09-26 提交 3:能收敛(预算 / 熔断 / 纪律 / 空闲自愈)

来源:同批真实模型实测的第三类缺陷——**任务在时限内不收敛**。6 轮编程 4 轮、6 轮写作 2 轮

### 十七、2026-09-30 编码能力包续做批次 1:命令执行可中止 + 进程树清理(Windows)

来源:HARNESS3-1(`计划.md`「HARNESS 提交 3 七项」表)。此前「点停止」只在**轮间**生效——
工具一旦起跑就要等它自己跑完(`bash` 最长等到命令自身超时),且 `cmd /C` 这类 shell 包装
派生的孙进程从来不在清理范围内(旧 `desktop.rs` 头注释却已承诺「含子孙进程」)。

1. **引擎侧取消闸门**:`agents/engine/executor.rs` 新增私有函数 `await_or_cancel`,把工具 future
   与 abort 信号竞争;取消赢 → 工具 future 被丢弃 → `execute_call` 立即回填
   `{"error":…,"code":"tool_cancelled"}`。该形状与「执行失败」同款,**不终止整轮**——真正的
   收场仍由调用侧既有的轮末 / 串行路径 abort 检查负责。**刻意不给 `ToolRegistry::execute*`
   加取消形参**:`ToolExecutor` 是 L1 公共契约(`models/types.rs`,注释自陈 `plugins/` 与 `mcp/`
   两个 L3 都要构造它),加形参等于动 L1 类型 + 全部工具闭包,与需求不成比例。
2. **进程树清理**:`services/exec/desktop.rs` 新增 `JobTree`(Windows Job Object,
   `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`)。直接子进程在 spawn 后立即入作业,其后它派生的**一切
   后代自动同属该作业**;三个出口都收——超时显式 `terminate()`、**上游取消(丢弃 future)→
   守卫 drop → 句柄关闭**、正常返回前先 `terminate()` 再读管道(顺带消除「后台进程握着
   stdout/stderr 写端 → `read_to_end` 一路挂到上层超时」这一既有隐患)。取消信号因此**不需要**
   穿透到 exec 层,这正是「调用侧竞争」方案成立的前提。**这是有意的行为收紧**:命令返回
   ≠ 它派生的进程可以继续活着。
3. **诚实边界(四条,勿在后续批次误判为遗漏)**:① **Unix 侧未实现**(`process_group(0)`+`killpg`)——
   本机 `cfg(unix)` 分支不参与任何可构建目标的编译(android 被 `#![cfg(not(target_os="android"))]`
   排除),且云端 `ci-linux` 已停用,不交付没编译过的代码;登记 `遗留.md` **EXEC-TREE-1**。
   ② 作业成员身份在 spawn **之后**才赋,抢在赋值前派生的进程不入作业 → 口径是「**尽力清理**」,
   不是「保证无残留」。③ `mcp/process.rs`(`遗留.md` L3)同形态未改、判定不变,但方向已具备
   (同一机制可复用)。④ 任务侧 `plan_scout_loop` 的工具执行(`services/task_service/executor.rs:992`)
   不经 `execute_call`,本批未覆盖(侦察轮只下发只读工具,风险面不同)。

**权威来源**:`server-rs/src/agents/engine/executor.rs`(`await_or_cancel` / `execute_call`)、
`server-rs/src/services/exec/desktop.rs`(`JobTree`)。

**验证**:新增 6 例(取消四态 4 例 + 进程树两出口 2 例)。两条进程树用例做过**负向验证**——
临时把 `JobTree::new()` 改为恒 `None`,超时出口报「57036 → 88146」、取消出口报
「19998 → 53706」(孙进程仍在写文件),断言有判别力而非空过;判据用「孙进程追加的日志
文件不再增长」,因为自动化环境取孙进程 PID 要靠 `tasklist` 输出格式(脆弱)。

### 十八、2026-09-30 编码能力包续做批次 2:自测闭环(单命令上限 1800s + 输出保头保尾)

来源:HARNESS3-4(`计划.md`「HARNESS 提交 3 七项」表)。编码执行者模板(§十六)要求「改完用项目
自身的构建/测试跑一遍」,但旧上限 300s 恰好卡在 `cargo test` 级校验(本机实测 1~16 分钟)之下——
自测跑不完,纪律就落空;而失败摘要在输出**尾部**,旧截断只保头,即便跑完也看不见为什么失败。

1. **上限抬档与两处跟随**:`services/exec/mod.rs` 的 `MAX_TIMEOUT_MS` 300_000 → 1_800_000
   (缺省 `DEFAULT_TIMEOUT_MS=60_000` **不动**,常态体感不变)。抬档不是单点改动,三处必须同批:
   ① `tools/bash.rs` 的**注册表整工具超时**改为由该常量 + 30s 收尾余量派生(旧值硬编码 330s,
   不跟就会由注册表先掐断,exec 层的强杀与审计路径全失效);② `bash` 工具 schema 里模型可见的
   上限文案改为常量插值(写死会让模型永远要不到长预算);③ `desktop.rs` 的超时文案本就插值该常量,
   自动跟随。
2. **任务侧两道闸门同批校准**(台账未记,实测才发现的耦合):
   - **空闲看守**:下限此前被硬编码成 601 三份(默认值注释 / PUT 校验文案 / load 钳制)。
     现改为单一出处 `settings_service::params::task_idle_floor_secs()`
     = 命令上限 + 单次模型调用上限(`executor::TASK_TOOL_LOOP_CALL_TIMEOUT`,改为 `pub(crate)`) + 1
     = **2101s**,默认值 900 → **2400**。不这么做的后果很隐蔽:工具循环期间既不落库也不发事件
     (见 `task_service/idle.rs` 模块头),一条跑满 1800s 的命令会因「静默 900s」被看守收尾,
     现象伪装成「任务空闲超时结束」。
   - **步骤墙钟预算**:默认 1200 → **3600**。该闸门在**轮末**判定,所以命令本身不会被截断——
     丢的是**后续轮次**:跑完一次长自测就「预算用尽、带产出收尾」,失败之后没有下一轮去修。
3. **输出截断改保头 + 保尾,两层一起改**:`exec::truncate_output` 按字符保留头 3/4 + 尾 1/4
   (`MAX_OUTPUT_CHARS=32_768` 预算不变);`tools/registry.rs` 的 64KB 字节预算同样改为保头+保尾。
   **为什么必须两层都改**:内层按字符、外层按字节,CJK 输出下内层结果可达 ~98KB > 外层 64KB,
   只改内层的话,辛苦留下的尾部会在外层被二次切掉。两层的省略说明都保留「已截断」字样,
   并写明保留量(审计日志里始终是全量)。
4. **刻意不做**:不复用节点级 `call_timeout_secs`(那个只管模型调用看门狗,语义不同);
   不加「任务级 bash 超时」设置字段(需走设置字段登记清单,而 per-call `timeout_ms` 已能覆盖);
   不给看守加「工具在飞时周期心跳」机制(会引入 SSE 噪音,且做坏了会让看守永不触发)。

**权威来源**:`server-rs/src/services/exec/mod.rs`、`server-rs/src/tools/{bash,registry}.rs`、
`server-rs/src/services/settings_service/{params,mod,secret}.rs`、`server-rs/src/api/settings.rs`。

**验证**:看守下限派生、两个默认值的容纳关系、空闲判据、内层最坏字节量、外层保头保尾 ——
均有单测锁死(见 `MAINTENANCE.md` §测试清单)。知情取舍写进 `功能-变更史.md`:看守默认 2400s 是
**有限值**(关掉要显式设 0),代价是僵尸任务要多等约 20 分钟才被收。

### 十九、2026-09-30 编码能力包续做批次 3:压缩与工具历史裁剪保留编码工作状态

来源:HARNESS3-3(`计划.md`「HARNESS 提交 3 七项」表)。长任务跨压缩后模型只记得

1. **工具历史占位里保留「工作状态锚点」**:单一出处在 `tools/tool_sets.rs::state_anchor_arg(name)`

2. **与台账原措辞的实质差别(重要,勿在后续批次当缺陷改回去)**:台账写的是

### 二十二、2026-09-30 编码能力包功能扩展批次 2:整任务回滚 + patch 导出(CODE-2)

来源:`计划.md`「编码能力包功能扩展(CODE-1~CODE-5)」章;用户确认按推荐档执行(**Q2=(a)**:
逐项报告、不整体否决)。

1. **整任务回滚**(`POST /api/tasks/{id}/changes/rollback-all`):对本任务台账里的每个路径
   逐项执行与单文件回滚**完全相同**的语义(取该路径最新一行;`create` → 删除;无基线 → 跳过;
   每项成功再记一条 `op=rollback`),顺序 = 首次出现在台账里的顺序。响应逐项报告
   `{ path, result: restored|removed|skipped|failed, restored_bytes?, reason? }` + 四个计数;
   **某项无基线/落盘失败不拦住其余项**(无基线的原因、失败项固定文案,逐条说得出来);
   running/planning → 409 整单拒绝;空台账 → 200 空报告(不是 404)。
   **可逆**:再调一次 = 逐项切回「改动后」状态(取最新一行的自然结果)。
2. **单文件回滚的行为修正(可逆性的前提)**:新建项的回滚改为**先取快照再删除**——此前是
   先删再拍快照(拍到的是「文件不存在」),回滚行没有正文,「点错一次文件永久消失」且再点
   只会得到「基线不可用」。修正后回滚行带上被删正文,自身可再被回滚(重建文件),
   与单文件「回滚再记一条、不隐身」的既有口径一致,只是那条记录从此**可用**。
3. **patch 导出**(`GET /api/tasks/{id}/changes/patch`):文本响应(`text/plain`,前端经
   `requestText` 文本通道取回,**不套 JSON 形状闸门**),由可 diff 行逐文件拼成 **git 可 apply**
   的补丁——修改 = `diff --git` + 头 + 单 hunk(`git_hunk` 严格按 unified diff 语义计行,
   `git apply` 会按计数校验;与给人看的 `unified_diff` 是同一套 head/tail+LCS 算法、
   **两套头部计数**);新建 = `new file mode` + `--- /dev/null` + 全量新增行。

## 变量与契约引擎

变量系统是「故事状态」的载体,契约引擎(Kaleido)是其唯一事实源与门控。

**现状能力**

- **mvu 变量系统**:直接操作 JSON 树,无独立 IR;`AssistantVars{tree: Value}` 根即 `stat_data`;
  路径归一化剥 `stat_data.` 前缀、点/斜杠双分隔、**过滤 `__proto__`/`constructor`/`prototype`
  防原型污染**;`PatchOp::{Replace,Delta,Remove,Move}` 四变体各带 `reason`。
- **双协议解析**:`<UpdateVariable><JSONPatch>[...]</JSONPatch></UpdateVariable>`
  (RFC 6902 子集 + `delta` 扩展;`insert`/`set` 并入 Replace;delta 非数字整条跳过;
  未知 op 跳过)与 MagVarUpdate `_.set('path', old, new);//原因`
  (手写平衡括号扫描 + 顶层逗号切分;reason 只出自这里,行注释优先、块注释次之;
  JS 字符串转义与前端 `parseJsString` 逐字对齐)。
- **容错**:顺序应用、首个失败返回 Err 不回滚;Move 源缺失整条跳过;引擎侧应用失败仅记 warn。
- **七作用域**:`Global` / `Chat` / `Character` / `Preset` / `Message` / `Script` / `Extension`。
  读优先级 `message → chat树 → chat扁平 → character → preset → global`
  (script/extension 不进读链;message 未命中强制回退 chat 兼容存量卡);
  写路由 chat 按「`stat_data.*` 前缀或已在树中」分流树/扁平层;回合内树写以 `env.vars` 实时权威;
  回合结束 `take_others()` 批量落 `scope_variables` 表。持久化三层:
  `session_assistant_vars`(树)+ `session_vars`(扁平)+ `scope_variables`(PK(scope, scope_id));
  SSE `Vars` 事件推最新树。message 作用域 = `extra` 镜像 + `scope_variables` 双写,引擎为唯一写者。
- **两步生成**:正文后追加一次独立 function-calling(工具 `update_variables`/`update_status_bar`,
  独立模型/温度档 `mvu_model` / `mvu_temperature`——默认共用正文模型、温度 0.3(HB-7 起
  两者在设置页可配:模型留空即共用,温度留空用内置 0.3),空输出以 0.7 重试一次);模型不调工具时回退旧文本协议;
  仍无状态栏用 `diff_status_bar`(以本轮初始树为基准)兜底。**首楼纪律**:含
  `<StatusPlaceHolderImpl/>` 占位符时服务端绝不改首楼;否则用 `extra.status_slot.last` 锚点就地替换并落库。

- **节点级连接(2026-09-23 新增,二维批次 5b)**:步骤编辑器多一个**「模型连接」下拉**——单个步骤
  可以指定自己走哪一套连接,**provider 与模型随该连接**(所以「给这一步换个模型」= 给这一步选一条
  带那个模型的连接)。用途:便宜的步骤走便宜模型、需要推理的步骤走推理模型、或让某一步走另一家的 API。
  - **默认是「默认连接」**:不动这一项时行为与以前完全一样。
  - **引用失效会明确报错,不会偷偷换回默认连接**:连接被删除或被停用时,跑到这一步会失败并点名
    「引用的连接「X」不在设置里/已停用」,其余步骤照跑(任务 `partial`)。编辑器里当场就能看见
    「(引用已失效)」保位提示与后果说明,画布节点卡片、列表行摘要也会标出本步换了连接。
  - **为什么不做保存期拦截**:流程库可以导出、也可以从别的机器导入,而连接是**本机**的设置——
    保存期拒绝会让流程变成本机专属。所以选择是「保存放行、运行时报错、编辑时提示」。
  - **调用追踪记真实模型**:调用情况面板的「模型」列显示该步**实际用的**模型(不再是全局默认模型),
    因此一眼能看出哪一步走了哪条连接。
  - **挂载子流程的节点**上这项不生效(子图各节点用自己的连接解析),配置保留。
- **逐任务选用连接(2026-09-24 新增,自定义流程 B 批)**:侧栏「下达目标」区多一个**连接选择器**
  ——创建任务时可指定这**一整个任务**走哪一套 API 连接。它与「逐节点选用连接」的分工是:
  节点级管「这一步」,任务级管「整个任务」的缺省值。要点:
  - **六种任务模式通用**:它绑的是 provider 而不是编排,故 legacy / solo / multi / plan / team /
    custom 都可见(不像流程选择器那样只在自定义流程模式下出现)——规划、逐步执行、汇总、
    工具循环、自定义节点全走它。
  - **节点级优先**:某一步单独选了连接的仍走那一步的连接(节点级 > 任务级 > 设置的默认连接),
    因此可以在「这个任务整体走便宜模型」之上再给个别步骤换推理模型。
  - **缺省 = 跟随设置**(「连接:默认连接(跟随设置)」):不选时行为与本批之前逐字节一致;
    选择会**持久化**(刷新后仍是它)。
  - **创建期即校验「存在且启用」**:引用不存在或已停用的连接,创建就被后端以中文错误拒绝
    (点名那条连接)。这与流程「保存放行、运行时报错」的取舍不同——流程要跨机搬运,而任务是
    **本机**对象,即时校验让用户不必跑到一半才发现选错。
  - **运行期引用失效仍明确报错、不静默回退默认连接**(与节点级同一口径):连接被删或停用后
    跑到该任务会失败并点名;选择器里**已被删除**的持久化选择会**就地重置为默认连接并给出提示**
    (不静默改选),所选连接只是被停用则即时提示「创建任务会被拒绝」而不擅自清掉。
  - **调用追踪记真实模型**:自定义节点的模型按**生效连接**(节点级 ∪ 任务级)解析,调用情况面板
    不会把任务级连接的调用记成默认连接的模型。
- **节点级工具轮次上限(2026-09-23 新增,二维批次 5b)**:步骤的「工具轮次上限」(1-200)限制
  **这一步最多让模型调用几轮工具**,留空沿用全局设置——给「容易在原地打转」的步骤单独收紧预算,
  而不必改全局值。严格档下该项不生效(严格 = 只调用一次模型),编辑区随之收起、配置保留。
- **节点级上下文上限(2026-09-24 新增,二维批次 8)**:步骤编辑器多一个「**上下文上限**」
  (256-1048576),限制**进入这一步的输入整体**有多大——即「系统提示 + 任务目标 + 各上游产出」的
  token 预算;与同排的「输出上限」正好一进一出。要点:
  - **留空 = 不限制**(与新增该字段之前的行为逐字节一致,存量流程无任何变化)——它的用途是
    给**单个步骤**设一个更小的窗口(例如「摘要」步骤只该看上游的关键结论,不该吞下整篇长稿)。
  - **超限时从「最旧的上游产出」开始省略**:该段的正文换成「(因本节点上下文上限省略)」标记、
    标签行保留,于是模型与人都看得出「这里原本有内容」;省到位的段仍在,顺序不变。
  - **任务目标恒保留、不静默截断**:若**目标本身**就超上限,这一步会**明确报错并点名**
    (错误带上实际 token 与所设上限,便于判断该调多大),而不是把目标切一半继续跑。
  - **只裁这一步的输入装配**:工具轮内的历史仍由「工具历史保留轮数 / 预算」设置管理(两者管的是
    不同东西,互不替代);严格档与宽松档都生效(它管输入,不管工具面)。
  - **缺省由任务侧设置提供(2026-09-24 起)**:节点没写这一项时,回落设置页的
    「节点默认上下文」(0 = 不裁剪,默认;否则 256-1048576)——**节点自己设的值优先**,
    所以把默认值留在 0 时,本条的行为与它落地时逐字节一致(见「任务侧流程调用闸与节点默认上下文」)。
  - **挂载子流程的节点**上这项不生效(子图各节点各自裁剪),配置保留——与其它执行参数同款旁路。
- **节点级单次调用超时(2026-09-24 新增,自定义流程 A 批)**:步骤的「**单次调用超时**」
  (30-3600 秒)是**这一步每次模型调用**的时间预算,留空沿用缺省 300 秒看门狗。要点:
  - **既可收紧也可放宽**:填 60 = 给本来就该快的步骤提前止损;填 900 = 给长文生成、外部工具
    这类本来就慢的步骤放宽,不会被 300 秒看门狗打断——它不是「只能往下调」的上限。
  - **宽松档逐轮各按它计**:工具自循环的每个工具轮都是一次调用、各自计时(与全局看门狗同粒度),
    所以它是**单次调用**预算而不是「本步骤的总预算」;要限轮数请用「工具轮次上限」。
  - **超时 = 本步失败,不自动重试**:走既有失败/降级口径(不会静默给一个空产出);想重试请配下一条
    「空产出重试」——但那条只管空产出,**超时不在它的重试范围内**。
  - **留空 = 现状**:与新增该字段之前逐字节一致(300 秒看门狗不变,存量流程无任何变化)。
  - **反思步骤同样适用**(它也会发起一次模型调用);**挂载子流程的节点**上这项不生效
    (子图各节点各自计时),配置保留——与其它执行参数同款旁路。
- **节点级空产出重试(2026-09-24 新增,自定义流程 A 批)**:步骤的「**空产出重试**」
  (1-5,是**额外**尝试上限:填 2 = 最多再试 2 次、总共 3 次)只负责一类失败——**模型返回了空文本**:
  - **只重试空产出**:连接失效、调用超时、上游报错这类**硬错误一律立即失败、不重试**——把重试预算
    花在同一个坏引用上只会成倍烧钱,还会让超时的语义被重试掩盖。
  - **每次重试自动翻倍输出预算**(与规划 / 逐步两侧的截断自愈同一算法,封顶 131072):空产出最常见的
    成因是推理把输出预算吃光了,只重试不加预算等于把同一次失败原样重放。
  - **重跑本步,不是接着聊**:每次尝试都用**同一份**输入重建请求,不在上一轮的消息上续写;
    两次尝试之间的退避等待期间点停止可以立即取消。
  - **记账不串**:每次尝试各记一行调用记录,面板上能看出这一步试了几次、各花了多少,
    「各行求和 == 用量合计」这条不变量照旧成立。
  - **留空 = 不重试**(与新增该字段之前逐字节一致);**只重试本步、不重试下游**;
    挂载子流程的节点上不生效(子图各节点各自重试),配置保留。
- **任务侧流程调用闸与节点默认上下文(2026-09-24 新增,自定义流程 A 批)**:设置 →「模型与生成」→

  - **取的是任务开跑时的设置快照**:正在跑的任务不受中途改设置影响,下一轮才按新值。
  - **默认值逐项等于引入它们之前的行为**(2 / 8 / 不裁剪),不动这三个输入时一切照旧。
    「节点默认上下文」的缺省刻意留在 0,是**不让既有流程突然受一层默认约束**——需要给任务侧

- **流程搬运:批量导出与导入合并(2026-09-23 新增,二维批次 7a)**:设置 → 「执行流程」的
  「导出流程(JSON)」把当前流程**连同它挂载的子流程**一起导出,「导出全部流程」导出整个库;
  导入时把文件里的流程**合并新增**进本机库。要点:
  - **为什么必须带上子流程**:节点挂的是「子流程 id」这种引用。只导一个入口流程,到别的机器导入
    必然报「引用的子流程不存在」——**导出即坏文件**。所以导出按**可达引用链**收集整套编排
    (与任务快照冻结用的是同一条判定),文件因此始终自洽。编辑器下方已写明这一范围。
  - **导入默认只新增,不覆盖**:本机已有同 id 的流程时**不会**改写它——内容完全相同则**跳过**
    (同一份文件重复导入不产生副本),内容不同则给导入的那份分配**新 id** 并同步改写它引用的
    子流程 id;导入后停留在刚导入的那套编排上。报告文案会点名「导入 N 个、跳过 M 个、
    其中 K 个因 id 冲突分配了新 id」。
  - **覆盖模式:勾选「覆盖同名流程」才就地替换(2026-09-24 新增,自定义流程 B 批)**:
    导入按钮下的复选框,**默认不勾选**(不勾选 = 上面那条的旧行为);勾选后:同 id 且内容不同的流程
    **覆盖本机那一份**(id 不变 → 节点里指向它的引用不破),内容相同仍**跳过**,**库里其它流程
    一律不动**(是逐份覆盖,不是整库替换,不删任何东西);因 id 冲突被保留的段照旧分配新 id。
    勾选后输入框下方当场出现「覆盖不可撤销」的警示,导入前还会二次确认一次;覆盖后的候选库照常做
    **全库校验**,任何一条引用变得非法都**整批拒绝**,库与磁盘一个字节都不变。覆盖结果进报告:
    在「导入 / 跳过 / 分配新 id」之外单列「**覆盖 J 个同 id 流程**」并点名是哪几份——
    不静默改写。
  - **失败不留半份**:所有校验在候选库上一次性完成,任何一条不合法(悬空引用 / 空文件 /
    文件内 id 重复)都整体拒绝,库与磁盘**一个字节都不变**——旧的逐个保存路径做不到这点。
  - **导出文件不含 API 连接与密钥**(连接是本机设置)。节点上选的「模型连接」原样保留,
    跨机导入后会在编辑器里显示「(引用已失效)」,跑到该步明确报错,不会偷偷换回默认连接。
  - **导出取的是已保存的版本**:改了步骤还没点「保存执行流程」就导出时,会先确认一次
    (避免静默拿到旧版编排再搬到别的机器)。「导出全部流程」在库为空时禁用。
  - **兼容旧文件**:单流程 `{name,steps}`、`{config:{…}}` 包装与旧的流程库格式都能导入
    (库格式按**整库**导入并沿用文件里的当前流程,不再只取其中一个而静默丢其余);新格式带版本号,
    遇到更高版本会提示「请升级 Kedai」而不是静默丢字段。

## 工程与质量基线

**现状能力**

- **测试套件**:后端 cargo 单测 + API 集成测试,前端 Vitest;
  覆盖范围见 `../MAINTENANCE.md` §11 的用例清单(状态机、planner/reflector、世界书注入与
  `scan_depth` 窗口、mvu/EJS、角色卡解析、正则脚本、@INJECT、GENERATE 注入、结构化错误码、
  任务编排工具契约、命令分级与权限矩阵、截断自愈、密钥保留、pending_runs RAII、DB 锁中毒回滚、
  世界书概率门控不变式、用量落库事务化、migrate 元测试、脚本沙箱 e2e 等)。
  **数量以 `../MAINTENANCE.md` 为准**,取得命令:

  ```bash
  node tools/count-tests.mjs          # 当前计数
  node tools/count-tests.mjs --check  # 校验文档描述是否漂移
  npm run count:tests -w web          # 等价 npm script 别名(以根 package.json 为准)
  ```

- **门禁清单(本地 CI 单一入口)**:`tools/check-all.ps1`(`npm run check`)——**阶段顺序与开关语义
  的唯一展开处是 `../MAINTENANCE.md` §2**,此处只列类别:后端段(fmt / clippy / cargo test)、
  审计段(`cargo audit` 双锁 + `npm audit`,**均为硬门禁**)、文档与契约段(check-docs / lock-sync /
  check-contract / check-arch / count-tests)、前端段(类型逃逸 ratchet / eslint / vue-tsc /
  vitest / vite build / bundle budget),外加须 `-Perf` 才跑的性能门禁。
  接**四处**触发,其中云端两档**自 2026-09-29 起服务端停用**(见 `../遗留.md` CI-BILL-1):
  `build.ps1` 构建前跑 `-Quick`(失败即中止构建)、`tools/hooks/pre-push`
  (推送前,`npm run hooks:install` 安装)——**停用期间本机只有这两处生效**;
  `.github/workflows/ci.yml`(2026-09-26 随远端配置激活,**2026-09-29 停用**;触发面限
  `push` 到 `main` + PR + 手动 `workflow_dispatch`,平台分支刻意不触发——与 `main` 逐字节同源)、
  `.github/workflows/ci-linux.yml`(**平台可移植性档**,2026-09-27 增,同日停用:`check-ubuntu` 跑平台无关段,
  `android-smoke` 仅手动 `workflow_dispatch` 触发做交叉编译冒烟;两档的红都按门禁对待)。
- **架构门禁**:`tools/arch-layers.json` 是代际归属与跨代依赖方向的唯一机器可读事实源(SSOT),
  `tools/check-arch.mjs` 的规则 I(每个顶层模块/目录必须登记代际,未登记即 FAIL)与
  规则 J(按登记代际校验 import 图,新增未登记越代边即 FAIL;存量越代边登记
  `reason` + `remediation`,只减不增)硬门禁锁定;另有规则 K(未接入 `JsonBody` 的提取器
  ratchet,只降不升)。
- **依赖供应链**:`check-lock-sync.mjs`(双 `Cargo.lock` 漂移,0 漂移为基线)、
  `cargo audit`(硬门禁,advisory DB 拉取失败降级 WARN)、`npm audit --omit=dev`(**硬门禁**,
  2026-09 批次 6.1 起由警告档提升——漏洞即 `exit 1`,仅离线时降 WARN)。
- **性能基线方法**:`tools/perf-baseline.mjs` 压测端点(`npm run perf`,输出 p50/p95/吞吐),
  基线存 `tools/perf-baseline.json`;阈值门禁口径为 **`当前 p95 <= 基线 p95 × factor` 且
  `errors == 0`**,`p95 < 5ms` 的端点跳过(小数据集抖动),经 `check-all.ps1 -Perf` 并入总门禁
  (**默认关闭**——需服务已在运行;服务不可用时 fail-closed 而非静默跳过)。
  基线是**本机 release 口径**,只作回归对比基准、不是跨机 SLA,换机器或数据量变化后须重采样。
  用法与实测定量见 [perf-baseline](archive/2026-09-16-consolidation/perf-baseline.md) §六与 §三。
- **性能治理已落地项**:工具参数计入 token 计数、裁剪回收工具参数(占位保持合法 JSON)、
  重复调用熔断(`utils/loop_guard.rs`,FNV 指纹 + 环形窗口 N=8/K=3)、世界书正则预编译
  (进程级缓存 + 小写化外提)、token 计数缓存、推理感知自愈、性能门禁、工具定义快照、
  世界书条目缓存、连接器读锁快照化(改 `read().await.clone()` 后立即释放,修复
  「生成期间保存设置阻塞到整轮生成结束」)、索引补齐
  (`idx_sessions_character` / `idx_tasks_character` / `idx_tasks_status`,新库建表即带、
  旧库经幂等迁移补建)、`trim` 量纲修正(极端兜底分支不再把 token 数当字符数用)。
- **构建指纹与双端同步**:测试版 `dist\kedai-server.exe` 与便携版
  `dist\Kedai-portable\Kedai.exe` 为两条独立编译链,各冻结编译时刻的 `web/dist`;
  `build.ps1` 双端同步产出并写 `<exe>.build.json` 指纹(`version/build_time/dist_hash`),
  启动器与 `start.ps1` 比对,不一致自动重建;设置中心底部可见两端指纹。

  交付/试用 exe 版前必须跑一次 `.\build.ps1`(快速迭代可用 `-TestOnly`,但便携版会因此未同步)。
  `cargo test` 统一带 `-j 8`(2026-09-17 P-13 实测后由 `-j 2` 放宽;原因此处不抄,见 `经验.md` 条目 29);
